## 동시성 제어와 락

여러 요청이 **같은 데이터를 동시에 바꾸려 할 때** 어느 쪽의 결과를 살릴지, 다른 쪽을 기다리게 할지 결정하는 것이 **동시성 제어(Concurrency Control)**다. 재고·좌석·포인트처럼 "정확히 하나만 성공해야 하는" 갱신은 격리 수준(unit01)만으로는 지켜지지 않으므로, **락(Lock)**을 어떤 방식으로 걸지 선택하는 기준을 알아야 한다.

<br>

### 1. 문제 상황 — 재고 차감 시나리오

재고 1개가 남은 상품을 두 사용자가 동시에 주문하는 경우를 보자. 아무 제어가 없으면 두 요청 모두 "재고 1개 확인 → 차감"을 수행해 **재고가 -1이 되거나, 두 번 팔았는데 1만 줄어드는** 결과가 나온다.

```
시간 →
요청 A: ── SELECT stock → 1 ── (검증 통과) ── UPDATE stock = 0 ── COMMIT
요청 B: ──── SELECT stock → 1 ── (검증 통과) ────── UPDATE stock = 0 ── COMMIT
결과: 재고 1개로 주문 2건 성공 → 초과 판매(Overselling)
```

```java
// 안티패턴: 읽기 → 검증 → 쓰기 사이에 다른 요청이 끼어들 수 있다 (Check-Then-Act)
@Transactional
public void order(Long productId) {
    Product p = productRepository.findById(productId).orElseThrow();
    if (p.getStock() < 1) throw new SoldOutException();
    p.setStock(p.getStock() - 1);   // 두 요청 모두 1 - 1 = 0 을 씀
}
```

- 이 문제는 격리 수준을 REPEATABLE READ로 올려도 해결되지 않음. 스냅샷은 "읽은 값이 안 바뀌게" 할 뿐, **"내가 읽은 값을 기준으로 남이 쓰지 못하게"** 하지는 않기 때문
- 결국 **읽기와 쓰기 사이를 하나의 원자적 단위로 묶는** 수단이 필요하며, 그 수단이 락과 원자적 갱신임

> 💡 "재고 차감을 어떻게 안전하게 구현하겠는가"는 백엔드 면접 단골 질문이다. 원자적 UPDATE → 비관적 락 → 낙관적 락 → 분산 락(unit04) 순으로 **단계별 선택지와 트레이드오프**를 말할 수 있어야 한다.

<br>

### 2. 가장 단순한 해법 — 원자적 UPDATE

DB가 **현재 값을 기준으로** 조건 검사와 갱신을 한 문장 안에서 수행하게 하면, 별도 락 없이도 정확히 한 요청만 성공한다. 행 단위 배타 락은 UPDATE 문장이 자동으로 획득한다.

```sql
UPDATE product
SET    stock = stock - 1
WHERE  id = 1 AND stock >= 1;   -- 영향받은 행 수가 0이면 재고 부족
```

- 두 요청이 동시에 와도 DB가 행 락으로 순서를 정하고, 두 번째 요청은 갱신된 값(0)을 기준으로 조건을 평가해 실패함
- **읽어서 계산하는 로직이 없을 때** 가장 빠르고 간단한 선택
- 차감 후 "주문 생성·이력 기록" 같은 후속 로직도 같은 트랜잭션에 넣으면 실패 시 함께 롤백됨

<br>

### 3. 비관적 락 (Pessimistic Lock)

**"충돌이 자주 날 것이다"**라고 가정하고, 데이터를 **읽는 시점에 미리 락을 걸어** 다른 트랜잭션이 끼어들지 못하게 하는 방식이다. `SELECT ... FOR UPDATE`가 대표적이다.

```
요청 A: ── SELECT ... FOR UPDATE (X-Lock 획득) ── 검증 ── UPDATE ── COMMIT (락 해제)
요청 B: ──── SELECT ... FOR UPDATE ────── 대기 ─────────────────────── 락 획득 → stock=0 확인 → 실패
```

```java
// JPA: 조회 시점에 SELECT ... FOR UPDATE 실행
public interface ProductRepository extends JpaRepository<Product, Long> {
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))
    @Query("SELECT p FROM Product p WHERE p.id = :id")
    Optional<Product> findByIdForUpdate(@Param("id") Long id);
}
```

- **장점**: 충돌을 "감지"하는 게 아니라 "예방"하므로 재시도 로직이 필요 없고, 성공 순서가 보장됨
- **단점**: 락을 잡은 동안 다른 요청이 줄을 서므로 **처리량이 락 보유 시간에 반비례**함. 트랜잭션이 길면(외부 API 호출 등) 병목이 급격히 커짐
- **주의**: `FOR UPDATE`의 WHERE 조건이 인덱스를 타지 못하면 스캔한 범위 전체에 락이 걸려 무관한 행까지 대기시킴 (unit02 참고)

> ⚠️ `SELECT ... FOR UPDATE`는 **트랜잭션 안에서만** 의미가 있다. 트랜잭션 없이 실행하면 문장이 끝나는 순간 락이 풀려 아무것도 보호하지 못한다. 또한 락 대기 타임아웃을 지정하지 않으면 요청 스레드가 무한정 묶여 커넥션 풀 고갈(unit10)로 번질 수 있다.

<br>

### 4. 낙관적 락 (Optimistic Lock)

**"충돌은 드물 것이다"**라고 가정하고, 읽을 때는 락을 걸지 않는다. 대신 행에 **버전(version) 컬럼**을 두고, 갱신할 때 "내가 읽었던 버전 그대로인가"를 확인해 충돌을 **감지**한다.

```
요청 A: ── SELECT (version=7) ── UPDATE ... WHERE version=7 → 1행 갱신, version=8 ── COMMIT
요청 B: ──── SELECT (version=7) ─────── UPDATE ... WHERE version=7 → 0행 갱신 → 충돌 감지 → 재시도 or 실패
```

```sql
-- 낙관적 락의 본질은 이 한 문장이다
UPDATE product
SET    stock = 0, version = version + 1
WHERE  id = 1 AND version = 7;   -- 갱신 행 수 0 → 다른 트랜잭션이 먼저 바꿈
```

```java
@Entity
public class Product {
    @Id private Long id;
    private int stock;
    @Version private Long version;   // JPA가 UPDATE 시 WHERE version = ? 를 자동으로 붙임
}

// 충돌 시 ObjectOptimisticLockingFailureException 발생 → 호출 측에서 재시도
@Retryable(retryFor = ObjectOptimisticLockingFailureException.class, maxAttempts = 3)
@Transactional
public void order(Long productId) { ... }
```

- **장점**: 락 대기가 없어 읽기 위주·충돌이 드문 환경에서 처리량이 높음. DB 락 자원을 점유하지 않음
- **단점**: 충돌 시 **재시도는 애플리케이션 책임**이며, 충돌이 잦으면 재시도가 폭증해 오히려 비관적 락보다 느려짐
- 게시글 수정처럼 "마지막 저장이 이전 저장을 덮어쓰는 것"을 막는 용도(사용자에게 충돌 알림)로도 널리 쓰임

> 💡 낙관적 락의 재시도는 무한 반복이 아니라 **횟수·간격 제한**을 두어야 한다. 특히 선착순 이벤트처럼 한 행에 수천 요청이 몰리는 경우 낙관적 락은 대부분 실패·재시도로 끝나므로 적합하지 않다.

<br>

### 5. 낙관적 락 vs 비관적 락 선택 기준

| **기준**                       | **비관적 락**                                  | **낙관적 락**                                   |
| ------------------------------ | ---------------------------------------------- | ----------------------------------------------- |
| **전제**                       | 충돌이 **잦다**                                | 충돌이 **드물다**                               |
| **충돌 처리 시점**             | 읽을 때 **예방** (대기)                        | 쓸 때 **감지** (실패·재시도)                    |
| **재시도 로직**                | 불필요                                         | **필요** (애플리케이션 책임)                    |
| **처리량 (충돌 적을 때)**      | 락 대기로 낮음                                 | 높음                                            |
| **처리량 (충돌 많을 때)**      | 순차 처리로 예측 가능                          | 재시도 폭증으로 급락                            |
| **데드락 위험**                | 있음 (여러 행 락 시)                           | 거의 없음                                       |
| **DB 자원**                    | 락·커넥션을 오래 점유                          | 점유 시간 짧음                                  |
| **적합한 예**                  | 재고 차감, 선착순 쿠폰, 계좌 이체              | 게시글·프로필 수정, 설정 변경, 읽기 위주 데이터 |

**실무 판단 순서**

- 읽어서 계산할 필요가 없으면 → **원자적 UPDATE** (가장 단순)
- 한 행에 요청이 집중되고 반드시 순서대로 처리돼야 하면 → **비관적 락** (+ 짧은 트랜잭션, 락 타임아웃)
- 충돌이 드물고 사용자에게 "다시 시도" 안내가 허용되면 → **낙관적 락** (+ 재시도 횟수 제한)
- 여러 서버·여러 DB에 걸친 자원이면 → **분산 락** (unit04 참고)

<br>

### 6. 데드락 (Deadlock)

두 트랜잭션이 **서로가 가진 락을 기다리며 영원히 멈추는** 상태다. 비관적 락을 쓰거나, 한 트랜잭션에서 여러 행을 갱신할 때 흔히 발생한다.

```
트랜잭션 A (상품 1 → 2 순서)          트랜잭션 B (상품 2 → 1 순서)
─────────────────────────            ─────────────────────────
① UPDATE product 1  (락 획득)
                                     ② UPDATE product 2  (락 획득)
③ UPDATE product 2  → 대기 ──┐
                                     ④ UPDATE product 1  → 대기
   └────────── 순환 대기: 데드락 ──────────┘
```

**DBMS의 대응**: 대기 그래프에서 사이클을 감지하면 한쪽을 강제 롤백하고 오류(MySQL은 `Deadlock found when trying to get lock`)를 반환한다. 즉, 데드락은 "무한 대기"가 아니라 **"한쪽이 실패하는 것"**으로 끝나므로 애플리케이션은 이 오류를 잡아 **재시도**해야 한다.

**예방 방법**

| **방법**                           | **설명**                                                                 |
| ---------------------------------- | ------------------------------------------------------------------------ |
| **접근 순서 통일**                 | 여러 행·테이블을 갱신할 때 항상 **같은 순서**(예: PK 오름차순)로 접근     |
| **트랜잭션 짧게**                  | 락 보유 시간을 줄여 겹칠 확률 자체를 낮춤. 외부 호출은 트랜잭션 밖으로   |
| **락 범위 축소**                   | WHERE 조건에 인덱스를 태워 필요한 행만 잠금 (unit02)                     |
| **락 타임아웃 설정**               | 무한 대기 대신 일정 시간 후 실패시켜 장애 전파 차단                      |
| **한 번에 잠그기**                 | `WHERE id IN (...) ORDER BY id FOR UPDATE`처럼 필요한 행을 한 문장으로 확보 |

```java
// 안티패턴: 요청마다 다른 순서로 잠금 → 데드락 가능
for (Long id : requestedIds) productRepository.findByIdForUpdate(id);

// 개선: 항상 PK 오름차순으로 정렬해 잠금 순서를 통일
requestedIds.stream().sorted().forEach(productRepository::findByIdForUpdate);
```

> ⚠️ 데드락 오류를 "DB가 이상하다"고 무시하면 안 된다. 로그에 남는 데드락 정보(MySQL은 `SHOW ENGINE INNODB STATUS`)로 **어느 두 쿼리가 어떤 순서로 충돌했는지** 확인하고 접근 순서를 고치는 것이 근본 대책이다.

<br>

### 7. 애플리케이션 레벨 락의 한계

`synchronized`나 `ReentrantLock` 같은 언어 수준 락으로 재고 차감을 감싸는 방식은 **단일 프로세스 안에서만** 유효하다.

- 서버를 2대 이상으로 늘리는 순간(unit10 스케일 아웃) 각 서버의 락은 서로를 모르므로 동시성 제어가 깨짐
- 트랜잭션 커밋 전에 락이 풀리면(락 범위가 트랜잭션보다 좁으면) 다른 스레드가 커밋 전 값을 읽어 동일한 문제가 재현됨
- 따라서 정합성의 최종 방어선은 **DB 락 또는 원자적 UPDATE**여야 하고, 애플리케이션 락은 DB 부하를 줄이는 보조 수단으로만 사용함. 여러 서버가 공유하는 락이 필요하면 **분산 락(unit04)**을 검토함

<br>

### 8. 면접·실무 체크포인트

- **Check-Then-Act** 패턴(읽고 검증하고 쓰기)이 왜 동시성에 취약한지, 격리 수준으로 왜 해결되지 않는지 설명할 수 있는가
- 재고 차감을 **원자적 UPDATE → 비관적 락 → 낙관적 락** 순으로 구현하고 각각의 트레이드오프를 말할 수 있는가
- 낙관적 락의 본질이 **`WHERE version = ?` 조건의 갱신 행 수 검사**임을 아는가
- 비관적 락은 **충돌이 잦고 순서 보장이 중요할 때**, 낙관적 락은 **충돌이 드물고 재시도가 허용될 때** 선택한다는 기준을 말할 수 있는가
- 데드락은 DBMS가 감지해 한쪽을 롤백하므로, 애플리케이션은 **재시도**하고 근본적으로는 **접근 순서를 통일**해야 함을 아는가
- `synchronized`가 다중 서버 환경에서 왜 무의미한지, 그럼 무엇을 써야 하는지(DB 락·분산 락) 설명할 수 있는가
