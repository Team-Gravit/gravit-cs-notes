## 트래픽 처리와 자원 관리

서버 장애의 대부분은 "코드가 틀려서"가 아니라 **트래픽이 예상을 넘었을 때 자원(스레드·커넥션·메모리)이 고갈되고, 그 여파가 다른 시스템으로 번져서** 일어난다. 이 유닛은 트래픽을 받아 내는 **스케일 아웃**, 자원 고갈의 대표 사례인 **커넥션 풀 고갈**, 장애 전파를 끊는 **타임아웃·서킷 브레이커**를 다룬다.

<br>

### 1. 스케일 업 vs 스케일 아웃

| **구분**           | **스케일 업 (Scale-up, 수직)**            | **스케일 아웃 (Scale-out, 수평)**                       |
| ------------------ | ----------------------------------------- | ------------------------------------------------------- |
| **방법**           | 서버 한 대의 CPU·메모리 증설              | 서버 **대수**를 늘리고 로드밸런서로 분산                 |
| **한계**           | 장비 상한, 비용 급증, 단일 장애점          | 서버 간 **상태 공유** 문제, 운영 복잡도                  |
| **장애 내성**      | 한 대가 죽으면 전체 중단                  | 일부가 죽어도 나머지가 서비스                            |
| **적합**           | DB, 상태가 큰 시스템                      | 무상태 API 서버                                          |

```
                     ┌──▶ [API 서버 1] ──┐
클라이언트 ──▶ [LB] ─┼──▶ [API 서버 2] ──┼──▶ [공유 저장소: DB / Redis / 메시지 큐]
                     └──▶ [API 서버 3] ──┘
        서버는 언제든 늘리고 줄일 수 있어야 함 → 서버 안에 상태를 두지 않는다
```

**스케일 아웃의 전제 — 무상태(Stateless) 서버**

- 세션은 외부 저장소로 (unit09), 캐시는 글로벌 캐시로 (unit05), 업로드 파일은 오브젝트 스토리지로
- 서버 로컬 메모리의 락·카운터는 서버마다 따로 동작하므로 동시성 제어에 쓸 수 없음 (unit03·unit04)
- 스케줄 배치가 모든 서버에서 동시에 돌지 않도록 분산 락이나 리더 선출이 필요함
- **오토스케일링**: CPU·요청 수 같은 지표로 서버 수를 자동 조절. 단, 새 서버가 뜨는 데 수십 초~수 분이 걸리므로 급격한 스파이크에는 대비가 안 됨 → 큐 버퍼링(unit06)이나 사전 증설로 보완

> 💡 스케일 아웃으로 API 서버를 늘려도 **DB는 한 대**라면 병목은 DB로 옮겨갈 뿐이다. "서버를 늘리면 DB 커넥션 총량이 어떻게 되는가"까지 이어서 답할 수 있어야 한다(2절).

<br>

### 2. 커넥션 풀과 고갈

### 2-1. 커넥션 풀이 필요한 이유

DB 커넥션 생성은 TCP 연결·인증·세션 초기화가 필요해 수십 ms가 걸리고, DB 쪽에도 커넥션당 메모리·프로세스 비용이 든다. 그래서 서버는 시작 시 커넥션을 **미리 여러 개 만들어 풀(Pool)에 보관**하고, 요청은 빌려 쓰고 반납한다.

```
[커넥션 풀 (최대 10)]  ●●●●●●●○○○   ● 사용 중 7   ○ 유휴 3
요청 A: 커넥션 빌림 → 쿼리 → 반납 (수 ms)
요청 B: 풀이 비었으면 → 대기 (connectionTimeout 까지) → 초과 시 예외
```

- 풀 크기는 "많을수록 좋은" 값이 아님. DB의 CPU 코어 수를 넘는 활성 커넥션은 서로 CPU를 뺏을 뿐이라, 널리 인용되는 출발점은 **`코어 수 × 2 + 디스크 수`** 정도이며 실제 값은 부하 테스트로 정함
- 서버가 N대면 DB가 받는 커넥션은 **풀 크기 × N**. 스케일 아웃 시 DB의 `max_connections`를 넘지 않는지 확인해야 함

<br>

### 2-2. 커넥션 풀 고갈 시나리오

**풀 고갈(Pool Exhaustion)**은 커넥션을 빌린 요청이 오래 반납하지 않아 새 요청이 커넥션을 얻지 못하고 줄줄이 대기·실패하는 상태다.

| **원인**                                        | **설명**                                                                   |
| ----------------------------------------------- | -------------------------------------------------------------------------- |
| **트랜잭션 안의 외부 호출**                     | 외부 API가 5초 걸리면 그 5초 동안 커넥션을 점유. 외부 장애가 곧 DB 풀 고갈 |
| **느린 쿼리·락 대기**                           | 인덱스 없는 쿼리(unit02), `FOR UPDATE` 대기(unit03)가 커넥션 반납을 지연    |
| **커넥션 누수**                                 | 예외 경로에서 반납(close)을 빠뜨림. 풀이 서서히 비어 감                     |
| **트래픽 급증**                                 | 요청 스레드 수 > 풀 크기가 되면 초과분은 대기                               |
| **풀 대기 타임아웃 미설정·과다**                | 대기가 길어져 요청 스레드까지 모두 묶임 → 서버 전체 응답 불능               |

```java
// 안티패턴: 트랜잭션(커넥션 점유) 안에서 외부 결제 API 호출
@Transactional
public void order(OrderRequest req) {
    Order order = orderRepository.save(Order.from(req));
    paymentClient.charge(order);            // 외부 API 3초 → 3초간 커넥션 점유
    order.markPaid();
}

// 개선: 커넥션이 필요한 구간과 외부 호출을 분리
public void order(OrderRequest req) {
    Order order = orderTx.create(req);      // 짧은 트랜잭션 1: 주문 저장 후 즉시 반납
    PaymentResult result = paymentClient.charge(order);   // 커넥션 없이 외부 호출
    orderTx.markPaid(order.getId(), result);              // 짧은 트랜잭션 2
}
```

**진단·대응**

- 풀 **활성/유휴/대기 수** 메트릭(unit12)을 상시 수집하고, 대기 스레드가 생기기 시작하면 경보
- 풀 크기를 늘리는 것은 임시방편. 근본 원인(긴 트랜잭션·느린 쿼리·누수)을 찾아야 함
- 누수는 풀의 **leak detection**(일정 시간 미반납 시 경고) 기능으로 위치를 특정

> ⚠️ "풀 크기를 200으로 올렸더니 해결됐다"는 대개 착각이다. DB 부하가 늘어 쿼리가 더 느려지고, 더 큰 트래픽에서 같은 장애가 더 크게 재현된다. 풀은 **DB를 보호하는 상한선**이기도 하다.

<br>

### 3. 타임아웃

타임아웃이 없는 호출은 상대가 응답하지 않을 때 **영원히 스레드·커넥션을 붙잡는다**. 모든 외부 의존(DB, 캐시, 다른 서비스, 외부 API)에는 타임아웃이 있어야 한다.

| **타임아웃 종류**            | **의미**                                              | **설정 기준**                                         |
| ---------------------------- | ----------------------------------------------------- | ----------------------------------------------------- |
| **연결(Connect) 타임아웃**   | TCP 연결이 맺어지기까지                               | 짧게 (수백 ms~수 초). 상대가 죽었으면 빨리 포기        |
| **읽기(Read/Socket) 타임아웃** | 연결 후 응답 데이터가 오기까지                      | 상대의 정상 응답 시간(p99) + 여유                      |
| **풀 대기 타임아웃**         | 커넥션 풀에서 커넥션을 얻기까지                       | 수 초 이내. 길면 요청 스레드가 함께 묶임               |
| **쿼리·트랜잭션 타임아웃**   | 한 쿼리·트랜잭션의 최대 실행 시간                     | 느린 쿼리가 커넥션을 독점하지 못하게                  |
| **요청 전체 타임아웃**       | 클라이언트가 응답을 기다리는 총 시간                  | 하위 타임아웃의 합보다 작게 두어 의미 없는 대기 방지  |

```yaml
http-client:                      # 예시 값 — 서비스 특성에 맞게 조정
  connect-timeout: 1s
  read-timeout: 3s
datasource:
  hikari:
    maximum-pool-size: 20
    connection-timeout: 3000      # 풀 대기 3초
    leak-detection-threshold: 10000
```

**타임아웃 설계 원칙**

- **상위 타임아웃 > 하위 타임아웃 합** 이 아니라, 오히려 **상위가 더 짧아야** 함. 클라이언트가 이미 포기한 요청을 서버가 계속 처리하는 낭비를 막기 위함
- 타임아웃 후 **재시도**는 멱등한 작업에만, 백오프와 함께 (unit04)
- 타임아웃 값은 "상대가 정상일 때 걸리는 시간"을 측정한 데이터로 정함. 감으로 30초를 주면 장애 시 30초 동안 모든 자원이 묶임

<br>

### 4. 서킷 브레이커 (Circuit Breaker)

타임아웃은 "한 번의 호출"을 보호하지만, 상대가 완전히 죽은 상태에서 요청마다 3초씩 기다리는 것 자체가 낭비다. **서킷 브레이커**는 실패가 임계치를 넘으면 **호출 자체를 즉시 차단**해 자원을 아끼고, 상대가 회복되면 자동으로 다시 연다.

```
            실패율 < 임계치                  실패율 ≥ 임계치
   ┌────────────────────┐            ┌────────────────────┐
   │  CLOSED (정상)      │ ─────────▶ │  OPEN (차단)        │
   │  호출 통과, 실패 집계 │            │  즉시 실패(폴백) 반환 │
   └────────────────────┘            └─────────┬──────────┘
             ▲                                  │ 대기 시간 경과
             │ 시험 호출 성공                    ▼
             │                       ┌────────────────────┐
             └────────────────────── │  HALF-OPEN (시험)   │ ── 시험 호출 실패 ──▶ OPEN
                                     │  일부 호출만 통과     │
                                     └────────────────────┘
```

| **상태**        | **동작**                                                  |
| --------------- | --------------------------------------------------------- |
| **CLOSED**      | 정상. 호출을 통과시키며 최근 N회(또는 N초)의 실패율을 집계 |
| **OPEN**        | 실패율이 임계치를 넘음. 호출하지 않고 **즉시 실패 또는 폴백** 반환 |
| **HALF-OPEN**   | 일정 시간 후 **소수의 시험 호출**만 통과. 성공하면 CLOSED, 실패하면 다시 OPEN |

```java
// Resilience4j 예시 — 실패율 50% 초과 시 30초간 차단, 폴백으로 캐시된 값 반환
@CircuitBreaker(name = "recommendation", fallbackMethod = "fallback")
public List<Item> recommend(Long userId) {
    return recommendationClient.fetch(userId);     // 타임아웃 3초
}

private List<Item> fallback(Long userId, Throwable t) {
    return popularItemCache.get();                  // 추천 대신 인기 상품 (기능 저하, 장애 아님)
}
```

- **폴백(Fallback)**의 설계가 핵심: 빈 목록·캐시된 값·기본값 등 "기능은 줄지만 서비스는 되는" 응답을 준비함. 폴백이 없으면 서킷은 빠른 실패만 제공
- 실패율 임계치·최소 호출 수·OPEN 유지 시간 같은 값은 라이브러리마다 기본값이 다르고 버전에 따라 바뀔 수 있으므로 **명시적으로 설정**함
- 서킷 브레이커는 **호출하는 쪽**(클라이언트)에 두며, 상대 서비스별로 분리해 한 의존성의 장애가 다른 호출까지 차단하지 않게 함

> 💡 면접에서 "타임아웃이 있는데 서킷 브레이커가 왜 필요한가"를 묻는다. 답은 **"타임아웃은 한 호출의 상한, 서킷 브레이커는 죽은 상대에게 계속 호출하는 것 자체를 멈추고 회복을 자동 감지하는 장치"**다.

<br>

### 5. 함께 쓰는 보호 장치

| **장치**                         | **역할**                                                              | **위치**              |
| -------------------------------- | --------------------------------------------------------------------- | --------------------- |
| **속도 제한 (Rate Limiting)**    | 사용자·IP·API 키별 요청 수 상한. 초과 시 **429** (unit08)              | 게이트웨이·서버 입구  |
| **벌크헤드 (Bulkhead)**          | 의존성별로 스레드 풀·커넥션을 **분리**해 한 의존성 장애가 전체를 못 잡게 | 호출하는 쪽           |
| **부하 차단 (Load Shedding)**    | 처리 불가능한 초과 요청을 **즉시 거절**해 나머지 요청의 품질을 지킴     | 서버 입구             |
| **백프레셔 (Backpressure)**      | 소비 속도에 맞춰 생산 속도를 늦춤. 큐 길이 상한                        | 큐·스트림 처리        |
| **재시도 + 백오프**              | 일시 장애 극복. 서킷과 결합해 죽은 상대에게는 재시도하지 않음          | 호출하는 쪽 (unit04)  |

- 이 장치들의 공통 목표는 **"부분 장애를 전체 장애로 만들지 않기"**임. 일부 기능이 저하되더라도 핵심 기능(로그인·주문)은 살아 있게 설계함 (우아한 성능 저하, Graceful Degradation)

<br>

### 6. 면접·실무 체크포인트

- 스케일 아웃의 전제가 **무상태 서버**임을 알고, 세션·캐시·락·배치가 각각 어디로 가야 하는지 말할 수 있는가
- 커넥션 풀 크기가 "클수록 좋지 않은" 이유와, 서버 대수 × 풀 크기가 DB 한계를 넘지 않는지 점검하는가
- **트랜잭션 안의 외부 호출**이 왜 풀 고갈로 이어지는지, 어떻게 분리하는지 코드로 설명할 수 있는가
- 연결·읽기·풀 대기·쿼리 타임아웃의 차이와, 상위 타임아웃을 하위보다 **짧게** 두는 이유를 아는가
- 서킷 브레이커의 **세 상태 전이**와 폴백 설계, 타임아웃과의 역할 차이를 설명할 수 있는가
- 속도 제한·벌크헤드·부하 차단이 각각 어떤 장애 전파를 막는지 구분할 수 있는가
