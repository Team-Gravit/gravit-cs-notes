## HTTP와 REST API 설계

**REST API**는 HTTP의 메서드·상태 코드·URI 같은 기존 규약 위에 자원(Resource)을 표현하는 설계 방식이다. 프레임워크가 라우팅을 대신해 주더라도, **어떤 메서드가 재시도해도 안전한지, 어떤 상태 코드가 클라이언트에게 올바른 행동을 유도하는지, API를 어떻게 바꿔도 기존 클라이언트가 깨지지 않는지**는 개발자가 직접 판단해야 하는 영역이다.

<br>

### 1. 자원 중심 설계의 기본

REST에서 URI는 **자원(명사)**을 가리키고, 그 자원에 대한 **행위는 HTTP 메서드**로 표현한다.

```
잘못된 설계 (행위가 URI에):   POST /getUser?id=7      POST /createOrder     GET /deleteOrder/7
자원 중심 설계:               GET  /users/7           POST /orders          DELETE /orders/7
계층 표현:                    GET  /users/7/orders    (사용자 7의 주문 목록)
필터·정렬·페이징은 쿼리로:     GET  /orders?status=PAID&sort=-createdAt&page=2&size=20
```

- 컬렉션은 복수형(`/orders`), 개별 자원은 식별자(`/orders/1001`)로 표현함
- 동사가 꼭 필요한 동작(결제 승인, 비밀번호 초기화)은 하위 자원이나 상태 변경으로 모델링함: `POST /orders/1001/cancellation`, `PATCH /orders/1001 {"status":"CANCELED"}`
- 응답 본문은 일관된 구조를 유지하고, 오류 응답에도 **기계가 읽을 수 있는 코드**와 사람이 읽을 메시지를 함께 담음

<br>

### 2. HTTP 메서드의 안전성과 멱등성

| **메서드**   | **의미**                         | **안전(Safe)** | **멱등(Idempotent)** | **요청 본문** | **비고**                                  |
| ------------ | -------------------------------- | -------------- | -------------------- | ------------- | ----------------------------------------- |
| **GET**      | 자원 조회                        | **O**          | **O**                | 없음          | 캐시 가능                                 |
| **HEAD**     | 헤더만 조회                      | **O**          | **O**                | 없음          | 존재 여부·크기 확인                        |
| **POST**     | 자원 생성, 처리 요청             | X              | **X**                | 있음          | 호출할 때마다 새 자원이 생길 수 있음       |
| **PUT**      | 자원 **전체 교체**               | X              | **O**                | 있음          | 같은 본문을 여러 번 보내도 결과 동일       |
| **PATCH**    | 자원 **부분 수정**               | X              | **경우에 따라 다름** | 있음          | `{"count": 5}`는 멱등, `{"op":"increment"}`는 아님 |
| **DELETE**   | 자원 삭제                        | X              | **O**                | 보통 없음     | 두 번째 호출은 404여도 상태는 동일         |

- **안전**: 서버 상태를 바꾸지 않음 → 브라우저·프록시가 마음대로 캐시·프리페치해도 됨
- **멱등**: 여러 번 호출해도 **서버 상태**가 한 번 호출한 것과 같음 → 네트워크 오류 시 **클라이언트가 안심하고 재시도** 가능. 응답 코드가 매번 같아야 한다는 뜻은 아님
- 멱등성이 중요한 이유: 타임아웃 후 재전송(unit04)을 자동화할 수 있는 메서드와 없는 메서드가 갈리기 때문

```
POST /orders 를 타임아웃 후 재시도하면?
1차: 서버는 주문 #1001 생성 → 응답 유실
2차: 서버는 주문 #1002 생성 → 중복 주문   ← POST는 멱등하지 않음
해결: Idempotency-Key 헤더로 서버가 같은 요청을 인식 (unit04 참고)
```

> ⚠️ "PUT은 항상 멱등"이라고 해서 구현이 자동으로 멱등해지는 것은 아니다. PUT 핸들러 안에서 `updated_count += 1` 같은 부수 효과를 넣으면 규약을 어기는 것이다. 멱등성은 **HTTP가 약속하는 계약이고, 지키는 것은 서버 구현의 책임**이다.

<br>

### 3. 상태 코드 선택

상태 코드는 클라이언트에게 **"다음에 무엇을 해야 하는가"**를 알려 주는 신호다. 모든 오류를 200으로 감싸거나 500으로 뭉뚱그리면 클라이언트는 재시도 여부조차 판단할 수 없다.

<br>

### 3-1. 자주 쓰는 코드와 선택 기준

| **코드**                      | **언제 쓰는가**                                              | **클라이언트가 할 일**                    |
| ----------------------------- | ------------------------------------------------------------ | ----------------------------------------- |
| **200 OK**                    | 조회·수정 성공, 응답 본문 있음                                | 본문 사용                                 |
| **201 Created**               | POST로 자원 생성 성공. `Location` 헤더에 새 자원 URI          | 새 자원 참조                              |
| **204 No Content**            | 성공했지만 돌려줄 본문이 없음 (DELETE, 일부 PUT)              | 본문 파싱하지 않음                        |
| **400 Bad Request**           | 형식 오류 (JSON 파싱 실패, 필수 필드 누락)                    | 요청 수정 후 재요청                       |
| **401 Unauthorized**          | **인증 실패** — 누구인지 모름 (토큰 없음·만료)                | 로그인·토큰 갱신 (unit09)                 |
| **403 Forbidden**             | **인가 실패** — 누구인지는 알지만 권한 없음                   | 재시도 무의미                             |
| **404 Not Found**             | 자원 없음                                                    | URI 확인                                  |
| **409 Conflict**              | 현재 상태와 충돌 (중복 가입, 낙관적 락 실패, 이미 취소된 주문) | 최신 상태 조회 후 재시도 여부 결정        |
| **422 Unprocessable Content** | 형식은 맞지만 **의미상 검증 실패** (과거 날짜 예약 등)         | 값 수정 후 재요청                         |
| **429 Too Many Requests**     | 요청 한도 초과. `Retry-After` 헤더 권장                       | 지정 시간 후 재시도 (unit10)              |
| **500 Internal Server Error** | 서버 내부 오류 (예상 못 한 예외)                              | 잠시 후 재시도, 계속되면 문의             |
| **502 / 503 / 504**           | 게이트웨이 오류 / 일시적 과부하·점검 / 업스트림 타임아웃      | 백오프 후 재시도                          |

**선택 원칙**

- **401 vs 403**: "로그인이 필요한가(401)" vs "로그인해도 안 되는가(403)". 존재 여부를 숨겨야 하는 자원은 403 대신 404를 쓰기도 함
- **400 vs 422**: 형식(문법) 문제는 400, 의미(업무 규칙) 문제는 422. 팀 컨벤션으로 400 하나로 통일하기도 하므로 **일관성이 우선**
- **4xx는 클라이언트 잘못, 5xx는 서버 잘못**: 재시도·알림·모니터링(unit12) 기준이 되므로 섞으면 안 됨. 업무 규칙 위반을 500으로 내보내면 서버 오류율 지표가 오염됨

<br>

### 3-2. 오류 응답 본문

```java
// 안티패턴: 모든 응답을 200으로, 성공 여부는 본문에서만 판단
return ResponseEntity.ok(Map.of("success", false, "message", "재고 부족"));

// 개선: 상태 코드로 분류하고, 본문에 기계가 읽을 코드와 상세를 담음
@ExceptionHandler(OutOfStockException.class)
public ResponseEntity<ErrorResponse> handle(OutOfStockException e) {
    return ResponseEntity.status(HttpStatus.CONFLICT)
        .body(new ErrorResponse("OUT_OF_STOCK", "재고가 부족합니다.", e.getProductId()));
}
```

- 오류 본문 형식은 서비스 전체에서 **하나로 통일**함. RFC 9457(Problem Details)처럼 표준 형식을 따르면 클라이언트 처리가 단순해짐
- 스택 트레이스·내부 테이블명 같은 **구현 세부는 노출하지 않음**

> 💡 면접에서 "회원가입 시 이미 존재하는 이메일이면 몇 번을 주겠는가"처럼 구체적 상황을 묻는다. 정답 하나보다 **409를 택한 근거와 400·422 대안의 차이**를 설명하는 것이 중요하다.

<br>

### 4. REST vs GraphQL

| **비교 항목**           | **REST**                                          | **GraphQL**                                              |
| ----------------------- | ------------------------------------------------- | -------------------------------------------------------- |
| **엔드포인트**          | 자원마다 여러 URI                                 | 보통 **단일 엔드포인트** (`POST /graphql`)               |
| **응답 형태**           | 서버가 정한 고정 구조                             | **클라이언트가 필요한 필드를 지정**                      |
| **과다·과소 조회**      | Over-fetching / Under-fetching 발생 가능          | 필요한 것만, 한 번에 여러 자원 조회 가능                 |
| **HTTP 캐시**           | GET·URI 기반으로 **잘 동작**                      | POST 위주라 HTTP 캐시 활용 어려움 (클라이언트 캐시 필요) |
| **상태 코드**           | 상태 코드로 오류 구분                             | 대개 200 + 본문의 `errors` 배열                          |
| **스키마·타입**         | 별도 문서(OpenAPI) 필요                           | 스키마가 곧 문서, 강타입                                 |
| **서버 부하 제어**      | 엔드포인트별로 예측 가능                          | 깊은 중첩 쿼리로 **비용 폭발** 가능 → 깊이·복잡도 제한 필요 |
| **N+1 문제**            | 엔드포인트 구현에서 관리                          | 리졸버 구조상 흔함 → DataLoader(배치 로딩) 필요           |
| **적합한 경우**         | 단순 CRUD, 공개 API, 캐시가 중요한 서비스          | 화면마다 필요한 데이터가 다른 클라이언트(모바일·BFF)      |

```graphql
query UserWithRecentOrders {   # 한 번의 요청으로 사용자와 최근 주문의 필요한 필드만 조회
  user(id: 7) {
    name
    orders(last: 3) { id totalAmount }
  }
}
```

- GraphQL은 REST의 대체재가 아니라 **클라이언트 다양성이 큰 문제를 푸는 도구**임. 팀에 GraphQL 운영 경험이 없고 API 소비자가 단일 웹 프론트뿐이면 REST가 단순함
- 두 방식 모두 인증·인가(unit09), 속도 제한(unit10), 관측성(unit12)은 동일하게 필요함

<br>

### 5. API 버전 관리

API를 바꾸면 이미 배포된 앱·외부 클라이언트가 깨질 수 있다. **호환성을 깨는 변경(Breaking Change)**을 어떻게 관리하느냐가 버전 관리의 핵심이다.

**호환성을 깨는 변경 vs 깨지 않는 변경**

| **깨지 않음 (버전 유지 가능)**                 | **깨짐 (새 버전 필요)**                                  |
| ---------------------------------------------- | -------------------------------------------------------- |
| 응답에 **필드 추가**                           | 응답 필드 **삭제·이름 변경·타입 변경**                   |
| 선택적 요청 파라미터 추가                      | 필수 파라미터 추가                                       |
| 새 엔드포인트 추가                             | 엔드포인트 삭제, URI 변경                                |
| 오류 메시지 문구 변경                          | 상태 코드·오류 코드 의미 변경                            |

**버전 표기 방식**

| **방식**                     | **예시**                                  | **장점**                          | **단점**                                  |
| ---------------------------- | ----------------------------------------- | --------------------------------- | ----------------------------------------- |
| **URI 경로**                 | `/v1/orders`, `/v2/orders`                | 명확, 브라우저·로그에서 바로 보임 | URI가 자원이 아닌 버전을 포함             |
| **쿼리 파라미터**            | `/orders?version=2`                       | 도입 쉬움                         | 기본값 관리 필요, 캐시 키 복잡            |
| **커스텀 헤더**              | `X-API-Version: 2`                        | URI 깔끔                          | 눈에 안 보여 디버깅 불편                  |
| **Accept 헤더 (미디어 타입)** | `Accept: application/vnd.shop.v2+json`    | HTTP 의미론에 가장 충실           | 클라이언트 구현 부담, 학습 비용           |

```java
// URI 경로 버전 — 가장 널리 쓰이며 실무에서 무난한 선택
@RestController
@RequestMapping("/v2/orders")
public class OrderV2Controller { ... }
```

**운영 원칙**

- 되도록 **깨지 않는 변경으로 흡수**하고, 버전은 최후 수단으로 올림. 버전이 늘수록 유지 비용은 배로 늘어남
- 이전 버전은 **지원 종료 일정(Deprecation)**을 공지하고, `Deprecation`·`Sunset` 헤더나 문서로 알림
- 클라이언트는 **모르는 필드를 무시**하도록 만들어(관용적 파싱) 필드 추가가 배포와 무관하게 가능하게 함

> 💡 "v1을 언제까지 유지하겠는가"라는 질문에는 "이전 버전 호출 비율을 **메트릭(unit12)**으로 추적해 임계치 아래로 떨어지면 종료 공지 후 제거한다"처럼 데이터 기반 답을 준비해 둔다.

<br>

### 6. 면접·실무 체크포인트

- URI는 **자원(명사)**, 행위는 **메서드**라는 원칙과, 동사가 필요한 동작을 자원으로 모델링하는 방법을 말할 수 있는가
- **안전 vs 멱등**의 차이와 메서드별 분류(GET·PUT·DELETE는 멱등, POST는 아님, PATCH는 경우에 따라)를 설명할 수 있는가
- POST의 비멱등성이 왜 **재시도·중복 문제**로 이어지는지, 멱등성 키로 어떻게 보완하는지 아는가
- **401 vs 403, 400 vs 422, 409의 용도**를 구체적 시나리오로 설명할 수 있는가
- 4xx·5xx를 섞으면 **모니터링·재시도 정책**이 왜 망가지는지 아는가
- REST와 GraphQL을 **캐시·과다 조회·N+1·서버 부하 제어** 관점에서 비교하고 선택 기준을 말할 수 있는가
- 호환성을 깨는 변경과 아닌 변경을 구분하고, **버전을 올리지 않고 흡수하는 방법**을 먼저 제시할 수 있는가
