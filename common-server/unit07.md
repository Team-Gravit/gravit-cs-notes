## 데이터베이스 확장

서버는 스케일 아웃(unit10)으로 쉽게 늘릴 수 있지만 **데이터베이스는 상태를 가지므로 가장 늦게, 가장 어렵게 확장되는 구성 요소**다. 이 유닛은 읽기 부하를 나누는 **복제(Replication)**, 그로 인해 생기는 **복제 지연**, 그리고 쓰기·저장 용량까지 나누는 **샤딩(Sharding)**의 원리와 설계 기준을 다룬다.

<br>

### 1. 확장의 단계 — 무엇이 병목인가에 따라

| **단계**                        | **해결하는 병목**                  | **방법**                                    | **복잡도** |
| ------------------------------- | ---------------------------------- | ------------------------------------------- | ---------- |
| **쿼리·인덱스 튜닝** (unit02)   | 비효율적 쿼리                      | 실행 계획 분석, 인덱스 추가, N+1 제거        | 낮음       |
| **캐시** (unit05)               | 반복 조회                          | 조회 결과를 Redis 등에 저장                  | 낮음~중간  |
| **스케일 업**                   | CPU·메모리·디스크 한계             | 더 큰 장비로 교체                            | 낮음 (비용↑) |
| **복제 + 읽기 분산**            | **읽기** 부하                      | 레플리카를 늘려 SELECT를 분산                | 중간       |
| **파티셔닝**                    | 한 테이블의 크기                   | 같은 DB 안에서 테이블을 논리적으로 분할      | 중간       |
| **샤딩**                        | **쓰기** 부하·저장 용량            | 데이터를 여러 DB 인스턴스로 물리적으로 분할  | **높음**   |

- 순서가 중요함. 대부분의 서비스는 **튜닝 + 캐시 + 복제**까지로 충분하며, 샤딩은 "쓰기 처리량이나 데이터 크기가 단일 인스턴스를 넘어설 때" 최후에 선택함

> 💡 "DB가 느린데 어떻게 하겠는가"라는 질문에 바로 "샤딩"으로 답하면 감점이다. **병목이 읽기인지 쓰기인지 먼저 진단**하고, 읽기면 캐시·복제, 쓰기면 샤딩이라는 흐름으로 답해야 한다.

<br>

### 2. 복제 (Replication)

### 2-1. 구조와 동작

**복제**는 하나의 **프라이머리(Primary, Source)** DB의 변경 내용을 하나 이상의 **레플리카(Replica)**에 똑같이 반영하는 것이다. 쓰기는 프라이머리에서만, 읽기는 레플리카에서도 처리한다.

```
                 쓰기 (INSERT/UPDATE/DELETE)
클라이언트 ─────────────────────────────▶ [프라이머리] ── 변경 로그(binlog/WAL) ──┬──▶ [레플리카 1]
                                              │                                    └──▶ [레플리카 2]
클라이언트 ─── 읽기 (SELECT) ──────────────────┴──────────────────────────────────────▶ 레플리카에서 응답
```

- 프라이머리는 변경 사항을 **로그(MySQL binlog, PostgreSQL WAL)**로 기록하고, 레플리카는 이 로그를 받아 **재실행(Replay)**함
- **목적 두 가지**: ① 읽기 부하 분산 ② 고가용성(프라이머리 장애 시 레플리카를 승격, **페일오버**)

**동기 vs 비동기 복제**

| **방식**          | **커밋 완료 시점**                          | **장점**                    | **단점**                                  |
| ----------------- | ------------------------------------------- | --------------------------- | ----------------------------------------- |
| **비동기**        | 프라이머리에 기록되면 즉시                  | 쓰기 지연 없음              | 레플리카가 **뒤처짐**, 장애 시 유실 가능  |
| **반동기**        | 최소 1대 레플리카가 **수신**하면            | 유실 위험 감소              | 쓰기 지연 약간 증가                       |
| **동기**          | 모든 레플리카가 **적용**하면                | 유실 없음                   | 쓰기 지연 큼, 레플리카 장애가 쓰기를 막음 |

<br>

### 2-2. 읽기 분산 라우팅

애플리케이션은 "이 쿼리가 읽기인가 쓰기인가"를 기준으로 커넥션을 프라이머리·레플리카 중 어디로 보낼지 결정한다. 흔한 기준은 **트랜잭션의 읽기 전용 여부**다.

```java
// 읽기 전용 트랜잭션 → 레플리카, 그 외 → 프라이머리로 라우팅하는 DataSource
public class RoutingDataSource extends AbstractRoutingDataSource {
    @Override
    protected Object determineCurrentLookupKey() {
        boolean readOnly = TransactionSynchronizationManager.isCurrentTransactionReadOnly();
        return readOnly ? "replica" : "primary";
    }
}

@Transactional(readOnly = true)   // 레플리카로 라우팅
public List<Product> search(String keyword) { ... }

@Transactional                    // 프라이머리로 라우팅
public void changePrice(Long id, long price) { ... }
```

- 실제 라우팅은 **커넥션을 획득하는 시점**에 결정되므로, 트랜잭션 시작 시 커넥션을 미리 잡는 프레임워크에서는 지연 획득(lazy) 프록시가 필요할 수 있음. 세부 동작은 프레임워크·버전에 따라 다를 수 있음
- 프록시 계층(ProxySQL 등)에서 SQL을 파싱해 자동 분기하는 방식도 있음

<br>

### 3. 복제 지연 (Replication Lag)

비동기 복제에서는 프라이머리에 커밋된 변경이 레플리카에 반영되기까지 **수 ms~수 초(장애 시 수 분)**의 간격이 생긴다. 이것이 **복제 지연**이며, 읽기 분산을 도입한 서비스에서 가장 흔한 버그 원인이다.

```
시간 →
프라이머리: ── UPDATE nickname='B'; COMMIT ──────────────────────── (binlog 전송)
레플리카:   ──────────────────────────── nickname='A' (아직 옛 값) ─────── 'B' 적용
사용자:     ── 닉네임 변경 요청 ── 변경 완료 응답 ── 내 프로필 조회(레플리카) → 'A' ← "왜 안 바뀌었지?"
```

**대표 증상**

- **쓰기 직후 읽기(Read-your-writes) 불일치**: 방금 수정한 내용이 조회에 안 나옴
- **캐시 오염**: 레플리카의 옛 값을 캐시에 채워 TTL 동안 불일치가 지속됨 (unit05 참고)
- **후속 작업 실패**: 주문 생성 직후 큐 컨슈머가 레플리카에서 주문을 조회했더니 "없음"

**대응 전략**

| **전략**                              | **설명**                                                                 | **비용**                  |
| ------------------------------------- | ------------------------------------------------------------------------ | ------------------------- |
| **쓰기 직후 읽기는 프라이머리로**     | 같은 트랜잭션·같은 요청 안의 조회는 프라이머리에서 수행                   | 단순, 프라이머리 부하 소폭 증가 |
| **사용자 단위 고정(Sticky)**          | 쓰기 후 N초 동안 해당 사용자의 읽기는 프라이머리로                        | 세션·타임스탬프 관리 필요 |
| **지연 허용 데이터 구분**             | 목록·통계처럼 지연이 무방한 조회만 레플리카로                              | 설계 시 분류 필요         |
| **지연 모니터링 + 임계치 초과 시 제외** | `Seconds_Behind_Source` 등 지연 지표가 크면 해당 레플리카를 라우팅에서 제외 | 운영 자동화 필요          |
| **쓰기 응답에 결과 포함**             | 조회 없이 응답에 갱신 결과를 담아 클라이언트가 재조회하지 않게 함          | API 설계 변경             |

```java
// 안티패턴: 쓰기 직후 레플리카에서 조회 → 복제 지연 시 옛 값
@Transactional
public void updateNickname(Long userId, String name) { userRepository.updateNickname(userId, name); }
@Transactional(readOnly = true)
public UserDto getProfile(Long userId) { return userRepository.findDto(userId); }   // 레플리카

// 개선: 쓰기 트랜잭션 안에서 결과를 만들어 반환 (프라이머리에서 읽음)
@Transactional
public UserDto updateNicknameAndGet(Long userId, String name) {
    userRepository.updateNickname(userId, name);
    return userRepository.findDto(userId);   // 같은 트랜잭션 → 프라이머리
}
```

> ⚠️ 복제 지연은 "없앨" 수 없고 "다룰" 수 있을 뿐이다. 읽기 분산을 도입할 때는 **모든 조회를 기계적으로 레플리카로 보내지 말고**, 어떤 조회가 최신 값을 요구하는지 먼저 분류해야 한다.

<br>

### 4. 파티셔닝 vs 샤딩

| **구분**           | **파티셔닝 (Partitioning)**                       | **샤딩 (Sharding)**                                  |
| ------------------ | ------------------------------------------------- | ---------------------------------------------------- |
| **분할 위치**      | **같은 DB 인스턴스** 안에서 테이블을 나눔          | **서로 다른 DB 인스턴스**로 데이터를 나눔             |
| **해결하는 문제**  | 큰 테이블의 조회·삭제 효율 (오래된 파티션 통째 삭제) | 단일 인스턴스의 **쓰기 처리량·저장 용량** 한계        |
| **애플리케이션 변경** | 거의 없음 (DB가 파티션 선택)                   | **크다** (어느 샤드로 갈지 애플리케이션·미들웨어가 결정) |
| **조인·트랜잭션**  | 정상 동작                                         | 샤드 간 조인·트랜잭션 **불가하거나 매우 비쌈**       |

- 파티셔닝은 로그·이력 테이블에 날짜 기준으로 흔히 적용하며, 오래된 데이터를 `DROP PARTITION`으로 즉시 제거할 수 있음
- 샤딩은 **수평 분할(Horizontal)**이 일반적이며, 각 샤드는 같은 스키마에 다른 행을 가짐

<br>

### 5. 샤딩 키 설계

**샤딩 키(Shard Key)**는 "이 행이 어느 샤드에 있는가"를 결정하는 컬럼이다. 한 번 정하면 바꾸기 매우 어려우므로 샤딩 설계의 핵심이다.

**분배 방식**

| **방식**               | **원리**                                    | **장점**                          | **단점**                                     |
| ---------------------- | ------------------------------------------- | --------------------------------- | -------------------------------------------- |
| **해시 (Hash)**        | `hash(key) % 샤드 수`                        | 고르게 분산                       | 범위 조회 불가, **샤드 추가 시 재배치** 큼    |
| **범위 (Range)**       | 키 구간별로 샤드 배정 (1~100만 → 샤드 1)     | 범위 조회 유리, 확장 단순         | 최신 구간에 쓰기가 몰리는 **핫스팟**         |
| **디렉터리 (Lookup)**  | 키 → 샤드 매핑 테이블을 별도 관리            | 유연한 이동·재배치                | 매핑 저장소가 단일 장애점·병목               |

- 해시 방식의 재배치 문제는 **일관된 해싱(Consistent Hashing)**이나 처음부터 논리 샤드를 많이 두고 물리 샤드에 매핑하는 방식으로 완화함

**좋은 샤딩 키의 조건**

- **카디널리티가 높고 분포가 고름**: 국가 코드처럼 값이 몇 개뿐이거나 특정 값에 편중되면 핫스팟이 생김
- **대부분의 쿼리가 키를 포함함**: 샤딩 키 없이 조회하면 **모든 샤드에 질의(Scatter-Gather)**해야 해 성능이 급락함
- **함께 조회되는 데이터가 같은 샤드에 모임**: 사용자 ID로 샤딩하면 그 사용자의 주문·장바구니도 같은 샤드에 두어 조인·트랜잭션이 샤드 안에서 끝나게 함
- **시간에 따라 값이 바뀌지 않음**: 키가 바뀌면 행을 다른 샤드로 옮겨야 함

```sql
-- 샤딩 키(user_id)를 포함한 조회: 한 샤드만 접근
SELECT * FROM orders WHERE user_id = 12345 AND status = 'PAID';   -- 샤드 = hash(12345) % N

-- 샤딩 키가 없는 조회: 모든 샤드에 질의 후 병합 (피해야 할 패턴)
SELECT * FROM orders WHERE created_at > '2026-09-01' ORDER BY created_at DESC LIMIT 20;
```

**샤딩이 만드는 새로운 문제**

- **전역 유니크 ID**: 샤드별 AUTO_INCREMENT는 충돌하므로 UUID·Snowflake 같은 분산 ID 생성기가 필요함
- **샤드 간 조인·집계**: 애플리케이션에서 병합하거나, 집계용 데이터를 별도 저장소(검색 엔진·DW)로 복제
- **샤드 간 트랜잭션**: 사실상 포기하고 멱등·보상 패턴(unit04)으로 최종적 일관성을 택함
- **리샤딩(Resharding)**: 샤드를 추가·축소할 때 데이터 이동이 필요하며, 무중단으로 하려면 이중 쓰기·검증 기간이 필요함

> 💡 샤딩 키 질문의 모범 답안 구조: **"쿼리 패턴을 먼저 분석해 대부분의 조회가 포함하는 컬럼(보통 사용자 ID·테넌트 ID)을 키로 잡고, 해시로 고르게 분산하되, 같은 키의 연관 데이터를 같은 샤드에 두어 샤드 간 조인을 피한다."**

<br>

### 6. 정리

| **주제**               | **핵심 한 줄**                                                                   |
| ---------------------- | -------------------------------------------------------------------------------- |
| **확장 순서**          | 튜닝 → 캐시 → 스케일 업 → 복제(읽기) → 파티셔닝 → 샤딩(쓰기)                       |
| **복제**               | 프라이머리 쓰기, 레플리카 읽기. 변경 로그를 재실행해 동기화. 고가용성도 제공        |
| **읽기 분산**          | 읽기 전용 트랜잭션 여부로 라우팅. 커넥션 획득 시점 주의                            |
| **복제 지연**          | 없앨 수 없음. 쓰기 직후 읽기는 프라이머리로, 지연 허용 조회만 레플리카로            |
| **파티셔닝 vs 샤딩**   | 같은 인스턴스 안 논리 분할 vs 여러 인스턴스로 물리 분할                             |
| **샤딩 키**            | 고른 분포 + 대부분의 쿼리에 포함 + 연관 데이터 동일 샤드 + 불변                    |
| **샤딩의 대가**        | 전역 ID, 샤드 간 조인·트랜잭션 포기, 리샤딩 비용                                   |
