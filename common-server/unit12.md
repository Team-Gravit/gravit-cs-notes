## 관측성

**관측성(Observability)**은 시스템이 밖으로 내보내는 데이터(로그·메트릭·트레이스)만으로 **"지금 안에서 무슨 일이 일어나고 있는가"**를 알아낼 수 있는 성질이다. 서버가 여러 대, 서비스가 여러 개로 나뉜 환경에서는 `ssh`로 들어가 로그를 뒤지는 방식이 통하지 않으므로, 장애를 **빨리 알아차리고(메트릭) → 어디서 났는지 찾고(트레이싱) → 왜 났는지 읽는(로그)** 구조를 처음부터 설계해야 한다.

<br>

### 1. 모니터링과 관측성, 세 가지 신호

- **모니터링**은 "미리 정한 지표를 보고 임계치를 넘으면 알린다"는 **알려진 문제**에 대한 대응임
- **관측성**은 "예상 못 한 문제가 나도 데이터로 원인을 추적할 수 있다"는 **모르는 문제**에 대한 준비임

| **신호**             | **무엇인가**                                  | **답하는 질문**                      | **특징**                               |
| -------------------- | --------------------------------------------- | ------------------------------------ | -------------------------------------- |
| **로그 (Logs)**      | 시점별 **이벤트 기록**                        | 그때 정확히 무슨 일이 있었나?        | 상세하지만 양이 많고 검색 비용 큼      |
| **메트릭 (Metrics)** | 시간에 따른 **수치의 집계**                   | 지금 상태가 정상인가? 추세는?        | 저렴, 알림·대시보드에 적합, 상세 부족  |
| **트레이스 (Traces)**| 하나의 요청이 거친 **경로와 구간별 시간**     | 느린 요청은 어디서 시간을 썼나?      | 서비스 간 흐름 파악, 샘플링 필요       |

```
[장애 대응 흐름]
메트릭: 오류율 5% ↑ 알림 ──▶ 트레이스: 느린 요청은 결제 서비스 → DB 구간에서 2.8초 소요
                                       ──▶ 로그: trace_id 로 검색 → "lock wait timeout" (unit03)
세 신호는 trace_id 같은 공통 식별자로 이어져야 한다
```

> 💡 세 신호를 각각 아는 것보다 **어떻게 연결하는가**가 핵심이다. "메트릭으로 감지 → 트레이스로 위치 특정 → 로그로 원인 확인"의 흐름을 설명하면 관측성을 이해한 것으로 평가받는다.

<br>

### 2. 구조화 로그

사람이 읽기 좋은 문장형 로그는 **기계가 검색·집계하기 어렵다**. "사용자 7의 주문 실패 건만 최근 1시간에서 찾기" 같은 질의를 하려면 로그가 **키-값 구조(JSON 등)**여야 한다.

```
문장형:  2026-09-08 10:21:03 ERROR OrderService - 주문 실패 user=7 order=1001 reason=OUT_OF_STOCK (took 312ms)
구조화:  {"ts":"2026-09-08T10:21:03Z","level":"ERROR","logger":"OrderService","msg":"order failed",
          "user_id":7,"order_id":1001,"reason":"OUT_OF_STOCK","duration_ms":312,
          "trace_id":"4bf92f3577b34da6","span_id":"00f067aa0ba902b7","service":"order-api","version":"1.4.2"}
```

```python
import json, logging, sys

class JsonFormatter(logging.Formatter):
    def format(self, record):
        payload = {
            "ts": self.formatTime(record, "%Y-%m-%dT%H:%M:%S%z"),
            "level": record.levelname,
            "logger": record.name,
            "msg": record.getMessage(),
            **getattr(record, "ctx", {}),          # user_id, order_id, trace_id 등 컨텍스트
        }
        if record.exc_info:
            payload["exception"] = self.formatException(record.exc_info)
        return json.dumps(payload, ensure_ascii=False)

handler = logging.StreamHandler(sys.stdout)          # 파일이 아니라 stdout → 수집기가 가져감
handler.setFormatter(JsonFormatter())
log = logging.getLogger("OrderService")
log.addHandler(handler)

log.error("order failed", extra={"ctx": {"user_id": 7, "order_id": 1001, "reason": "OUT_OF_STOCK"}})
```

**로그 설계 원칙**

| **원칙**                             | **설명**                                                                     |
| ------------------------------------ | ---------------------------------------------------------------------------- |
| **공통 필드 표준화**                 | `ts`, `level`, `service`, `version`, `trace_id`를 모든 서비스가 같은 이름으로 |
| **컨텍스트를 자동으로**              | 요청 진입 시 `trace_id`·`user_id`를 스레드/코루틴 컨텍스트(MDC 등)에 넣어 모든 로그에 자동 포함 |
| **레벨을 의미 있게**                 | ERROR는 사람이 봐야 하는 것만. 예상된 실패(잘못된 입력)는 WARN·INFO            |
| **민감 정보 마스킹**                 | 비밀번호·토큰·카드번호·주민번호는 절대 기록하지 않음. 이메일·전화는 마스킹      |
| **stdout으로, 파일 관리는 수집기가** | 컨테이너 환경(unit11)에서는 stdout → 수집 에이전트 → 중앙 저장소(검색 엔진 등) |
| **비용 통제**                        | 디버그 로그 남발은 저장·검색 비용. 샘플링·보관 기간·레벨 동적 조정             |

> ⚠️ 로그에 "무엇이 실패했는지"만 남기고 **식별자(주문 ID, 사용자 ID, trace_id)**를 빠뜨리면, 장애 때 수만 줄 중 그 한 건을 찾을 수 없다. 로그 한 줄은 "나중에 이 줄로 무엇을 검색할 것인가"를 생각하고 쓴다.

### 3. 메트릭 수집

**메트릭 타입**

| **타입**            | **의미**                                       | **예시**                                     | **주의**                                  |
| ------------------- | ---------------------------------------------- | -------------------------------------------- | ----------------------------------------- |
| **카운터 (Counter)**| **증가만** 하는 누적값                          | 총 요청 수, 오류 수                          | 절대값보다 **증가율(rate)**로 봄           |
| **게이지 (Gauge)**  | 오르내리는 **현재 값**                          | 활성 커넥션 수, 큐 길이, 메모리 사용량       | 순간값이라 스파이크를 놓칠 수 있음        |
| **히스토그램 (Histogram)** | 값의 **분포**를 구간별로 집계               | 응답 시간, 요청 크기                         | 평균이 아니라 **백분위(p95·p99)**를 봄     |

```java
// Micrometer 예시 — 주문 처리 시간 히스토그램과 실패 카운터
Timer orderTimer = Timer.builder("order.process.duration")
    .tag("type", "standard")
    .publishPercentiles(0.5, 0.95, 0.99)
    .register(meterRegistry);

orderTimer.record(() -> orderService.process(request));
meterRegistry.counter("order.failed", "reason", "OUT_OF_STOCK").increment();
```

- 메트릭은 이름 + **레이블(태그)**로 식별됨. `status=500`, `endpoint=/orders`처럼 차원을 붙이면 원하는 조합으로 집계 가능
- **레이블 카디널리티 폭발** 주의: `user_id`처럼 값이 무한히 늘어나는 것을 레이블로 쓰면 시계열 수가 폭발해 저장소가 죽음. 그런 정보는 로그·트레이스에 둠

**무엇을 봐야 하는가 — RED와 USE**

| **관점**                 | **지표**                                                     | **대상**             |
| ------------------------ | ------------------------------------------------------------ | -------------------- |
| **RED** (요청 중심)      | **R**ate(초당 요청 수) · **E**rrors(오류율) · **D**uration(응답 시간 분포) | API·서비스           |
| **USE** (자원 중심)      | **U**tilization(사용률) · **S**aturation(포화도·대기열) · **E**rrors(오류) | CPU·메모리·커넥션 풀·스레드 풀 |

- 서비스 대시보드는 RED, 인프라·자원 대시보드는 USE로 구성하면 빠짐없이 볼 수 있음
- 백엔드에서 특히 중요한 게이지: **커넥션 풀 활성/대기 수**(unit10), **스레드 풀 큐 길이**, **컨슈머 랙**(unit06), **캐시 히트율**(unit05), **복제 지연**(unit07)
- 수집 방식은 서버가 엔드포인트를 열어 두고 수집기가 주기적으로 긁어가는 **풀(Pull)** 방식(Prometheus 계열)과 서버가 밀어 보내는 **푸시(Push)** 방식이 있으며, 도구에 따라 다름

```
[응답 시간을 평균으로 보면 안 되는 이유]
요청 100건: 95건은 50ms, 5건은 3,000ms
평균 = 197ms ("괜찮네")   p95 = 50ms   p99 = 3,000ms ("1%의 사용자는 3초를 기다린다")
```

### 4. 분산 트레이싱

### 4-1. 개념과 구조

하나의 사용자 요청이 게이트웨이 → 주문 서비스 → 결제 서비스 → DB로 흘러갈 때, **각 구간의 시작·끝 시각을 기록하고 하나의 ID로 묶은 것**이 **트레이스(Trace)**다. 각 구간을 **스팬(Span)**이라 하며, 스팬은 부모-자식 관계로 트리를 이룬다.

```
trace_id = 4bf92f35...                                  0ms        500ms      1000ms     1500ms
├─ [gateway]      GET /orders/1001                      ├────────────────────────────────────┤
│  └─ [order-api]   getOrder                                ├────────────────────────────────┤
│     ├─ [order-api]   SELECT orders                          ├──┤ 40ms
│     ├─ [payment-api] GET /payments?orderId=1001                 ├──────────────────────┤ 1,100ms  ← 병목
│     │  └─ [payment-api] SELECT payments                             ├───────────────────┤ 1,050ms (락 대기?)
│     └─ [order-api]   cache.get(user:7)                                                   ├┤ 3ms
```

- **trace_id**: 요청 전체를 식별. 모든 서비스·로그에 같은 값이 실림
- **span_id / parent_span_id**: 구간과 호출 관계를 표현
- 각 스팬에는 서비스명·작업명·시작/종료 시각·속성(HTTP 상태, SQL 문 요약)·오류 여부가 붙음

<br>

### 4-2. 컨텍스트 전파

트레이스가 서비스 경계를 넘으려면 **호출할 때 trace_id를 함께 전달**해야 한다. HTTP에서는 W3C Trace Context 표준의 `traceparent` 헤더가 널리 쓰인다.

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  └─ trace_id (16바이트)            └─ parent span_id     └─ 플래그(샘플링 여부)
             └─ 버전
```

- HTTP 클라이언트·서버, 메시지 프로듀서·컨슈머(unit06, 메시지 헤더로 전달), DB 클라이언트에 **자동 계측(Auto-instrumentation)**을 붙이면 대부분의 스팬은 코드 수정 없이 생성됨. OpenTelemetry가 사실상의 표준
- 비동기 처리(스레드 풀, 코루틴, 큐)에서는 컨텍스트가 **끊기기 쉬움**. 실행기(Executor)를 컨텍스트 전파 가능한 것으로 감싸거나 메시지 헤더에 명시적으로 실어야 함
- **샘플링**: 모든 요청을 기록하면 비용이 크므로 일정 비율만 저장하되, 오류·느린 요청은 우선 보존하는 **테일 샘플링** 전략을 씀

```java
// 수동 스팬 예시 (OpenTelemetry) — 자동 계측이 닿지 않는 내부 로직 구간을 표시
Span span = tracer.spanBuilder("inventory.reserve").startSpan();
try (Scope scope = span.makeCurrent()) {
    span.setAttribute("product.id", productId);
    inventoryService.reserve(productId, qty);        // 이 안의 DB 호출은 자식 스팬으로 자동 생성
} catch (Exception e) {
    span.recordException(e);
    span.setStatus(StatusCode.ERROR);
    throw e;
} finally {
    span.end();
}
```

> 💡 로그에 `trace_id`를 넣는 것(2절)과 트레이싱은 **같은 ID로 연결**될 때 힘을 발휘한다. 트레이스 화면에서 느린 스팬을 찾고, 그 `trace_id`로 로그를 검색해 예외 메시지를 읽는 것이 실제 디버깅 흐름이다.

### 5. 알림 설계

- **증상 기반 알림**: "CPU 80%"보다 **"오류율 2% 초과", "p99 지연 1초 초과"**처럼 사용자가 겪는 증상을 기준으로 알림. 자원 지표는 원인 분석용 대시보드에
- **SLO 기반**: "월간 가용성 99.9%" 같은 목표(SLO)를 정하고, 오류 예산(Error Budget) 소진 속도로 알림 강도를 결정
- **알림 피로 방지**: 조치가 필요 없는 알림은 제거. 새벽에 울리는 알림은 **반드시 사람이 뭔가 해야 하는 것**이어야 함
- **런북(Runbook) 연결**: 알림에 "무엇을 확인하고 어떻게 조치하는가" 문서를 링크해 대응 시간을 줄임

<br>

### 6. 면접·실무 체크포인트

- 로그·메트릭·트레이스가 각각 **어떤 질문에 답하고**, 실제 장애 대응에서 **어떤 순서로 연결**되는지 설명할 수 있는가
- 구조화 로그가 왜 필요한지, 모든 로그에 **trace_id·식별자**를 자동으로 싣는 방법(MDC·컨텍스트)을 아는가
- 카운터·게이지·히스토그램의 차이와, 응답 시간을 **평균이 아닌 백분위**로 봐야 하는 이유를 말할 수 있는가
- 메트릭 레이블에 `user_id`를 넣으면 안 되는 이유(**카디널리티 폭발**)를 아는가
- RED/USE로 대시보드를 구성하고, 커넥션 풀·컨슈머 랙·복제 지연처럼 **백엔드 특유의 지표**를 챙기는가
- 트레이스의 trace_id·span 구조, **`traceparent` 헤더로 컨텍스트를 전파**하는 방식, 비동기 구간에서 끊기는 이유를 설명할 수 있는가
- 알림을 **증상(오류율·지연) 기준**으로 설계하고 알림 피로를 관리하는가
