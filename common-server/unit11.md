## 배포와 무중단 전환

**배포(Deployment)**는 새 버전의 코드를 운영 환경에서 실행 상태로 만드는 과정이고, **무중단 배포(Zero-downtime Deployment)**는 그 과정에서 사용자 요청이 실패하거나 끊기지 않게 하는 것이다. 컨테이너가 "어디서나 같은 실행 환경"을 제공하지만, **어떤 순서로 구버전을 내리고 신버전을 올릴지, 신버전이 준비됐는지 어떻게 판단할지**는 여전히 설계의 몫이다.

<br>

### 1. 컨테이너 기반 배포

컨테이너는 애플리케이션과 그 실행 환경(런타임, 라이브러리, 설정)을 **이미지(Image)**라는 불변 단위로 묶는다. "내 PC에서는 되는데 서버에서는 안 됨" 문제를 줄이고, 배포를 **"이미지를 받아 실행"**이라는 단순한 동작으로 바꾼다.

| **구분**            | **전통 배포 (서버에 직접 설치)**             | **컨테이너 배포**                                   |
| ------------------- | -------------------------------------------- | --------------------------------------------------- |
| **배포 단위**       | 빌드 산출물(jar·바이너리) + 서버 설정         | **이미지** (앱 + 런타임 + 의존성)                   |
| **환경 일관성**     | 서버마다 다를 수 있음                        | 이미지가 같으면 어디서나 동일                       |
| **롤백**            | 이전 산출물 재배포, 설정 되돌리기 필요        | **이전 이미지 태그로 재실행**                       |
| **확장**            | 서버 준비·설정에 시간                        | 같은 이미지를 여러 개 띄우면 됨 (unit10 스케일 아웃) |
| **부팅 속도**       | VM 수 분                                     | 수 초                                               |

```dockerfile
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
COPY build/libs/app.jar app.jar
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75"
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

**이미지 운영 원칙**

- **불변(Immutable) 이미지**: 실행 중인 컨테이너에 들어가 고치지 않음. 수정은 새 이미지 빌드 → 재배포로만
- **태그는 고유하게**: `latest` 대신 커밋 해시·버전(`app:1.4.2`, `app:a1b2c3d`)으로 태그해 "지금 무엇이 떠 있는지"와 롤백 대상을 명확히 함
- **설정은 이미지 밖으로**: DB 주소·비밀 키는 환경 변수·시크릿으로 주입. 같은 이미지를 개발·스테이징·운영에 그대로 씀
- **프로세스 하나, 로그는 표준 출력으로**: 컨테이너 안에서 파일로 로그를 쌓지 않고 stdout으로 내보내 수집기가 가져가게 함 (unit12)
- **컨테이너 메모리 제한을 인지**: JVM 등 런타임이 컨테이너 한계를 인식하지 못하면 OOM으로 강제 종료됨. 런타임 버전에 따라 기본 동작이 다를 수 있으므로 힙 상한을 명시함

> 💡 오케스트레이터(쿠버네티스 등)는 "원하는 상태(레플리카 3개, 이미지 v2)"를 선언하면 현재 상태를 거기에 맞추는 방식으로 동작한다. 아래 배포 전략들은 이 **선언적 모델 위에서 "구버전을 신버전으로 어떤 순서로 바꿀지"**를 정하는 것이다.

### 2. 배포 전략

### 2-1. 롤링 배포 (Rolling)

인스턴스를 **한 번에 한 개(또는 일정 비율)씩** 신버전으로 교체한다. 추가 자원이 거의 필요 없어 가장 널리 쓰인다.

```
시작:   [v1] [v1] [v1] [v1]
1단계:  [v2] [v1] [v1] [v1]   ← v2 하나 띄우고 준비 확인 → v1 하나 내림
2단계:  [v2] [v2] [v1] [v1]
3단계:  [v2] [v2] [v2] [v1]
완료:   [v2] [v2] [v2] [v2]
        교체 중에는 v1과 v2가 동시에 트래픽을 받는다
```

- **장점**: 추가 서버 불필요, 점진적이라 문제 발견 시 중간에 멈출 수 있음
- **단점**: **구버전과 신버전이 공존**하는 시간이 있음 → API·DB 스키마가 양쪽과 호환돼야 함(4절). 롤백도 다시 롤링이라 시간이 걸림

<br>

### 2-2. 블루-그린 배포 (Blue-Green)

현재 운영 중인 환경(**블루**)과 동일한 규모의 새 환경(**그린**)을 준비해 신버전을 띄우고, 검증이 끝나면 **로드밸런서의 트래픽을 한 번에 전환**한다.

```
전환 전:  [LB] ──▶ 블루 [v1][v1][v1]          그린 [v2][v2][v2] (대기, 내부 검증)
전환:     [LB] ──▶ 그린 [v2][v2][v2]          블루 [v1][v1][v1] (대기, 롤백용 유지)
문제 시:  [LB] ──▶ 블루 로 즉시 되돌림 (수 초)
```

- **장점**: 버전 공존 시간이 거의 없음, **롤백이 즉각적**(LB 스위치만 되돌림), 전환 전 그린에서 실제 환경 테스트 가능
- **단점**: **자원이 2배** 필요, DB 스키마는 여전히 양쪽 호환 필요(롤백 대비), 전환 순간 진행 중이던 요청·세션 처리 주의

<br>

### 2-3. 카나리 배포 (Canary)

신버전을 **소수 인스턴스(또는 트래픽의 1~5%)**에만 먼저 내보내고, 오류율·지연(unit12)을 관찰하며 비율을 늘려 간다. 롤링·블루그린과 결합해 "위험을 작게 노출"하는 전략이다.

| **전략**          | **추가 자원** | **버전 공존** | **롤백 속도**     | **위험 노출 범위**    | **적합한 경우**                          |
| ----------------- | ------------- | ------------- | ----------------- | --------------------- | ---------------------------------------- |
| **롤링**          | 거의 없음     | 있음          | 느림 (재롤링)     | 점진적 전체           | 일반적인 상시 배포                       |
| **블루-그린**     | **2배**       | 거의 없음     | **즉시**          | 전환 순간 전체        | 롤백이 빨라야 하는 중요 서비스            |
| **카나리**        | 소량          | 있음 (의도적) | 빠름 (비율 0으로) | **소수 사용자**       | 큰 변경, 성능 영향이 불확실한 배포        |

> ⚠️ 어떤 전략이든 **"트래픽을 받기 전에 준비됐는지"**와 **"내리기 전에 처리 중인 요청을 끝냈는지"**를 확인하지 않으면 무중단이 아니다. 이 두 지점을 담당하는 것이 헬스 체크와 그레이스풀 셧다운이다(3절).

<br>

### 3. 헬스 체크와 그레이스풀 셧다운

**헬스 체크의 종류**

| **종류**                    | **질문**                                      | **실패 시 조치**                          | **검사 내용 예**                                       |
| --------------------------- | --------------------------------------------- | ----------------------------------------- | ------------------------------------------------------ |
| **Liveness (살아 있는가)**  | 프로세스가 복구 불가능하게 멈췄는가            | 컨테이너 **재시작**                       | 프로세스 응답 여부, 데드락 여부                        |
| **Readiness (준비됐는가)**  | 지금 트래픽을 받아도 되는가                    | 로드밸런서에서 **제외** (재시작 아님)     | 초기화 완료, DB·캐시 연결, 캐시 워밍 완료              |
| **Startup (기동 중인가)**   | 초기화가 아직 진행 중인가                      | 완료 전까지 Liveness 검사 유예            | 느린 부팅 앱에서 Liveness 오판 방지                    |

```yaml
readinessProbe:
  httpGet: { path: /health/ready, port: 8080 }
  initialDelaySeconds: 5
  periodSeconds: 5
  failureThreshold: 3            # 3회 연속 실패 시 트래픽 제외
livenessProbe:
  httpGet: { path: /health/live, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3            # 3회 연속 실패 시 컨테이너 재시작
```

**흔한 함정**

- **Liveness에 DB 연결을 넣음**: DB가 잠시 느려지면 모든 컨테이너가 동시에 재시작되어 장애가 커짐. 외부 의존성 검사는 Readiness에만
- **Readiness 없이 배포**: 신버전이 부팅 중인데 트래픽이 들어가 5xx 발생 → "배포할 때마다 잠깐 에러"의 원인
- **헬스 체크 자체가 무거움**: 매번 복잡한 쿼리를 실행하면 헬스 체크가 부하가 됨. 가볍고 빠르게

**그레이스풀 셧다운(Graceful Shutdown)** — 구버전 인스턴스를 내릴 때 **처리 중인 요청을 끝내고, 새 요청은 받지 않은 채** 종료하는 절차다.

```
① 종료 신호(SIGTERM) 수신
② Readiness 를 실패로 전환 → 로드밸런서가 새 요청을 보내지 않게 됨 (전파에 수 초 소요)
③ 잠시 대기 (LB 전파 시간) → 이미 들어온 요청은 계속 처리
④ 새 요청 거부, 진행 중 요청 완료 대기 (상한: 예 30초)
⑤ 커넥션 풀·메시지 컨슈머 정리 → 프로세스 종료
   상한 초과 시 오케스트레이터가 SIGKILL 로 강제 종료
```

```java
// Spring Boot 예시 — 서버가 종료 신호를 받으면 진행 중 요청을 마친 뒤 종료
// application.yml:
//   server.shutdown: graceful
//   spring.lifecycle.timeout-per-shutdown-phase: 30s
@PreDestroy
public void onShutdown() {
    messageConsumer.stop();        // 새 메시지 수신 중단, 처리 중 메시지는 완료 후 커밋
}
```

- 오케스트레이터의 **종료 유예 시간(terminationGracePeriod)**이 애플리케이션의 셧다운 대기보다 짧으면 강제 종료되므로 두 값을 맞춤
- 메시지 컨슈머(unit06)는 처리 중 메시지를 커밋하지 못한 채 죽으면 재처리되므로, 멱등성이 없다면 셧다운 순서가 특히 중요함

<br>

### 4. 버전 공존과 하위 호환

롤링·카나리에서는 구버전과 신버전이 **동시에** 트래픽을 받고 **같은 DB**를 본다. 따라서 "신버전만 되는" 변경은 무중단 배포를 깨뜨린다.

**DB 스키마 변경 — 확장·수축(Expand-Contract) 패턴**

```
목표: 컬럼 user_name 을 nickname 으로 변경
1) 확장:  nickname 컬럼 추가 (nullable) — v1·v2 모두 동작
2) 이중 쓰기: v2 는 두 컬럼에 모두 쓰고, 배치로 기존 데이터 복사
3) 전환:  모든 인스턴스가 v2 가 된 뒤 읽기를 nickname 으로
4) 수축:  다음 배포에서 user_name 컬럼 제거
```

- **한 배포에서 "컬럼 삭제·이름 변경·NOT NULL 추가"를 하지 않음**. 구버전이 아직 그 컬럼을 쓰고 있음
- API도 같은 원칙: 필드 추가는 안전, 삭제·의미 변경은 여러 배포에 걸쳐 단계적으로 (unit08 버전 관리)
- 캐시·메시지 형식도 버전 공존을 전제로 설계함. 신버전이 넣은 캐시를 구버전이 읽어도 깨지지 않아야 함
- 대용량 테이블의 스키마 변경은 락으로 서비스를 멈출 수 있으므로 **온라인 DDL 도구**나 DBMS의 온라인 변경 기능을 사용함

> 💡 "무중단 배포를 어떻게 하겠는가"라는 질문에 롤링·블루그린 이름만 대면 절반이다. **Readiness 헬스 체크, 그레이스풀 셧다운, DB 스키마의 하위 호환(확장·수축)**까지 답해야 실제로 해 본 사람의 답이 된다.

<br>

### 5. 정리 — 무중단 배포 체크리스트

| **항목**                        | **확인 질문**                                                             |
| ------------------------------- | ------------------------------------------------------------------------- |
| **이미지**                      | 불변인가, 태그가 고유한가, 설정이 밖으로 빠져 있는가                       |
| **전략 선택**                   | 자원 여유·롤백 속도·위험 노출 범위 기준으로 롤링/블루그린/카나리를 골랐는가 |
| **Readiness**                   | 초기화·의존성 준비를 확인한 뒤에만 트래픽을 받는가                         |
| **Liveness**                    | 외부 의존성을 넣어 연쇄 재시작을 유발하지 않는가                           |
| **그레이스풀 셧다운**           | 종료 신호 → 트래픽 제외 → 진행 중 요청 완료 → 종료 순서와 유예 시간이 맞는가 |
| **버전 공존**                   | DB 스키마·API·캐시·메시지가 구버전과 호환되는가 (확장·수축)                 |
| **롤백 계획**                   | 이전 이미지로 몇 초 안에 돌아갈 수 있는가, DB 변경은 롤백 가능한가          |
| **관측**                        | 배포 직후 오류율·지연·자원 지표를 보고 있는가 (unit12)                      |
