## 비동기 메시징

**비동기 메시징(Asynchronous Messaging)**은 요청을 즉시 처리하는 대신 **메시지 큐(Message Queue)**에 넣어 두고 다른 프로세스가 나중에 꺼내 처리하는 통신 방식이다. 응답 지연을 줄이고 시스템 간 결합을 끊어 주지만, "메시지가 두 번 오거나 순서가 바뀔 수 있다"는 새로운 전제를 받아들여야 하므로 **도입 판단 기준과 전달 보장 모델**을 정확히 이해해야 한다.

<br>

### 1. 동기 호출의 한계와 메시지 큐 도입 판단

주문 API가 "주문 저장 → 결제 → 재고 차감 → 알림 발송 → 통계 집계"를 모두 동기로 수행하면, 응답 시간은 모든 단계의 합이 되고 알림 서버 장애가 주문 실패로 번진다.

```
[동기]  클라이언트 → 주문 서버 → 결제(300ms) → 알림(500ms) → 통계(200ms) → 응답 (1초+)
                                  하나라도 죽으면 주문 전체 실패

[비동기] 클라이언트 → 주문 서버 → 주문 저장 + "주문됨" 메시지 발행 → 응답 (50ms)
                                            │
                                     [메시지 큐] ──▶ 알림 컨슈머 (독립적으로 처리·재시도)
                                                 ──▶ 통계 컨슈머
```

**도입을 고려해야 하는 신호**

| **신호**                                       | **큐가 해결하는 방식**                                          |
| ---------------------------------------------- | --------------------------------------------------------------- |
| **응답에 꼭 필요 없는 후속 작업**이 응답을 늦춤 | 후속 작업을 큐로 넘겨 응답 시간 단축                            |
| **트래픽이 폭주**해 다운스트림(DB·외부 API)이 버티지 못함 | 큐가 **버퍼** 역할, 컨슈머가 처리 가능한 속도로 소비   |
| 한 시스템 장애가 **다른 시스템 장애로 전파**됨 | 발행자는 큐에만 의존, 컨슈머 장애 시 메시지는 큐에 남음          |
| 한 이벤트를 **여러 시스템**이 각자 처리해야 함 | 발행-구독(Pub/Sub)으로 발행자가 구독자를 몰라도 됨               |
| **실패 시 재시도**가 필요한 작업이 많음        | 컨슈머가 실패한 메시지를 재처리, 최종 실패는 DLQ로 격리          |

**도입하지 말아야 할 경우**

- 호출자가 **결과를 즉시 알아야** 하는 작업(재고 확인, 인증) — 비동기로 바꾸면 폴링·콜백이 필요해 오히려 복잡해짐
- 트래픽이 작고 후속 작업이 가벼워 동기로도 충분한 경우 — 큐 운영 비용(브로커 관리, 모니터링, 멱등성 처리)이 이득보다 큼

> 💡 "메시지 큐를 왜 도입했나"에 "비동기 처리를 위해서"라고만 답하면 부족하다. **응답 시간 단축·부하 완충(버퍼링)·장애 격리·시스템 간 결합도 감소** 중 어떤 문제를 풀었는지, 그리고 그 대가로 **중복·순서·지연**을 어떻게 다뤘는지까지 답해야 한다.

<br>

### 2. 메시지 브로커의 두 계열

| **구분**               | **큐 모델** (RabbitMQ, SQS 등)                   | **로그 모델** (Kafka 등)                                |
| ---------------------- | ------------------------------------------------ | ------------------------------------------------------- |
| **메시지 보관**        | 컨슈머가 확인(ack)하면 **삭제**                  | 보존 기간 동안 **로그에 유지**, 컨슈머는 위치만 기억     |
| **재소비**             | 어려움 (이미 삭제됨)                             | **오프셋을 되돌려** 다시 읽기 가능                       |
| **라우팅**             | 익스체인지·라우팅 키로 유연한 분배               | 토픽·파티션 기준의 단순한 구조                          |
| **처리량**             | 중간                                             | **매우 높음** (순차 디스크 쓰기, 배치)                   |
| **적합한 용도**        | 작업 큐, 요청-응답, 복잡한 라우팅                | 이벤트 스트림, 로그 수집, 여러 시스템이 같은 이벤트 소비 |

이 유닛의 파티션·오프셋 설명은 로그 모델(Kafka)을 기준으로 하되, 전달 보장·멱등 소비 원칙은 두 계열에 공통으로 적용된다.

<br>

### 3. 파티션과 오프셋

### 3-1. 구조

**토픽(Topic)**은 메시지의 논리적 분류이고, 토픽은 여러 **파티션(Partition)**으로 나뉜다. 각 파티션은 **추가만 가능한(append-only) 순서 있는 로그**이며, 메시지 위치를 **오프셋(Offset)**이라는 정수로 가리킨다.

```
토픽 "order-events"
파티션 0: [0][1][2][3][4][5] ──▶ (뒤에 계속 추가)        컨슈머 A가 담당 (현재 오프셋 4)
파티션 1: [0][1][2][3] ──▶                                  컨슈머 B가 담당 (현재 오프셋 3)
파티션 2: [0][1][2][3][4][5][6][7] ──▶                      컨슈머 B가 담당 (현재 오프셋 6)
                      ▲
          컨슈머 그룹 "notification-service" 의 커밋된 오프셋 = "여기까지 처리했다"
```

- **파티션 = 병렬 처리 단위**: 파티션이 3개면 같은 컨슈머 그룹에서 최대 3개 컨슈머가 동시에 소비할 수 있음. 컨슈머가 파티션보다 많으면 남는 컨슈머는 놀게 됨
- **컨슈머 그룹(Consumer Group)**: 같은 그룹 안에서는 파티션을 나눠 갖고(작업 분배), 다른 그룹은 각자 전체를 읽음(발행-구독)
- **오프셋 커밋**: 컨슈머가 "어디까지 처리했는지"를 브로커에 기록. 컨슈머가 재시작되면 커밋된 오프셋부터 다시 읽음

<br>

### 3-2. 메시지는 어느 파티션으로 가는가

- **키(key)가 있으면** `hash(key) % 파티션 수`로 결정 → **같은 키는 항상 같은 파티션**
- 키가 없으면 라운드 로빈 또는 배치 단위로 분산

```java
// 같은 주문의 이벤트는 같은 파티션에 → 주문 단위 순서 보장
producer.send(new ProducerRecord<>("order-events", orderId.toString(), payload));
```

> ⚠️ 파티션 수를 나중에 늘리면 `hash(key) % 파티션 수` 결과가 바뀌어 **같은 키가 다른 파티션으로 가기 시작**한다. 순서 보장에 의존하는 토픽은 파티션 수를 처음부터 여유 있게 잡고, 늘려야 한다면 순서가 깨질 수 있음을 감안해야 한다.

<br>

### 4. 전달 보장 모델

메시지가 "몇 번 전달되는가"에 대한 약속이다. 어떤 시점에 오프셋을 커밋하느냐가 모델을 결정한다.

| **모델**                | **의미**                             | **컨슈머 동작**                                   | **위험**                |
| ----------------------- | ------------------------------------ | ------------------------------------------------- | ----------------------- |
| **At-most-once**        | 0번 또는 1번. **유실 가능**          | 오프셋 **먼저 커밋** → 처리                        | 처리 중 죽으면 유실     |
| **At-least-once**       | 1번 이상. **중복 가능**              | 처리 → 오프셋 **나중에 커밋**                      | 커밋 전 죽으면 재처리   |
| **Exactly-once**        | 정확히 1번                           | 브로커 트랜잭션 + 멱등 프로듀서, 또는 **멱등 컨슈머** | 범위·성능 제약          |

```
[At-least-once 에서 중복이 생기는 순간]
컨슈머: 메시지 #7 읽기 → 알림 발송 (완료) → 오프셋 커밋 직전에 프로세스 종료
재시작: 커밋된 오프셋은 6 → 메시지 #7 을 다시 읽음 → 알림이 두 번 발송됨
```

**실무 기본값은 At-least-once + 멱등 컨슈머**

- 유실은 대부분 허용되지 않으므로 At-most-once는 로그·메트릭처럼 빠져도 되는 데이터에만 씀
- Exactly-once는 브로커 안(읽기 → 처리 → 다른 토픽 쓰기)에서는 지원되지만, **외부 시스템(DB, 이메일 발송)까지 포함한 정확히 한 번은 브로커가 보장할 수 없음**. 결국 컨슈머가 멱등해야 함(unit04)

```python
def handle(message):
    event_id = message.headers["event-id"]
    # 처리 기록과 실제 처리를 하나의 DB 트랜잭션으로 묶는다 → 재전달 시 두 번째는 건너뜀
    with db.transaction():
        inserted = db.execute(
            "INSERT INTO processed_events (event_id) VALUES (%s) ON CONFLICT DO NOTHING",
            event_id,
        )
        if inserted.rowcount == 0:
            return                            # 이미 처리한 메시지
        send_notification(message.body)       # 실제 처리
    consumer.commit()                         # 처리·기록 후 오프셋 커밋
```

> 💡 "Exactly-once를 지원한다"는 브로커 문구를 보고 컨슈머 멱등성을 생략하면 안 된다. 면접에서는 **"at-least-once를 전제로 컨슈머를 멱등하게 만든다"**가 정답에 가까운 태도다.

### 5. 순서 보장

메시지 큐는 기본적으로 **전체 순서를 보장하지 않는다**. 보장되는 범위와 조건을 정확히 알아야 한다.

| **범위**                        | **보장 여부**  | **조건**                                                       |
| ------------------------------- | -------------- | -------------------------------------------------------------- |
| **하나의 파티션 안**            | **보장**       | 파티션은 순서 있는 로그이므로 쓰인 순서대로 읽힘                |
| **같은 키의 메시지끼리**        | **보장**       | 같은 키 → 같은 파티션 (3-2절)                                   |
| **토픽 전체**                   | 보장 안 됨     | 파티션이 여럿이면 파티션 간 순서는 무관                         |
| **재시도 중인 메시지와 다음 메시지** | 깨질 수 있음 | 실패한 메시지를 뒤로 미루면 순서 역전                           |

**순서가 중요한 경우의 설계**

- "주문 생성 → 주문 취소"처럼 **같은 개체의 이벤트**는 개체 ID를 키로 사용해 한 파티션에 모음
- 컨슈머는 파티션당 **단일 스레드**로 처리함. 파티션 안에서 멀티스레드로 처리하면 순서가 깨짐
- 순서 역전에 대비해 이벤트에 **버전·타임스탬프**를 넣고, 컨슈머가 오래된 이벤트를 무시하도록 함
- 처리량과 순서는 트레이드오프임: 파티션 수를 늘리면 처리량은 오르지만 순서 보장 범위는 키 단위로 좁아짐

<br>

### 6. 실패 처리와 운영 포인트

- **재시도(Retry)**: 일시 오류는 백오프를 두고 재시도. 같은 파티션을 막지 않도록 **재시도 토픽**으로 옮기는 방식도 흔함
- **DLQ(Dead Letter Queue)**: 재시도 상한을 넘긴 메시지를 별도 큐에 격리해 나머지 처리를 막지 않게 함. 격리된 메시지는 원인 분석 후 수동 재처리
- **컨슈머 랙(Consumer Lag)**: "마지막 오프셋 − 커밋된 오프셋". 랙이 계속 커지면 컨슈머가 처리량을 못 따라가는 것이므로 파티션·컨슈머 증설 또는 처리 최적화 필요 (unit12 메트릭 참고)
- **발행 유실 방지**: DB 저장과 발행이 따로 실패하지 않도록 **트랜잭셔널 아웃박스**(unit04) 사용
- **포이즌 메시지(Poison Message)**: 형식 오류로 영원히 실패하는 메시지는 재시도해도 소용없으므로 즉시 DLQ로 보냄

```
발행자 ──▶ [주 토픽] ──▶ 컨슈머 ──(실패)──▶ [재시도 토픽] ──(N회 실패)──▶ [DLQ] ──▶ 알림·수동 처리
                          └──(성공)──▶ 오프셋 커밋
```

### 7. 면접·실무 체크포인트

- 메시지 큐 도입 이유를 **응답 시간·버퍼링·장애 격리·결합도** 중 무엇으로 설명할 수 있는가, 반대로 도입하면 안 되는 경우는 무엇인가
- **파티션이 병렬 처리 단위**이고 **오프셋이 처리 위치**임을 알고, 컨슈머 수가 파티션 수를 넘으면 왜 놀게 되는지 설명할 수 있는가
- At-least-once에서 **어느 시점에 중복이 생기는지**(처리 후 커밋 전 장애)를 타임라인으로 설명할 수 있는가
- Exactly-once가 **외부 시스템까지 보장되지 않는** 이유와, 그래서 **멱등 컨슈머**가 필요한 이유를 아는가
- 순서 보장 범위가 **파티션(키) 단위**임을 알고, 같은 개체의 이벤트를 같은 키로 보내는 이유를 설명할 수 있는가
- DLQ·재시도 토픽·컨슈머 랙 모니터링 등 **운영 관점의 실패 처리**를 설계에 포함했는가
