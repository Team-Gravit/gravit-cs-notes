## 분산 환경의 정합성

서버가 여러 대로 늘어나고 결제·알림·외부 API처럼 **서로 다른 시스템에 걸친 작업**이 생기면, 단일 DB 트랜잭션(unit01)과 락(unit03)만으로는 "정확히 한 번" 처리를 보장할 수 없다. 이 유닛은 그 빈틈을 메우는 세 가지 도구 — **분산 락**, **멱등성 키**, **재시도와 중복 처리 설계** — 를 다룬다.

<br>

### 1. 왜 분산 환경에서는 정합성이 어려운가

단일 서버·단일 DB에서는 "트랜잭션 하나로 묶으면" 끝났지만, 분산 환경에서는 다음 전제가 무너진다.

- **공유 메모리가 없음**: 서버 A의 `synchronized`는 서버 B를 막지 못함
- **네트워크는 실패함**: 요청은 갔는데 응답만 유실되면 호출자는 "성공했는지 모르는" 상태가 됨
- **부분 실패**: 결제는 됐는데 주문 저장에 실패하는 식으로 시스템마다 결과가 달라질 수 있음

```
클라이언트 ── 결제 요청 ──▶ 결제 서버 (승인 완료, DB 반영)
클라이언트 ◀── 응답 ✕ ──── (타임아웃, 네트워크 유실)
클라이언트 ── 결제 요청 재전송 ──▶ 결제 서버 → 같은 결제가 두 번?  ← 중복 처리 문제
```

> 💡 분산 시스템 설계의 출발점은 **"네트워크 요청은 항상 0번·1번·2번 이상 도착할 수 있다"**는 가정이다. 이 가정에서 "여러 번 와도 결과가 같게" 만드는 것이 멱등성이고, "동시에 와도 하나만 진행하게" 만드는 것이 분산 락이다.

<br>

### 2. 분산 락 (Distributed Lock)

**분산 락**은 여러 서버(프로세스)가 공유하는 외부 저장소(Redis, ZooKeeper, DB 등)에 "내가 자원 X를 쓰고 있다"는 표시를 남겨 **서버 경계를 넘어 상호 배제**를 구현하는 기법이다.

- 대표 사용처: 선착순 쿠폰 발급, 배치 작업의 중복 실행 방지, 여러 테이블·여러 시스템에 걸친 갱신의 직렬화
- DB 행 락(unit03)으로 충분하다면 분산 락은 **불필요**함. 분산 락은 "DB 락으로 표현되지 않는 자원"이나 "DB 부하를 앞단에서 줄이고 싶을 때" 선택함

**Redis 기반 구현** — 가장 흔한 구현은 Redis의 **`SET key value NX PX ttl`** 명령이다. `NX`(없을 때만 설정)로 원자적 획득을, `PX`(만료 시간)로 장애 시 자동 해제를 보장한다.

```python
import uuid, redis

r = redis.Redis()

def acquire(resource: str, ttl_ms: int = 3000) -> str | None:
    token = str(uuid.uuid4())                     # 내 락임을 증명하는 값
    ok = r.set(f"lock:{resource}", token, nx=True, px=ttl_ms)
    return token if ok else None

RELEASE = """
-- 해제: 값이 내 토큰일 때만 삭제. 비교와 삭제가 원자적이어야 하므로 Lua 스크립트 사용
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
"""

def release(resource: str, token: str) -> None:
    r.eval(RELEASE, 1, f"lock:{resource}", token)
```

**흔한 함정**

| **함정**                          | **무슨 일이 생기나**                                                            | **대응**                                                   |
| --------------------------------- | ------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| **TTL 없이 락 획득**              | 락을 잡은 서버가 죽으면 영원히 해제되지 않음                                    | 반드시 만료 시간 설정                                      |
| **남의 락을 해제**                | A의 작업이 TTL보다 길어져 만료 → B가 획득 → A가 끝나며 B의 락을 지움            | 고유 토큰 비교 후 삭제 (위 Lua 스크립트)                   |
| **TTL보다 긴 작업**               | 락이 풀린 상태로 두 서버가 동시에 실행됨                                        | 작업 시간 예측·TTL 여유, 또는 락 연장(watchdog)            |
| **락 안에서 트랜잭션 커밋 전 해제** | 락은 풀렸는데 DB에는 아직 반영 전 → 다음 서버가 옛 값을 읽음                     | **커밋 이후에** 락 해제 (락 범위 ⊇ 트랜잭션 범위)          |
| **단일 Redis 장애**               | 락 저장소가 죽으면 전체 서비스 정지, 복제 지연 중 두 서버가 동시에 획득 가능    | 가용성 요구에 따라 Redlock·ZooKeeper 등 검토, 최종 방어는 DB |

> ⚠️ 분산 락은 **"거의 항상" 상호 배제를 보장하는 도구**이지, 수학적으로 완벽한 보장이 아니다(시계 오차·GC 정지·네트워크 분할). 그래서 분산 락을 걸었더라도 최종 정합성은 **DB의 원자적 UPDATE나 유니크 제약**으로 한 번 더 지켜야 한다.

### 3. 멱등성과 멱등성 키

**멱등성(Idempotency)**은 같은 요청을 **여러 번 수행해도 결과가 한 번 수행한 것과 같은** 성질이다. 네트워크 재전송·클라이언트 더블 클릭·메시지 큐의 재전달(unit06)이 모두 "같은 요청이 두 번 도착"하는 상황이므로, 쓰기 API는 멱등하게 설계하는 것이 원칙이다.

| **연산**                              | **멱등한가** | **이유**                                             |
| ------------------------------------- | ------------ | ---------------------------------------------------- |
| `UPDATE account SET balance = 100`    | **O**        | 몇 번 실행해도 100                                   |
| `UPDATE account SET balance = balance - 100` | **X** | 실행할 때마다 100씩 줄어듦                           |
| `DELETE FROM orders WHERE id = 7`     | **O**        | 두 번째부터는 대상이 없을 뿐 상태는 동일             |
| `INSERT INTO orders (...) VALUES (...)` | **X**      | 실행할 때마다 행이 추가됨                            |
| `INSERT ... ` + **유니크 제약**       | **O**        | 두 번째는 제약 위반으로 실패하지만 최종 상태는 동일  |

**멱등성 키(Idempotency Key)** — 본질적으로 멱등하지 않은 연산(결제, 주문 생성, 포인트 차감)을 멱등하게 만드는 표준 기법이다. 클라이언트가 요청마다 **고유 키**를 생성해 보내고, 서버는 그 키로 **"이미 처리한 요청인지"**를 판단한다.

```
클라이언트                          서버                            저장소
   │── POST /payments ──────────▶  키 조회 ─────────────────────▶  idempotency_key 없음
   │   Idempotency-Key: abc-123    처리 + 결과 저장 (키, 응답) ──▶  저장 (유니크 제약)
   │◀── 201 Created ──────────────
   │
   │── POST /payments (재전송) ──▶  키 조회 ─────────────────────▶  abc-123 존재
   │   Idempotency-Key: abc-123    처리하지 않고 저장된 응답 반환
   │◀── 201 Created (동일 응답) ──
```

```java
@Transactional
public PaymentResponse pay(String idempotencyKey, PaymentRequest req) {
    // 1) 키를 먼저 INSERT — 유니크 제약이 동시 요청의 최종 심판자
    try {
        idempotencyRepository.save(new IdempotencyRecord(idempotencyKey, "IN_PROGRESS"));
    } catch (DataIntegrityViolationException e) {
        IdempotencyRecord r = idempotencyRepository.findByKey(idempotencyKey);
        if (r.isCompleted()) return r.getStoredResponse();   // 이미 처리됨 → 같은 응답
        throw new RequestInProgressException();              // 아직 처리 중 → 409로 안내
    }
    // 2) 실제 처리
    PaymentResponse res = paymentGateway.charge(req);
    // 3) 결과를 키와 함께 저장 (같은 트랜잭션)
    idempotencyRepository.complete(idempotencyKey, res);
    return res;
}
```

**설계 포인트**

- 키는 **클라이언트가 생성**(UUID)하고 재시도 시 **같은 키**를 보내야 의미가 있음
- 키 저장은 **유니크 제약이 있는 저장소**에 해야 동시 요청 두 개가 모두 "처음"으로 판단되는 경쟁을 막을 수 있음. Redis `SET NX`도 가능하나 응답 본문까지 저장하려면 DB가 편함
- 키에는 **만료 기간**(예: 24시간)을 두어 무한히 쌓이지 않게 함
- 같은 키인데 요청 본문이 다르면 재전송이 아니라 오류이므로 **422/400으로 거절**하는 것이 안전함

> 💡 HTTP 메서드 자체의 멱등성(GET·PUT·DELETE는 멱등, POST는 아님)은 **unit08**에서 다룬다. "POST는 멱등하지 않으니 멱등성 키로 멱등하게 만든다"가 두 유닛을 잇는 문장이다.

### 4. 재시도와 중복 처리

### 4-1. 재시도가 안전하려면

재시도(Retry)는 일시적 장애(네트워크 순단, 타임아웃, 락 충돌)를 넘기는 가장 기본적인 수단이지만, **멱등하지 않은 작업을 재시도하면 중복이 발생**한다. 즉 "재시도 가능성"과 "멱등성"은 항상 한 쌍으로 설계해야 한다.

| **원칙**                           | **설명**                                                                  |
| ---------------------------------- | ------------------------------------------------------------------------- |
| **재시도할 오류를 구분**           | 타임아웃·503·락 충돌은 재시도, 400·401·422 같은 클라이언트 오류는 즉시 실패 |
| **지수 백오프 + 지터**             | 1s → 2s → 4s처럼 간격을 늘리고 무작위 지연을 더해 동시 재시도 폭주 방지     |
| **횟수·총 시간 상한**              | 무한 재시도는 장애를 길게 만들 뿐. 상한 초과 시 실패 처리·알림             |
| **멱등성 키 동반**                 | 재전송이 서버에서 중복 처리되지 않도록 같은 키 사용                        |
| **서킷 브레이커와 결합**           | 상대가 완전히 죽었으면 재시도 자체를 멈춤 (unit10 참고)                    |

```python
import random, time

def call_with_retry(fn, max_attempts=4, base=0.5):
    for attempt in range(1, max_attempts + 1):
        try:
            return fn()
        except TransientError:                       # 타임아웃·503 등만 잡는다
            if attempt == max_attempts:
                raise
            sleep = base * (2 ** (attempt - 1)) + random.uniform(0, 0.2)   # 지수 백오프 + 지터
            time.sleep(sleep)
```

<br>

### 4-2. 중복 처리를 막는 세 가지 층

재시도가 여러 경로(클라이언트, 게이트웨이, 메시지 큐)에서 일어날 수 있으므로 중복 방어도 여러 층에 둔다.

- **API 계층**: 멱등성 키 (같은 응답을 재사용)
- **DB 계층**: 유니크 제약 — 코드가 실수해도 두 번째 INSERT는 반드시 실패함. 가장 단순하고 확실한 방어선
- **메시징 계층**: at-least-once 전달을 전제로 컨슈머가 처리한 메시지 ID를 저장해 중복을 건너뜀

<br>

### 5. 여러 시스템에 걸친 작업 — 보상과 아웃박스

"주문 저장(DB) + 결제(외부) + 알림(큐)"처럼 하나의 트랜잭션으로 묶을 수 없는 작업은 다음 패턴으로 다룬다.

- **보상 트랜잭션(Compensating Transaction)**: 뒤 단계가 실패하면 앞 단계를 "취소하는 작업"을 실행함(결제 취소 등). 이 흐름을 조율하는 것이 사가(Saga) 패턴
- **트랜잭셔널 아웃박스(Transactional Outbox)**: "DB 저장"과 "메시지 발행"이 따로 실패하는 문제를 막기 위해, 메시지를 **같은 DB 트랜잭션 안의 outbox 테이블에 먼저 기록**하고 별도 프로세스가 큐로 전달함. 메시지는 at-least-once로 전달되므로 컨슈머는 멱등해야 함(unit06)

```
[아웃박스 흐름]
TX ┌ INSERT orders (주문)            ┐  같은 트랜잭션 → 둘 다 성공하거나 둘 다 실패
   └ INSERT outbox (ORDER_CREATED)  ┘
릴레이 프로세스: outbox에서 미발행 행 읽기 → 큐 발행 → published=true 표시
```

> ⚠️ 2단계 커밋(2PC) 같은 분산 트랜잭션은 이론적으로 원자성을 주지만, 참여자 하나가 느려지면 전체가 묶이고 코디네이터 장애 시 복구가 어려워 **일반 웹 서비스에서는 거의 쓰지 않는다**. 대신 "멱등 + 재시도 + 보상"으로 **최종적 일관성(Eventual Consistency)**을 택하는 것이 일반적이다.

### 6. 정리

| **도구**            | **해결하는 문제**                             | **핵심 구현**                                       | **한계·주의**                                    |
| ------------------- | --------------------------------------------- | --------------------------------------------------- | ------------------------------------------------ |
| **분산 락**         | 여러 서버의 **동시 실행** 차단                | `SET NX PX` + 고유 토큰 + Lua 해제                   | TTL·락 범위·저장소 장애. DB 제약으로 최종 방어   |
| **멱등성 키**       | 같은 요청의 **중복 처리** 차단                | 클라이언트 생성 키 + 유니크 저장 + 응답 재사용       | 키 만료·본문 불일치 처리                         |
| **재시도**          | **일시 장애** 극복                            | 재시도 대상 구분 + 지수 백오프 + 지터 + 상한         | 멱등하지 않은 작업에 쓰면 중복 발생              |
| **유니크 제약**     | 코드 실수까지 막는 **최후 방어**              | 업무 키(주문번호·결제키)에 UNIQUE                    | 제약 위반 예외를 정상 흐름으로 처리해야 함       |
| **아웃박스·보상**   | 여러 시스템에 걸친 **부분 실패**              | 같은 TX에 이벤트 기록 → 릴레이 발행 / 취소 작업 정의 | 최종적 일관성, 컨슈머 멱등성 전제                |

- 면접 한 줄 요약: **"분산 환경에서는 요청이 0번·1번·여러 번 도착할 수 있다고 가정하고, 동시 실행은 분산 락으로, 중복 실행은 멱등성 키와 유니크 제약으로, 일시 장애는 백오프 재시도로 대응한다."**
