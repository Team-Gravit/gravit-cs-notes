## 인덱스와 실행 계획

**인덱스(Index)**는 테이블 전체를 훑지 않고 원하는 행을 빠르게 찾기 위한 별도의 자료구조이고, **실행 계획(Execution Plan)**은 DBMS 옵티마이저가 "이 쿼리를 어떤 순서·방법으로 처리하겠다"고 결정한 결과다. 서버 성능 문제의 상당수는 결국 "인덱스를 안 탄 쿼리" 하나에서 시작되므로, 인덱스가 언제 쓰이고 언제 무시되는지를 구조 수준에서 이해해야 한다.

<br>

### 1. B-Tree 인덱스의 구조

대부분의 RDBMS는 인덱스를 **B-Tree(정확히는 B+Tree)**로 구현한다. 키가 정렬된 채로 저장되며, 루트에서 리프까지의 깊이가 어느 키든 같다(균형 트리).

```
                 [ 30 | 60 ]                 ← 루트 노드
               /      |      \
        [10|20]    [40|50]    [70|80]        ← 브랜치 노드
        /  |  \    /  |  \    /  |  \
  [1..9][10..19][20..29] ... [80..89]        ← 리프 노드 (정렬됨, 서로 연결됨)
     └────────── 리프끼리 연결 리스트 → 범위 검색에 유리 ──────────┘
```

- **탐색 비용은 O(log N)**: 수천만 행이어도 트리 깊이는 보통 3~4단계라 디스크 접근이 몇 번이면 끝남
- 리프 노드가 **정렬된 연결 리스트**이므로 `BETWEEN`, `>`, `ORDER BY`, `LIKE 'abc%'` 같은 **범위·정렬 조건에 강함**
- 반대로 정렬 순서를 활용할 수 없는 조건(`!=`, 앞부분 와일드카드 등)에는 약함

**클러스터드 인덱스 vs 세컨더리 인덱스 (MySQL InnoDB 기준)**

| **구분**                  | **클러스터드 인덱스**                       | **세컨더리(논클러스터드) 인덱스**                  |
| ------------------------- | ------------------------------------------- | -------------------------------------------------- |
| **대상**                  | **PK** (테이블당 1개)                       | 개발자가 추가한 인덱스 (여러 개 가능)              |
| **리프 노드에 있는 것**   | **실제 행 데이터 전체**                     | 인덱스 컬럼 값 + **PK 값**                         |
| **조회 흐름**             | 인덱스 → 바로 데이터                        | 세컨더리 인덱스 → PK → 클러스터드 인덱스 → 데이터  |
| **시사점**                | PK 순서로 물리 저장, PK는 짧고 단조 증가 권장 | 인덱스가 많을수록 쓰기 비용 증가                   |

> 💡 세컨더리 인덱스로 찾은 뒤 PK로 다시 데이터를 찾아가는 과정을 **"디스크 랜덤 I/O"**라고 생각하면 된다. 조회 결과 행 수가 많아지면 이 랜덤 I/O 비용이 풀 스캔보다 커져서 옵티마이저가 인덱스를 **일부러 안 쓰는** 일이 생긴다(4절).

<br>

### 2. 인덱스가 성능을 바꾸는 방식

인덱스는 **읽기를 빠르게 하는 대신 쓰기를 느리게** 만든다. INSERT·UPDATE·DELETE마다 관련된 모든 인덱스 트리를 갱신해야 하기 때문이다.

- **선택도(Selectivity)**: 조건으로 걸러지는 행의 비율. 성별처럼 값 종류가 적으면(카디널리티 낮음) 인덱스 효과가 거의 없음
- **인덱스는 검색 조건(WHERE)·조인 조건(ON)·정렬(ORDER BY)·그룹(GROUP BY)에 쓰이는 컬럼**에 만듦
- 인덱스가 너무 많으면 쓰기 성능·저장 공간·옵티마이저 판단 비용이 모두 늘어남

```sql
-- 카디널리티 확인: 값 종류가 적은 컬럼은 인덱스 후보에서 제외
SELECT COUNT(DISTINCT status), COUNT(*) FROM orders;   -- 5 / 10,000,000 → 부적합
SELECT COUNT(DISTINCT user_id), COUNT(*) FROM orders;  -- 2,000,000 / 10,000,000 → 적합
```

<br>

### 3. 복합 인덱스와 컬럼 순서

여러 컬럼을 묶은 **복합 인덱스(Composite Index)**는 **첫 번째 컬럼으로 먼저 정렬하고, 같은 값 안에서 두 번째 컬럼으로 정렬**한 구조다. 그래서 컬럼 순서가 곧 사용 가능 여부를 결정한다.

```
INDEX (user_id, created_at) 의 리프 노드 정렬 상태
(1, 01-01) (1, 01-05) (1, 02-10) (2, 01-03) (2, 03-01) (3, 01-01) ...
 └── user_id 로 먼저 정렬 ──┘ └── 같은 user_id 안에서 created_at 정렬 ──┘

WHERE user_id = 2                       → 사용 O  (앞 컬럼)
WHERE user_id = 2 AND created_at > ...  → 사용 O  (앞 컬럼 + 범위)
WHERE created_at > ...                  → 사용 X  (앞 컬럼 없이 뒤 컬럼만: 정렬 이용 불가)
```

**컬럼 순서를 정하는 원칙 (왼쪽 접두어, Leftmost Prefix 규칙)**

| **원칙**                                 | **이유**                                                       |
| ---------------------------------------- | -------------------------------------------------------------- |
| **등치(=) 조건 컬럼을 앞에**             | 등치로 좁힌 뒤 범위 조건을 적용해야 스캔 범위가 최소가 됨      |
| **범위(>, <, BETWEEN) 컬럼은 뒤에**      | 범위 조건 이후의 컬럼은 인덱스 정렬을 더 이상 활용하지 못함    |
| **자주 단독으로 쓰이는 컬럼을 앞에**     | 접두어만으로도 인덱스를 탈 수 있어 인덱스 개수를 줄일 수 있음  |
| **정렬(ORDER BY) 컬럼을 마지막에**       | 인덱스 순서 그대로 읽으면 별도 정렬(filesort)이 사라짐         |

```sql
-- 안티패턴: 범위 컬럼이 앞에 있어 status 조건에는 인덱스를 못 씀
CREATE INDEX idx_orders_bad ON orders (created_at, status);
SELECT * FROM orders WHERE status = 'PAID' AND created_at > '2026-01-01';

-- 개선: 등치 조건(status)을 앞에, 범위 조건(created_at)을 뒤에
CREATE INDEX idx_orders_good ON orders (status, created_at);
```

> ⚠️ `(a, b)` 인덱스가 있으면 `(a)` 단독 인덱스는 대부분 **불필요한 중복**이다. 반대로 `(a, b)`가 있어도 `b`만으로 조회하는 쿼리는 인덱스를 타지 못하므로 별도 인덱스가 필요하다.

<br>

### 4. 커버링 인덱스

쿼리에 필요한 **모든 컬럼이 인덱스 안에 있어서 테이블(클러스터드 인덱스)에 접근하지 않아도 되는** 경우를 **커버링 인덱스(Covering Index)**라고 한다. 세컨더리 인덱스 → PK → 데이터로 이어지는 랜덤 I/O가 사라지므로 매우 빠르다.

```sql
CREATE INDEX idx_orders_user ON orders (user_id, created_at);

-- 커버링: user_id, created_at 모두 인덱스에 있음 → 테이블 접근 없음
SELECT user_id, created_at FROM orders WHERE user_id = 7;

-- 커버링 아님: amount는 인덱스에 없어 행마다 테이블을 찾아감
SELECT user_id, created_at, amount FROM orders WHERE user_id = 7;
```

- MySQL 실행 계획의 `Extra` 컬럼에 **`Using index`**가 표시되면 커버링 인덱스가 동작한 것임
- 페이징 최적화에서도 자주 쓰임: 커버링 인덱스로 PK만 먼저 뽑고, 그 PK로 필요한 행만 조인하는 방식
- 단, 커버링을 위해 컬럼을 무작정 추가하면 인덱스가 비대해져 쓰기·메모리 비용이 커짐

<br>

### 5. 인덱스가 사용되지 않는 조건

인덱스가 있어도 옵티마이저가 쓰지 못하거나, 쓰지 않기로 판단하는 대표 상황이다.

| **상황**                              | **예시**                                        | **원인 / 개선**                                              |
| ------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------ |
| **인덱스 컬럼을 가공**                | `WHERE YEAR(created_at) = 2026`                 | 저장된 값과 비교 불가 → `created_at >= '2026-01-01' AND < '2027-01-01'` |
| **암시적 형변환**                     | `WHERE phone = 01012345678` (phone은 VARCHAR)   | 컬럼 쪽이 변환됨 → 리터럴 타입을 컬럼에 맞춤 `'01012345678'` |
| **앞부분 와일드카드**                 | `WHERE name LIKE '%철수'`                       | 정렬 순서를 이용할 수 없음 → 전문 검색 인덱스 검토           |
| **부정 조건**                         | `WHERE status != 'DONE'`, `NOT IN`              | 대부분의 행이 해당 → 풀 스캔이 더 쌈. 긍정 조건으로 재작성   |
| **OR로 다른 컬럼 결합**               | `WHERE a = 1 OR b = 2`                          | 각각 인덱스가 있으면 병합 가능하나 종종 풀 스캔. `UNION`으로 분리 |
| **복합 인덱스의 앞 컬럼 누락**        | `INDEX(a, b)`에서 `WHERE b = 1`                 | 왼쪽 접두어 규칙 위반(3절)                                    |
| **선택도가 낮음**                     | 전체의 30%가 해당하는 조건                      | 옵티마이저가 풀 스캔이 더 싸다고 판단 (정상 동작)            |
| **NULL 비교 방식**                    | `WHERE col IS NOT NULL`                         | 해당 행이 많으면 풀 스캔 선택                                |

```sql
-- 안티패턴: 함수 적용 + 암시적 형변환
SELECT * FROM users WHERE DATE(created_at) = '2026-09-01' AND phone = 1012345678;

-- 개선: 컬럼은 그대로 두고 범위 조건으로, 리터럴 타입은 컬럼에 맞춤
SELECT * FROM users
WHERE  created_at >= '2026-09-01' AND created_at < '2026-09-02'
AND    phone = '01012345678';
```

> ⚠️ "인덱스를 안 탄다 = 버그"가 아니다. 결과가 전체의 상당 비율이면 **풀 스캔이 정답**일 수 있다. 실행 계획을 보고 옵티마이저가 왜 그 선택을 했는지 통계(카디널리티·행 수 추정)를 확인하는 것이 먼저다.

<br>

### 6. 실행 계획 읽기

`EXPLAIN`을 붙이면 옵티마이저가 선택한 접근 방식을 보여 준다. MySQL 기준으로 가장 먼저 봐야 할 컬럼은 **`type`, `key`, `rows`, `Extra`**다.

```sql
EXPLAIN SELECT id, created_at FROM orders WHERE user_id = 7 ORDER BY created_at DESC LIMIT 20;
```

```
id | select_type | table  | type | key             | rows | Extra
---+-------------+--------+------+-----------------+------+-------------
1  | SIMPLE      | orders | ref  | idx_orders_user | 120  | Using index
```

**`type` 컬럼 — 접근 방식 (좋음 → 나쁨)**

| **type**   | **의미**                                             | **판단**              |
| ---------- | ---------------------------------------------------- | --------------------- |
| **const**  | PK·유니크 인덱스로 단 1행 조회                       | 최상                  |
| **ref**    | 유니크가 아닌 인덱스로 등치 조회                     | 양호                  |
| **range**  | 인덱스 범위 스캔 (`BETWEEN`, `>`, `IN`)              | 양호 (범위가 좁을 때) |
| **index**  | 인덱스 **전체**를 처음부터 끝까지 스캔               | 주의                  |
| **ALL**    | 테이블 풀 스캔                                       | 대용량이면 위험       |

**`Extra` 컬럼 — 자주 보는 값**

- **`Using index`**: 커버링 인덱스 동작 (좋음)
- **`Using where`**: 인덱스로 가져온 뒤 추가 필터링 (흔함)
- **`Using filesort`**: 인덱스 순서를 못 써서 별도 정렬 수행 → ORDER BY 컬럼을 인덱스에 포함하는 것을 검토
- **`Using temporary`**: 임시 테이블 생성 (GROUP BY·DISTINCT 등) → 대용량이면 튜닝 대상

> 💡 PostgreSQL은 `EXPLAIN ANALYZE`로 **실제 실행 시간과 추정 행 수**를 함께 보여 준다. 추정 행 수(rows)와 실제 행 수가 크게 다르면 통계가 오래된 것이므로 `ANALYZE`로 통계를 갱신하는 것이 튜닝의 시작이다. MySQL도 8.0 이후 `EXPLAIN ANALYZE`를 지원하며, 출력 형식은 버전에 따라 다를 수 있다.

### 7. 정리 — 인덱스 설계 체크리스트

| **질문**                                                  | **확인 포인트**                                                  |
| --------------------------------------------------------- | ---------------------------------------------------------------- |
| **B-Tree가 왜 범위 검색에 강한가**                        | 리프 노드가 정렬된 연결 리스트라서 시작점을 찾은 뒤 순차 스캔     |
| **세컨더리 인덱스 조회가 왜 느려질 수 있는가**            | 인덱스 → PK → 데이터의 랜덤 I/O. 결과가 많으면 풀 스캔이 더 쌈    |
| **복합 인덱스 컬럼 순서는 어떻게 정하는가**               | 등치 → 범위 순, 자주 단독 사용되는 컬럼 앞, 정렬 컬럼 마지막      |
| **커버링 인덱스란**                                       | 필요한 컬럼이 전부 인덱스에 있어 테이블 접근 생략 (`Using index`) |
| **인덱스를 못 타는 대표 조건 3가지**                      | 컬럼 가공(함수), 암시적 형변환, 앞부분 와일드카드 LIKE            |
| **실행 계획에서 가장 먼저 볼 것**                         | `type`(ALL·index 경계), `key`(실제 사용 인덱스), `rows`, `Extra`  |
| **인덱스를 늘리면 생기는 비용**                           | 쓰기 지연, 저장 공간, 옵티마이저 판단 비용                       |

- 동시성 문제로 인한 락 대기는 인덱스와 별개의 문제이나, **인덱스가 없으면 락 범위가 넓어져** 데드락이 늘어난다는 점은 **unit03**에서 이어서 다룬다
