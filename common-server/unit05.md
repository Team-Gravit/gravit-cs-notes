## 캐시 전략

**캐시(Cache)**는 비용이 큰 연산(DB 조회, 외부 API, 복잡한 계산)의 결과를 더 빠른 저장소에 복사해 두고 재사용하는 기법이다. 잘 쓰면 DB 부하를 수십 배 줄이지만, "원본과 다른 값을 보여 주는" 정합성 문제와 "만료 순간 요청이 몰리는" 스탬피드 문제를 함께 데려오므로 **읽기·쓰기 전략, TTL, 무효화 방식**을 의도적으로 설계해야 한다.

<br>

### 1. 캐시가 효과적인 조건

캐시는 만능이 아니다. 다음 조건을 만족할수록 효과가 크다.

- **읽기가 쓰기보다 압도적으로 많음**: 상품 정보, 게시글 조회, 설정값 등. 쓰기마다 캐시를 갱신·삭제해야 하므로 쓰기가 잦으면 이득이 줄어듦
- **접근이 일부 키에 집중됨**(핫 데이터): 파레토 법칙처럼 상위 20% 데이터가 80% 요청을 받는 경우 작은 캐시로도 히트율이 높음
- **약간의 지연(stale)이 허용됨**: 몇 초~몇 분 전 값이어도 업무에 문제가 없는 데이터

```
캐시 적중률(Hit Ratio) = 캐시 히트 수 / 전체 조회 수
히트율 90%: DB 부하 1/10   |   히트율 50%: DB 부하 1/2 (캐시 관리 비용을 고려하면 이득이 적음)
```

**캐시 위치에 따른 구분**

| **구분**              | **로컬 캐시** (프로세스 메모리)              | **글로벌 캐시** (Redis·Memcached)              |
| --------------------- | -------------------------------------------- | ---------------------------------------------- |
| **속도**              | **가장 빠름** (네트워크 없음)                | 네트워크 왕복 필요 (1ms 내외)                  |
| **서버 간 일관성**    | 서버마다 다른 값 가능                        | **모든 서버가 같은 값**                        |
| **용량**              | 힙 메모리 한계, GC 영향                      | 별도 서버라 크게 확장 가능                     |
| **적합한 데이터**     | 거의 안 변하는 설정·코드 테이블              | 세션, 상품 정보 등 서버 간 공유가 필요한 데이터 |

<br>

### 2. 읽기 전략 — Look-aside vs Read-through

**Look-aside(Cache-aside)** — 애플리케이션이 **캐시를 먼저 확인하고, 없으면 DB에서 읽어 캐시에 채우는** 방식이다. 가장 널리 쓰이며, 캐시가 죽어도 DB로 서비스가 유지된다.

```
요청 ──▶ 캐시 조회 ──(히트)──▶ 반환
            │
          (미스)
            ▼
         DB 조회 ──▶ 캐시에 저장 (TTL) ──▶ 반환
```

```python
def get_product(product_id: int) -> dict:
    key = f"product:{product_id}"
    cached = redis.get(key)
    if cached is not None:
        return json.loads(cached)                       # 캐시 히트
    product = db.query_one("SELECT * FROM product WHERE id = %s", product_id)
    redis.set(key, json.dumps(product), ex=300)         # 미스 → DB 조회 후 5분 TTL로 저장
    return product
```

- **장점**: 구현 단순, 실제로 요청된 데이터만 캐시됨, 캐시 장애 시에도 동작
- **단점**: 첫 요청은 항상 미스(콜드 스타트), 캐시 채우는 로직이 애플리케이션 코드에 흩어짐

**Read-through** — 캐시 라이브러리나 캐시 서버가 **미스 시 DB를 대신 읽어 채우는** 방식이다. 애플리케이션은 캐시만 바라보므로 코드가 간결하지만, 캐시 계층이 DB 접근 방법을 알아야 한다. 로컬 캐시 라이브러리의 "로더(loader)" 기능이 이 방식이다.

<br>

### 3. 쓰기 전략 — Write-through vs Write-back vs Write-around

| **전략**              | **동작**                                          | **장점**                              | **단점**                                        |
| --------------------- | ------------------------------------------------- | ------------------------------------- | ----------------------------------------------- |
| **Write-through**     | 쓸 때 **캐시와 DB를 동시에** 갱신                 | 캐시가 항상 최신, 읽기 미스 적음      | 쓰기 지연 증가, 안 읽는 데이터도 캐시됨         |
| **Write-back (behind)** | **캐시에만 쓰고** 나중에 모아서 DB 반영          | 쓰기 매우 빠름, DB 쓰기 횟수 감소     | 캐시 장애 시 **데이터 유실** 위험               |
| **Write-around**      | **DB에만 쓰고** 캐시는 건드리지 않음(또는 삭제)   | 쓰기 단순, 캐시 오염 없음             | 직후 읽기는 미스 → DB 재조회                    |

- 일반 웹 서비스의 기본 조합은 **Look-aside(읽기) + Write-around(쓰기 시 캐시 삭제)**임. 단순하고 정합성 문제가 가장 적음
- **Write-through**는 "쓰자마자 읽히는" 데이터(내 프로필 수정 후 바로 조회)에 유리함
- **Write-back**은 조회수·좋아요 수처럼 유실을 감수할 수 있고 쓰기가 폭주하는 카운터에 제한적으로 사용함

> 💡 면접에서 "Look-aside와 Write-through의 차이"를 물으면 하나는 **읽기** 전략, 하나는 **쓰기** 전략이라는 점부터 짚어야 한다. 두 축은 독립적이라 조합해서 쓴다.

<br>

### 4. TTL 설계

**TTL(Time To Live)**은 캐시 항목의 수명이다. TTL이 없으면 오래된 값이 영원히 남고, 너무 짧으면 캐시 효과가 사라진다.

| **데이터 성격**                     | **TTL 예시**   | **근거**                                              |
| ----------------------------------- | -------------- | ----------------------------------------------------- |
| **거의 안 바뀜** (카테고리, 설정)   | 수 시간~1일    | 변경 시 명시적 삭제로 보완                            |
| **자주 조회, 가끔 변경** (상품)     | 수 분          | 변경 시 삭제 + TTL은 안전망                           |
| **실시간성 중요** (재고, 잔액)      | 수 초 또는 캐시 안 함 | 잘못된 값의 비용이 큼                           |
| **외부 API 응답** (환율, 날씨)      | 제공자 갱신 주기 | 호출 비용·쿼터 절약                                   |

**TTL 설계 원칙**

- TTL은 **"최대 얼마나 오래된 값을 허용하는가"**라는 업무 질문에서 출발함
- 같은 시각에 대량 저장된 키가 **동시에 만료**되지 않도록 **지터(Jitter)**를 더함: `ttl = 300 + random(0, 60)`
- "변경 시 삭제(무효화)"가 있으면 TTL은 삭제가 누락됐을 때의 **안전망** 역할이므로 길게 잡아도 됨
- 캐시 서버 메모리가 가득 차면 **퇴출 정책(Eviction Policy)**이 동작함. Redis는 `maxmemory-policy`로 LRU·LFU 등을 선택할 수 있으며 기본값은 버전·설정에 따라 다를 수 있음

<br>

### 5. 캐시 스탬피드 (Cache Stampede)

인기 키가 **만료되는 순간** 수많은 요청이 동시에 미스를 겪고 **모두 DB로 몰려가는** 현상이다. **썬더링 허드(Thundering Herd)**라고도 부르며, 트래픽이 큰 서비스에서 DB 장애의 흔한 원인이다.

```
시간 →       TTL 만료
캐시:  ████████████│(비어 있음)         │████████
요청:  히트 히트 히트│미스 미스 미스 미스 │히트
DB:    ─────────────│▲▲▲▲ 동시에 같은 쿼리 ─┘   ← 이 순간 DB 부하 급증
```

**대응 기법**

| **기법**                                   | **원리**                                                                   |
| ------------------------------------------ | -------------------------------------------------------------------------- |
| **락(뮤텍스)으로 재계산 단일화**           | 미스 시 한 요청만 DB를 조회하고 나머지는 잠시 대기 후 캐시에서 읽음         |
| **확률적 조기 갱신 (PER)**                 | 만료 직전에 일부 요청이 **확률적으로 미리** 갱신해 만료 순간을 분산          |
| **Stale-while-revalidate**                 | 만료된 값을 **일단 반환**하고 백그라운드에서 갱신                            |
| **TTL 지터**                               | 만료 시각을 흩어 놓아 동시 만료 방지                                       |
| **워밍(Warming)·배치 갱신**                | 만료를 기다리지 않고 스케줄러가 주기적으로 미리 채움                        |

```python
def get_with_lock(key: str, loader, ttl: int = 300):
    value = redis.get(key)
    if value is not None:
        return value
    lock_key = f"lock:{key}"
    if redis.set(lock_key, "1", nx=True, ex=5):            # 한 요청만 DB 조회 권한 획득
        try:
            value = loader()
            redis.set(key, value, ex=ttl + random.randint(0, 60))   # TTL 지터
            return value
        finally:
            redis.delete(lock_key)
    time.sleep(0.05)                                        # 나머지는 잠시 대기 후 재시도
    return get_with_lock(key, loader, ttl)
```

> ⚠️ 위 방식은 락을 못 잡은 요청이 대기하므로 대기 횟수 상한을 두어야 한다. 트래픽이 매우 큰 키라면 아예 **만료시키지 않고 배치로 갱신**하는 편이 안전하다.

### 6. 캐시-DB 정합성

캐시는 원본의 복사본이므로 **원본이 바뀌면 복사본도 바뀌거나 사라져야** 한다. 여기서 "어떤 순서로 무엇을 할 것인가"가 정합성을 좌우한다.

**갱신 vs 삭제**

- **갱신(Update)**: 쓰기 시 캐시에 새 값을 덮어씀. 두 쓰기가 교차하면 **오래된 값이 나중에 덮어쓰는** 경쟁이 생길 수 있음
- **삭제(Delete/Invalidate)**: 쓰기 시 캐시를 지우고 다음 읽기가 채우게 함. 경쟁 창이 훨씬 작아 **기본 선택은 삭제**

**순서 — DB 먼저, 캐시 삭제는 나중에**

| **순서**                     | **문제 시나리오**                                                          | **평가**                    |
| ---------------------------- | -------------------------------------------------------------------------- | --------------------------- |
| **캐시 삭제 → DB 쓰기**      | 삭제 직후 다른 읽기가 **옛 값**을 DB에서 읽어 캐시를 다시 채움 → 장기 불일치 | 위험                        |
| **DB 쓰기 → 캐시 삭제**      | 쓰기 중 읽기가 옛 값을 캐시할 수 있으나 곧 삭제됨. 삭제 실패 시 TTL이 안전망 | **권장**                    |

```java
// 안티패턴: 캐시 먼저 지우면 DB 쓰기 전에 옛 값이 다시 캐시된다
cache.evict(productId);
productRepository.updatePrice(productId, newPrice);

// 개선: DB 커밋 후 캐시 삭제 (트랜잭션 커밋 이벤트에 걸어 롤백 시 삭제가 실행되지 않게 함)
@Transactional
public void updatePrice(Long productId, long newPrice) {
    productRepository.updatePrice(productId, newPrice);
    eventPublisher.publishEvent(new PriceChanged(productId));   // AFTER_COMMIT 리스너에서 cache.evict
}
```

- "DB 쓰기 → 캐시 삭제"도 완벽하지는 않으므로(삭제 실패, 복제 지연 시 레플리카의 옛 값 캐싱 — unit07 참고) **TTL을 반드시 두고**, 강한 정합성이 필요한 데이터는 캐시하지 않거나 짧은 TTL을 쓴다
- 다중 서버의 로컬 캐시는 삭제 신호가 각 서버에 전달돼야 하므로 Pub/Sub 같은 **무효화 브로드캐스트**가 필요함

> 💡 "캐시와 DB 정합성을 어떻게 맞추나"라는 질문에는 **①갱신 대신 삭제 ②DB 먼저·캐시 삭제 나중 ③TTL 안전망 ④커밋 이후에 삭제** 네 가지를 순서대로 답하면 충분히 깊이 있는 답이 된다.

<br>

### 7. 정리 — 캐시 설계 체크리스트

| **질문**                                  | **기본 답**                                                       |
| ----------------------------------------- | ----------------------------------------------------------------- |
| **읽기 전략은**                           | Look-aside (캐시 미스 시 DB 조회 후 채움)                          |
| **쓰기 전략은**                           | DB 쓰기 후 캐시 **삭제** (Write-around). 즉시 재조회가 잦으면 Write-through |
| **TTL은**                                 | "허용 가능한 최대 stale 시간" + 지터                               |
| **스탬피드 대비는**                       | 락 단일화, 조기 갱신, stale-while-revalidate, 배치 워밍             |
| **정합성 순서는**                         | DB 커밋 → 캐시 삭제, 갱신보다 삭제, TTL 안전망                      |
| **캐시하면 안 되는 데이터는**             | 잔액·재고처럼 잘못된 값의 비용이 큰 것 (unit03 락으로 보호)          |
| **캐시 장애 시**                          | Look-aside면 DB로 폴백되지만 DB가 버틸 수 있는지 사전 점검 필요 (unit10) |
