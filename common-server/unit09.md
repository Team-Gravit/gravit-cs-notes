## 인증과 인가

**인증(Authentication)**은 "당신이 누구인가"를 확인하는 것이고, **인가(Authorization)**는 "확인된 당신이 이 작업을 해도 되는가"를 판단하는 것이다. HTTP는 상태를 저장하지 않으므로 로그인 상태를 요청마다 어떻게 이어 갈지 — **세션**으로 할지 **JWT**로 할지 — 가 서버 설계의 첫 결정이며, 그 선택에 따라 **토큰 갱신·로그아웃·탈취 대응** 방식이 완전히 달라진다.

<br>

### 1. 인증 vs 인가

| **구분**          | **인증 (Authentication)**                 | **인가 (Authorization)**                        |
| ----------------- | ----------------------------------------- | ----------------------------------------------- |
| **질문**          | 누구인가?                                 | 무엇을 할 수 있는가?                            |
| **수단**          | 비밀번호, OTP, 소셜 로그인, 인증서         | 역할(Role), 권한(Permission), 소유권 검사        |
| **실패 시 코드**  | **401 Unauthorized**                      | **403 Forbidden**                               |
| **순서**          | 먼저                                      | 인증 뒤에                                       |

```
요청 ──▶ [인증] 토큰·세션으로 사용자 식별 ──(실패)──▶ 401
              │ (성공: user=7, roles=[USER])
              ▼
          [인가] "주문 1001의 소유자가 user 7인가?" ──(실패)──▶ 403
              │ (성공)
              ▼
          비즈니스 로직
```

- 인가는 **역할 기반(RBAC)** 검사("관리자만 삭제 가능")와 **소유권 검사**("자기 주문만 조회 가능")가 모두 필요함. 후자를 빠뜨리면 다른 사용자의 자원을 ID만 바꿔 접근하는 취약점(IDOR)이 생김
- 인가 판단은 컨트롤러 진입 전(필터·인터셉터)뿐 아니라 **자원을 실제로 조회한 뒤** 소유자를 비교하는 서비스 계층에서도 이뤄져야 함

> ⚠️ "로그인만 되면 모든 API 호출 가능"인 서버가 의외로 많다. 인증과 인가는 별개이며, **모든 쓰기·개인정보 조회 API는 인가 검사를 개별적으로** 가져야 한다.

<br>

### 2. 세션 기반 인증

로그인 성공 시 서버가 **세션 저장소에 사용자 정보를 보관**하고, 클라이언트에는 그 저장소를 가리키는 **세션 ID**만 쿠키로 준다. 이후 요청마다 쿠키의 세션 ID로 저장소를 조회해 사용자를 식별한다.

```
로그인 ──▶ 서버: 세션 생성 { sid=ab12 → user=7 } ──▶ Set-Cookie: SESSIONID=ab12; HttpOnly; Secure
요청   ──▶ Cookie: SESSIONID=ab12 ──▶ 서버: 저장소 조회(ab12) → user=7 ──▶ 처리
로그아웃 ▶ 서버: 저장소에서 ab12 삭제 → 즉시 무효
```

- **상태는 서버에**: 클라이언트는 의미 없는 난수만 가지므로 위·변조로 얻을 것이 없음
- **즉시 무효화 가능**: 로그아웃·강제 종료·비밀번호 변경 시 저장소에서 지우면 끝
- **다중 서버에서는 공유 저장소 필요**: 서버 메모리에 세션을 두면 스케일 아웃(unit10) 시 다른 서버가 세션을 모름 → Redis 같은 **외부 세션 저장소**로 중앙화하거나, 로드밸런서의 스티키 세션을 씀(권장하지 않음)
- **요청마다 저장소 조회**: 조회 비용이 있지만 Redis 기준 1ms 내외라 대부분의 서비스에서 병목이 아님

<br>

### 3. 토큰 기반 인증 — JWT

**JWT(JSON Web Token)**는 사용자 정보(클레임)를 담은 JSON을 서버의 **비밀 키로 서명**한 토큰이다. 서버는 저장소를 조회하지 않고 **서명만 검증**해 사용자를 식별한다.

```
헤더.페이로드.서명
eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiI3Iiwicm9sZSI6IlVTRVIiLCJleHAiOjE3NTcwMDAwMDB9 . 4kD3...
   {"alg":"HS256"}       {"sub":"7","role":"USER","exp":1757000000}          HMAC(헤더.페이로드, 비밀키)
```

```python
import jwt, time

SECRET = load_secret()

def issue_access_token(user_id: int, role: str) -> str:
    payload = {"sub": str(user_id), "role": role,
               "iat": int(time.time()), "exp": int(time.time()) + 15 * 60}   # 15분
    return jwt.encode(payload, SECRET, algorithm="HS256")

def authenticate(token: str) -> dict:
    return jwt.decode(token, SECRET, algorithms=["HS256"])   # 서명·만료 검증 실패 시 예외
```

- **페이로드는 암호화되지 않고 인코딩만** 되어 있어 누구나 읽을 수 있음. 비밀번호·개인정보를 넣으면 안 됨
- **서명은 위·변조를 막을 뿐**, 토큰 자체가 유출되면 만료 전까지 누구든 그 사용자로 행동할 수 있음
- **무상태(Stateless)**: 서버가 아무것도 저장하지 않으므로 스케일 아웃이 쉽고, 서비스 간 인증 전달(마이크로서비스·외부 API)에 유리함
- **즉시 무효화가 어려움**: 서버에 상태가 없다는 장점이 그대로 "로그아웃해도 토큰은 만료 전까지 유효"라는 단점이 됨

> 💡 `alg: none` 허용, 알고리즘을 토큰 헤더에서 읽어 검증에 사용, 서명 검증 생략 등은 실제로 반복된 JWT 취약점 유형이다. **서버가 허용하는 알고리즘을 코드에 고정**하고 라이브러리의 검증 옵션을 명시적으로 켜야 한다.

<br>

### 4. 세션 vs JWT 선택 근거

| **기준**                         | **세션**                                          | **JWT**                                              |
| -------------------------------- | ------------------------------------------------- | ---------------------------------------------------- |
| **상태 저장 위치**               | 서버(저장소)                                      | 클라이언트(토큰 자체)                                |
| **요청당 비용**                  | 저장소 조회                                       | 서명 검증(CPU)                                       |
| **즉시 무효화**                  | **쉬움** (저장소 삭제)                            | 어려움 (블랙리스트 등 별도 상태 필요)                |
| **스케일 아웃**                  | 공유 세션 저장소 필요                             | **추가 인프라 없이 가능**                            |
| **다른 서비스·도메인에 전달**    | 어려움 (쿠키·저장소 공유 문제)                    | **쉬움** (토큰을 헤더로 전달)                        |
| **토큰 크기**                    | 세션 ID (수십 바이트)                             | 수백 바이트~ (클레임이 많을수록 커짐)                |
| **탈취 시 피해 범위**            | 삭제로 즉시 차단                                  | 만료까지 유효 → **짧은 만료 + 리프레시** 필요        |
| **적합한 경우**                  | 단일 웹 서비스, 즉시 차단·동시 로그인 제어가 중요  | 모바일·SPA·MSA·외부 API처럼 여러 클라이언트·서비스   |

**판단 기준**

- "JWT가 최신이라서"는 근거가 아님. **즉시 무효화가 중요한가** vs **서비스 간 전달·무상태가 중요한가**로 결정함
- 실무에서는 두 방식을 섞기도 함: JWT를 쓰되 리프레시 토큰은 서버 저장소에 두어 **무효화 가능 지점**을 확보함(5절)

<br>

### 5. 리프레시 토큰

JWT의 "탈취 시 만료까지 유효" 문제를 줄이려면 액세스 토큰의 수명을 **짧게(수 분~수십 분)** 잡아야 하는데, 그러면 사용자가 계속 재로그인해야 한다. 이를 해결하는 것이 **리프레시 토큰(Refresh Token)**이다.

| **구분**          | **액세스 토큰**                         | **리프레시 토큰**                                      |
| ----------------- | --------------------------------------- | ------------------------------------------------------ |
| **용도**          | API 호출 시 인증                        | 액세스 토큰 **재발급**                                 |
| **수명**          | 짧음 (예: 15분~1시간)                   | 김 (예: 7일~30일)                                      |
| **저장**          | 클라이언트 (서버는 저장하지 않음)       | 클라이언트 + **서버 저장소**(사용자·기기별 기록)        |
| **전송 빈도**     | 매 요청                                 | 재발급 시에만                                          |

```
로그인 ─▶ 액세스(15분) + 리프레시(14일) 발급, 리프레시는 DB/Redis에 기록
API 호출 ─▶ 액세스 토큰 검증 ─(만료: 401)─▶ 클라이언트: POST /auth/refresh (리프레시 토큰)
                                            서버: 저장소 대조 → 새 액세스 + 새 리프레시 발급 (회전)
                                                  → 이전 리프레시는 폐기
```

```java
@Transactional
public TokenPair refresh(String presented) {
    RefreshToken stored = refreshTokenRepository.findByToken(hash(presented))
        .orElseThrow(() -> new UnauthorizedException("invalid refresh token"));
    if (stored.isRevoked()) {                      // 이미 폐기된 토큰이 다시 사용됨 → 탈취 의심
        refreshTokenRepository.revokeAllOf(stored.getUserId());   // 해당 사용자의 모든 세션 종료
        throw new UnauthorizedException("refresh token reuse detected");
    }
    stored.revoke();                                              // 회전: 기존 토큰 폐기
    RefreshToken next = refreshTokenRepository.save(RefreshToken.issue(stored.getUserId()));
    return new TokenPair(issueAccessToken(stored.getUserId()), next.getRawValue());
}
```

**설계 포인트**

- **회전(Rotation)**: 재발급 때마다 리프레시 토큰도 새로 발급하고 이전 것은 폐기함
- **재사용 감지(Reuse Detection)**: 폐기된 리프레시 토큰이 다시 오면 "공격자와 정상 사용자 중 하나가 옛 토큰을 쓴 것"이므로 그 사용자의 모든 토큰을 무효화하고 재로그인시킴
- 리프레시 토큰은 **해시해서 저장**함(비밀번호처럼). 저장소가 유출돼도 원문을 알 수 없게 함
- 리프레시 토큰은 액세스 토큰보다 **더 좁은 경로**(재발급 API)에서만 전송하고, 웹이라면 `HttpOnly` 쿠키에 담음

### 6. 로그아웃과 탈취 대응

### 6-1. 로그아웃 구현

| **방식**                            | **동작**                                                      | **평가**                                            |
| ----------------------------------- | ------------------------------------------------------------- | --------------------------------------------------- |
| **세션 삭제** (세션 방식)           | 저장소에서 세션 제거                                          | 완전한 로그아웃                                     |
| **클라이언트에서 토큰 삭제만** (JWT) | 서버는 아무것도 안 함                                        | 토큰은 만료까지 유효 → 탈취된 토큰은 못 막음        |
| **리프레시 토큰 폐기** (JWT)        | 저장소의 리프레시 토큰 삭제                                   | 재발급 차단. 액세스 토큰은 짧은 만료로 자연 소멸    |
| **액세스 토큰 블랙리스트** (JWT)    | 로그아웃한 토큰 ID(`jti`)를 만료 시각까지 Redis에 보관, 요청마다 조회 | 즉시 차단 가능하나 "요청마다 저장소 조회"로 무상태 장점 일부 상실 |

- 실무 기본: **리프레시 토큰 폐기 + 짧은 액세스 토큰 만료**. 즉시 차단이 꼭 필요한 서비스(금융·관리자)는 블랙리스트를 추가함

<br>

### 6-2. 탈취를 어렵게 만들기

- **저장 위치**: 웹에서 `localStorage`는 XSS로 그대로 읽히므로, 토큰은 **`HttpOnly` + `Secure` + `SameSite` 쿠키**에 두는 것이 안전함. 쿠키를 쓰면 CSRF 대응(SameSite·CSRF 토큰)이 함께 필요함
- **짧은 수명**: 액세스 토큰 만료가 짧을수록 탈취된 토큰의 유효 시간이 줄어듦
- **바인딩 정보 검증**: 리프레시 시 기기 식별자·IP 대역·User-Agent가 크게 바뀌면 재인증 요구
- **비밀번호 변경·기기 로그아웃 시 전체 무효화**: 사용자 단위 토큰 버전(`token_version`)을 두고 검증 시 비교하면 서명 키를 바꾸지 않고도 특정 사용자 토큰을 일괄 무효화할 수 있음
- **전송 보호**: HTTPS 필수. 토큰을 URL 쿼리에 싣지 않음(로그·리퍼러로 유출)

> ⚠️ "JWT는 무상태라 저장소가 필요 없다"는 말은 **액세스 토큰에 한해서만** 사실이다. 로그아웃·탈취 대응을 제대로 하려면 리프레시 토큰 저장소나 블랙리스트 같은 **최소한의 서버 상태**가 결국 필요하다. 이 점을 인정하고 어디까지 상태를 둘지 설계하는 것이 성숙한 답이다.

<br>

### 7. 면접·실무 체크포인트

- 인증과 인가의 차이, **401과 403**의 차이, 소유권 검사를 빠뜨리면 생기는 취약점(IDOR)을 설명할 수 있는가
- 세션은 **상태가 서버에**, JWT는 **상태가 토큰에** 있다는 근본 차이에서 장단점(무효화·스케일 아웃·서비스 간 전달)을 도출할 수 있는가
- JWT 페이로드가 **암호화가 아닌 인코딩**임을 알고, 서명이 막는 것(위·변조)과 못 막는 것(탈취)을 구분하는가
- 리프레시 토큰의 목적, **회전과 재사용 감지**, 해시 저장을 설명할 수 있는가
- JWT 로그아웃의 한계와 **리프레시 폐기·블랙리스트·토큰 버전** 같은 대응책의 트레이드오프를 말할 수 있는가
- 토큰 저장 위치(`HttpOnly` 쿠키 vs `localStorage`)와 XSS·CSRF의 관계를 설명할 수 있는가
