## 선언형 UI와 Recomposition

**Jetpack Compose**는 "UI는 상태의 함수다"라는 선언형(Declarative) 모델을 따르며, 상태가 바뀌면 영향받는 컴포저블 함수만 다시 실행하는 **재구성(Recomposition)**으로 화면을 갱신한다. 상태 변경이 어떤 경로로 UI에 도달하고 재구성 범위가 어떻게 결정되는지 이해해야 성능 문제와 이상 동작을 설명할 수 있다.

<br>

### 1. 명령형 UI와 선언형 UI

기존 View 시스템은 객체를 찾아 속성을 **직접 바꾸는 명령형(Imperative)** 방식이고, Compose는 현재 상태에 대한 UI를 **묘사만 하는 선언형** 방식이다.

```kotlin
// 명령형(View 시스템): 상태가 바뀔 때마다 개발자가 직접 화면을 동기화해야 함
fun onCountChanged(count: Int) {
    countText.text = count.toString()
    resetButton.isEnabled = count > 0      // 하나라도 빠뜨리면 화면과 상태가 어긋남
}

// 선언형(Compose): 상태를 읽어 "지금 화면이 어떠해야 하는지"만 서술함
@Composable
fun Counter(count: Int, onReset: () -> Unit) {
    Text(text = count.toString())
    Button(onClick = onReset, enabled = count > 0) { Text("초기화") }
}
```

| **항목**            | **명령형 (View)**                        | **선언형 (Compose)**                          |
| ------------------- | ---------------------------------------- | --------------------------------------------- |
| **UI 갱신 방식**    | 위젯 참조를 얻어 속성을 직접 변경        | 상태 변경 → 함수 재실행으로 **자동 갱신**     |
| **진실의 원천**     | View 객체 내부 상태 + 앱 상태 (이중 관리) | 앱 상태 **하나**                              |
| **흔한 버그**       | 갱신 누락으로 화면과 상태 불일치         | 불필요한 재구성으로 인한 성능 저하            |
| **UI 정의 언어**    | XML + Kotlin                             | Kotlin만 사용                                 |

> 💡 선언형의 핵심 가치는 **"동기화 코드가 사라진다"**는 점이다. 화면 상태와 앱 상태가 어긋나는 버그의 원인 자체가 없어지며, 개발자는 "어떻게 바꿀지"가 아니라 "무엇을 보여줄지"만 기술한다.

<br>

### 2. 상태 변경이 UI로 이어지는 경로

### 2-1. Snapshot 상태와 읽기 추적

- Compose는 `mutableStateOf()`로 만든 **Snapshot 상태**를 특별하게 다룸. 일반 변수의 변경은 Compose가 감지할 수 없음
- 컴포저블이 실행되는 동안 어떤 상태 객체의 `.value`를 **읽었는지** 런타임이 기록함 → 이것이 **읽기 추적(Read Tracking)**
- 이후 그 상태에 쓰기가 발생하면 런타임은 "이 상태를 읽은 컴포저블"을 **무효화(Invalidate)**하고 다음 프레임에 재실행 대상으로 예약함

```
상태 쓰기 (state.value = 새 값)
   │
   ▼
① 스냅샷에 변경 기록 → 이 상태를 읽은 리컴포지션 스코프를 무효화
   │
   ▼
② 다음 프레임(Choreographer)에서 Recomposer가 무효화된 스코프만 재실행
   │
   ▼
③ 컴포지션(Composition)  ── 무엇을 그릴지 트리 갱신
④ 레이아웃(Layout)       ── 각 노드의 크기·위치 결정
⑤ 그리기(Draw)           ── 화면에 픽셀 출력
```

<br>

### 2-2. 세 단계와 갱신 비용

| **단계**       | **하는 일**                       | **상태를 읽으면 다시 실행되는 범위**     | **비용** |
| -------------- | --------------------------------- | ---------------------------------------- | -------- |
| **컴포지션**   | 컴포저블 실행, UI 트리 구성       | 해당 리컴포지션 스코프의 **재구성**      | 가장 큼  |
| **레이아웃**   | 측정(Measure)·배치(Place)         | 레이아웃 단계만 재실행                   | 중간     |
| **그리기**     | Canvas에 그림                     | 그리기 단계만 재실행                     | 가장 작음 |

- 상태를 **어느 단계에서 읽느냐**에 따라 다시 실행되는 범위가 달라짐. 예를 들어 오프셋 값을 `Modifier.offset { }` 람다 안에서 읽으면 레이아웃 단계만 재실행되고 재구성은 일어나지 않음

<br>

### 3. 재구성 범위 — 무엇이 다시 실행되는가

### 3-1. 리컴포지션 스코프

- 컴파일러는 값을 반환하지 않는(`Unit`) 컴포저블 함수와 일부 인라인이 아닌 람다를 **리컴포지션 스코프**로 삼음
- 무효화는 **상태를 읽은 가장 가까운 스코프** 단위로 일어나며, 그 안쪽 자식은 아래 3-2의 건너뛰기 규칙에 따라 재실행 여부가 결정됨
- `Column`, `Row`, `Box` 같은 인라인 함수는 자체 스코프를 만들지 않으므로, 이 안에서 상태를 읽으면 **부모 컴포저블 전체**가 재구성됨

```kotlin
@Composable
fun Screen(viewModel: CounterViewModel) {
    val count by viewModel.count.collectAsStateWithLifecycle()
    Column {                              // Column은 인라인 → 스코프가 아님
        Header()                          // count와 무관하지만 Screen 스코프 안에 있음
        Text("현재 값: $count")            // count 읽기 → Screen 전체가 무효화됨
        ExpensiveChart(data = viewModel.chartData)
    }
}
```

위 코드에서 `count`가 바뀌면 `Screen` 스코프가 재실행되지만, `Header()`와 `ExpensiveChart()`는 인자가 그대로이므로 **건너뛰기(Skip)**된다. 그러나 인자가 불안정한 타입이면 건너뛰지 못해 매번 재실행된다 (unit04 참고).

<br>

### 3-2. 건너뛰기 조건

컴포저블이 재구성 대상 스코프 안에 있더라도 다음 조건을 모두 만족하면 실행을 건너뛴다.

- 함수가 **건너뛸 수 있는(Skippable)** 함수로 컴파일됨 — 모든 매개변수 타입이 안정적(Stable)이거나 Strong Skipping 모드가 적용됨
- 이전 호출과 비교해 **모든 인자가 같음** (안정적 타입은 `equals`, 불안정한 타입은 Strong Skipping 시 참조 동일성으로 비교)
- 해당 함수 내부에서 읽은 상태가 변경되지 않음

> ⚠️ 재구성 범위를 넓히는 가장 흔한 실수는 **상태를 너무 높은 곳에서 읽는 것**이다. 값을 실제로 사용하는 가장 작은 컴포저블 안에서 읽거나, 상태 객체 자체를 넘기고 자식이 `.value`를 읽게 하면 무효화 범위가 좁아진다.

<br>

### 3-3. 읽기 위치를 낮춰 재구성 범위 줄이기

```kotlin
// 안티패턴: 스크롤 오프셋을 부모에서 읽어 부모 전체가 매 프레임 재구성됨
@Composable
fun Parallax(scrollState: ScrollState) {
    val offset = scrollState.value / 2          // 컴포지션 단계에서 읽음
    Column {
        HeavyHeader()                            // 매 프레임 재구성 대상 스코프에 포함
        Image(modifier = Modifier.offset(y = offset.dp), painter = bg, contentDescription = null)
    }
}

// 개선: 람다 안에서 읽어 레이아웃 단계만 다시 실행됨 (재구성 없음)
@Composable
fun Parallax(scrollState: ScrollState) {
    Column {
        HeavyHeader()
        Image(
            modifier = Modifier.offset { IntOffset(x = 0, y = scrollState.value / 2) },
            painter = bg, contentDescription = null,
        )
    }
}
```

### 4. 재구성이 만드는 제약 — 컴포저블이 지켜야 할 규칙

재구성은 **언제든, 여러 번, 어떤 순서로든, 병렬로** 일어날 수 있다고 가정해야 한다. 그래서 컴포저블 함수는 다음 성질을 지켜야 한다.

- **멱등성(Idempotent)**: 같은 인자로 몇 번을 실행해도 같은 UI를 만들어야 함
- **부수효과 금지**: 본문에서 네트워크 호출, 전역 변수 변경, 로그 전송 등을 하면 재구성 횟수만큼 반복됨 → 부수효과 API로 분리해야 함 (unit05 참고)
- **순서 가정 금지**: 형제 컴포저블이 위에서 아래 순서로 실행된다고 가정하면 안 됨
- **빠른 실행**: 무거운 계산은 `remember`로 캐시하거나 ViewModel로 옮김

```kotlin
// 안티패턴: 본문에서 직접 부수효과 실행 → 재구성마다 이벤트가 중복 전송됨
@Composable
fun ProductScreen(id: Long) {
    analytics.logScreenView(id)        // 재구성될 때마다 호출됨
    Text("상품 $id")
}

// 개선: id가 바뀔 때 한 번만 실행되도록 부수효과 API 사용
@Composable
fun ProductScreen(id: Long) {
    LaunchedEffect(id) { analytics.logScreenView(id) }
    Text("상품 $id")
}
```

> 💡 "왜 Compose는 컴포저블 안에서 네트워크 호출을 금지하나요?"라는 질문에는 **재구성이 프레임마다도 일어날 수 있고 실행 횟수·순서를 보장하지 않기 때문**이라고 답하면 된다. 이 성질이 unit05의 부수효과 API가 존재하는 이유다.

<br>

### 5. 재구성 디버깅 방법

- **Layout Inspector**의 재구성 횟수·건너뛰기 횟수 표시로 어떤 컴포저블이 과도하게 재실행되는지 확인함
- **Compose 컴파일러 리포트**로 각 함수가 Skippable·Restartable인지, 어떤 매개변수가 불안정한지 파악함 (unit04 참고)
- 개발 중에는 `SideEffect { Log.d(TAG, "재구성") }`를 임시로 넣어 실행 횟수를 직접 셀 수도 있음
- 재구성 자체는 정상 동작이므로 **횟수가 많다는 사실만으로 문제라고 단정하지 말고**, 실제 프레임 드랍·지연이 있는지 함께 봐야 함

<br>

### 6. 정리

| **개념**              | **핵심 내용**                                                                      |
| --------------------- | ---------------------------------------------------------------------------------- |
| **선언형 UI**         | 상태에 대한 UI를 서술하고, 동기화는 런타임이 담당함                                 |
| **Snapshot 상태**     | `mutableStateOf`로 만든 상태만 읽기 추적 대상이며 변경 시 무효화가 발생함           |
| **재구성 경로**       | 상태 쓰기 → 읽은 스코프 무효화 → 다음 프레임 재실행 → 컴포지션·레이아웃·그리기     |
| **재구성 범위**       | 상태를 읽은 **가장 가까운 리컴포지션 스코프**, 인라인 레이아웃은 스코프가 아님       |
| **건너뛰기**          | Skippable 함수 + 인자 동일 + 내부 상태 불변이면 실행 생략                          |
| **컴포저블 규칙**     | 멱등성, 부수효과 금지, 순서·횟수 가정 금지                                         |

- 상태를 **사용하는 곳에서 읽고**, 프레임마다 바뀌는 값은 **람다(레이아웃·그리기 단계)**에서 읽어 재구성을 피함
- 상태를 어디에 두고 어떻게 끌어올릴지는 **unit03(Compose 상태 관리)**, 안정성과 건너뛰기 최적화는 **unit04**, 부수효과 처리는 **unit05**를 참고할 것
