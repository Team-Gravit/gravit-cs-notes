## SwiftUI 뷰 정체성과 업데이트

SwiftUI의 `View`는 화면에 그려지는 객체가 아니라 **"무엇을 보여줄지"를 기술한 가벼운 값(구조체)**이며, 프레임워크는 이 값을 비교해 실제 렌더 트리를 갱신한다. 뷰가 왜 구조체인지, `body`가 언제 다시 평가되는지, 그리고 뷰의 **정체성(Identity)**이 상태·애니메이션에 어떤 영향을 주는지 이해해야 "왜 값이 초기화됐는지", "왜 애니메이션이 안 되는지" 같은 문제를 설명할 수 있다.

<br>

### 1. View는 왜 구조체인가

SwiftUI의 `View` 프로토콜을 채택하는 타입은 거의 항상 **구조체(struct)**다. UIKit의 `UIView`가 클래스이고 화면 위에 실제로 존재하는 객체인 것과 달리, SwiftUI의 뷰는 **UI의 선언(description)**일 뿐이다.

```swift
struct CounterView: View {
    @State private var count = 0

    var body: some View {          // 저장 프로퍼티가 아닌 계산 프로퍼티
        VStack {
            Text("count: \(count)")
            Button("증가") { count += 1 }
        }
    }
}
```

| **항목**        | **UIKit `UIView` (클래스)**             | **SwiftUI `View` (구조체)**                  |
| --------------- | --------------------------------------- | -------------------------------------------- |
| **정체**        | 화면에 존재하는 **객체**                | 화면을 기술한 **값**                         |
| **수명**        | 개발자가 생성·제거를 관리               | 프레임워크가 필요할 때마다 **새로 생성**     |
| **상태 보관**   | 인스턴스 프로퍼티에 직접 저장           | 뷰 밖(프레임워크 저장소)에 두고 래퍼로 참조  |
| **갱신 방식**   | 프로퍼티를 직접 바꿈 (명령형)           | 상태가 바뀌면 `body`를 **다시 계산** (선언형) |
| **비용**        | 힙 할당, 참조 카운팅                    | 스택 값 복사, 매우 저렴                      |

- **값 타입이므로 가볍다**: `body`는 초당 수십 번 재계산될 수 있으므로, 뷰 값 자체는 복사 비용이 거의 없어야 한다
- **불변 선언이므로 비교가 쉽다**: 프레임워크는 "이전 선언 값"과 "새 선언 값"을 비교해 **달라진 부분만** 실제 렌더 트리(속성 그래프)에 반영한다
- **상태를 뷰 안에 두지 않는다**: 뷰 값은 매번 새로 만들어지므로, 유지돼야 할 상태는 `@State` 등으로 프레임워크 저장소에 맡긴다 (unit02 참고)

> 💡 면접에서 "SwiftUI 뷰는 왜 구조체인가"를 물으면 "가볍다"에서 끝내지 말고, **뷰 값은 매 갱신마다 새로 생성되는 UI 설명서이고, 실제 상태와 렌더 객체는 프레임워크가 따로 관리한다**는 구조까지 답해야 한다.

<br>

### 2. body 재평가 시점

### 2-1. 의존성 추적

SwiftUI는 `body`를 평가하는 동안 **어떤 상태(`@State`, `@Binding`, `@Environment`, `Observable` 프로퍼티 등)를 읽었는지** 기록한다. 그 상태가 바뀌면 해당 뷰를 "무효화(invalidate)"하고 다음 렌더 사이클에 `body`를 다시 계산한다.

```
[상태 변경: count += 1]
        │
        ▼
 CounterView 무효화 ──▶ body 재평가 ──▶ 새 뷰 값 트리 생성
        │                                   │
        │                                   ▼
        │                        이전 트리와 비교(diff)
        │                                   │
        ▼                                   ▼
 자식 뷰 값도 새로 생성            달라진 노드만 렌더 트리 갱신
 (init은 호출되지만 body는 필요할 때만)
```

- **읽지 않은 상태가 바뀌면 재평가되지 않는다**: 의존성은 "읽었는가"로 결정된다
- **부모가 재평가되면 자식 뷰 값은 다시 생성된다**: 하지만 자식의 입력(프로퍼티)이 이전과 같다고 판단되면 자식의 `body`는 건너뛴다
- `body` 재평가 ≠ 화면 다시 그리기. 재평가 결과가 같으면 렌더 트리는 그대로다

<br>

### 2-2. 흔한 함정 — 상위 뷰에서 상태를 몰아 쓰기

```swift
// 안티패턴: 루트 뷰가 모든 상태를 읽어서 작은 변화에도 루트 전체 body가 재평가됨
struct RootView: View {
    @State private var query = ""
    @State private var isOn = false
    var body: some View {
        VStack {
            TextField("검색", text: $query)   // 타이핑마다 RootView 전체 재평가
            Toggle("설정", isOn: $isOn)
            HeavyChart()                       // 입력이 같으면 body는 건너뛰지만 값 생성 비용은 발생
        }
    }
}
```

```swift
// 개선: 상태를 실제로 쓰는 하위 뷰로 내려서 무효화 범위를 좁힘
struct RootView: View {
    var body: some View {
        VStack {
            SearchBar()          // query는 이 안에서만 소유
            SettingToggle()      // isOn은 이 안에서만 소유
            HeavyChart()
        }
    }
}
```

> ⚠️ `body` 안에서 무거운 연산(정렬, 포매팅, 네트워크 호출)을 하면 재평가마다 반복 실행된다. `body`는 **순수하고 빠르게** 유지하고, 계산 결과는 상태나 모델에 캐시한다. 어떤 이유로 재평가됐는지는 `body` 안에서 `let _ = Self._printChanges()`로 디버그 콘솔에 출력해 확인할 수 있다 (디버그 전용 API).

<br>

### 3. 뷰 정체성(Identity)

SwiftUI는 "이 뷰가 이전 렌더의 그 뷰와 **같은 뷰인가**"를 정체성으로 판단한다. 정체성이 같으면 상태·애니메이션·전환이 유지되고, 다르면 **이전 뷰는 제거되고 새 뷰가 생성**된다.

### 3-1. 구조적 정체성 (Structural Identity)

뷰 트리에서의 **위치**로 결정되는 정체성이다. 타입과 트리 안의 경로가 같으면 같은 뷰로 본다. 가장 흔한 오해가 `if/else` 분기다.

```swift
// if/else: 두 분기는 서로 다른 위치 → 서로 다른 정체성
if isExpanded {
    CardView().frame(height: 200)   // 분기 A
} else {
    CardView().frame(height: 80)    // 분기 B
}
// isExpanded가 바뀌면 A가 제거되고 B가 새로 생성됨 → 내부 @State 초기화, 크기 애니메이션 불가

// 삼항/모디파이어 파라미터: 같은 뷰가 계속 유지 → 같은 정체성
CardView().frame(height: isExpanded ? 200 : 80)
// 같은 뷰의 속성만 바뀌므로 withAnimation으로 자연스럽게 높이가 변함
```

<br>

### 3-2. 명시적 정체성 (Explicit Identity)

`ForEach`의 `id`나 `.id()` 모디파이어로 **개발자가 직접 부여**하는 정체성이다.

```swift
// ForEach: id가 안정적이어야 항목 이동·삭제 시 상태와 애니메이션이 올바르게 따라감
ForEach(items) { item in          // Identifiable → item.id 사용
    RowView(item: item)
}

// 안티패턴: 인덱스를 id로 사용 → 삭제 시 "뒤 항목이 앞 항목의 상태를 물려받음"
ForEach(items.indices, id: \.self) { i in RowView(item: items[i]) }

// .id(): 값이 바뀌면 새로운 뷰로 취급 → 의도적으로 상태를 초기화하거나 전환 애니메이션을 유도
DetailView(post: post).id(post.id)
```

| **정체성 종류** | **결정 요인**                   | **바뀌면 일어나는 일**                     | **주의**                              |
| --------------- | ------------------------------- | ------------------------------------------ | ------------------------------------- |
| **구조적**      | 타입 + 뷰 트리 상의 위치        | 이전 뷰 제거, 새 뷰 생성 (상태 소실)       | `if/else` 분기는 서로 다른 정체성     |
| **명시적**      | `ForEach` id, `.id()`           | 같은 위치라도 다른 뷰로 취급               | 불안정한 id(인덱스·랜덤)는 버그 원인  |

> 💡 `@State`의 수명은 **뷰 값이 아니라 뷰의 정체성**에 묶여 있다. 뷰 값은 렌더마다 새로 만들어져도 정체성이 유지되면 상태는 보존되고, 정체성이 바뀌는 순간 상태도 사라진다. "화면을 갔다 왔더니 입력값이 초기화됐다"는 대부분 정체성 변화 때문이다.

<br>

### 4. 정체성·수명·의존성의 관계

```
정체성(Identity)  ──  "같은 뷰인가"          ──▶ 상태·애니메이션 유지 여부 결정
       │
수명(Lifetime)    ──  정체성이 유지되는 기간  ──▶ @State, onAppear/onDisappear 범위
       │
의존성(Dependency)──  body가 읽은 상태 집합   ──▶ 어떤 변화가 body를 재평가시키는가
```

- 정체성이 유지되는 동안 뷰 값은 여러 번 생성될 수 있으며, `onAppear`는 정체성이 처음 생길 때 한 번 호출된다
- 뷰 값 생성(`init`)은 저렴하지만, `init`에서 `@StateObject`가 아닌 객체를 새로 만들면 매 렌더마다 재생성된다 (unit02 참고)

<br>

### 5. 재평가 비용 줄이기

- **상태를 사용하는 뷰까지 내려보내기**: 무효화 범위를 최소 단위로 만든다
- **`body`를 작은 하위 뷰로 분리하기**: 분리된 하위 뷰는 입력이 같으면 `body`가 건너뛰어진다 (분리 기준은 unit04 참고)
- **`Equatable` 채택 + `.equatable()`**: 값 비교로 재평가 자체를 막을 수 있으나, 비교 비용이 더 클 수 있어 무거운 뷰에만 적용한다
- **iOS 17+ Observation**: 객체 전체가 아니라 **읽은 프로퍼티 단위**로 의존성이 추적돼 불필요한 재평가가 크게 줄어든다 (unit03 참고)

> ⚠️ "자식 뷰의 입력이 같은지"는 SwiftUI가 내부적으로 판단한다. 클로저나 참조 타입을 프로퍼티로 넘기면 매번 다르다고 판단될 수 있어 재평가를 막지 못한다. `Self._printChanges()`로 원인을 확인한 뒤 최적화한다.

<br>

### 6. 면접·실무 체크포인트

| **질문**                                      | **핵심 답변**                                                                                  |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| **뷰가 구조체인 이유는?**                     | UI를 기술한 **가벼운 값**이며, 프레임워크가 매 갱신마다 새로 만들고 비교함. 상태는 외부에 보관 |
| **body는 언제 재평가되는가?**                 | `body` 평가 중 **읽은 상태**가 바뀔 때. 부모 재평가 시 자식 값은 재생성되지만 body는 조건부   |
| **if/else와 삼항 연산자의 차이는?**           | `if/else`는 **구조적 정체성이 다른 두 뷰**, 삼항은 같은 뷰의 속성 변경 → 상태·애니메이션 차이 |
| **ForEach에 인덱스를 id로 쓰면 안 되는 이유?** | 삭제·삽입 시 정체성이 밀려 **상태가 다른 항목에 붙고** 애니메이션이 어긋남                     |
| **@State는 언제 초기화되는가?**               | 뷰 값이 아니라 **정체성**에 묶여 있어, 정체성이 바뀌는 순간 초기화됨                            |

- 값이 초기화되거나 애니메이션이 끊기면 먼저 **정체성이 바뀌었는지** 의심한다
- 성능 문제는 **상태를 아래로 내리고 뷰를 분리**해 무효화 범위를 줄이는 것부터 시작한다
- 상태 래퍼의 소유권 규칙은 unit02, 프로퍼티 단위 추적은 unit03에서 이어진다
