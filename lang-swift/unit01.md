## 값 타입 vs 참조 타입

Swift의 모든 타입은 **값 타입(Value Type)**과 **참조 타입(Reference Type)** 중 하나로 동작하며, `struct`와 `class` 중 무엇을 고르느냐가 복사 비용·소유권·동시성 안전성을 결정한다. 이 유닛에서는 두 타입의 메모리 동작 차이, 표준 라이브러리가 값 타입의 복사 비용을 숨기는 **Copy-on-Write(COW)**, 그리고 실무에서의 선택 기준을 정리한다.

<br>

### 1. 값 타입과 참조 타입의 차이

- **값 타입**: 변수에 대입하거나 함수에 전달할 때 **값 자체가 복사**됨. `struct`, `enum`, 튜플, 그리고 `Int`·`String`·`Array`·`Dictionary` 등 표준 라이브러리 대부분이 해당함
- **참조 타입**: 변수에는 인스턴스의 **주소(참조)**만 담기고, 대입하면 같은 인스턴스를 여러 변수가 공유함. `class`, `actor`, 클로저가 해당함

```swift
struct PointValue { var x = 0 }
final class PointRef { var x = 0 }

var v1 = PointValue()
var v2 = v1          // 값 복사 → 서로 독립
v2.x = 10
print(v1.x)          // 0

let r1 = PointRef()
let r2 = r1          // 참조 복사 → 같은 인스턴스
r2.x = 10
print(r1.x)          // 10 (r1도 함께 바뀜)
```

```
값 타입                          참조 타입
v1 ┌────┐   v2 ┌────┐            r1 ──┐      ┌──────────┐
   │x=0 │      │x=10│               ├───→ │ x=10     │ (힙, 참조 카운트 2)
   └────┘      └────┘            r2 ──┘      └──────────┘
   (스택 또는 소유자 인라인 저장)
```

> 💡 `let`으로 선언한 값 타입은 내부 프로퍼티까지 전부 불변이지만, `let`으로 선언한 참조 타입은 **참조만 고정**될 뿐 내부 프로퍼티는 여전히 바꿀 수 있다. 위 예시에서 `r2`가 `let`인데도 `r2.x = 10`이 가능한 이유다.

<br>

### 2. 메모리와 성능 관점

### 2-1. 저장 위치와 참조 카운팅

- 값 타입 인스턴스는 보통 **스택**이나 소유자(컨테이너·구조체) 안에 인라인으로 저장되어 할당·해제가 빠르고, 참조 카운트 관리가 필요 없음
- 참조 타입 인스턴스는 **힙**에 할당되며, ARC가 참조 카운트를 원자적으로 증감하는 비용이 따름 (unit02 참고)
- 단, 값 타입이라도 내부에 참조 타입 프로퍼티가 있으면 복사할 때 그 참조의 카운트가 증가하므로 완전히 "공짜"는 아님

> ⚠️ 값 타입이 항상 스택에 있는 것은 아니다. 클로저에 캡처되거나 프로토콜 타입(existential)에 담겨 크기가 인라인 버퍼(3워드)를 넘으면 힙에 박싱(boxing)된다. "struct = 스택"은 경향일 뿐 보장이 아니다.

<br>

### 2-2. 값 타입의 복사 비용과 Copy-on-Write

배열처럼 큰 값 타입을 대입할 때마다 전체를 복사하면 성능이 무너진다. 표준 라이브러리의 `Array`·`Dictionary`·`Set`·`String`은 **Copy-on-Write(COW, 쓰기 시 복사)**로 이 문제를 해결한다.

- 대입 시에는 내부 버퍼의 **참조만 공유**하고 참조 카운트를 올림 (O(1))
- 어느 한쪽이 **변경(mutating)**하려는 순간, 버퍼가 다른 곳과 공유 중이면 그때 처음으로 복사함
- 사용자 입장에서는 값 의미론(독립적인 복사본)이 유지되면서 실제 복사는 필요한 순간까지 지연됨

```
var a = [1, 2, 3]        a ──→ [버퍼 1,2,3] (rc=1)
var b = a                a ──┐
                         b ──┴→ [버퍼 1,2,3] (rc=2)   ← 복사 없음
b.append(4)              a ──→ [버퍼 1,2,3]   (rc=1)
                         b ──→ [버퍼 1,2,3,4] (rc=1)   ← 쓰기 직전에 복사
```

> 💡 COW는 언어 기능이 아니라 **표준 라이브러리가 `isKnownUniquelyReferenced(_:)`로 구현한 최적화**다. 따라서 직접 만든 `struct`는 자동으로 COW가 되지 않는다. 큰 버퍼를 가진 커스텀 값 타입에 COW가 필요하면 아래처럼 직접 구현해야 한다.

```swift
final class Storage { var data: [Int] = [] }

struct BigValue {
    private var storage = Storage()

    var data: [Int] { storage.data }

    mutating func append(_ x: Int) {
        // 버퍼를 나 혼자만 참조하는지 확인 → 아니면 복사 후 수정
        if !isKnownUniquelyReferenced(&storage) {
            let copy = Storage()
            copy.data = storage.data
            storage = copy
        }
        storage.data.append(x)
    }
}
```

### 3. 흔한 함정

### 3-1. mutating과 프로퍼티 변경 전파

- 값 타입의 메서드에서 자신의 프로퍼티를 바꾸려면 `mutating` 키워드가 필요하며, `let` 상수에는 호출할 수 없음
- 값 타입을 다른 값 타입의 프로퍼티로 두면, 내부 프로퍼티 하나를 바꿔도 **바깥 구조체 전체가 "변경됨"**으로 취급됨 → `didSet`이 호출되고, SwiftUI의 `@State` 등에서 뷰 갱신이 발생함

```swift
struct Profile { var name: String }
struct AppState {
    var profile = Profile(name: "kim") {
        didSet { print("profile 변경됨") }
    }
}
var state = AppState()
state.profile.name = "lee"   // "profile 변경됨" 출력 — 내부 필드만 바꿔도 전체 변경으로 감지
```

<br>

### 3-2. 루프 안의 복사와 의도치 않은 공유

- `for item in array`는 각 요소의 **복사본**을 꺼내므로, `item`을 수정해도 원본 배열은 바뀌지 않음. 원본을 바꾸려면 인덱스로 접근하거나 `indices`를 순회해야 함
- 반대로 참조 타입을 배열에 담아 두면, 배열을 복사해도 요소 인스턴스는 공유되어 **한쪽 수정이 다른 쪽에 반영**됨. "배열을 복사했으니 안전하다"는 착각이 자주 일어남

> ⚠️ 참조 타입 배열을 복사한 뒤 요소를 수정하면 원본에도 영향이 간다. 깊은 복사(deep copy)가 필요하면 `NSCopying` 채택이나 명시적 복제 메서드를 구현해야 한다. 값 타입과 참조 타입을 섞어 쓸 때 가장 많이 나오는 버그다.

<br>

### 4. struct vs class 선택 기준

| **기준**                     | **struct (값 타입)**                       | **class (참조 타입)**                          |
| ---------------------------- | ------------------------------------------ | ---------------------------------------------- |
| **복사 의미**                | **독립적인 복사본** (값 의미론)            | 같은 인스턴스를 **공유** (참조 의미론)         |
| **상속**                     | 불가 (프로토콜로 확장)                     | **가능** (단일 상속)                           |
| **정체성(identity)**         | 없음 — 값이 같으면 같은 것                 | **있음** — `===`로 동일 인스턴스 비교          |
| **소멸 시점 훅**             | 없음                                       | `deinit` 사용 가능                             |
| **메모리 관리**              | 참조 카운팅 불필요 (내부 참조 제외)        | ARC 관리, 순환 참조 위험                       |
| **동시성**                   | 대부분 자동으로 `Sendable`                 | 기본적으로 `Sendable` 아님 (unit07 참고)       |
| **Objective-C 상호운용**     | 불가                                       | `NSObject` 상속으로 가능                       |
| **대표 예시**                | 좌표·모델(DTO)·설정값·컬렉션               | 뷰 컨트롤러·네트워크 세션·공유 캐시            |

**선택 가이드**

- 데이터를 **비교·복사**하는 것이 자연스럽고, 인스턴스에 고유한 정체성이 없다면 → `struct` (Apple 공식 권장 기본값)
- 여러 곳에서 **같은 인스턴스를 공유하며 상태를 변경**해야 하거나, 생명주기(`deinit`)를 관리해야 하거나, 상속·Objective-C 연동이 필요하다면 → `class`
- 값 타입의 데이터에 참조 타입의 "한 곳에서 관리" 특성이 필요하면 → `class` 안에 `struct` 모델을 두거나, 뷰모델 계층에서 참조 타입으로 감싸는 구조가 일반적임

> 💡 열거형(`enum`)도 값 타입이다. 연관값(associated value)을 가진 열거형은 상태 표현에 적합하며, `indirect`로 재귀 구조도 만들 수 있다. "상태가 몇 가지로 정해져 있다면 struct보다 enum이 먼저"라는 판단 기준을 함께 기억해 두자.

<br>

### 5. 면접·실무 체크포인트

| **질문**                                              | **핵심 답변**                                                                                 |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| **struct와 class의 차이는?**                          | 복사 의미론 vs 참조 의미론, 상속·정체성·`deinit` 유무, ARC 관리 여부                          |
| **Array를 대입하면 전체가 복사되나?**                 | 아니다. **COW**로 버퍼를 공유하다가 변경 시점에 복사한다                                      |
| **직접 만든 struct도 COW인가?**                       | 아니다. `isKnownUniquelyReferenced`로 직접 구현해야 한다                                     |
| **`let` 클래스 인스턴스의 프로퍼티를 바꿀 수 있나?** | 가능하다. `let`은 참조만 고정하며, 값 타입은 내부까지 불변이다                                |
| **struct가 항상 스택에 저장되나?**                    | 아니다. 클로저 캡처·existential 박싱·클래스 프로퍼티 등에서는 힙에 놓인다                    |
| **기본 선택은 무엇인가?**                             | `struct`. 공유 상태·정체성·상속·`deinit`이 필요할 때만 `class`                                |

- 값 타입은 **예측 가능성**과 **동시성 안전성**이 장점이고, 참조 타입은 **공유와 생명주기 관리**가 장점임
- 두 타입을 섞을 때는 "참조 타입 프로퍼티가 복사 뒤에도 공유된다"는 점을 항상 의식할 것
- 참조 타입의 메모리 관리와 순환 참조는 **unit02(ARC와 순환 참조)**에서 이어서 다룸
