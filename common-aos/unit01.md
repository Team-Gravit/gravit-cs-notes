## 4대 컴포넌트와 인텐트

안드로이드 앱은 하나의 `main()`에서 출발하지 않고, 시스템이 필요할 때 깨우는 **4대 컴포넌트(Activity·Service·BroadcastReceiver·ContentProvider)**의 조합으로 동작한다. 컴포넌트를 실행하고 서로 연결하는 메시지 객체가 **인텐트(Intent)**이며, 이 구조를 이해해야 생명주기·프로세스 수명·보안 등 이후 모든 개념이 자연스럽게 이어진다.

<br>

### 1. 안드로이드 앱 구조의 특징

- 앱에는 단일 진입점이 없고, 매니페스트(`AndroidManifest.xml`)에 등록된 컴포넌트를 **시스템이 직접 인스턴스화**한다
- 컴포넌트는 앱 **밖**에서도 실행될 수 있다 — 다른 앱이 카메라 액티비티를 띄우거나, 시스템이 부팅 완료 브로드캐스트를 보내는 식이다
- 그래서 컴포넌트 간 통신은 객체 참조가 아니라 **인텐트**라는 직렬화 가능한 메시지로 이루어진다

```
사용자 탭 / 시스템 이벤트 / 다른 앱
        │  Intent
        ▼
┌─────────────── 안드로이드 시스템 (ActivityManager 등) ───────────────┐
│  매니페스트에서 대상 컴포넌트 검색 → 프로세스가 없으면 생성 → 콜백 호출  │
└──────────────────────────────────────────────────────────────────────┘
        │                │                   │                  │
   Activity          Service          BroadcastReceiver   ContentProvider
```

> 💡 "앱의 진입점이 어디인가"라는 질문에 `MainActivity`라고만 답하면 부족하다. **런처 인텐트(`MAIN` + `LAUNCHER`)를 받는 액티비티**가 진입점일 뿐, 브로드캐스트나 서비스 시작으로도 프로세스가 생성될 수 있다고 설명해야 한다.

<br>

### 2. 4대 컴포넌트

### 2-1. 액티비티(Activity)

사용자와 상호작용하는 **하나의 화면**을 담당한다. 시스템은 액티비티를 **백 스택(Back Stack)**으로 관리하며, 뒤로 가기를 누르면 스택 상단의 액티비티가 제거된다.

- 매니페스트에 `<activity>`로 반드시 선언해야 하며, 선언되지 않은 액티비티를 시작하면 `ActivityNotFoundException`이 발생한다
- 화면 전환·구성 변경마다 생명주기 콜백이 호출된다 (unit02 참고)

<br>

### 2-2. 서비스(Service)

UI 없이 **백그라운드에서 오래 걸리는 작업**을 수행한다. 서비스는 별도 스레드가 아니라 **메인 스레드에서 실행**된다는 점을 반드시 기억해야 한다.

| **종류**                     | **시작 방법**            | **종료 시점**                        | **대표 용도**              |
| ---------------------------- | ------------------------ | ------------------------------------ | -------------------------- |
| **시작된 서비스(Started)**   | `startService()`         | `stopSelf()` 또는 `stopService()`    | 파일 다운로드, 업로드      |
| **바인드 서비스(Bound)**     | `bindService()`          | 모든 클라이언트가 `unbindService()`  | 음악 재생 제어, IPC        |
| **포그라운드 서비스**        | `startForegroundService()` | 알림 표시 필수, 명시적 중지         | 내비게이션, 음악 재생      |

- Android 8.0(API 26)부터 백그라운드 상태의 앱은 `startService()`로 서비스를 시작할 수 없고, 포그라운드 서비스 또는 `WorkManager`를 사용해야 한다 (unit06 참고)

<br>

### 2-3. 브로드캐스트 리시버(BroadcastReceiver)

시스템이나 다른 앱이 보내는 **이벤트(브로드캐스트)를 수신**하는 컴포넌트다. 배터리 부족, 네트워크 변경, 부팅 완료 등이 대표적이다.

- `onReceive()`는 메인 스레드에서 실행되며 **짧게 끝나야 한다** — 오래 걸리면 ANR이 발생한다 (unit04 참고)
- 매니페스트 등록 방식과 코드(`registerReceiver`) 등록 방식이 있으며, Android 8.0부터 대부분의 **암시적 브로드캐스트는 매니페스트 등록으로 받을 수 없다**

<br>

### 2-4. 콘텐츠 프로바이더(ContentProvider)

앱의 데이터를 **다른 앱에 표준화된 URI 인터페이스로 공개**하는 컴포넌트다. 연락처, 미디어 저장소가 대표적이며, `content://authority/path` 형태의 URI로 접근한다.

- `query()`, `insert()`, `update()`, `delete()` 등 CRUD 메서드를 구현하며, 내부 저장소는 보통 SQLite(Room)다
- 다른 컴포넌트와 달리 **앱 프로세스가 시작될 때 `Application.onCreate()`보다 먼저 초기화**되므로, 라이브러리 초기화 용도(`App Startup`)로도 활용된다

| **컴포넌트**            | **역할**                | **UI** | **실행 스레드** | **매니페스트 선언** |
| ----------------------- | ----------------------- | ------ | --------------- | ------------------- |
| **Activity**            | 화면·사용자 상호작용    | 있음   | 메인            | 필수                |
| **Service**             | 장기 백그라운드 작업    | 없음   | 메인            | 필수                |
| **BroadcastReceiver**   | 이벤트 수신             | 없음   | 메인            | 선택 (코드 등록 가능) |
| **ContentProvider**     | 데이터 공유             | 없음   | 호출자 스레드 풀 | 필수                |

> ⚠️ 네 컴포넌트 중 Service와 BroadcastReceiver는 이름 때문에 "백그라운드 스레드에서 돈다"고 오해하기 쉽다. **모두 메인 스레드에서 콜백이 호출**되므로 네트워크·DB 작업은 반드시 코루틴이나 별도 스레드로 넘겨야 한다.

<br>

### 3. 인텐트(Intent)

인텐트는 "무엇을 하고 싶다"는 **의도를 담은 메시지 객체**다. 액티비티 시작(`startActivity`), 서비스 시작(`startService`), 브로드캐스트 전송(`sendBroadcast`)에 공통으로 사용된다.

**인텐트의 구성 요소**

- **컴포넌트 이름**: 대상 클래스 (명시적 인텐트에서만 지정)
- **액션(Action)**: 수행할 동작 (`ACTION_VIEW`, `ACTION_SEND` 등)
- **데이터(Data)·타입(Type)**: 대상 URI와 MIME 타입
- **카테고리(Category)**: 추가 분류 (`CATEGORY_LAUNCHER`, `CATEGORY_BROWSABLE` 등)
- **엑스트라(Extras)**: 키-값 형태의 부가 데이터 (`Bundle`)
- **플래그(Flags)**: 백 스택 동작 제어 (`FLAG_ACTIVITY_NEW_TASK`, `FLAG_ACTIVITY_CLEAR_TOP` 등)

<br>

### 3-1. 명시적 인텐트(Explicit Intent)

대상 컴포넌트의 **클래스를 직접 지정**한다. 같은 앱 내부의 화면 전환·서비스 시작에 사용한다.

```kotlin
// 명시적 인텐트: 대상 클래스를 직접 지정
val intent = Intent(this, DetailActivity::class.java).apply {
    putExtra("itemId", 42L)
}
startActivity(intent)

// 받는 쪽 (DetailActivity)
val itemId = intent.getLongExtra("itemId", -1L)
```

<br>

### 3-2. 암시적 인텐트(Implicit Intent)

대상 클래스를 지정하지 않고 **액션·데이터·카테고리만 명시**한다. 시스템이 매니페스트의 **인텐트 필터(Intent Filter)**와 대조해 처리할 수 있는 컴포넌트를 찾는다. 브라우저 열기, 공유하기, 전화 걸기처럼 "누가 처리하든 상관없는" 작업에 쓴다.

```kotlin
// 암시적 인텐트: 액션 + 데이터만 지정, 처리할 앱은 시스템이 결정
val intent = Intent(Intent.ACTION_VIEW, Uri.parse("https://developer.android.com"))

// 처리할 앱이 없으면 ActivityNotFoundException → 반드시 확인
if (intent.resolveActivity(packageManager) != null) {
    startActivity(intent)
}
```

```xml
<!-- 받는 쪽: 인텐트 필터로 "나는 이런 인텐트를 처리할 수 있다" 선언 -->
<activity android:name=".ShareActivity" android:exported="true">
    <intent-filter>
        <action android:name="android.intent.action.SEND" />
        <category android:name="android.intent.category.DEFAULT" />
        <data android:mimeType="text/plain" />
    </intent-filter>
</activity>
```

**인텐트 해석(Resolution) 과정** — 액션·데이터(URI 스킴·MIME 타입)·카테고리 세 가지를 모두 통과해야 매칭된다. 여러 앱이 매칭되면 시스템은 **선택 대화상자(Chooser)**를 띄우거나 사용자가 지정한 기본 앱으로 보낸다.

| **항목**             | **명시적 인텐트**                      | **암시적 인텐트**                            |
| -------------------- | -------------------------------------- | -------------------------------------------- |
| **대상 지정**        | **클래스 이름** 직접 지정              | **액션·데이터·카테고리**로 간접 지정         |
| **인텐트 필터**      | 불필요                                 | 수신 측에 **필수**                           |
| **주 용도**          | 앱 내부 화면 전환, 서비스 시작         | 타 앱 기능 호출 (공유, 브라우저, 전화)       |
| **실패 가능성**      | 낮음 (클래스가 존재하면 성공)          | 처리 앱이 없으면 예외 → 사전 확인 필요       |
| **보안**             | 안전                                   | 악의적 앱이 가로챌 수 있어 주의 필요         |

> 💡 Android 11(API 30)부터는 **패키지 가시성(Package Visibility)** 제한 때문에 `resolveActivity()`나 `queryIntentActivities()`가 다른 앱을 보지 못할 수 있다. 특정 앱을 조회하려면 매니페스트에 `<queries>`를 선언해야 한다. 단, `ACTION_VIEW`·`ACTION_SEND` 같은 주요 액션은 예외적으로 허용된다.

<br>

### 4. 인텐트와 보안

- **`android:exported`**: 다른 앱이 이 컴포넌트를 시작할 수 있는지 결정한다. Android 12(API 31)부터 인텐트 필터가 있는 컴포넌트는 이 값을 **명시하지 않으면 설치가 거부**된다
- **서비스는 명시적 인텐트로만 시작**해야 한다 — Android 5.0(API 21)부터 암시적 인텐트로 `bindService()`를 호출하면 예외가 발생한다
- **PendingIntent**: 다른 앱(알림, 알람 매니저)이 "내 앱의 권한으로" 인텐트를 나중에 실행하도록 위임하는 토큰이다. Android 12부터 `FLAG_IMMUTABLE` 또는 `FLAG_MUTABLE`을 반드시 지정해야 한다

❗️**인텐트 엑스트라는 신뢰할 수 없는 입력**: `exported="true"`인 컴포넌트가 받는 인텐트는 임의의 앱이 보낼 수 있다. 엑스트라에서 꺼낸 값으로 파일 경로·URL을 구성한다면 반드시 검증해야 한다 (unit10 참고).

<br>

### 5. 정리 — 면접·실무 체크포인트

| **질문**                                     | **핵심 답변**                                                                                   |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| **4대 컴포넌트는?**                          | Activity(화면), Service(백그라운드 작업), BroadcastReceiver(이벤트 수신), ContentProvider(데이터 공유) |
| **Service는 별도 스레드인가?**               | **아니다.** 메인 스레드에서 실행되므로 무거운 작업은 직접 스레드를 분리해야 함                    |
| **명시적 vs 암시적 인텐트 차이는?**          | 대상 클래스 지정 여부. 암시적은 **인텐트 필터**로 매칭되며 처리 앱이 없을 수 있음                  |
| **인텐트 필터 매칭 조건은?**                 | 액션·데이터·카테고리 **세 가지 모두** 통과                                                        |
| **`exported` 속성의 의미는?**                | 외부 앱의 컴포넌트 시작 허용 여부. API 31부터 인텐트 필터가 있으면 명시 필수                       |

- 컴포넌트는 시스템이 인스턴스화하며, 앱에는 단일 진입점이 없다
- 인텐트는 컴포넌트 간 **직렬화 가능한 메시지**이며, 명시적(내부)·암시적(외부 협업)으로 나뉜다
- 서비스·브로드캐스트의 시작 제약과 백그라운드 실행은 **unit04·unit06**에서 이어진다
