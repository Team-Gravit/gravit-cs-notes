## 프로세스 수명과 메모리 압력

안드로이드는 메모리가 부족하면 **개발자에게 묻지 않고 프로세스를 종료**한다. 어떤 프로세스가 먼저 죽는지는 그 안에서 실행 중인 컴포넌트의 상태로 결정되는 **중요도(우선순위)**에 따르며, 반대로 메인 스레드가 오래 막히면 시스템이 앱을 강제로 멈추는 **ANR(Application Not Responding)**이 발생한다. 이 두 메커니즘을 알아야 "왜 백그라운드에서 앱이 초기화되는가", "왜 앱이 응답 없음 대화상자를 띄우는가"에 답할 수 있다.

<br>

### 1. 안드로이드 프로세스 모델

- 기본적으로 **앱 하나 = 리눅스 프로세스 하나**이며, 모든 컴포넌트는 같은 프로세스의 **메인 스레드(UI 스레드)**에서 콜백을 받는다
- 프로세스는 최초 컴포넌트 실행 시 **Zygote**에서 fork되어 생성되고, 컴포넌트가 모두 끝나도 **즉시 종료되지 않는다** — 다음 실행을 빠르게 하기 위해 캐시된 상태로 남겨둔다
- 메모리가 부족해지면 시스템(**LMK, Low Memory Killer**)이 중요도가 낮은 프로세스부터 종료해 메모리를 회수한다

```
앱 최초 실행               사용자가 홈으로 이동           메모리 부족
   │                            │                            │
   ▼                            ▼                            ▼
Zygote fork ──▶ 포그라운드 ──▶ 캐시 프로세스(백그라운드) ──▶ LMK가 종료 (onDestroy 미호출)
                프로세스                │
                                        ▼  사용자가 다시 열면
                                  빠르게 복귀 (웜 스타트)
```

> 💡 앱을 "종료했다"고 생각하는 순간에도 프로세스는 살아 있는 경우가 많다. 반대로 살아 있다고 믿은 프로세스가 이미 죽어 있을 수도 있다. 정적 변수·싱글턴에 담은 상태가 **어느 순간 사라져 있는 이유**가 바로 이것이다.

<br>

### 2. 프로세스 중요도 계층

시스템은 프로세스 안에서 **가장 중요한 컴포넌트의 상태**를 기준으로 프로세스의 중요도를 매긴다. 순위가 낮을수록 먼저 종료된다.

| **순위** | **분류**                        | **조건**                                                                       | **종료 가능성**              |
| -------- | ------------------------------- | ------------------------------------------------------------------------------ | ---------------------------- |
| **1**    | **포그라운드 프로세스**         | `onResume()` 상태의 액티비티, 실행 중인 `onReceive()`, 포그라운드 서비스, 바인드된 서비스가 포그라운드 액티비티와 연결 | 시스템이 극한 상황이 아니면 유지 |
| **2**    | **가시 프로세스**               | `onPause()` 상태지만 보이는 액티비티 (다이얼로그 뒤), 그와 연결된 서비스       | 포그라운드를 위해 필요할 때만 |
| **3**    | **서비스 프로세스**             | `startService()`로 시작된 일반 서비스 실행 중                                  | 메모리 부족 시 종료 가능 (오래 실행되면 강등) |
| **4**    | **캐시(백그라운드) 프로세스**   | `onStop()` 상태의 액티비티만 있음. 최근 사용 순 **LRU 목록**으로 관리          | **가장 먼저 종료**            |

- 순위 1~3은 화면에 보이거나 사용자가 인지하는 작업이 있는 경우이고, 순위 4는 "언제든 죽여도 되는" 상태다
- 어떤 프로세스가 다른 프로세스에 **바인드**되어 있거나 그 프로세스의 콘텐츠 프로바이더를 쓰고 있으면, 서비스를 제공하는 쪽의 중요도는 **의존하는 쪽 이상**으로 올라간다
- 옛 문서의 "빈 프로세스(Empty Process)" 분류는 현재 **캐시 프로세스**에 통합되어 설명된다 (버전에 따라 세부 분류가 다를 수 있음)

> ⚠️ 서비스 프로세스라고 안심할 수 없다. 오래 실행되는 시작된 서비스는 시간이 지나면 캐시 목록 쪽으로 **강등**되며, Android 8.0 이후에는 백그라운드 앱의 서비스가 일정 시간 뒤 시스템에 의해 중단된다. 사용자가 인지해야 하는 작업은 **포그라운드 서비스**, 미룰 수 있는 작업은 **WorkManager**를 쓴다 (unit06 참고).

<br>

### 3. 메모리 압력에 대응하기

### 3-1. onTrimMemory() 콜백

시스템은 메모리 회수 전에 `ComponentCallbacks2.onTrimMemory(level)`로 앱에 기회를 준다. 캐시를 비워 메모리를 반납하면 프로세스가 죽을 확률을 낮출 수 있다.

```kotlin
class ImageCacheHolder : Application() {
    val memoryCache = LruCache<String, Bitmap>(maxSizeBytes)

    override fun onTrimMemory(level: Int) {
        super.onTrimMemory(level)
        when {
            // 앱이 백그라운드로 갔음 → UI 관련 캐시는 과감히 정리
            level >= ComponentCallbacks2.TRIM_MEMORY_UI_HIDDEN -> memoryCache.evictAll()
            // 포그라운드지만 메모리가 빠듯함 → 절반 정도 비움
            level >= ComponentCallbacks2.TRIM_MEMORY_RUNNING_LOW -> memoryCache.trimToSize(memoryCache.maxSize() / 2)
        }
    }
}
```

- `TRIM_MEMORY_UI_HIDDEN`은 **모든 UI가 사라졌을 때** 한 번 호출되므로 "앱이 백그라운드로 갔다"는 신호로 널리 쓰인다
- 최근 버전에서는 세분화된 레벨 대신 `TRIM_MEMORY_UI_HIDDEN`과 `TRIM_MEMORY_BACKGROUND` 계열만 의미 있게 취급되는 방향으로 정리되고 있다 (버전에 따라 다를 수 있음)

<br>

### 3-2. 프로세스 종료를 전제로 설계하기

- **`onDestroy()`를 믿지 않는다**: LMK는 프로세스를 `kill`하므로 콜백 없이 사라진다. 중요한 데이터는 `onStop()` 이전에 영속화한다 (unit02·unit03 참고)
- **싱글턴·정적 변수는 캐시일 뿐**: 프로세스가 재생성되면 초기 상태로 돌아간다. "로그인 정보를 싱글턴에만 저장"하면 백그라운드에서 복귀 시 로그아웃된 것처럼 보인다
- **복원 경로를 테스트**한다: `adb shell am kill <패키지>` 또는 개발자 옵션의 "백그라운드 프로세스 제한"으로 캐시 프로세스 종료를 재현한다

<br>

### 4. ANR(Application Not Responding)

ANR은 앱의 **메인 스레드가 일정 시간 이상 이벤트를 처리하지 못할 때** 시스템이 "앱이 응답하지 않습니다" 대화상자를 띄우고, 사용자가 선택하면 프로세스를 종료하는 메커니즘이다. 메인 스레드는 **입력 이벤트 처리·화면 그리기·생명주기 콜백**을 모두 담당하므로, 여기서 블로킹이 일어나면 앱 전체가 멈춘다.

### 4-1. 발생 조건

| **트리거**                       | **제한 시간(대략)**            | **설명**                                                        |
| -------------------------------- | ------------------------------ | --------------------------------------------------------------- |
| **입력 이벤트 디스패치**         | **5초**                        | 터치·키 입력을 메인 스레드가 5초 내에 처리하지 못함 — 가장 흔함 |
| **BroadcastReceiver.onReceive()** | 포그라운드 **10초** / 백그라운드 60초 | 리시버가 제한 시간 내에 반환하지 못함                   |
| **Service 생명주기 콜백**        | 포그라운드 **20초** / 백그라운드 200초 | `onCreate`·`onStartCommand` 등이 제한 시간 내에 끝나지 않음 |
| **startForeground() 미호출**     | 약 5~10초 (버전에 따라 다름)   | `startForegroundService()` 후 제한 시간 내 `startForeground()` 미호출 |
| **ContentProvider 게시**         | 약 10초                        | 프로바이더 초기화가 지연됨                                      |

- 제한 시간 수치는 **버전과 기기 제조사에 따라 다를 수 있으며**, 공식 문서가 명시하는 대표 값은 입력 이벤트 5초다
- 입력 이벤트가 **없는** 동안 메인 스레드가 10초 막혀 있어도 ANR은 나지 않는다. ANR은 "막힘"이 아니라 "**처리해야 할 일이 있는데 못 함**"일 때 발생한다

<br>

### 4-2. 흔한 원인과 개선

```kotlin
class SyncReceiver : BroadcastReceiver() {
    // 안티패턴: onReceive(메인 스레드)에서 네트워크·DB 직접 수행 → 10초 초과 시 ANR
    // override fun onReceive(context: Context, intent: Intent) {
    //     val response = api.syncNow()      // 블로킹 I/O
    //     db.save(response)
    // }

    // 개선: 리시버는 작업을 위임만 하고 즉시 반환
    override fun onReceive(context: Context, intent: Intent) {
        val request = OneTimeWorkRequestBuilder<SyncWorker>().build()
        WorkManager.getInstance(context).enqueue(request)
    }
}
```

**주요 원인**

- 메인 스레드에서 **네트워크·파일·DB I/O** 수행 (`runBlocking`, `Thread.join()`, `Future.get()` 포함)
- **락 경쟁**: 메인 스레드가 `synchronized` 블록을 기다리는데 워커 스레드가 오래 점유
- **Binder 호출 지연**: 다른 프로세스(시스템 서비스 등)의 응답을 메인 스레드에서 동기 대기
- `onCreate()`·`Application.onCreate()`에서 과도한 초기화 → 콜드 스타트 지연과 함께 ANR
- 데드락, 무한 루프, 지나치게 복잡한 레이아웃 인플레이트

**진단 도구**

- 기기의 `/data/anr/` 트레이스 파일(`traces.txt`)에서 ANR 시점 **메인 스레드의 스택**을 확인한다
- **StrictMode**를 디버그 빌드에서 켜면 메인 스레드 디스크·네트워크 접근을 즉시 로그·크래시로 알려준다
- Play Console의 **Android Vitals**는 ANR 비율을 집계하며, 일정 기준(대략 일일 사용자 기준 0.47% 등, 시기에 따라 조정됨)을 넘으면 노출에 불이익이 있다

```kotlin
// 디버그 빌드에서 메인 스레드 I/O를 조기에 잡아내기
if (BuildConfig.DEBUG) {
    StrictMode.setThreadPolicy(
        StrictMode.ThreadPolicy.Builder()
            .detectDiskReads().detectDiskWrites().detectNetwork()
            .penaltyLog()
            .build()
    )
}
```

> 💡 ANR과 크래시는 다르다. **크래시**는 예외로 프로세스가 즉시 죽는 것이고, **ANR**은 예외 없이 메인 스레드가 막혀 시스템이 개입하는 것이다. 예외 처리를 아무리 잘해도 ANR은 막지 못하며, 해법은 항상 "메인 스레드에서 오래 걸리는 일을 치우는 것"이다.

<br>

### 5. 정리 — 면접·실무 체크포인트

| **질문**                                              | **핵심 답변**                                                                    |
| ----------------------------------------------------- | -------------------------------------------------------------------------------- |
| **백그라운드 앱이 초기화되어 있는 이유는?**           | 캐시 프로세스가 **LMK에 의해 종료**된 뒤 재생성되어 메모리 상태가 사라짐         |
| **프로세스 종료 우선순위는?**                         | 포그라운드 → 가시 → 서비스 → **캐시(LRU)** 순으로 낮은 쪽부터 종료               |
| **onDestroy()가 호출되지 않는 경우는?**               | 메모리 부족으로 프로세스가 kill될 때 — 저장은 onStop 이전에                      |
| **ANR 발생 조건은?**                                  | 메인 스레드가 **입력 이벤트 5초**, 리시버 10초, 서비스 20초 등을 초과해 응답 못함 |
| **ANR과 크래시의 차이는?**                            | 크래시는 예외로 종료, ANR은 **메인 스레드 블로킹**으로 시스템 개입                |
| **ANR 예방 방법은?**                                  | I/O를 코루틴·워커로 분리, StrictMode로 조기 감지, 리시버·서비스 콜백은 위임만    |

- 프로세스는 개발자가 아니라 **시스템이 종료 시점을 결정**하며, 중요도는 컴포넌트 상태로 정해진다
- 메모리 압력에는 `onTrimMemory()`로 협조하고, 상태는 항상 프로세스 밖(저장소)에 둔다
- 메인 스레드를 막지 않는 백그라운드 작업 실행 방법은 **unit06**, 메모리 누수는 **unit05**에서 다룬다
