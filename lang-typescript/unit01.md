## 구조적 타이핑

TypeScript의 타입 시스템은 이름이 아니라 **구조(모양)**로 타입의 호환 여부를 판단하는 **구조적 타이핑(Structural Typing)**을 따른다. "왜 이 값이 저 타입에 대입되는가(또는 안 되는가)"를 설명하려면 호환성 규칙과 초과 프로퍼티 검사(Excess Property Check)의 동작 원리를 정확히 알아야 한다.

<br>

### 1. 명목적 타이핑 vs 구조적 타이핑

Java·C#·Swift처럼 **선언된 이름(명목, Nominal)**으로 타입을 구분하는 언어에서는 두 클래스의 필드가 완전히 같아도 서로 다른 타입이다. 반면 TypeScript는 JavaScript의 **덕 타이핑(Duck Typing)** 관행을 정적으로 옮긴 언어라서, "필요한 프로퍼티를 모두 갖고 있으면 그 타입"으로 취급한다.

```typescript
interface Point {
  x: number;
  y: number;
}

class Vector {
  constructor(public x: number, public y: number) {}
}

const p: Point = new Vector(1, 2); // OK — Point가 요구하는 x, y를 모두 가짐
const q: Point = { x: 1, y: 2 };    // OK — 이름 없는 객체 리터럴도 구조만 맞으면 됨
```

| **항목**          | **명목적 타이핑 (Java 등)**          | **구조적 타이핑 (TypeScript)**              |
| ----------------- | ------------------------------------ | ------------------------------------------- |
| **호환 판단 기준** | 선언 이름·상속 관계                  | **프로퍼티 이름과 타입의 집합**             |
| **같은 모양 다른 이름** | 서로 **다른** 타입                | 서로 **같은** 타입으로 취급                 |
| **장점**          | 의도치 않은 혼용 차단                | 유연한 조합, 기존 JS 코드와 자연스럽게 결합 |
| **단점**          | 어댑터·보일러플레이트 증가           | `UserId`와 `OrderId`처럼 의미가 다른 값이 섞일 수 있음 |

> 💡 면접에서 "TypeScript는 왜 구조적 타이핑을 택했는가"를 묻는다면, TypeScript가 **기존 JavaScript 코드베이스에 점진적으로 타입을 입히는 것**을 목표로 설계됐다는 점을 짚어야 한다. 명목적 타이핑이었다면 이미 존재하는 수많은 객체 리터럴에 일일이 타입 이름을 붙여야 했을 것이다.

<br>

### 2. 타입 호환성 규칙

### 2-1. 객체 타입 — 부분 집합이면 대입 가능

타입 `S`를 타입 `T`에 대입하려면, **T가 요구하는 모든 프로퍼티를 S가 호환되는 타입으로 갖고 있어야** 한다. S가 프로퍼티를 더 갖는 것은 문제가 되지 않는다. 즉 "더 구체적인(정보가 많은) 타입"이 "덜 구체적인 타입"에 대입된다.

```
        Named { name }             ← 요구하는 프로퍼티가 적음(넓은 타입)
           ▲ 대입 가능
     Person { name, age }          ← 프로퍼티가 많음(좁은 타입)
           ▲ 대입 가능
Employee { name, age, company }    ← 가장 좁은 타입

방향: 좁은 타입 → 넓은 타입 으로만 대입 가능 (반대는 프로퍼티 누락 오류)
```

```typescript
interface Named { name: string }
interface Person { name: string; age: number }

const person: Person = { name: "김철수", age: 30 };
const named: Named = person; // OK — age가 남아도 무방

const back: Person = named;  // 오류 — Named에는 age가 없음
```

이 규칙은 프로퍼티 단위로 **재귀적으로** 적용된다. 중첩 객체의 프로퍼티도 같은 규칙으로 비교된다.

<br>

### 2-2. 함수 타입 — 매개변수와 반환값의 방향이 다르다

함수 타입의 호환성은 **반환값은 공변(covariant)**, **매개변수는 반공변(contravariant)**으로 검사된다.

- **매개변수 개수**: 매개변수가 **적은** 함수는 많은 함수 자리에 들어갈 수 있음 (JS에서 남는 인수는 무시되므로). `arr.forEach((x) => ...)`가 `(value, index, array)` 시그니처에 들어가는 이유
- **매개변수 타입**: `strictFunctionTypes`가 켜져 있으면 함수 타입 표기(`(x: T) => void`)에는 반공변 검사가 적용되고, **메서드 표기(`method(x: T): void`)에는 양변(bivariant) 검사**가 유지됨
- **반환 타입**: 반환값이 더 좁은(구체적인) 함수가 넓은 반환을 기대하는 자리에 들어갈 수 있음

```typescript
type Handler = (e: MouseEvent) => void;

const onEvent = (e: Event) => console.log(e.type);
const h1: Handler = onEvent;         // OK — 더 넓은 매개변수(Event)를 받는 함수는 안전함

const onClick = (e: MouseEvent) => console.log(e.clientX);
const h2: (e: Event) => void = onClick; // 오류 — Event에는 clientX가 없을 수 있음
```

> ⚠️ 메서드 표기가 양변 검사를 유지하는 것은 `Array<Dog>`를 `Array<Animal>`에 대입하는 등 흔한 패턴을 허용하기 위한 **의도적 타협**이다. 라이브러리 콜백 타입을 설계할 때 안전성이 중요하다면 메서드 표기 대신 **함수 타입 프로퍼티** 표기를 사용해야 반공변 검사를 받을 수 있다.

<br>

### 2-3. 그 밖의 호환성 규칙 요약

| **상황**                          | **호환 여부**   | **설명**                                                      |
| --------------------------------- | --------------- | ------------------------------------------------------------- |
| **선택적 프로퍼티(`a?: T`)**      | 없어도 대입 가능 | 대상 타입의 선택적 프로퍼티는 원본에 없어도 됨                |
| **`readonly` 프로퍼티**           | 호환에 영향 없음 | `readonly`는 수정 가능 여부만 제한, 대입 자체는 양방향 가능    |
| **클래스의 `private`·`protected`** | **같은 선언에서 유래해야 함** | 구조가 같아도 비공개 멤버가 다른 클래스 출신이면 호환 불가 → 사실상 명목적 타이핑 |
| **`enum`**                        | 서로 다른 enum은 불호환 | 숫자 enum은 `number`와 상호 호환되지만, enum끼리는 이름으로 구분함 |
| **제네릭 타입**                   | 인자를 대입한 결과 구조로 비교 | `Box<string>`과 `Box<number>`는 `value` 프로퍼티 타입이 달라 불호환 |

<br>

### 3. 초과 프로퍼티 검사(Excess Property Check)

구조적 타이핑대로라면 프로퍼티가 더 많은 객체는 항상 대입 가능해야 한다. 그런데 **객체 리터럴을 직접 대입할 때**만은 예외적으로 "타입에 없는 프로퍼티"가 오류로 잡힌다. 이것이 초과 프로퍼티 검사다.

```typescript
interface Options {
  title: string;
  color?: string;
}

const a: Options = { title: "제목", colour: "red" }; // 오류 — 'colour'는 Options에 없음 (오타 방지)

const tmp = { title: "제목", colour: "red" };
const b: Options = tmp; // OK — 변수를 거치면 "신선한" 리터럴이 아니므로 검사하지 않음
```

**동작 원리**

- 객체 리터럴이 만들어지는 순간 그 타입은 **신선한(fresh) 객체 리터럴 타입**으로 표시됨
- 신선한 타입을 명시된 타입에 대입할 때만 초과 프로퍼티 검사를 수행함
- 변수에 한 번 담기거나 함수의 반환값으로 나가면 신선함이 사라져 일반 구조적 호환성 규칙으로 되돌아감

```
{ title, colour } 리터럴 생성
        │ (fresh)
        ├──▶ 타입이 명시된 자리에 바로 대입 ──▶ 초과 프로퍼티 검사 O ──▶ 'colour' 오류
        │
        └──▶ const tmp = ... 에 담김 ──▶ 신선함 소멸 ──▶ tmp를 대입 ──▶ 검사 X, 구조만 비교
```

> 💡 초과 프로퍼티 검사는 타입 안전성 규칙이라기보다 **"오타·잘못된 옵션 이름"을 잡기 위한 편의 기능**이다. 그래서 검사 대상을 "직접 작성한 리터럴"로 한정한다. 이 구분을 알고 있으면 "왜 어떤 경우엔 오류가 나고 어떤 경우엔 안 나는가"를 설명할 수 있다.

**초과 프로퍼티 검사를 우회·완화하는 방법**

| **방법**                          | **예시**                                | **적합한 상황**                              |
| --------------------------------- | --------------------------------------- | -------------------------------------------- |
| **인덱스 시그니처 추가**          | `[key: string]: unknown`                | 임의의 추가 필드를 허용해야 하는 설정 객체   |
| **중간 변수 사용**                | `const tmp = {...}; const o: T = tmp;`  | 검사를 의도적으로 피할 때 (권장하지 않음)    |
| **타입 단언**                     | `{ ... } as Options`                    | 검사 무력화 — 오타도 함께 통과되므로 주의    |
| **스프레드로 조합**               | `{ ...base, extra: 1 }`                 | 스프레드 결과도 리터럴이므로 검사 대상임      |

> ⚠️ 모든 프로퍼티가 선택적인 타입(**약한 타입, weak type**)에는 별도 규칙이 있다. 원본과 겹치는 프로퍼티가 **하나도 없으면** 리터럴이 아니어도 오류가 발생한다. `{ title?: string; color?: string }` 타입에 `{ width: 10 }`을 담은 변수를 대입하면 실수로 판단해 거부한다.

### 4. 구조적 타이핑의 함정과 대응

### 4-1. 의미가 다른 같은 모양 — 브랜드 타입

`string` 기반의 `UserId`와 `OrderId`는 구조가 같아서 서로 섞여도 컴파일러가 잡지 못한다. 이럴 때는 **브랜드(Brand) 타입**으로 명목적 타이핑을 흉내 낸다.

```typescript
// 안티패턴: 별칭만 다르고 구조는 동일 → 혼용 가능
type UserId = string;
type OrderId = string;
function findOrder(id: OrderId) {}
const uid: UserId = "u-1";
findOrder(uid); // 통과됨 — 버그 가능성

// 개선: 존재하지 않는 프로퍼티로 구조를 다르게 만듦
type Brand<T, B extends string> = T & { readonly __brand: B };
type SafeUserId = Brand<string, "UserId">;
type SafeOrderId = Brand<string, "OrderId">;

function findOrderSafe(id: SafeOrderId) {}
const sid = "u-1" as SafeUserId;
findOrderSafe(sid); // 오류 — __brand가 "UserId"라 "OrderId"와 불호환
```

`__brand`는 런타임에 존재하지 않는 **타입 전용 표식**이며, 값을 만들 때만 단언 또는 검증 함수를 거치게 하면 된다(런타임에는 그냥 `string`이다. 타입 소거는 unit07 참고).

**"좁은 타입이 넓은 타입으로 흘러가는" 정보 손실**

구조적 호환 덕분에 `Person`을 `Named`에 대입할 수 있지만, 그 뒤 `Named` 타입 변수에서는 `age`에 접근할 수 없다. `Object.keys()`가 `string[]`을 반환하는 것도 같은 이유다. 컴파일러는 실제 객체에 **선언되지 않은 프로퍼티가 더 있을 수 있다**고 가정하므로 키를 `keyof T`로 좁혀주지 않는다.

```typescript
function printKeys(obj: Named) {
  for (const key of Object.keys(obj)) {
    // key는 string — obj에 name 외의 프로퍼티가 있을 수 있음을 반영
    console.log(key, (obj as Record<string, unknown>)[key]);
  }
}
```

### 5. 정리 — 면접·실무 체크포인트

| **질문**                                              | **핵심 답변**                                                                 |
| ----------------------------------------------------- | ----------------------------------------------------------------------------- |
| **구조적 타이핑이란?**                                | 이름이 아니라 **프로퍼티 구조**로 호환성을 판단하는 방식. JS 덕 타이핑의 정적 버전 |
| **어떤 방향으로 대입되는가?**                         | 프로퍼티가 **더 많은(좁은) 타입 → 더 적은(넓은) 타입**                        |
| **함수 매개변수는 왜 반대 방향인가?**                 | 매개변수는 **반공변** — 더 넓은 타입을 받는 함수가 안전. 메서드 표기는 양변 검사 |
| **객체 리터럴에서만 오류가 나는 이유는?**             | **초과 프로퍼티 검사**는 신선한 리터럴에만 적용되는 오타 방지 기능              |
| **같은 구조의 다른 의미를 구분하려면?**               | **브랜드 타입**으로 명목적 타이핑을 흉내 냄                                    |
| **`private` 멤버가 있으면 왜 구조가 같아도 불호환인가?** | 비공개 멤버는 **같은 선언 출처**여야 호환 — 클래스는 부분적으로 명목적으로 동작 |

- 타입 좁히기와 판별 유니온에서 구조적 타이핑이 어떻게 활용되는지는 **unit03**, 인터페이스와 타입 별칭의 확장 방식 차이는 **unit05**를 참고할 것
