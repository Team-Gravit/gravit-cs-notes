## 렌더링과 재조정

React 컴포넌트가 **언제 다시 실행되고(리렌더), 그 결과가 실제 DOM에 어떻게 반영되는지(재조정)**를 다룬다. "상태가 바뀌면 화면이 바뀐다"는 말 뒤에 숨은 동작 원리를 알아야 불필요한 리렌더를 진단하고 `key` 관련 버그를 설명할 수 있다.

<br>

### 1. 렌더링이란 무엇인가

React에서 **렌더링(Rendering)**은 "DOM을 그리는 것"이 아니라 **컴포넌트 함수를 호출해 어떤 UI를 원하는지 React 엘리먼트 트리로 설명받는 것**이다. 실제 DOM 갱신은 그 다음 단계인 커밋에서 일어난다.

```
① 트리거(Trigger)   : 초기 마운트 또는 상태 변경 요청
        ↓
② 렌더(Render)      : 컴포넌트 함수 호출 → 새 엘리먼트 트리 생성 (순수 계산, 부수효과 없음)
        ↓
③ 재조정(Reconcile) : 이전 Fiber 트리와 비교(diff) → 바뀐 부분만 표시
        ↓
④ 커밋(Commit)      : 표시된 변경만 실제 DOM에 반영 → useLayoutEffect → 브라우저 페인트 → useEffect
```

- 렌더 단계는 **순수 함수**여야 함. 여기서 부수효과를 일으키면 동시성 렌더링(unit08)에서 렌더가 중단·재시도될 때 예측 불가능한 결과가 생김
- 커밋 단계는 **동기적이고 중단되지 않음**. 렌더 결과와 실제 DOM이 항상 일관되게 유지되는 이유임

> 💡 "리렌더가 일어났다 = DOM이 바뀌었다"가 아니다. 렌더는 자주 일어나도 diff 결과 바뀐 것이 없으면 DOM 조작은 0번이다. 성능 문제의 원인은 대부분 "DOM 갱신"이 아니라 "너무 많은 컴포넌트 함수 재실행"에 있다(unit06 참고).

<br>

### 2. 리렌더가 일어나는 조건

리렌더 트리거는 딱 세 가지로 정리할 수 있다.

| **트리거**                 | **설명**                                                        | **흔한 오해**                              |
| -------------------------- | --------------------------------------------------------------- | ------------------------------------------ |
| **자신의 상태 변경**       | `useState`·`useReducer`의 setter 호출, `Object.is`로 다르면 예약 | 같은 값으로 set하면 리렌더가 대부분 생략됨 |
| **부모의 리렌더**          | 부모가 다시 렌더되면 **자식은 props 변화와 무관하게** 리렌더됨   | "props가 안 바뀌었으니 안 그려진다"는 오해 |
| **구독한 Context 값 변경** | `useContext`로 구독한 Provider의 `value`가 바뀌면 리렌더됨      | 중간 컴포넌트가 `memo`여도 소비자는 리렌더 |

- **props 변경 자체는 트리거가 아님**. props는 부모가 리렌더될 때 따라 바뀌는 것이며, 부모의 리렌더가 진짜 원인임
- 자식이 `React.memo`로 감싸져 있을 때만 "props가 얕은 비교로 같으면 건너뛰기"가 적용됨

```tsx
function Parent() {
  const [count, setCount] = useState(0);
  return (
    <>
      <button onClick={() => setCount((c) => c + 1)}>{count}</button>
      {/* count와 아무 관계가 없어도 Parent가 리렌더되면 함께 리렌더됨 */}
      <Child />
    </>
  );
}
```

> ⚠️ 상태 setter에 같은 값을 넘기면 React는 리렌더를 건너뛰지만, 안전을 위해 해당 컴포넌트 함수를 한 번 더 호출해 보고 자식으로 내려가지 않는 경우가 있다. "setter를 호출했는데 컴포넌트 함수가 실행됐다"고 해서 반드시 자식까지 리렌더된 것은 아니다.

<br>

### 3. 재조정(Reconciliation)과 diffing 전략

두 트리를 완전히 비교하는 알고리즘은 O(n³)이라 실용적이지 않다. React는 두 가지 **휴리스틱 가정**을 두고 O(n)으로 diff한다.

- **가정 1**: 타입이 다른 두 엘리먼트는 완전히 다른 트리를 만든다
- **가정 2**: 개발자가 `key`로 "어떤 자식이 렌더 사이에서 동일한지" 힌트를 준다

### 3-1. 타입 비교

| **비교 상황**                          | **React의 처리**                                                   |
| -------------------------------------- | ------------------------------------------------------------------ |
| **타입이 다름** (`div` → `span`, `A` → `B`) | 기존 서브트리 전체 **언마운트** 후 새로 마운트. 하위 상태 전부 소실 |
| **같은 DOM 타입**                      | 노드 유지, 바뀐 속성만 갱신 (`className`, `style` 등)              |
| **같은 컴포넌트 타입**                 | 인스턴스(상태) 유지, 새 props로 리렌더                             |

```tsx
// 안티패턴: 렌더마다 컴포넌트 타입이 새로 정의됨
function Form() {
  function Field() { return <input />; }  // 매 렌더마다 다른 함수 객체 → 다른 타입
  return <Field />;                        // Form이 리렌더될 때마다 input이 언마운트·재마운트되어 입력값이 사라짐
}
```

```tsx
// 개선: 컴포넌트는 항상 모듈 최상위에서 정의
function Field() { return <input />; }
function Form() { return <Field />; }
```

<br>

### 3-2. 자식 목록 비교와 key

같은 위치의 자식 목록을 비교할 때 `key`가 없으면 **인덱스 순서**로 짝을 맞춘다. 앞에 항목을 삽입하면 뒤의 모든 항목이 "내용이 바뀐 것"으로 판단된다.

```
key 없음 (인덱스 매칭)                    key 있음 (id 매칭)
이전: [A(0)] [B(1)] [C(2)]               이전: [A:a] [B:b] [C:c]
이후: [X(0)] [A(1)] [B(2)] [C(3)]        이후: [X:x] [A:a] [B:b] [C:c]
결과: 0,1,2 모두 갱신 + 3 삽입 (4회)       결과: x 하나만 삽입, 나머지는 이동 (1회)
      각 항목의 내부 상태가 한 칸씩 밀림          각 항목의 상태가 그대로 따라감
```

<br>

### 4. key의 실제 역할

`key`는 "경고를 없애는 장치"가 아니라 **엘리먼트의 정체성(identity)을 React에 알려주는 유일한 수단**이다.

- **같은 key** = 같은 엘리먼트로 취급 → 상태·DOM·ref가 유지되고 props만 갱신됨
- **다른 key** = 다른 엘리먼트로 취급 → 언마운트 후 새로 마운트됨
- key는 **형제(sibling) 사이에서만** 고유하면 됨. 전역 고유일 필요는 없음

| **key 선택**            | **적합한 경우**                                       | **문제점**                                                     |
| ----------------------- | ----------------------------------------------------- | -------------------------------------------------------------- |
| **데이터의 고유 id**    | 서버에서 온 목록, 삽입·삭제·정렬이 있는 목록          | 없음 (권장)                                                    |
| **배열 인덱스**         | 정적이고 순서가 절대 바뀌지 않는 목록                 | 삽입·삭제·정렬 시 상태가 엉뚱한 항목에 붙음, 불필요한 DOM 갱신 |
| **`Math.random()` 등**  | 없음                                                  | 매 렌더마다 전부 언마운트·재마운트 → 성능·상태 모두 붕괴       |

```tsx
// 안티패턴: 삭제 가능한 목록에 인덱스 key
{todos.map((todo, i) => <TodoItem key={i} todo={todo} />)}
// 0번을 삭제하면 1번 항목이 key=0을 물려받아 0번의 체크 상태·입력값을 그대로 가짐

// 개선: 안정적인 id
{todos.map((todo) => <TodoItem key={todo.id} todo={todo} />)}
```

**key로 의도적으로 상태를 초기화하기** — key를 바꾸면 React가 "새 컴포넌트"로 취급한다는 성질을 활용해, 다른 사용자의 프로필로 전환할 때 폼 상태를 깨끗이 리셋할 수 있다.

```tsx
<ProfileForm key={userId} userId={userId} />
// userId가 바뀌면 useEffect로 상태를 초기화할 필요 없이 폼이 통째로 새로 마운트됨
```

> 💡 "key가 왜 필요한가"에 "경고 때문"이라고 답하면 감점이다. **정체성 유지 → 상태 보존과 최소 DOM 조작**, 그리고 **key 변경으로 상태 초기화**까지 언급하면 원리를 이해했다고 평가받는다.

<br>

### 5. 배치(Batching)와 렌더 타이밍

setter 호출은 즉시 렌더를 일으키지 않고 **예약(enqueue)**만 한다. React는 같은 이벤트 루프 틱 안의 여러 상태 변경을 모아 한 번만 렌더한다.

```tsx
function handleClick() {
  setCount((c) => c + 1);
  setFlag((f) => !f);
  // 여기서 count를 읽어도 아직 이전 값 — 렌더는 핸들러가 끝난 뒤 한 번만 실행됨
}
```

- **React 17 이하**: React 이벤트 핸들러 안에서만 배치되고, `setTimeout`·`Promise.then` 등 외부 콜백에서는 setter마다 렌더됨
- **React 18 이상**: `createRoot`를 쓰면 **자동 배치(Automatic Batching)**로 어디서 호출하든 배치됨. 강제로 동기 렌더가 필요하면 `flushSync`를 사용함

> ⚠️ 이전 상태에 의존하는 갱신은 `setCount(count + 1)`이 아니라 `setCount((c) => c + 1)` 형태로 써야 한다. 배치 때문에 같은 틱에서 `count`는 갱신되지 않은 옛 값이기 때문이다(stale closure, unit02 참고).

<br>

### 6. 리렌더 진단 방법

- **React DevTools → Components → "Highlight updates when components render"**: 리렌더되는 컴포넌트가 화면에서 깜빡임
- **Profiler 탭**: 어떤 컴포넌트가 몇 번, 왜(props·state·부모·hooks 변경) 렌더됐는지 확인. "Record why each component rendered" 옵션을 켤 것
- **개발 모드 StrictMode**: 컴포넌트 함수를 두 번 호출해 렌더 단계의 순수성 위반을 드러냄. 프로덕션에서는 한 번만 호출됨

### 7. 면접·실무 체크포인트

| **질문**                                    | **핵심 답변**                                                                    |
| ------------------------------------------- | -------------------------------------------------------------------------------- |
| **리렌더 트리거 세 가지는?**                | 자신의 상태 변경, 부모의 리렌더, 구독한 Context 변경. props 변경은 원인이 아님   |
| **렌더와 커밋의 차이는?**                   | 렌더는 엘리먼트 트리 계산(순수), 커밋은 diff 결과를 DOM에 반영(동기·중단 불가)   |
| **diff가 O(n)인 이유는?**                   | 타입이 다르면 서브트리 교체, key로 자식 정체성 힌트 — 두 휴리스틱 가정 덕분      |
| **인덱스 key가 위험한 이유는?**             | 삽입·삭제·정렬 시 상태가 다른 항목에 붙고 DOM 갱신이 불필요하게 늘어남           |
| **key를 바꾸면 어떻게 되는가?**             | 다른 엘리먼트로 취급되어 언마운트·재마운트 → 상태 초기화 용도로 활용 가능        |
| **React 18의 자동 배치란?**                 | 이벤트 핸들러 밖(`setTimeout`, `Promise`)에서도 여러 setter가 한 번의 렌더로 묶임 |

- 컴포넌트를 다른 컴포넌트 **안에서 정의하지 않는다** — 매 렌더 타입이 바뀌어 상태가 날아감
- 목록의 key는 **데이터의 안정적인 id**를 쓰고, 상태 초기화가 필요하면 **key 변경**을 먼저 고려한다
- 훅의 동작과 stale closure는 **unit02**, 최적화 판단은 **unit06**을 참고할 것
