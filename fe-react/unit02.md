## 훅의 동작 원리

**훅(Hook)**은 함수 컴포넌트가 상태와 생명주기를 다룰 수 있게 하는 함수인데, 내부적으로는 **호출 순서에 의존하는 연결 리스트**로 구현되어 있다. 이 구조를 알아야 "훅의 규칙"이 왜 존재하는지, 왜 `stale closure`가 생기는지, 의존성 배열을 어떻게 판단해야 하는지 설명할 수 있다.

<br>

### 1. 훅은 어디에 저장되는가

함수 컴포넌트는 매 렌더마다 **처음부터 다시 실행**된다. 그럼에도 `useState`가 이전 값을 기억하는 이유는 값이 함수 안이 아니라 **컴포넌트의 Fiber 노드**에 저장되기 때문이다.

```
Fiber 노드 (컴포넌트 인스턴스당 하나)
 └─ memoizedState ──▶ [훅 #0: useState] ──▶ [훅 #1: useEffect] ──▶ [훅 #2: useRef] ──▶ null
                        (state, queue)        (effect, deps)        ({ current })

렌더 시 컴포넌트 함수 실행
  useState() 첫 호출  → 리스트의 0번째 셀을 읽음
  useEffect() 호출    → 리스트의 1번째 셀을 읽음
  useRef() 호출       → 리스트의 2번째 셀을 읽음
```

- 훅은 이름이나 변수명이 아니라 **"몇 번째로 호출됐는가"**로 자기 셀을 찾음
- 마운트 시에는 셀을 만들고(`mountState`), 이후 렌더에서는 같은 순서로 셀을 꺼내 씀(`updateState`)

> 💡 "훅은 클로저다"라는 설명은 절반만 맞다. 값을 **보관**하는 곳은 Fiber의 연결 리스트이고, 컴포넌트 함수 안의 지역 변수는 그 값을 **그 렌더 동안만 복사해 둔 스냅샷**이다. 이 구분이 stale closure를 이해하는 열쇠다.

<br>

### 2. 훅의 규칙과 그 이유

### 2-1. 최상위에서만 호출한다

조건문·반복문·중첩 함수 안에서 훅을 호출하면 렌더마다 호출 순서가 달라져 **리스트의 셀이 어긋난다**.

```tsx
// 안티패턴: 조건부 훅 호출
function Profile({ user }: { user?: User }) {
  if (user) {
    const [name, setName] = useState(user.name); // user가 없을 때는 이 훅이 건너뛰어짐
  }
  const [open, setOpen] = useState(false);       // 첫 렌더에서는 #1, 다음 렌더에서는 #0 → 값이 뒤섞임
  // ...
}
```

```tsx
// 개선: 훅은 항상 호출하고, 조건은 훅 내부나 반환값에서 처리
function Profile({ user }: { user?: User }) {
  const [name, setName] = useState(user?.name ?? "");
  const [open, setOpen] = useState(false);
  if (!user) return null;  // 이른 반환은 모든 훅 호출 뒤에
  // ...
}
```

### 2-2. React 함수 안에서만 호출한다

훅은 "현재 렌더 중인 Fiber"라는 전역 포인터에 의존한다. 일반 함수나 클래스 메서드에서 호출하면 가리킬 Fiber가 없다. 커스텀 훅(`use`로 시작하는 함수)은 결국 컴포넌트 렌더 중에 호출되므로 허용된다.

> ⚠️ 두 규칙은 관습이 아니라 **구현 제약**이다. ESLint의 `react-hooks/rules-of-hooks`가 이를 정적으로 검사하므로 반드시 켜 둔다. React 19에서 추가된 `use` 훅은 예외적으로 조건문·이른 반환 뒤에서도 호출할 수 있다(unit08 참고).

<br>

### 3. 렌더는 스냅샷이다

컴포넌트 함수가 실행될 때 `useState`가 돌려준 값은 **그 렌더 시점의 값으로 고정**된다. 그 렌더에서 만들어진 이벤트 핸들러·이펙트·타이머 콜백은 모두 그 고정된 값을 클로저로 붙잡는다.

```tsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);  // 이 렌더의 count = 0
    setCount(count + 1);  // 여전히 0 → 결과는 1 (2가 아님)
    setTimeout(() => alert(count), 1000); // 1초 뒤에도 0을 출력
  }
  return <button onClick={handleClick}>{count}</button>;
}
```

- `count`는 변수가 아니라 **상수처럼** 동작함. 렌더 안에서 절대 바뀌지 않음
- 다음 렌더는 새 `count` 값을 가진 **새 클로저**를 만들어 냄

<br>

### 4. stale closure(오래된 클로저)

**stale closure**란 "이전 렌더의 값을 붙잡은 함수가 나중에 실행되어 낡은 값을 쓰는 현상"이다. 특히 `useEffect` 안에서 만든 구독·타이머에서 자주 발생한다.

```tsx
// 안티패턴: 마운트 시 만든 인터벌이 첫 렌더의 count(0)만 계속 봄
useEffect(() => {
  const id = setInterval(() => {
    setCount(count + 1);  // 항상 0 + 1 → 화면이 1에서 멈춤
  }, 1000);
  return () => clearInterval(id);
}, []);  // 의존성 비움 → 이펙트가 한 번만 실행되어 클로저가 갱신되지 않음
```

```tsx
// 개선 ①: 함수형 업데이트로 최신 상태를 React에게서 받음
useEffect(() => {
  const id = setInterval(() => setCount((c) => c + 1), 1000);
  return () => clearInterval(id);
}, []);
```

```tsx
// 개선 ②: 값 자체가 필요하면 의존성에 넣고, 바뀔 때마다 이펙트를 재구성
useEffect(() => {
  const id = setInterval(() => console.log(count), 1000);
  return () => clearInterval(id);
}, [count]);
```

| **해결 방법**                     | **적합한 상황**                                          | **비고**                                        |
| --------------------------------- | -------------------------------------------------------- | ----------------------------------------------- |
| **함수형 업데이트** `set(c => …)` | 이전 상태를 기반으로 갱신할 때                           | 가장 먼저 시도할 것                             |
| **의존성 배열에 추가**            | 값이 바뀔 때 이펙트를 다시 구성해도 괜찮을 때            | 정직한 방법. 재구성 비용이 크면 아래 고려       |
| **ref로 최신 값 보관**            | 재구성 비용이 크고(웹소켓 등) 콜백만 최신이면 될 때      | `ref.current = value`를 렌더마다 갱신, unit07  |
| **`useEffectEvent`**              | 이펙트 안에서 최신 props·state를 읽되 의존성으론 빼고 싶을 때 | React 19.2에서 정식 제공(그 이전은 실험 채널) |

<br>

### 5. 의존성 배열 판단 기준

의존성 배열은 "언제 실행할지 정하는 스위치"가 아니라 **"이 이펙트 코드가 읽는 반응형 값의 목록"**이다. 따라서 판단 기준은 하나다.

- 이펙트(또는 `useMemo`·`useCallback`) 본문에서 **읽는 모든 props·state·그로부터 파생된 값**을 넣는다
- 컴포넌트 밖의 상수, `useRef`의 ref 객체, `useState`의 setter, `dispatch`는 렌더 간 동일함이 보장되므로 넣지 않아도 됨(넣어도 무해)
- "너무 자주 실행돼서" 의존성을 빼고 싶다면, **답은 배열을 속이는 것이 아니라 코드를 바꾸는 것**임

| **증상**                                    | **잘못된 대응**                    | **올바른 대응**                                                      |
| ------------------------------------------- | ---------------------------------- | -------------------------------------------------------------------- |
| **객체·배열 의존성이 매 렌더 새로 생김**    | 배열에서 뺀다                      | 원시값으로 쪼개 넣거나, 객체 생성을 이펙트 안으로 옮김               |
| **함수 의존성이 매 렌더 새로 생김**         | 배열에서 뺀다                      | 함수를 이펙트 안으로 옮기거나 `useCallback`으로 고정(unit06)         |
| **이전 상태 기반 갱신 때문에 state 의존**   | 배열에서 뺀다                      | 함수형 업데이트 `set(prev => …)`으로 state 읽기 자체를 제거          |
| **최신 값은 필요하지만 재실행은 원치 않음** | 배열에서 뺀다                      | ref 또는 `useEffectEvent`                                            |

```tsx
// 안티패턴: options 객체가 매 렌더 새로 만들어져 이펙트가 무한 재실행
const options = { roomId, serverUrl };
useEffect(() => { connect(options); }, [options]);

// 개선: 원시값만 의존하고 객체는 이펙트 안에서 생성
useEffect(() => { connect({ roomId, serverUrl }); }, [roomId, serverUrl]);
```

> ⚠️ `// eslint-disable-next-line react-hooks/exhaustive-deps`로 경고를 끄는 것은 거의 항상 버그를 숨기는 행위다. 린터가 지적한 값을 정말 빼고 싶다면 "그 값이 바뀌어도 이 이펙트는 다시 돌 필요가 없다"는 근거를 코드로 표현(ref, 함수형 업데이트, 이펙트 이벤트)해야 한다.

<br>

### 6. 자주 쓰는 훅의 내부 동작 비교

| **훅**            | **저장하는 것**                 | **렌더 트리거** | **동일성 보장**                 | **주 용도**                              |
| ----------------- | ------------------------------- | --------------- | ------------------------------- | ---------------------------------------- |
| **useState**      | 값 + 업데이트 큐                | 값 변경 시      | setter는 항상 동일              | 화면에 반영되는 상태                     |
| **useReducer**    | 값 + 액션 큐 + 리듀서           | 값 변경 시      | dispatch는 항상 동일            | 여러 상태가 함께 바뀌는 복잡한 전이       |
| **useRef**        | `{ current }` 객체              | **없음**        | 객체 자체가 동일                | 렌더와 무관한 값, DOM 참조(unit07)       |
| **useMemo**       | 계산 결과 + 의존성              | 없음            | 의존성이 같으면 같은 참조       | 비싼 계산·참조 안정화(unit06)            |
| **useCallback**   | 함수 + 의존성                   | 없음            | 의존성이 같으면 같은 함수       | 자식 memo·이펙트 의존성 안정화(unit06)  |
| **useEffect**     | 이펙트 함수 + 클린업 + 의존성   | 없음            | -                               | 외부 시스템과 동기화(unit05)             |

- `useState`의 setter는 큐에 갱신을 넣기만 하고, 실제 값 계산은 **다음 렌더에서 큐를 순서대로 소비**하며 이루어짐. 그래서 `set(c => c + 1)`을 두 번 호출하면 2가 됨
- `useState`에 함수를 넘기면(`useState(() => expensive())`) **초기 렌더에만** 호출되는 지연 초기화가 됨. `useState(expensive())`는 매 렌더 호출됨

> 💡 React 19의 **React Compiler**는 `useMemo`·`useCallback`을 자동으로 넣어 주지만, 훅의 규칙과 렌더의 순수성을 지킨 코드에만 적용된다. 컴파일러 시대에도 이 유닛의 원리는 그대로 유효하다.

<br>

### 7. 면접·실무 체크포인트

| **질문**                                              | **핵심 답변**                                                                                 |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| **훅을 조건문 안에서 부르면 안 되는 이유는?**         | 훅은 Fiber의 연결 리스트에서 **호출 순서**로 자기 셀을 찾으므로 순서가 바뀌면 값이 뒤섞임      |
| **함수가 매번 실행되는데 상태가 유지되는 이유는?**    | 값은 함수 지역 변수가 아니라 Fiber 노드에 저장되고, 함수는 그 값을 스냅샷으로 받을 뿐          |
| **stale closure란?**                                  | 이전 렌더의 값을 붙잡은 콜백이 나중에 실행되어 낡은 값을 쓰는 현상. 함수형 업데이트·의존성·ref로 해결 |
| **setCount(count+1) 두 번이 1이 되는 이유는?**        | 두 호출 모두 같은 렌더의 `count`(0)를 읽음. `set(c => c+1)`은 큐를 순서대로 적용해 2가 됨       |
| **의존성 배열의 판단 기준은?**                        | "언제 실행할지"가 아니라 "본문이 읽는 반응형 값 전부". 줄이고 싶으면 코드 구조를 바꿈           |

- 린터 경고를 끄는 대신 **함수형 업데이트 → 의존성 추가 → ref/useEffectEvent** 순으로 해결책을 찾는다
- 훅의 규칙은 관습이 아니라 **연결 리스트 구현의 제약**임을 설명할 수 있어야 한다
- 이펙트의 본질과 클린업은 **unit05**, 메모이제이션 훅의 사용 판단은 **unit06**을 참고할 것
