## useEffect의 정의와 오용

`useEffect`는 "무언가 바뀌면 실행되는 콜백"이 아니라 **React 컴포넌트를 외부 시스템과 동기화하는 도구**다. 이 정의를 잘못 이해하면 이펙트로 상태를 연쇄 갱신하거나 이벤트 처리를 이펙트에 넣는 오용이 생긴다. 이 유닛은 이펙트의 역할, 클린업의 의미, `useLayoutEffect`와의 타이밍 차이를 다룬다.

<br>

### 1. 이펙트란 무엇인가 — 동기화 도구

렌더는 순수 계산이어야 한다(unit01). 그런데 네트워크 연결, 브라우저 API 구독, 타이머, 서드파티 위젯처럼 **React 바깥의 시스템**은 렌더 결과만으로 제어할 수 없다. 이펙트는 "이 컴포넌트가 이런 props·state로 화면에 있는 동안, 외부 시스템은 이런 상태여야 한다"는 **동기화 선언**이다.

```
컴포넌트가 화면에 있음 (props: roomId="A")
   ↓ 이펙트 실행: 채팅방 A에 연결
roomId가 "B"로 바뀜
   ↓ 이전 이펙트의 클린업: 채팅방 A 연결 해제
   ↓ 새 이펙트 실행: 채팅방 B에 연결
컴포넌트가 사라짐
   ↓ 클린업: 채팅방 B 연결 해제
```

- 이펙트는 **커밋 후, 브라우저가 화면을 그린 뒤** 실행됨(정확한 타이밍은 4절 참고)
- 이펙트는 "마운트 시 한 번" 같은 **생명주기 관점이 아니라, "이 의존성 값이면 이 외부 상태" 라는 동기화 관점**으로 생각해야 함
- 의존성 배열은 "실행 시점을 제어하는 스위치"가 아니라 "이 동기화가 읽는 값의 목록"임(unit02)

> 💡 이펙트가 필요한지 판단하는 질문은 하나다. **"이 코드가 React 바깥의 무언가와 동기화하는가?"** 아니라면 이펙트가 아니라 렌더 중 계산 또는 이벤트 핸들러에 있어야 한다.

<br>

### 2. 클린업(Cleanup)의 의미

이펙트가 반환하는 함수가 **클린업**이다. React는 다음 두 시점에 클린업을 호출한다.

- 같은 이펙트가 **다시 실행되기 직전** (의존성이 바뀌어 재동기화할 때)
- 컴포넌트가 **언마운트될 때**

클린업은 "언마운트 처리"가 아니라 **"이 이펙트가 만든 동기화를 되돌리는 것"**이다. 이펙트와 클린업이 짝을 이루면 어떤 순서로 몇 번 실행되든 외부 시스템은 항상 현재 props·state와 일치한다.

```tsx
// 안티패턴: 클린업이 없어 roomId가 바뀔 때마다 연결이 쌓임
useEffect(() => {
  const conn = createConnection(roomId);
  conn.connect();
}, [roomId]);  // A → B로 바뀌면 A 연결이 남은 채 B 연결 추가 → 메시지 중복 수신, 메모리 누수
```

```tsx
// 개선: 만든 것을 되돌리는 클린업을 반드시 짝으로
useEffect(() => {
  const conn = createConnection(roomId);
  conn.connect();
  return () => conn.disconnect();
}, [roomId]);
```

**비동기 요청의 경쟁 조건(race condition)** — fetch는 취소가 어렵기 때문에 클린업에서 "이 응답은 이미 낡았다"는 플래그를 세운다.

```tsx
useEffect(() => {
  let ignore = false;
  fetchUser(userId).then((user) => {
    if (!ignore) setUser(user);  // userId가 바뀐 뒤 도착한 옛 응답은 버림
  });
  return () => { ignore = true; };
}, [userId]);
```

> ⚠️ 개발 모드의 `StrictMode`는 마운트 직후 **이펙트 → 클린업 → 이펙트**를 한 번 더 실행해 클린업이 올바른지 검증한다. "이펙트가 두 번 실행돼요"는 버그가 아니라 **클린업이 빠졌다는 신호**다. 이펙트 실행 횟수를 세는 방식으로 `useRef` 플래그를 두어 우회하지 말고 클린업을 고쳐야 한다.

### 3. 흔한 오용과 개선

### 3-1. 파생 값을 이펙트로 계산

```tsx
// 안티패턴: 렌더 → 이펙트 → setState → 또 렌더. 첫 렌더에서 잠깐 낡은 값 노출
const [fullName, setFullName] = useState("");
useEffect(() => { setFullName(first + " " + last); }, [first, last]);

// 개선: 렌더 중 계산 (unit03)
const fullName = first + " " + last;
```

### 3-2. 이벤트 처리를 이펙트로

```tsx
// 안티패턴: "구매 완료 상태가 되면" 요청을 보냄 → 새로고침·StrictMode·재마운트 시 중복 전송
useEffect(() => {
  if (submitted) postOrder(cart);
}, [submitted]);

// 개선: "사용자가 버튼을 눌렀을 때"는 이벤트 핸들러의 몫
function handleSubmit() {
  postOrder(cart);
  setSubmitted(true);
}
```

- 판단 기준: **"사용자가 무엇을 했기 때문에" 실행되는 코드는 이벤트 핸들러**, **"화면에 이런 상태로 존재하기 때문에" 실행되는 코드는 이펙트**

### 3-3. 부모에게 상태 변화를 이펙트로 알림

```tsx
// 안티패턴: 자식이 상태를 바꾼 뒤 이펙트로 부모에게 알림 → 렌더 2회, 타이밍이 어긋남
useEffect(() => { onChange(isOn); }, [isOn, onChange]);

// 개선: 같은 이벤트 안에서 두 갱신을 함께 처리 (배치되어 렌더 1회)
function handleClick() {
  const next = !isOn;
  setIsOn(next);
  onChange(next);
}
```

### 3-4. 서버 데이터 요청

`useEffect` + `fetch`는 동작은 하지만 캐시·중복 제거·경쟁 조건·재검증을 전부 직접 처리해야 한다. 규모가 커지면 서버 상태 라이브러리로 위임한다(unit04).

| **하려는 일**                          | **이펙트인가?** | **대안**                                      |
| -------------------------------------- | --------------- | --------------------------------------------- |
| **props·state에서 값 계산**            | 아니오          | 렌더 중 계산, `useMemo`                       |
| **props 변경 시 상태 리셋**            | 아니오          | `key` 변경(unit01)                            |
| **사용자 액션에 반응(요청·알림)**      | 아니오          | 이벤트 핸들러                                 |
| **부모에게 변화 통지**                 | 아니오          | 이벤트 핸들러에서 콜백 호출                   |
| **외부 스토어 구독**                   | 대체로 아니오   | `useSyncExternalStore`                        |
| **브라우저 API·소켓·타이머·위젯 동기화** | **예**        | `useEffect` + 클린업                          |
| **페이지 진입 분석 로그**              | **예**          | `useEffect` (화면에 존재했다는 사실이 트리거) |

### 4. useEffect vs useLayoutEffect — 실행 타이밍

두 훅의 API는 같지만 **실행 시점**이 다르다.

```
렌더 단계 (컴포넌트 함수 실행, 순수 계산)
   ↓
커밋 단계 ─ DOM 변경 반영
   ↓
useLayoutEffect 실행 ───────── 동기. 브라우저가 화면을 그리기 **전**. 여기서 setState하면 페인트 전에 재렌더
   ↓
브라우저 페인트 (사용자가 화면을 봄)
   ↓
useEffect 실행 ─────────────── 페인트 **후**. 화면을 막지 않음
```

| **항목**              | **useEffect**                           | **useLayoutEffect**                                       |
| --------------------- | --------------------------------------- | --------------------------------------------------------- |
| **실행 시점**         | 페인트 후 (비동기적으로 예약)           | DOM 변경 직후, 페인트 전 (동기)                           |
| **화면 차단**         | 없음                                    | 있음 — 무거우면 프레임 드롭                               |
| **깜빡임(flicker)**   | DOM을 측정해 다시 그리면 한 프레임 보임 | 페인트 전에 보정하므로 깜빡임 없음                        |
| **서버 렌더링(SSR)**  | 문제없음                                | 서버에서 경고 발생(레이아웃 정보 없음) — 클라이언트 전용 처리 필요 |
| **적합한 용도**       | 대부분의 동기화(구독, 요청, 로그)       | DOM 측정 후 위치·크기 보정(툴팁, 스크롤 위치 복원)        |

```tsx
// 툴팁이 화면 아래로 넘치면 위로 뒤집기: 측정 → 보정이 페인트 전에 끝나야 깜빡임이 없음
function Tooltip({ anchorRect }: { anchorRect: DOMRect }) {
  const ref = useRef<HTMLDivElement>(null);
  const [flip, setFlip] = useState(false);

  useLayoutEffect(() => {
    const height = ref.current!.getBoundingClientRect().height;
    setFlip(anchorRect.bottom + height > window.innerHeight);  // 페인트 전에 재렌더 → 사용자는 최종 위치만 봄
  }, [anchorRect]);

  return <div ref={ref} style={{ top: flip ? anchorRect.top - 8 : anchorRect.bottom + 8 }}>…</div>;
}
```

> ⚠️ `useLayoutEffect`를 "useEffect보다 빨라서 좋다"고 생각해 남용하면 모든 이펙트가 페인트를 막아 성능이 나빠진다. **DOM을 읽고 그 결과로 즉시 레이아웃을 바꿔야 하는 경우**로 한정한다.

### 5. 이펙트 작성 체크리스트

```
이 코드는 외부 시스템과 동기화하는가?
 ├─ 아니오 → 렌더 중 계산 / 이벤트 핸들러 / key 리셋
 └─ 예
     ├─ 만든 것을 되돌리는 클린업이 있는가? (구독 해제, 타이머 취소, 낡은 응답 무시)
     ├─ 본문이 읽는 반응형 값이 모두 의존성에 있는가? (unit02)
     ├─ StrictMode의 이중 실행에서 결과가 같은가? (멱등성)
     └─ 페인트 전에 DOM을 보정해야 하는가? → 예 → useLayoutEffect, 아니면 useEffect
```

- 하나의 이펙트는 **하나의 동기화**만 담당한다. 서로 다른 외부 시스템을 한 이펙트에 묶으면 한쪽 의존성 변경이 다른 쪽을 불필요하게 재실행시킴
- 반복되는 이펙트 패턴은 커스텀 훅(`useChatRoom`, `useWindowSize`)으로 추출해 의도를 이름에 담는다(unit10)

> 💡 React 19.2의 `useEffectEvent`는 "이펙트 안에서 최신 props·state를 읽지만 그 값의 변화로 재동기화하고 싶지는 않을 때"를 위한 도구다. 예를 들어 채팅 연결(roomId 의존)은 유지하면서 알림 테마(theme)는 최신값만 읽고 싶을 때 `theme`을 의존성에서 빼는 정당한 방법이 된다.

### 6. 면접·실무 체크포인트

| **질문**                                              | **핵심 답변**                                                                              |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **useEffect는 언제 쓰는가?**                          | React 바깥 시스템과 동기화할 때만. 파생 값 계산·이벤트 처리·부모 통지는 이펙트가 아님        |
| **클린업은 언제 실행되는가?**                         | 의존성 변경으로 이펙트가 재실행되기 직전, 그리고 언마운트 시. "만든 것을 되돌리는" 역할        |
| **StrictMode에서 이펙트가 두 번 도는 이유는?**        | 클린업이 올바른지 검증하기 위해 이펙트→클린업→이펙트를 수행. 우회 말고 클린업을 고쳐야 함       |
| **useEffect와 useLayoutEffect의 차이는?**             | 전자는 페인트 후 비동기, 후자는 DOM 변경 직후 페인트 전 동기. 후자는 DOM 측정·보정에만 사용     |
| **fetch의 경쟁 조건은 어떻게 막는가?**                | 클린업에서 `ignore` 플래그를 세워 낡은 응답을 무시. 규모가 커지면 서버 상태 라이브러리로 위임   |

- 이펙트를 쓰기 전에 **"동기화인가, 이벤트인가, 계산인가"**를 먼저 분류한다
- 이펙트와 클린업은 **항상 짝**이며, 어떤 순서로 몇 번 실행돼도 외부 상태가 현재 props·state와 일치해야 한다
- 의존성 배열과 stale closure는 **unit02**, ref를 통한 DOM 측정은 **unit07**을 참고할 것
