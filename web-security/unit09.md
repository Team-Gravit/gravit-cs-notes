## 비밀번호의 안전한 저장

비밀번호는 유출을 전제로 저장 방식을 설계해야 한다. 평문 저장과 단순 해시가 왜 위험한지, 그리고 **Salt + Key Stretching**을 내장한 bcrypt 계열이 왜 표준이 되었는지를 단계적으로 정리한다.

<br>

### 1. 평문 저장의 위험

데이터베이스에 비밀번호를 그대로 저장하면, DB가 유출되는 순간 **전체 회원의 비밀번호가 즉시 노출**된다. 실제로 국내외에서 평문 또는 복호화 가능한 형태로 저장하던 서비스의 대규모 유출 사고가 반복되어 왔다.

피해는 해당 서비스에서 끝나지 않는다. 다수 사용자가 여러 사이트에서 **같은 비밀번호를 재사용**하기 때문에, 한 곳의 유출이 다른 서비스 계정 탈취(크리덴셜 스터핑)로 번진다. 관리자조차 사용자의 비밀번호 원문을 알 수 없어야 한다는 것이 저장 설계의 출발점이다.

> 💡 국내 **개인정보보호법**(및 개인정보의 안전성 확보조치 기준)은 비밀번호를 복호화되지 않도록 **일방향 암호화(해시)하여 저장**할 것을 의무화하고 있다. 안전한 비밀번호 저장은 권장 사항이 아니라 **법적 의무**다.

<br>

### 2. 단순 해시 저장의 한계

해시는 단방향이므로 `SHA-256(비밀번호)`을 저장하면 안전해 보이지만, 두 가지 공격에 뚫린다.

- **레인보우 테이블**: 자주 쓰이는 비밀번호의 해시 값을 **미리 계산해 둔 사전**이다. 유출된 해시를 테이블에서 역으로 찾기만 하면 원문이 나온다
- **무차별 대입**(Brute Force): SHA-256 같은 범용 해시는 **의도적으로 빠르게** 설계되어, GPU로 초당 수십억 회 계산이 가능하다. 짧은 비밀번호는 전수 대입으로 금방 깨진다

또한 같은 비밀번호는 항상 같은 해시가 되므로, 해시 값이 같은 계정끼리 **같은 비밀번호를 쓴다는 사실**까지 드러난다.

<br>

### 3. Salt — 사용자별 무작위 값

**Salt**는 해시 전에 비밀번호에 덧붙이는 **사용자별 무작위 값**이다. Salt는 비밀이 아니며, 해시 값과 함께 저장한다.

```
사용자 A:  "1234" + Salt "x9f2" ──[ 해시 ]──▶ a81f3c...
사용자 B:  "1234" + Salt "k7q8" ──[ 해시 ]──▶ 5e2d90...

같은 비밀번호 "1234" ──▶ Salt가 다르므로 완전히 다른 해시
```

- 미리 계산해 둔 **레인보우 테이블이 무력화**된다 — 공격자는 Salt별로 테이블을 새로 만들어야 한다
- 같은 비밀번호라도 저장 값이 달라져 **동일 비밀번호 사용자를 식별할 수 없다**

<br>

### 4. Key Stretching — 의도적으로 느리게

Salt는 사전 계산을 막을 뿐, **개별 계정에 대한 무차별 대입** 자체는 막지 못한다. **Key Stretching**은 해시를 수천~수십만 번 **반복 적용**해 한 번의 검증 비용을 의도적으로 키우는 기법이다.

```
비밀번호 + Salt ──해시──▶ 결과1 ──해시──▶ 결과2 ── ... ──▶ 결과N (저장)
                          (N회 반복: 정상 로그인은 0.1초, 전수 대입은 수백 년)
```

정상 사용자는 로그인당 한 번만 계산하므로 수십~수백 밀리초의 지연은 체감되지 않지만, 수십억 번을 시도해야 하는 공격자에게는 **비용이 수십억 배**로 불어난다.

> ⚠️ **빠른 해시(SHA-256)를 비밀번호에 쓰면 안 되는 이유**가 바로 여기에 있다. 알고리즘 공부에서는 빠를수록 좋지만, 비밀번호 저장은 정반대로 **느릴수록 안전**하다. 무결성 검증용 해시(빠름)와 비밀번호 저장용 해시(느림)는 목적이 다른 별개의 도구다.

<br>

### 5. 전용 알고리즘 비교 — bcrypt·PBKDF2·Argon2

| **항목**          | **bcrypt**                     | **PBKDF2**                     | **Argon2**                          |
| ----------------- | ------------------------------ | ------------------------------ | ----------------------------------- |
| **Salt**          | **내장** (자동 생성·자동 포함) | 직접 생성해 전달               | 내장                                |
| **비용 조절**     | **cost factor** (2^n회 반복)   | 반복 횟수(iterations)          | 시간·**메모리**·병렬도 3축          |
| **GPU 공격 내성** | 양호                           | 상대적으로 낮음                | **높음** (메모리 하드)              |
| **특징**          | 가장 널리 검증된 실무 표준     | 표준 규격(NIST) 기반, FIPS 환경 | 2015년 암호 해싱 대회 **우승**, 최신 권장 |

<br>

### 6. bcrypt 사용 예시

bcrypt는 Salt 생성·저장을 라이브러리가 알아서 처리하며, 결과 문자열 안에 **알고리즘·cost·Salt·해시**가 모두 담긴다.

```python
import bcrypt

# 저장: Salt 자동 생성, cost factor 12 (2^12회 연산)
hashed = bcrypt.hashpw("myPassword!".encode(), bcrypt.gensalt(rounds=12))
print(hashed)
# b'$2b$12$GhvMmNVjRW29ulnudl.LbuAnUtN/LRfe1JsBm1Xu6LE3059z5Tr8m'
#    └알고리즘┘└cost┘└──────Salt──────┘└──────────해시──────────┘

# 검증: 저장된 문자열에서 Salt를 꺼내 같은 방식으로 재계산 후 비교
bcrypt.checkpw("myPassword!".encode(), hashed)   # True
bcrypt.checkpw("wrongPass".encode(), hashed)     # False
```

Java(Spring Security) 환경에서도 동일한 구조로 사용한다.

```java
PasswordEncoder encoder = new BCryptPasswordEncoder(12);  // cost factor 12

String hashed = encoder.encode("myPassword!");   // Salt 자동 생성 포함
encoder.matches("myPassword!", hashed);          // true
encoder.matches("wrongPass", hashed);            // false
```

❗️**cost factor 선택**: cost를 1 올리면 연산량이 **2배**가 된다. 서버에서 검증 1회가 수백 밀리초 안팎이 되도록 설정하고, 하드웨어 성능이 향상되면 cost를 함께 올려 공격 비용을 유지해야 한다.

<br>

### 6-1. Pepper — 서버만 아는 추가 비밀 값

**Pepper**는 Salt와 달리 DB가 아니라 **애플리케이션 설정·별도 보안 저장소**에 두는 전역 비밀 값이다. 해시 전에 비밀번호에 함께 섞으면, DB만 유출된 상황에서는 Pepper를 모르는 공격자가 대입 공격 자체를 시작할 수 없다.

- **Salt**: 사용자별, DB에 함께 저장, 목적은 **사전 계산 방지**
- **Pepper**: 전역, DB 밖에 보관, 목적은 **DB 단독 유출 시 방어선 추가**

<br>

### 7. 저장 방식의 진화 정리

| **단계**            | **저장 값 예시**            | **막을 수 있는 것**            | **남는 약점**                    |
| ------------------- | --------------------------- | ------------------------------ | -------------------------------- |
| **평문**            | `1234`                      | 없음                           | 유출 즉시 전원 노출              |
| **단순 해시**       | `SHA-256(1234)`             | 원문 즉시 노출                 | 레인보우 테이블, 고속 무차별 대입 |
| **Salt + 해시**     | `SHA-256(1234+salt)`        | 레인보우 테이블, 동일 해시 노출 | 고속 해시라 무차별 대입 여전     |
| **bcrypt 계열**     | `$2b$12$...`                | 위 전부 + **대입 비용 폭증**   | 약한 비밀번호 자체는 못 막음     |

<br>

### 8. 정리 — 실무 원칙

- 비밀번호는 복호화 가능한 암호화가 아니라 **일방향 해시**로 저장한다 (법적 의무)
- 범용 해시(SHA-256) 단독 사용은 금지하고, **bcrypt·Argon2 같은 전용 알고리즘**을 사용한다
- Salt는 **사용자별 무작위**로 생성한다 (bcrypt 계열은 자동 처리)
- cost factor는 **주기적으로 상향**해 하드웨어 발전을 따라간다
- 마지막 약점인 "약한 비밀번호"는 저장 방식으로 못 막으므로, **최소 길이·복잡도 정책**과 로그인 시도 제한을 병행한다
