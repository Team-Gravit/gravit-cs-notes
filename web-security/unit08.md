## 암호학 기초

암호화는 보안 3요소 중 **기밀성**(Confidentiality)을 지키는 핵심 수단이며, 해시와 전자서명은 **무결성**(Integrity)과 **부인방지**까지 확장한다. 대칭키·공개키 암호, 해시 함수, 전자서명의 원리를 정리한다.

<br>

### 1. 암호화의 목적 — CIA와의 연결

| **보안 요소**              | **위협**                    | **대응 기술**                     |
| -------------------------- | --------------------------- | --------------------------------- |
| **기밀성**(Confidentiality) | 도청, 정보 유출             | **대칭키/공개키 암호화**          |
| **무결성**(Integrity)      | 데이터 위변조               | **해시 함수, 전자서명**           |
| **가용성**(Availability)   | 서비스 마비(DoS)            | 이중화, 트래픽 제어 (암호화 밖 영역) |

암호 기술은 CIA 중 주로 기밀성과 무결성을 담당하며, 여기에 "보낸 사실을 부인할 수 없게 하는" **부인방지**(Non-repudiation)가 전자서명으로 추가된다.

<br>

### 2. 대칭키 암호

**암호화와 복호화에 같은 키**를 사용하는 방식이다. 대표 알고리즘은 **AES**다.

```
송신자                                        수신자
평문 ──[ 암호화: 키 K ]──▶ 암호문 ──전송──▶ 암호문 ──[ 복호화: 키 K ]──▶ 평문

                    (양쪽이 동일한 비밀 키 K를 공유해야 함)
```

- 연산이 단순해 **속도가 빠르고** 대용량 데이터 암호화에 적합하다
- 통신 상대마다 키를 따로 관리해야 하므로 키 개수가 급증한다 (n명 상호 통신 시 **n(n-1)/2개**)

❗️**키 배송 문제**: 키를 안전하게 전달할 방법이 없다는 근본적 딜레마가 있다. 키를 평문으로 보내면 도청되는 순간 끝이고, 키를 암호화해 보내려면 그 키를 또 전달해야 한다. 이 문제를 푸는 것이 공개키 암호다.

<br>

### 3. 공개키(비대칭키) 암호

수학적으로 연결된 **공개키·개인키 쌍**을 사용하는 방식이다. 공개키로 암호화한 것은 **짝이 되는 개인키로만** 복호화할 수 있다. 대표 알고리즘은 **RSA**다.

```
                 수신자의 공개키 (누구나 획득 가능)
                        │
송신자: 평문 ──[ 암호화 ]──▶ 암호문 ──전송──▶ 수신자: ──[ 복호화 ]──▶ 평문
                                                        │
                                          수신자의 개인키 (본인만 보관)
```

- 공개키는 공개해도 안전하므로 **키 배송 문제가 해결**된다
- 수학 연산(큰 수의 소인수분해 등)이 무거워 대칭키보다 **수백~수천 배 느리다**

<br>

### 4. 대칭키 vs 공개키 비교

| **항목**       | **대칭키 암호 (AES)**            | **공개키 암호 (RSA)**                  |
| -------------- | -------------------------------- | -------------------------------------- |
| **키 개수**    | 통신 쌍마다 1개 (n명: n(n-1)/2)  | 1인당 **키 쌍 1개** (n명: 2n)          |
| **속도**       | **빠름**                         | 느림                                   |
| **키 배송**    | 문제 있음                        | **문제 없음** (공개키는 공개 가능)     |
| **주 용도**    | 대용량 **데이터 본문** 암호화    | **키 교환**, 전자서명                  |

<br>

### 5. 하이브리드 암호화 — TLS의 방식

실제 시스템은 두 방식을 조합한다. **공개키 암호로 대칭키를 안전하게 교환**하고, 이후 본문은 **빠른 대칭키 암호**로 처리한다.

```
① 클라이언트: 대칭키(세션 키) 생성
② 서버의 공개키로 세션 키를 암호화해 전송   ← 공개키 암호 (키 교환)
③ 서버: 개인키로 복호화해 세션 키 확보
④ 이후 모든 통신은 세션 키로 암호화        ← 대칭키 암호 (본문, 고속)
```

HTTPS의 기반인 **TLS**가 정확히 이 구조다. 상세한 핸드셰이크 과정은 network 과목의 HTTPS/TLS 유닛과 연계해 학습한다.

<br>

### 6. 해시 함수

임의 길이 입력을 **고정 길이 출력**으로 변환하는 함수로, 암호화와 달리 **복호화 개념이 없다**. 대표 알고리즘은 **SHA-256**이다.

- **단방향성**: 해시 값으로부터 원문을 역산할 수 없다
- **충돌 저항성**: 같은 해시 값을 갖는 서로 다른 입력을 찾기가 계산적으로 어렵다
- **눈사태 효과**: 입력이 1비트만 달라져도 출력이 전혀 다른 값이 된다

```python
import hashlib

print(hashlib.sha256("hello".encode()).hexdigest())
# 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824

print(hashlib.sha256("hellp".encode()).hexdigest())  # 한 글자 차이
# 5a39e919a1a1a4e4b2f0a02a9b7a4b7d... (완전히 다른 값)
```

파일 다운로드 시 제공되는 **체크섬**이 대표적 활용 사례로, 해시 값이 일치하면 전송 중 변조가 없었음을 확인할 수 있다.

<br>

### 7. 암호화 vs 인코딩 vs 해싱

| **구분**   | **암호화**             | **인코딩**                 | **해싱**                   |
| ---------- | ---------------------- | -------------------------- | -------------------------- |
| **목적**   | **기밀성** (내용 은닉) | 표현 방식 변환 (전송 호환) | **무결성** 검증, 원문 대조 |
| **역변환** | 키가 있어야 가능       | **누구나 가능**            | **불가능** (단방향)        |
| **키**     | 필요                   | 불필요                     | 불필요                     |
| **예시**   | AES, RSA               | Base64, URL 인코딩         | SHA-256, bcrypt            |

> ⚠️ **Base64는 암호화가 아니다.** 키 없이 누구나 즉시 원문으로 되돌릴 수 있는 단순 표현 변환일 뿐이다. JWT의 Payload가 Base64URL 인코딩이라 누구나 읽을 수 있는 것이 대표적인 예로, "Base64로 인코딩했으니 안전하다"는 판단은 심각한 보안 착오다.

<br>

### 8. 전자서명

공개키 암호를 **역방향으로** 활용한 기술이다. 본인만 가진 **개인키로 서명**하고, 누구나 **공개키로 검증**한다.

```
서명자                                          검증자
문서 ──[ 해시 ]──▶ 다이제스트                    문서 + 서명 수신
        다이제스트 ──[ 개인키로 서명 ]──▶ 서명      │
        (문서 + 서명 전송)                        ├─ 문서를 직접 해시 ──▶ 값 A
                                                 ├─ 서명을 공개키로 검증 ──▶ 값 B
                                                 └─ A == B ? 진본 : 위조
```

- **무결성**: 문서가 1비트라도 바뀌면 해시가 달라져 검증에 실패한다
- **인증**: 해당 공개키로 검증된다는 것은 짝이 되는 개인키 소유자가 서명했다는 뜻이다
- **부인방지**: 개인키는 본인만 가지므로 "내가 서명하지 않았다"고 부인할 수 없다

> 💡 암호화와 전자서명은 키 사용 방향이 반대다. **암호화는 상대의 공개키로 잠그고 상대가 개인키로 열지만**, **서명은 내 개인키로 잠그고 모두가 내 공개키로 확인한다**. 이 대비를 정확히 설명할 수 있는지가 면접의 단골 확인 포인트다.

<br>

### 9. PKI와 인증서 개요

공개키 암호에는 마지막 허점이 남는다. "지금 받은 공개키가 **정말 그 사람의 것인가**"를 보증할 수 없다는 점이다. 공격자가 자신의 공개키를 은행의 공개키라고 속이면(중간자 공격) 모든 암호화가 무의미해진다.

- **PKI**(공개키 기반 구조)는 신뢰할 수 있는 제3자인 **CA**(인증 기관)가 "이 공개키는 이 주체의 것"임을 전자서명으로 보증하는 체계다
- 그 보증 문서가 **인증서**이며, HTTPS 접속 시 브라우저가 검증하는 서버 인증서가 대표적이다
- ROOT → 중간 → 서버로 이어지는 인증서 체인의 상세 검증 과정은 unit10에서 다룬다
