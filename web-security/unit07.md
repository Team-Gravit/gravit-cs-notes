## 세션 공격 — 하이재킹·고정

세션 기반 인증에서 **세션 ID는 곧 인증 상태 그 자체**다. 세션 ID만 손에 넣으면 비밀번호 없이도 해당 사용자로 행세할 수 있으므로, 세션 ID를 노리는 **세션 하이재킹**과 **세션 고정** 공격의 원리와 방어를 정리한다.

<br>

### 1. 전제 — 세션 ID가 곧 신분증이다

서버는 매 요청마다 아이디/비밀번호를 다시 확인하지 않는다. 쿠키에 담긴 **세션 ID가 유효한지만** 확인해 사용자를 식별한다.

```
정상 사용자:  Cookie: SESSIONID=abc123  ──▶  서버: "user1이군요" (통과)
공격자:      Cookie: SESSIONID=abc123  ──▶  서버: "user1이군요" (구분 불가)
```

서버는 세션 ID를 **누가 보냈는지 알 방법이 없다**. 따라서 세션 ID의 기밀성이 무너지면 인증 체계 전체가 무너진다.

<br>

### 2. 세션 하이재킹(Session Hijacking)

이미 로그인된 사용자의 **유효한 세션 ID를 탈취**해 그 세션을 가로채는 공격이다.

<br>

### 2-1. 주요 탈취 경로

| **경로**                 | **원리**                                                | **선행 조건**              |
| ------------------------ | ------------------------------------------------------- | -------------------------- |
| **XSS**                  | 주입한 스크립트가 `document.cookie`로 쿠키를 읽어 유출   | XSS 취약점 존재            |
| **네트워크 스니핑**      | 암호화되지 않은 HTTP 트래픽에서 쿠키를 도청              | 평문 통신(공용 와이파이 등) |
| **예측 가능한 세션 ID**  | 규칙적/순차적으로 생성된 세션 ID를 추측(무차별 대입 포함) | 난수 품질이 낮은 세션 생성 |

<br>

### 2-2. 공격 흐름

```
피해자                     공격자                      서버
  │  로그인 완료             │                          │
  │  (SESSIONID=abc123)     │                          │
  │                         │                          │
  │──── XSS·스니핑 등으로 ──▶│                          │
  │     세션 ID 유출         │                          │
  │                         │  Cookie: SESSIONID=abc123│
  │                         │ ────────────────────────▶│
  │                         │ ◀──── 피해자로 인증됨 ─── │
  │                         │   (개인정보 열람, 결제 등) │
```

피해자는 정상적으로 서비스를 이용 중이므로 **탈취 사실을 인지하기 어렵다**.

<br>

### 3. 세션 고정(Session Fixation)

하이재킹이 "피해자의 세션 ID를 훔치는" 공격이라면, 세션 고정은 반대로 **공격자가 미리 알고 있는 세션 ID를 피해자에게 심어 두는** 공격이다. 로그인 전후에 세션 ID가 바뀌지 않는 서버가 대상이 된다.

```
공격자                      피해자                      서버
  │  ① 사이트 접속, 세션 발급 │                          │
  │ ◀──────────────────────────────────────────────── │
  │    (SESSIONID=evil99)    │                          │
  │  ② 세션 ID가 심어진 링크  │                          │
  │ ───────────────────────▶│                          │
  │   (URL 파라미터·스크립트  │  ③ evil99 상태로 로그인   │
  │    등으로 evil99 주입)    │ ────────────────────────▶│
  │                          │   서버가 세션 ID를 바꾸지  │
  │                          │   않으면 evil99 = 인증 세션│
  │  ④ Cookie: evil99 로 접속 │                          │
  │ ─────────────────────────────────────────────────▶│
  │ ◀──────── 피해자 계정으로 인증됨 ─────────────────── │
```

공격자는 세션 ID를 훔칠 필요가 없다. **자기가 발급받은 세션 ID가 피해자의 로그인으로 "인증된 세션"으로 승격되기를 기다리면 된다.**

<br>

### 4. 두 공격 비교

| **항목**          | **세션 하이재킹**              | **세션 고정**                        |
| ----------------- | ------------------------------ | ------------------------------------ |
| **세션 ID 출처**  | **피해자**의 세션을 탈취       | **공격자**가 미리 발급받아 주입      |
| **공격 시점**     | 피해자 **로그인 이후**         | 피해자 **로그인 이전**에 심어 둠     |
| **필요 조건**     | XSS·스니핑 등 탈취 수단        | 로그인 시 세션 ID를 갱신하지 않는 서버 |
| **핵심 방어**     | HttpOnly·HTTPS로 노출 차단     | **로그인 성공 시 세션 ID 재발급**    |

<br>

### 5. 방어 대책

❗️**핵심 원칙**: **로그인 성공 시점에 반드시 세션 ID를 재발급한다.** 인증 전 세션과 인증 후 세션을 단절시키면, 공격자가 심어 둔 세션 ID는 로그인 순간 휴지 조각이 되므로 세션 고정이 원천 차단된다.

```java
// Spring 예시 — 로그인 성공 처리 시
request.getSession().invalidate();          // 기존(주입되었을 수 있는) 세션 파기
HttpSession newSession = request.getSession(true);  // 새 세션 ID 발급
newSession.setAttribute("user", loginUser);
```

<br>

### 5-1. 쿠키 속성과 전송 구간 보호

- **HttpOnly**: 자바스크립트의 `document.cookie` 접근을 차단해 **XSS로 인한 쿠키 유출**을 막는다
- **Secure**: 쿠키를 **HTTPS 연결에서만** 전송해 평문 노출을 막는다
- **HTTPS 전면 적용**: 로그인 페이지만이 아니라 **모든 구간**을 암호화해야 스니핑을 차단할 수 있다

```http
Set-Cookie: SESSIONID=xk29fj; HttpOnly; Secure; SameSite=Lax
```

> ⚠️ HttpOnly는 쿠키 "탈취"를 막을 뿐 XSS 자체를 막지 못한다. 스크립트가 실행되는 순간 공격자는 쿠키 없이도 피해자의 브라우저에서 직접 요청을 보낼 수 있으므로, XSS 방어(이스케이프·CSP)는 별도로 갖춰야 한다.

<br>

### 5-2. 보조 수단

- **세션 타임아웃**: 유휴 세션을 짧게 만료시켜 탈취된 세션의 **악용 가능 시간**을 줄인다
- **예측 불가능한 세션 ID**: 충분한 길이의 **암호학적 난수**로 생성해 추측·무차별 대입을 무력화한다
- **IP / User-Agent 검증**: 세션 생성 시의 IP·브라우저 정보와 요청 시의 값을 비교해 이상 접근을 탐지한다

> 💡 IP/User-Agent 검증은 **보조 수단일 뿐 완전한 방어가 아니다**. 모바일 환경에서는 정상 사용자도 IP가 수시로 바뀌어 오탐이 생기고, User-Agent는 공격자가 얼마든지 위조할 수 있다. 핵심 방어(세션 ID 재발급, HttpOnly·Secure, HTTPS) 위에 얹는 탐지 계층으로 이해해야 한다.
