## SSRF·오픈 리다이렉트·클릭재킹

**SSRF**, **오픈 리다이렉트**, **클릭재킹**은 서로 다른 공격이지만 **"시스템이나 사용자가 부여한 신뢰를 우회해 악용한다"** 는 공통점을 가진다. 세 공격 모두 검증되지 않은 입력을 그대로 신뢰할 때 발생하며, 방어의 핵심 원칙도 공통적으로 **허용 목록(Allowlist)** 기반 검증이다.

<br>

### 1. 세 공격의 공통점

- **SSRF**: 서버가 사용자가 준 URL을 **의심 없이 요청**해 내부 자원이 노출된다
- **오픈 리다이렉트**: 서버가 사용자가 준 이동 주소를 **검증 없이 리다이렉트**해 피싱에 악용된다
- **클릭재킹**: 사용자가 **자신이 보는 화면을 신뢰**하는 심리를 악용해 의도치 않은 클릭을 유도한다

세 경우 모두 "입력받은 대상을 검증 없이 신뢰"하는 지점이 취약점의 뿌리다.

<br>

### 2. SSRF — 서버 측 요청 위조

**SSRF**(Server-Side Request Forgery)는 공격자가 서버를 속여, **서버가 공격자 대신 내부 자원에 요청**을 보내게 만드는 공격이다. 외부에서 직접 접근할 수 없는 내부망이나 클라우드 메타데이터도, 외부에 열려 있는 웹서버를 경유하면 접근할 수 있다.

```
[공격자] ──"이 URL의 미리보기 보여줘"──▶ [웹서버]
                                            │  서버가 대신 요청
        외부에서 직접 접근 차단됨 ✕          ▼
                              [내부망 / 클라우드 메타데이터 서버]
                                            │
        [공격자] ◀── 내부 응답이 서버를 통해 반환됨
```

이미지 URL 미리보기, 웹훅, PDF 변환처럼 **서버가 사용자 지정 URL로 요청하는 모든 기능**이 SSRF의 표적이 된다.

> ⚠️ **2019년 Capital One 침해사고**는 SSRF에서 시작되었다. 공격자가 SSRF로 클라우드 **메타데이터 서버**에 접근해 임시 자격 증명을 탈취했고, 이를 이용해 대량의 고객 정보가 유출되었다. 내부 자원 접근이 SSRF로 어떻게 확장되는지를 보여주는 대표 사례다.

<br>

### 2-1. SSRF 방어

- **Allowlist 검증**: 사용자가 URL 전체를 자유 입력하게 하지 말고, **미리 정한 도메인/경로 집합**만 허용한다
- **내부 IP 대역 차단**: `127.0.0.1`, `169.254.169.254`(메타데이터), 사설 IP 대역(`10.0.0.0/8`, `192.168.0.0/16` 등)으로의 요청을 차단한다
- **리다이렉트 추적 주의**: 허용된 URL이 내부 주소로 **리다이렉트**되어 우회될 수 있으므로, 리다이렉트를 따라갈 때도 매번 목적지를 재검증한다

<br>

### 3. 오픈 리다이렉트

**오픈 리다이렉트**(Open Redirect)는 서버가 이동 주소를 담은 파라미터를 **검증 없이 그대로 리다이렉트**할 때 발생한다. 공격자는 신뢰받는 도메인의 링크를 미끼로 삼아 피해자를 피싱 사이트로 유도한다.

```
https://trusted.com/login?redirect=https://evil-phishing.com
                                     └── 검증 없이 이 주소로 이동
```

사용자는 신뢰하는 `trusted.com` 도메인을 보고 링크를 클릭하지만, 로그인 후 공격자의 피싱 사이트로 이동하게 된다. 도메인 앞부분이 정상이라 속기 쉽다.

<br>

### 3-1. 오픈 리다이렉트 방어

- **Allowlist**: 이동 가능한 목적지를 **사전에 등록된 목록**으로 제한한다
- **상대 경로만 허용**: 외부 절대 URL을 막고 자사 사이트 내부의 **상대 경로**(`/mypage` 등)만 허용한다
- **간접 참조**: URL 자체가 아니라 미리 매핑된 **키 값**을 파라미터로 받아 서버가 실제 주소로 변환한다

<br>

### 4. 클릭재킹

**클릭재킹**(Clickjacking)은 공격자의 페이지 위에 **투명한 iframe으로 정상 사이트를 겹쳐** 두고, 사용자가 보이는 버튼을 누른다고 생각하지만 실제로는 그 아래 숨겨진 정상 사이트의 버튼을 클릭하게 만드는 공격이다.

```
┌─────────────────────────────────┐
│  공격자 페이지 (보이는 화면)     │
│    [ 경품 받기! ]  ← 사용자가 봄 │
├─────────────────────────────────┤  겹침
│  투명 iframe (실제 클릭 대상)    │
│    [ 계정 삭제 ]   ← 실제 클릭됨 │
└─────────────────────────────────┘
   opacity: 0 으로 투명 처리
```

<br>

### 4-1. 클릭재킹 방어

자신의 페이지가 **다른 사이트의 iframe에 삽입되는 것을 서버가 차단**하면 된다.

| **방어 수단**              | **설정**                          | **의미**                                   |
| -------------------------- | --------------------------------- | ------------------------------------------ |
| **X-Frame-Options**        | `DENY`                            | 어떤 사이트도 iframe 삽입 **전면 금지**     |
| **X-Frame-Options**        | `SAMEORIGIN`                      | **같은 출처**에서만 iframe 삽입 허용        |
| **CSP frame-ancestors**    | `frame-ancestors 'none'`          | 최신 표준, 더 세밀한 출처 제어 가능        |

```http
X-Frame-Options: DENY
Content-Security-Policy: frame-ancestors 'none'
```

> 💡 `X-Frame-Options`는 널리 지원되는 전통적 헤더이고, CSP의 `frame-ancestors`는 여러 허용 출처를 지정하는 등 더 유연한 최신 방식이다. 두 헤더를 함께 내려 호환성과 세밀함을 모두 확보하는 것이 권장된다.

<br>

### 5. 세 공격 종합 비교

| **공격**          | **공격 대상**              | **원리**                              | **핵심 방어**                     |
| ----------------- | -------------------------- | ------------------------------------- | --------------------------------- |
| **SSRF**          | **서버**(내부 자원)        | 서버가 대신 내부 요청 수행            | **Allowlist**, 내부 IP 차단       |
| **오픈 리다이렉트** | **사용자**(피싱 유도)      | 검증 없는 이동 주소로 우회            | **Allowlist**, 상대 경로만 허용   |
| **클릭재킹**       | **사용자**(의도치 않은 클릭) | 투명 iframe으로 화면 신뢰 악용        | **X-Frame-Options**, CSP          |

> 💡 세 공격의 방어를 관통하는 원칙은 **"금지 목록(Denylist)보다 허용 목록(Allowlist)"** 이다. 막아야 할 나쁜 값을 나열하는 방식은 언제나 누락과 우회의 여지가 남지만, 허용할 좋은 값만 통과시키는 방식은 예상하지 못한 입력을 기본적으로 차단한다.
