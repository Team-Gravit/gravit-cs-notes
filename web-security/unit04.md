## CSRF(Cross-Site Request Forgery)

**CSRF**는 인증된 사용자가 자신도 모르게 공격자가 의도한 요청을 서버에 보내도록 만드는 공격이다. 사이트가 요청을 보낸 **주체가 아니라 세션(쿠키)만 신뢰**하는 허점을 파고든다. 국내 기술 면접에서 XSS와의 비교로 자주 출제된다.

<br>

### 1. 원리

브라우저는 특정 사이트로 요청을 보낼 때 그 사이트의 **쿠키를 자동으로 함께 전송**한다. 공격자는 피해자가 이미 로그인한 상태를 악용해, 피해자의 브라우저가 **위조된 요청**을 정상 세션 쿠키와 함께 보내게 만든다. 서버는 정상 사용자의 요청으로 착각하고 처리한다.

<br>

### 2. 공격 성립의 3가지 조건

아래 세 조건이 모두 충족되어야 CSRF가 성립한다.

1. 피해자가 대상 사이트에 **로그인(인증)된 상태**여야 한다
2. 요청에 필요한 값이 **예측 가능**해야 한다(추가 비밀값이 없어야 한다)
3. 인증 수단이 **쿠키처럼 자동 전송**되어 별도 확인 없이 요청이 처리되어야 한다

<br>

### 3. 공격 시나리오 (은행 송금 예시)

```
1. [피해자] 은행 사이트(bank.com)에 로그인 → 세션 쿠키 보유

2. [공격자] 악성 페이지(evil.com)로 피해자를 유인

3. [피해자] evil.com 접속 → 페이지에 숨겨진 송금 요청이 자동 실행

        evil.com ──(송금 요청 + 은행 쿠키 자동 첨부)──▶ bank.com

4. [bank.com] 유효한 세션 쿠키가 있으므로 정상 요청으로 처리 → 송금 실행
```

<br>

### 3-1. 위조 요청 예시

이미지 태그나 자동 제출 폼만으로도 요청을 발생시킬 수 있다.

```html
<!-- 이미지 로딩만으로 GET 요청이 자동 발생 -->
<img src="https://bank.com/transfer?to=attacker&amount=1000000">

<!-- 자동 제출되는 숨겨진 폼 (POST 요청) -->
<form action="https://bank.com/transfer" method="POST" id="f">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="1000000">
</form>
<script>document.getElementById("f").submit();</script>
```

<br>

### 4. 방어 — CSRF 토큰 (핵심)

서버가 폼을 내려줄 때 **예측 불가능한 임의의 토큰**을 함께 심고, 요청 시 이 토큰을 검증한다. 공격자는 토큰 값을 알 수 없으므로 유효한 요청을 위조하지 못한다.

```
1. [서버] 폼 응답에 임의 CSRF 토큰 포함 (세션에도 저장)
2. [사용자] 요청 시 폼에 담긴 토큰을 함께 전송
3. [서버] 전송된 토큰과 세션의 토큰 비교 → 일치해야만 처리

   evil.com은 토큰 값을 알 수 없음 → 위조 요청 차단
```

<br>

### 5. SameSite 쿠키

쿠키의 **SameSite** 속성은 다른 출처(cross-site)에서의 요청에 쿠키를 함께 보낼지 제어한다.

| **값**     | **동작**                                                    |
| ---------- | ----------------------------------------------------------- |
| **Strict** | 다른 사이트발 요청에는 쿠키를 **전혀 전송하지 않음**         |
| **Lax**    | 안전한 방식(링크 이동 등)만 허용, 폼 POST 등은 **차단**      |
| **None**   | 항상 전송(단, `Secure` 필요) — CSRF 방어 효과 없음          |

> 💡 최신 브라우저는 SameSite 미지정 쿠키를 기본적으로 **Lax**로 취급한다. 이것만으로 상당수의 CSRF가 완화되지만, 완전한 방어를 위해서는 CSRF 토큰과 병행하는 것이 안전하다.

<br>

### 6. 추가 방어 대책

- **Referer/Origin 검증**: 요청 헤더의 출처가 우리 사이트인지 확인한다
- **재인증**: 송금·비밀번호 변경 등 중요한 작업 시 비밀번호를 다시 요구한다

<br>

### 7. XSS vs CSRF 비교

두 공격은 **신뢰의 방향**이 정반대다.

| **구분**       | **XSS**                        | **CSRF**                         |
| -------------- | ------------------------------ | -------------------------------- |
| **신뢰의 대상** | 사용자가 **사이트를 신뢰**함 을 악용 | 사이트가 **사용자(세션)를 신뢰**함 을 악용 |
| **공격 방식**   | 악성 스크립트를 실행시킴         | 위조된 요청을 보내게 함           |
| **스크립트 실행** | 필요함                         | **불필요**(요청만 발생시키면 됨)  |
| **핵심 방어**   | 이스케이프·CSP                  | CSRF 토큰·SameSite 쿠키           |

> 💡 "XSS는 사이트가 사용자를 신뢰하는 것을, CSRF는 사이트가 사용자를 신뢰하는 것을 악용한다" — 더 정확히는 **XSS는 사용자의 브라우저를 장악**하고, **CSRF는 사용자의 인증 상태를 도용**한다. 이 신뢰 방향의 차이는 면접 단골 질문이다.

❗️**주의**: CSRF 토큰이 있어도 XSS 취약점이 있으면 스크립트로 토큰을 읽어내 무력화할 수 있다. 두 방어는 함께 갖춰야 한다.
