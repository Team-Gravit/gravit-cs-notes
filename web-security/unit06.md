## 인증과 인가 — 세션 vs JWT

**인증**(Authentication)은 사용자가 누구인지 확인하는 과정이고, **인가**(Authorization)는 확인된 사용자에게 어떤 권한을 허용할지 결정하는 과정이다. 웹에서 인증 상태를 유지하는 대표적인 두 방식인 **세션 기반 인증**과 **토큰(JWT) 기반 인증**의 구조와 차이를 정리한다.

<br>

### 1. 인증 vs 인가

| **구분**      | **인증(Authentication)**       | **인가(Authorization)**             |
| ------------- | ------------------------------ | ----------------------------------- |
| **질문**      | 너는 누구인가?                 | 너는 이것을 할 수 있는가?           |
| **시점**      | 인가보다 **먼저** 수행         | 인증 **이후** 수행                  |
| **예시**      | 아이디/비밀번호 로그인         | 관리자만 게시글 삭제 가능           |
| **실패 응답** | **401 Unauthorized**           | **403 Forbidden**                   |

> 💡 HTTP 상태 코드의 이름과 실제 의미가 어긋나는 지점이다. **401**은 이름과 달리 "인증되지 않음"을, **403**은 "인증은 되었으나 권한이 없음"을 의미한다. 면접에서 인증/인가 구분과 함께 자주 묻는 포인트다.

<br>

### 2. 세션 기반 인증

인증 상태를 **서버가 저장**하는 방식이다. 로그인에 성공하면 서버가 세션 저장소에 사용자 정보를 기록하고, 그 세션을 가리키는 **세션 ID**만 쿠키로 클라이언트에 내려준다.

```
클라이언트                          서버                    세션 저장소
    │  ① 로그인 (ID/PW)              │                          │
    │ ─────────────────────────────▶ │  ② 검증 후 세션 생성      │
    │                                │ ───────────────────────▶ │
    │  ③ Set-Cookie: SESSIONID=abc   │      { abc: user1 }      │
    │ ◀───────────────────────────── │                          │
    │  ④ 요청 + Cookie: SESSIONID    │  ⑤ 세션 ID로 사용자 조회  │
    │ ─────────────────────────────▶ │ ───────────────────────▶ │
    │  ⑥ 응답 (인증된 사용자로 처리)  │ ◀─────────────────────── │
    │ ◀───────────────────────────── │                          │
```

- 서버가 상태를 갖는 **스테이트풀**(Stateful) 방식이다
- 세션 ID 자체에는 아무 정보가 없으므로 탈취되어도 **서버에서 즉시 무효화**할 수 있다
- 서버가 여러 대로 늘어나면 세션 저장소를 **공유**(예: Redis)해야 하는 부담이 생긴다

<br>

### 3. 토큰(JWT) 기반 인증

인증 상태를 **클라이언트가 토큰 형태로 보관**하는 방식이다. 서버는 로그인 시 서명된 토큰을 발급할 뿐, 이후에는 아무것도 저장하지 않는다.

```
클라이언트                          서버
    │  ① 로그인 (ID/PW)              │
    │ ─────────────────────────────▶ │  ② 검증 후 JWT 발급 (서명 포함)
    │  ③ 응답 본문으로 JWT 전달       │     서버는 아무것도 저장하지 않음
    │ ◀───────────────────────────── │
    │  ④ Authorization: Bearer JWT   │
    │ ─────────────────────────────▶ │  ⑤ 서명만 검증하면 사용자 식별 완료
    │  ⑥ 응답                        │     (저장소 조회 불필요)
    │ ◀───────────────────────────── │
```

- 서버가 상태를 갖지 않는 **스테이트리스**(Stateless) 방식이다
- 저장소 조회가 없어 서버 **확장(Scale-out)에 유리**하다
- 발급된 토큰은 만료 전까지 서버가 강제로 회수하기 **어렵다**

<br>

### 4. JWT 구조

**JWT**(JSON Web Token)는 `Header.Payload.Signature` 세 부분을 점(`.`)으로 이어 붙인 문자열이다. 각 부분은 Base64URL로 인코딩된다.

**Header** — 서명에 사용한 알고리즘과 토큰 타입을 명시한다.

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

**Payload** — 사용자 식별자, 만료 시각 등 **클레임**(Claim)을 담는다.

```json
{
  "sub": "user1",
  "role": "USER",
  "iat": 1710000000,
  "exp": 1710003600
}
```

**Signature** — Header와 Payload를 서버만 아는 **비밀 키**로 서명한 값이다.

> ⚠️ Payload는 암호화가 아니라 **인코딩**일 뿐이므로 누구나 디코딩해 내용을 볼 수 있다. 비밀번호 등 민감 정보를 Payload에 넣어서는 안 된다.

<br>

### 5. 서명 검증 원리

서버는 요청으로 받은 토큰의 Header와 Payload를 자신의 비밀 키로 **다시 서명**해 보고, 그 결과가 토큰에 붙어 온 Signature와 일치하는지 비교한다.

```
수신한 JWT:  Header . Payload . Signature
                │        │
                └───┬────┘
                    ▼
   서버의 비밀 키로 HMAC-SHA256(Header.Payload) 재계산
                    │
                    ▼
        재계산 값 == Signature ?  → 일치: 위변조 없음 (신뢰)
                                  → 불일치: 조작된 토큰 (거부)
```

공격자가 Payload를 조작하면 서명이 달라지므로 위변조가 즉시 탐지된다. 즉 서명은 내용을 숨기는 것이 아니라 **무결성**을 보장하는 장치다.

<br>

### 6. 세션 vs JWT 종합 비교

| **항목**        | **세션 기반**                        | **JWT 기반**                              |
| --------------- | ------------------------------------ | ----------------------------------------- |
| **상태**        | 스테이트풀 (서버가 저장)             | **스테이트리스** (클라이언트가 보관)       |
| **확장성**      | 세션 저장소 공유 필요                | **수평 확장에 유리**                       |
| **무효화**      | 서버에서 **즉시 삭제 가능**          | 만료 전 강제 무효화 **어려움**             |
| **탈취 위험**   | 세션 ID 탈취 시 세션 파기로 대응     | 토큰 탈취 시 만료까지 악용 가능            |
| **요청 크기**   | 세션 ID만 전송 (작음)                | 클레임 포함으로 상대적으로 큼              |
| **주 사용처**   | 전통적 서버 렌더링 웹                | REST API, 모바일, MSA                      |

<br>

### 7. Access Token + Refresh Token 패턴

JWT의 탈취 위험과 무효화 문제를 완화하기 위해 토큰을 둘로 나눈다.

- **Access Token**: 수명을 **짧게**(수 분~수십 분) 설정해 탈취 피해를 최소화한다
- **Refresh Token**: 수명이 길고, Access Token이 만료되면 **재발급 용도로만** 사용한다
- Refresh Token은 서버(DB)에 저장해 두므로, 유출이 의심되면 **서버에서 폐기**해 재발급을 차단할 수 있다

❗️**무효화의 역설**: Refresh Token을 서버에 저장하는 순간 완전한 스테이트리스는 포기하는 것이다. JWT를 쓰면서도 즉시 차단이 필요하다면 결국 일부 상태 관리(블랙리스트 등)를 도입해야 하며, 이는 세션 방식과의 절충이다.

<br>

### 8. OAuth 2.0 개요

**OAuth 2.0**은 비밀번호를 직접 넘기지 않고 **제3자 서비스에 권한을 위임**하는 표준이다. "구글로 로그인" 같은 소셜 로그인이 대표 사례이며, 가장 널리 쓰이는 방식은 **권한 부여 코드**(Authorization Code) 방식이다.

```
사용자          우리 서비스           인증 서버(구글)
  │  ① 소셜 로그인 클릭  │                    │
  │ ──────────────────▶ │  ② 인증 서버로 이동  │
  │ ◀─────────────────────────────────────── │  ③ 구글 로그인 + 동의
  │ ────────────────────────────────────────▶│
  │                     │ ◀── ④ 인가 코드 ─── │
  │                     │ ─── ⑤ 코드 + 클라이언트 비밀 ──▶
  │                     │ ◀── ⑥ Access Token │
  │  ⑦ 로그인 완료       │  (토큰으로 프로필 조회 후 회원 처리)
  │ ◀────────────────── │                    │
```

- 사용자의 구글 비밀번호는 우리 서비스에 **절대 전달되지 않는다**
- 인가 코드를 토큰으로 교환하는 ⑤ 단계는 브라우저를 거치지 않는 **서버 간 통신**이라 코드가 노출되어도 피해가 제한된다

> 💡 OAuth 2.0은 본래 **인가**(권한 위임) 프로토콜이다. 이를 인증 용도로 표준화한 확장이 **OIDC**(OpenID Connect)이며, 소셜 로그인은 대부분 OAuth 2.0 + OIDC 조합으로 구현된다.
