## 접근 통제와 시큐어 코딩

**접근 통제 실패**(Broken Access Control)는 **OWASP Top 10의 1위(A01)** 를 차지하는 가장 흔하고 치명적인 취약점이다. 이 유닛에서는 접근 통제의 원리와 **시큐어 코딩**의 체계를 다루며, web-security 과목 전체의 방어 기법을 마무리로 총정리한다.

<br>

### 1. 접근 통제 실패가 1위인 이유

**접근 통제**란 인증된 사용자라도 **자신에게 허용된 자원과 기능만** 사용할 수 있도록 제한하는 것이다. 이 제어가 없거나 부실하면, 로그인한 사용자가 **다른 사용자의 데이터나 관리자 기능에 접근**할 수 있게 된다. 구현 곳곳에 검증을 빠뜨리기 쉬워 실무에서 빈번하게 발생하며, 그래서 OWASP는 이를 A01로 분류한다.

<br>

### 2. 수직적·수평적 권한 상승

권한 상승은 두 방향으로 나뉜다.

- **수직적 권한 상승**: 일반 사용자가 **더 높은 권한**(관리자)의 기능에 접근한다. 예) 일반 회원이 관리자 전용 페이지에 직접 접근
- **수평적 권한 상승**: **같은 등급의 다른 사용자** 자원에 접근한다. 예) 내 게시물이 아닌 남의 게시물을 삭제

수평적 권한 상승의 대표 유형이 **IDOR**(Insecure Direct Object Reference)다. 식별자를 조작해 남의 자원에 직접 접근하는 문제다.

```
정상:  DELETE /posts/1001   ← 내 게시물(1001)
공격:  DELETE /posts/1002   ← 식별자만 바꿔 남의 게시물(1002) 삭제 시도

서버가 "이 게시물이 요청자의 것인가"를 검증하지 않으면 삭제됨
```

❗️**인가 검증은 반드시 서버에서**: 화면에서 버튼을 숨기거나 비활성화하는 것은 보안이 아니다. 공격자는 UI를 거치지 않고 요청을 직접 보낼 수 있으므로, **모든 요청마다 서버가 "이 사용자가 이 자원에 권한이 있는가"를 검증**해야 한다.

<br>

### 3. 접근 통제 모델

접근 통제는 몇 가지 모델로 체계화된다. 실무에서는 역할 기반의 **RBAC**가 가장 널리 쓰인다.

| **모델**   | **기준**                        | **특징**                                   |
| ---------- | ------------------------------- | ------------------------------------------ |
| **DAC**    | 자원 소유자가 권한 부여         | 유연하나 일관성 관리 어려움                |
| **MAC**    | 시스템이 **보안 등급**으로 강제 | 군·정부 등 엄격한 환경                     |
| **RBAC**   | 사용자의 **역할(Role)** 기반    | 관리 편리, **실무 표준**                   |

> 💡 **RBAC**(Role-Based Access Control)는 권한을 사용자마다가 아니라 **역할 단위**로 묶어 부여한다. "관리자", "일반 회원" 같은 역할에 권한을 정의하고 사용자에게 역할을 할당하므로, 사용자가 늘어도 권한 관리가 단순해진다.

<br>

### 4. 시큐어 코딩과 KISA 진단 항목

**시큐어 코딩**(Secure Coding)은 개발 단계에서 보안 약점을 제거하며 코드를 작성하는 것이다. KISA(한국인터넷진흥원)의 소프트웨어 개발보안 가이드는 보안 약점을 아래와 같은 **진단 항목 분류**로 체계화한다.

| **분류**            | **대표 약점**                              |
| ------------------- | ------------------------------------------ |
| **입력 데이터 검증**| SQL 인젝션, XSS, 경로 조작                 |
| **보안 기능**       | 부적절한 인가, 취약한 암호화, 하드코딩 키  |
| **시간 및 상태**    | 경쟁 조건(Race Condition), 세션 관리 오류  |
| **에러 처리**       | 오류 메시지의 정보 노출, 부적절한 예외 처리|
| **코드 오류**       | 널 포인터 역참조, 자원 해제 누락           |
| **캡슐화**          | 민감 정보 노출, 잘못된 접근 제어자         |
| **API 오용**        | 위험한 함수 사용, 취약한 API 호출          |

> 💡 국내는 **2012년부터 SW 개발보안 의무제**가 시행되어, 일정 규모 이상의 **공공 정보화 사업**은 행정안전부 기준의 보안 약점 진단을 통과해야 한다. 시큐어 코딩이 권장을 넘어 **제도적 의무**인 배경이다.

<br>

### 5. 대표 시큐어 코딩 수칙 — 입력 검증

가장 많은 취약점이 입력 데이터 검증 부재에서 비롯된다. SQL 인젝션 방어의 예로, 문자열을 직접 이어 붙이는 대신 **파라미터 바인딩**을 사용한다.

```java
// 취약: 사용자 입력을 직접 연결 → SQL 인젝션 위험
String sql = "SELECT * FROM users WHERE id = '" + userId + "'";

// 안전: PreparedStatement로 파라미터 바인딩
String sql = "SELECT * FROM users WHERE id = ?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, userId);
```

<br>

### 6. 대표 시큐어 코딩 수칙 — 인가 검증

IDOR를 막으려면 자원 접근 시 **소유권을 반드시 확인**한다.

```python
# 취약: 게시물 존재만 확인하고 소유자 검증 없음
def delete_post(post_id, current_user):
    post = Post.get(post_id)
    post.delete()  # 누구든 남의 글 삭제 가능

# 안전: 요청자가 소유자인지 서버에서 검증
def delete_post(post_id, current_user):
    post = Post.get(post_id)
    if post.owner_id != current_user.id:
        raise PermissionError("권한 없음")
    post.delete()
```

<br>

### 7. 에러 처리와 정보 노출

> ⚠️ 에러 메시지에 **스택 트레이스, SQL 쿼리, 내부 경로, 서버 버전** 같은 내부 정보를 노출하면 공격자에게 시스템 구조에 대한 단서를 제공한다. 사용자에게는 일반화된 오류 메시지만 보여주고, 상세 내용은 **서버 로그에만** 기록해야 한다.

<br>

### 8. 과목 마무리 — 방어 기법 총정리

web-security 과목에서 다룬 공격과 핵심 방어를 한눈에 정리한다. 관통하는 원칙은 **입력을 신뢰하지 말 것**, **검증은 서버에서 할 것**, **금지보다 허용 목록**이다.

| **공격/영역**       | **핵심 방어**                                 |
| ------------------- | --------------------------------------------- |
| **SQL 인젝션**      | PreparedStatement(파라미터 바인딩)            |
| **XSS**             | 출력 이스케이프, **CSP**                      |
| **CSRF**            | CSRF 토큰, **SameSite 쿠키**                  |
| **세션 공격**       | 로그인 시 **세션 ID 재발급**, HTTPS 전송      |
| **비밀번호 저장**   | **bcrypt** + Salt + Key Stretching            |
| **HTTPS 인증서**    | CA 체인 검증, 신뢰 저장소                     |
| **파일 업로드**     | 화이트리스트·시그니처·파일명 랜덤화·경로 분리 |
| **SSRF/리다이렉트/클릭재킹** | **Allowlist**, X-Frame-Options       |
| **접근 통제**       | 서버 측 **인가 검증**, RBAC                   |
