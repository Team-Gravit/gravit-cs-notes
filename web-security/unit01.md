## 웹 보안 기초와 OWASP Top 10

**웹 보안**은 웹 애플리케이션과 그 이용자를 공격으로부터 보호하는 활동이다. 웹은 누구나 접근 가능한 개방된 환경이므로 공격 표면이 넓고, 작은 취약점 하나가 개인정보 유출·서비스 마비로 이어진다. 이 유닛은 이후 유닛들의 공통 기반이 되는 개념과 업계 표준 취약점 분류인 **OWASP Top 10**을 다룬다.

<br>

### 1. 웹 보안이 중요한 이유

- 웹 서비스는 **인터넷에 항상 노출**되어 있어 전 세계 어디서나 공격이 가능하다
- 로그인 정보·결제 정보·개인정보 등 **민감한 데이터**를 다룬다
- 하나의 취약점이 **대규모 개인정보 유출**이나 **서비스 중단**으로 직결된다
- 국내에서는 개인정보 유출 시 **개인정보보호법**에 따른 법적 책임이 발생한다

<br>

### 2. 정보 보안의 3요소 (CIA)

보안의 목표는 흔히 **CIA**로 요약되는 세 가지 속성을 지키는 것이다.

| **요소**               | **의미**                             | **위협하는 공격 예시**            |
| ---------------------- | ------------------------------------ | --------------------------------- |
| **기밀성(Confidentiality)** | 인가된 사용자만 정보에 접근 가능 | SQL 인젝션으로 DB 탈취, XSS 세션 탈취 |
| **무결성(Integrity)**  | 정보가 위·변조되지 않고 정확함        | CSRF로 데이터 변조, 파라미터 조작 |
| **가용성(Availability)** | 필요할 때 정상적으로 사용 가능      | DDoS 공격, 서비스 자원 고갈       |

> 💡 세 요소는 상충하기도 한다. 예를 들어 기밀성을 높이려고 인증 단계를 늘리면 가용성(편의성)은 떨어진다. 보안 설계는 서비스 성격에 맞는 **균형점**을 찾는 일이다.

<br>

### 3. 취약점·위협·공격의 용어 구분

세 용어는 자주 혼용되지만 정확히 구분해야 한다.

- **취약점(Vulnerability)**: 시스템에 존재하는 **결함이나 약점** (예: 입력값을 검증하지 않는 코드)
- **위협(Threat)**: 취약점을 이용해 피해를 줄 수 있는 **잠재적 원인** (예: 악의적 공격자의 존재)
- **공격(Attack)**: 위협이 실제로 **실행되어 취약점을 악용**하는 행위 (예: 실제로 SQL 인젝션을 시도)

```
[취약점] 문이 잠기지 않음  →  [위협] 도둑이 있음  →  [공격] 도둑이 실제로 침입함
```

<br>

### 4. OWASP와 OWASP Top 10

**OWASP**(Open Worldwide Application Security Project)는 웹 애플리케이션 보안을 연구하는 비영리 국제 단체다. 그중 **OWASP Top 10**은 가장 심각하고 빈번한 웹 취약점 10가지를 주기적으로 선정해 발표하는 **사실상의 업계 표준 문서**다.

<br>

### 4-1. OWASP Top 10 (2021) 목록

| **순위** | **항목**                              | **한국어 설명**                              |
| -------- | ------------------------------------- | -------------------------------------------- |
| **A01**  | Broken Access Control                 | 취약한 접근 통제 — 권한 없는 자원 접근       |
| **A02**  | Cryptographic Failures                | 암호화 실패 — 민감 데이터 노출               |
| **A03**  | Injection                             | 인젝션 — SQL 인젝션, XSS 등 포함             |
| **A04**  | Insecure Design                       | 안전하지 않은 설계 — 설계 단계의 결함        |
| **A05**  | Security Misconfiguration             | 보안 설정 오류 — 기본 설정·불필요한 기능     |
| **A06**  | Vulnerable and Outdated Components     | 취약하고 오래된 구성 요소 — 낡은 라이브러리  |
| **A07**  | Identification and Authentication Failures | 인증·식별 실패 — 취약한 로그인·세션 관리 |
| **A08**  | Software and Data Integrity Failures   | 소프트웨어·데이터 무결성 실패               |
| **A09**  | Security Logging and Monitoring Failures | 보안 로깅·모니터링 실패                    |
| **A10**  | Server-Side Request Forgery (SSRF)     | 서버 측 요청 위조                            |

> 💡 2021년 개정에서 XSS는 별도 항목이 아니라 **A03 인젝션**에 통합되었고, SSRF(A10)가 새로 등장했다. 순위는 실제 발생 빈도와 심각도 데이터를 반영한다.

### 6. 공격자 관점의 사고

방어를 잘하려면 먼저 **공격자처럼 생각**해야 한다. "이 입력창에 무엇을 넣으면 예상과 다르게 동작할까"를 끊임없이 자문하는 습관이 안전한 코드를 만든다.

> 💡 개발자는 보통 정상 입력만 가정하고 코드를 짠다. 그러나 공격자는 **경계값·비정상 입력·예상 밖의 순서**를 파고든다. 방어적 프로그래밍의 출발점은 "모든 입력은 신뢰할 수 없다"는 전제다.
