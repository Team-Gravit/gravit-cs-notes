## HTTPS 인증서와 CA 체인

**HTTPS**가 안전하려면 서버가 보낸 **공개키가 진짜 그 서버의 것**임을 보증할 수단이 필요하다. 이 신뢰 문제를 해결하는 것이 **인증서(Certificate)** 와 **CA(Certificate Authority, 인증 기관)** 체계이며, 브라우저는 **인증서 체인 검증**을 통해 접속 대상의 신원을 확인한다.

<br>

### 1. 공개키 배포의 신뢰 문제

공개키 암호 방식만으로는 "이 공개키가 정말 example.com의 것인가"를 알 수 없다. 공격자가 통신 중간에 끼어들어 **자신의 공개키를 서버의 공개키인 것처럼 바꿔치기**하면, 클라이언트는 공격자의 키로 암호화하게 되고 공격자는 모든 통신을 복호화할 수 있다. 이것이 **중간자 공격**(MITM, Man-In-The-Middle)이다.

```
[클라이언트] ──"공개키 주세요"──▶ [공격자] ──"공개키 주세요"──▶ [서버]
[클라이언트] ◀──공격자의 공개키── [공격자] ◀──서버의 공개키──── [서버]

클라이언트는 공격자의 키로 암호화 → 공격자가 복호화·열람 후 재암호화하여 전달
```

따라서 **신뢰할 수 있는 제3자가 "이 공개키는 이 도메인의 것"이라고 보증**해 주어야 하며, 그 역할을 CA가 담당한다.

<br>

### 2. CA와 인증서에 담긴 정보

**CA**는 서버 운영자의 도메인 소유권 등을 확인한 뒤, 서버의 공개키에 **자신의 개인키로 전자서명**하여 인증서를 발급한다. 인증서에는 다음 정보가 담긴다.

| **항목**          | **설명**                                        |
| ----------------- | ----------------------------------------------- |
| **주체(Subject)** | 인증서가 보증하는 **도메인 이름**(CN, SAN)      |
| **공개키**        | 서버의 **공개키**                               |
| **발급자(Issuer)**| 인증서를 발급한 **CA의 이름**                   |
| **전자서명**      | 발급 CA가 **개인키로 서명**한 값                |
| **유효기간**      | 인증서의 **시작일과 만료일**                    |

CA의 서명은 CA의 공개키로만 검증할 수 있으므로, 서명이 유효하다면 "CA가 이 내용을 보증했다"는 사실이 증명된다.

<br>

### 3. 3단계 인증서 체인

실제 서비스에서는 ROOT CA가 서버 인증서에 직접 서명하지 않고, **중간 CA**(Intermediate CA)를 거치는 **3단계 체인** 구조를 사용한다. ROOT CA의 개인키 노출 위험을 줄이고, 문제 발생 시 중간 CA만 폐기하면 되기 때문이다.

```
[ROOT CA 인증서]           ← 자기 자신이 서명 (Self-Signed)
       │  ROOT CA의 개인키로 서명
       ▼
[중간 CA 인증서]           ← ROOT CA가 신원을 보증
       │  중간 CA의 개인키로 서명
       ▼
[서버(Leaf) 인증서]        ← 중간 CA가 example.com을 보증
```

<br>

### 4. 브라우저의 체인 검증 과정

브라우저는 서버가 보낸 인증서의 **서명을 상위 인증서의 공개키로 검증하며 위로 거슬러 올라간다.** 최종적으로 신뢰 저장소에 있는 ROOT CA에 도달하면 체인 전체가 신뢰된다.

```
1. 서버 인증서 수신
      │ "이 서명, 중간 CA의 공개키로 검증되는가?"
      ▼
2. 중간 CA 인증서 확인 → 서버 인증서의 서명 검증 성공
      │ "그럼 중간 CA는 믿을 수 있는가?"
      ▼
3. ROOT CA 인증서 확인 → 중간 CA 인증서의 서명 검증 성공
      │ "ROOT CA가 신뢰 저장소에 있는가?"
      ▼
4. 신뢰 저장소에 존재 → 체인 전체 신뢰 → 자물쇠 표시
```

이와 함께 브라우저는 **유효기간**, **도메인 일치 여부**, **폐기 여부**(CRL/OCSP)도 확인한다.

> 💡 **ROOT CA 인증서는 OS와 브라우저에 미리 내장**되어 있다. 이 내장 목록을 **신뢰 저장소**(Trust Store)라고 하며, 인증서 체인 검증의 최종 기준점이 된다. 사용자가 별도로 설치하지 않아도 되는 이유가 여기에 있다.

<br>

### 5. 인증서 검증 실패 사례

검증 과정 중 하나라도 실패하면 브라우저는 경고 화면을 표시하고 접속을 차단한다.

- **유효기간 만료**: 인증서의 만료일이 지난 경우 즉시 실패한다
- **도메인 불일치**: 인증서의 CN/SAN과 접속한 도메인이 다른 경우 실패한다
- **자체 서명 인증서**: 신뢰 저장소의 ROOT CA로 이어지는 체인이 없어 신뢰할 수 없다
- **체인 불완전**: 서버가 중간 CA 인증서를 함께 전송하지 않으면 검증이 끊길 수 있다

> ⚠️ 브라우저의 인증서 경고를 "계속 진행"으로 무시하는 습관은 중간자 공격에 그대로 노출되는 행동이다. 특히 공용 와이파이 환경에서 인증서 경고가 뜬다면 공격이 진행 중일 가능성을 의심해야 한다.

<br>

### 6. 인증서 종류 — DV / OV / EV

CA가 발급 전에 **무엇을 얼마나 검증했는지**에 따라 인증서 등급이 나뉜다.

| **종류**                        | **검증 수준**                         | **특징**                                   |
| ------------------------------- | ------------------------------------- | ------------------------------------------ |
| **DV**(Domain Validation)       | **도메인 소유권**만 확인              | 발급 빠름, 무료 발급 가능, 개인·블로그용   |
| **OV**(Organization Validation) | 도메인 + **조직 실재성** 확인         | 기업·기관 웹사이트에 적합                  |
| **EV**(Extended Validation)     | 도메인 + 조직 + **엄격한 심사**       | 금융·대형 서비스, 가장 높은 신뢰 수준      |

> 💡 **Let's Encrypt**는 DV 인증서를 무료·자동으로 발급하는 비영리 CA다. 발급·갱신이 자동화되어 있어 HTTPS 보편화에 크게 기여했으며, 소규모 서비스라도 HTTPS를 적용하지 않을 이유가 없어졌다.

<br>

### 7. TLS 핸드셰이크와의 관계

인증서 검증은 **TLS 핸드셰이크 과정의 한 단계**로 수행된다. 서버가 핸드셰이크 중에 인증서 체인을 전송하면, 클라이언트는 본 유닛의 검증 과정을 거친 뒤에야 키 교환을 진행한다.

- **인증서 체인 검증(본 유닛)**: 상대방이 진짜인지 확인하는 **신원 보증** 단계이다
- **TLS 핸드셰이크(network 과목 HTTPS/TLS 유닛 참조)**: 검증된 공개키를 이용해 **대칭키(세션 키)를 안전하게 교환**하는 단계이다

두 유닛을 함께 이해해야 "HTTPS는 어떻게 안전한가"라는 질문에 완결된 답을 할 수 있다.

| **구분**       | **인증서 체인 (web-security)** | **TLS 핸드셰이크 (network)**   |
| -------------- | ------------------------------ | ------------------------------ |
| **해결 문제**  | 공개키의 **신원 보증**         | 대칭키의 **안전한 교환**       |
| **핵심 수단**  | CA의 **전자서명**              | 공개키 암호 + **대칭키 암호**  |
| **실패 시**    | 브라우저 경고·접속 차단        | 연결 수립 실패                 |
