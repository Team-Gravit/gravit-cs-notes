## 동시성 제어 — 격리 수준·락·MVCC

unit13(트랜잭션)의 후속 문서로, 여러 트랜잭션이 **동시에 실행될 때 발생하는 문제와 이를 제어하는 기법**을 다룬다. 동시성 문제 3종을 타임라인으로 살펴보고, 격리 수준·락·MVCC·데드락을 정리한다.

<br>

### 1. 동시성 제어가 필요한 이유

- DBMS는 처리량을 높이기 위해 여러 트랜잭션을 **동시에(병행)** 실행함
- 아무 제어 없이 병행 실행하면 서로의 중간 결과를 읽거나 덮어써서 **데이터 정합성**이 깨짐
- 모든 트랜잭션을 순차 실행하면 안전하지만 성능이 크게 떨어지므로, **정합성과 성능의 균형**을 맞추는 것이 동시성 제어의 목표임

> 💡 동시성 문제 3종과 격리 수준 4단계의 대응 관계, 그리고 MVCC의 동작 원리는 **백엔드 면접 최빈출 주제**다. "격리 수준을 낮추면 어떤 문제가 생기는가"를 타임라인으로 직접 그려 설명할 수 있어야 한다.

<br>

### 2. 동시성 문제 3종

### 2-1. Dirty Read

다른 트랜잭션이 **아직 커밋하지 않은 값**을 읽는 현상이다. 상대가 롤백하면 존재한 적 없는 값을 읽은 것이 된다.

```
시간 →
트랜잭션 A: ── UPDATE x=200 ──────────── ROLLBACK (x는 100으로 복구)
트랜잭션 B: ──────────── SELECT x → 200 ─────────── (없던 값 200을 읽음)
```

<br>

### 2-2. Non-Repeatable Read

한 트랜잭션 안에서 **같은 행을 두 번 읽었는데 값이 달라지는** 현상이다. 사이에 다른 트랜잭션이 UPDATE 후 커밋했기 때문이다.

```
시간 →
트랜잭션 A: ── SELECT x → 100 ──────────────────── SELECT x → 200 (값이 바뀜)
트랜잭션 B: ──────────────── UPDATE x=200; COMMIT ──
```

<br>

### 2-3. Phantom Read

한 트랜잭션 안에서 **같은 범위를 두 번 조회했는데 없던 행이 나타나는** 현상이다. 사이에 다른 트랜잭션이 INSERT 후 커밋했기 때문이다.

```
시간 →
트랜잭션 A: ── SELECT WHERE age>20 → 2행 ─────────────── 같은 SELECT → 3행 (유령 행)
트랜잭션 B: ────────────────── INSERT (age=25); COMMIT ──
```

<br>

### 3. 격리 수준 4단계와 이상 현상 매트릭스

격리 수준이 높아질수록 이상 현상은 줄지만 동시 처리 성능은 떨어진다. 각 수준의 상세 설명은 unit13을 참고할 것.

| **격리 수준**        | **Dirty Read** | **Non-Repeatable Read** | **Phantom Read** | **비고**                        |
| -------------------- | -------------- | ----------------------- | ---------------- | ------------------------------- |
| **READ UNCOMMITTED** | 발생           | 발생                    | 발생             | 사용 비권장                     |
| **READ COMMITTED**   | -              | 발생                    | 발생             | Oracle·PostgreSQL 기본값        |
| **REPEATABLE READ**  | -              | -                       | 발생 가능        | MySQL(InnoDB) 기본값            |
| **SERIALIZABLE**     | -              | -                       | -                | 가장 엄격, 성능 최저            |

> 💡 MySQL InnoDB의 REPEATABLE READ는 **넥스트 키 락(Next-Key Lock)**과 MVCC 덕분에 표준과 달리 Phantom Read가 대부분 차단된다. "표준 기준"과 "InnoDB 실제 동작"을 구분해 답하면 면접에서 좋은 평가를 받는다.

<br>

### 4. 락(Lock) 기반 제어

### 4-1. 공유 락(S) vs 배타 락(X)

| **항목**            | **공유 락 (S-Lock)**       | **배타 락 (X-Lock)**       |
| ------------------- | -------------------------- | -------------------------- |
| **용도**            | **읽기** (SELECT)          | **쓰기** (INSERT/UPDATE/DELETE) |
| **다른 S-Lock 허용** | **가능** (동시 읽기 허용)  | 불가능                     |
| **다른 X-Lock 허용** | 불가능                     | 불가능                     |
| **사용 예시**       | `SELECT ... FOR SHARE`     | `SELECT ... FOR UPDATE`    |

- 읽기끼리는 공존할 수 있지만, 쓰기가 개입하는 순간 서로 배제됨
- 락 경합으로 대기가 발생하는 블로킹(Blocking)은 unit13 참고

<br>

### 4-2. 비관적 잠금 vs 낙관적 잠금

- **비관적 잠금(Pessimistic Lock)**: 충돌이 일어날 것이라 가정하고 **읽는 시점부터 락을 획득**함. `SELECT ... FOR UPDATE`가 대표적이며, 충돌이 잦은 데이터에 유리하지만 대기·데드락 비용이 있음
- **낙관적 잠금(Optimistic Lock)**: 충돌이 드물다고 가정하고 락 없이 진행한 뒤, **커밋(갱신) 시점에 버전 번호를 비교**해 충돌을 감지함. 충돌 시 재시도가 필요하며, 읽기가 많고 충돌이 적은 서비스에 유리함

```sql
-- 낙관적 잠금: version 컬럼으로 충돌 감지
UPDATE products
SET    stock = stock - 1, version = version + 1
WHERE  id = 1 AND version = 7;  -- 갱신된 행이 0이면 충돌 → 재시도
```

<br>

### 5. MVCC (다중 버전 동시성 제어)

**MVCC(Multi-Version Concurrency Control)**는 데이터를 변경할 때 이전 버전을 **Undo 영역 등에 보관**하고, 읽기 트랜잭션에게는 자신의 시점에 맞는 과거 버전(스냅샷)을 보여주는 기법이다.

- **잠금 없는 읽기**: 읽기가 쓰기를 기다리지 않고, 쓰기도 읽기를 기다리지 않음 → 동시 처리 성능이 크게 향상됨
- 각 트랜잭션은 시작(또는 문장 실행) 시점의 **일관된 스냅샷**을 읽으므로 Dirty Read가 원천 차단됨
- **MySQL InnoDB**는 Undo 로그와 트랜잭션 ID로, **PostgreSQL**은 행에 버전 정보(xmin/xmax)를 직접 저장하는 방식으로 MVCC를 구현함

```
        x의 버전 체인 (최신 → 과거)
        ┌─────────────┐    ┌─────────────┐
현재 값 │ x=200 (TX52) │ → │ x=100 (TX40) │  (Undo/이전 버전)
        └─────────────┘    └─────────────┘
TX45(읽기): 자기보다 늦은 TX52의 변경은 무시 → x=100 을 읽음 (대기 없음)
```

> ⚠️ MVCC는 이전 버전을 계속 보관하므로 오래 실행되는 트랜잭션이 있으면 Undo 영역(또는 PostgreSQL의 죽은 튜플)이 비대해져 성능이 저하될 수 있다. 트랜잭션은 짧게 유지해야 한다.

<br>

### 6. 데드락(Deadlock)

두 개 이상의 트랜잭션이 **서로가 가진 락을 기다리며 무한 대기**하는 상태이다.

```
트랜잭션 A                     트랜잭션 B
──────────                    ──────────
① X-Lock(계좌1) 획득
                              ② X-Lock(계좌2) 획득
③ X-Lock(계좌2) 요청 → 대기 ─┐
                              ④ X-Lock(계좌1) 요청 → 대기
   └───────── 서로를 기다림: 데드락 ─────────┘
```

**발생 조건** — 다음 네 조건이 모두 성립할 때 발생함 (OS의 교착상태 조건과 동일)

- **상호 배제**: 락은 한 번에 하나의 트랜잭션만 소유함
- **점유와 대기**: 락을 보유한 채 다른 락을 기다림
- **비선점**: 다른 트랜잭션의 락을 강제로 빼앗을 수 없음
- **순환 대기**: 대기 관계가 원형을 이룸

**해결·예방 방법**

- DBMS의 **데드락 감지**: 대기 그래프에서 사이클을 발견하면 한 트랜잭션을 강제 롤백(희생자 선정)함
- **락 타임아웃**: 일정 시간 대기 후 자동 롤백함
- **접근 순서 통일**: 모든 트랜잭션이 같은 순서로 테이블·행에 접근하면 순환 대기가 생기지 않음
- **트랜잭션 최소화**: 트랜잭션을 짧게 유지하고 자주 커밋함

<br>

### 7. 정리

- 동시성 문제는 **Dirty Read → Non-Repeatable Read → Phantom Read** 순으로 격리 수준을 높여 차단함
- 락 기반 제어는 **S-Lock(읽기 공존) / X-Lock(배타)**으로 접근을 직렬화함
- 충돌 빈도에 따라 **비관적 잠금**(선점)과 **낙관적 잠금**(버전 검증)을 선택함
- **MVCC**는 버전 스냅샷으로 잠금 없는 읽기를 제공하며 MySQL InnoDB·PostgreSQL이 채택함
- 데드락은 네 가지 조건이 모두 성립할 때 발생하며, **감지 후 롤백**과 **접근 순서 통일**로 대응함
- 트랜잭션의 기본 개념과 ACID, 블로킹은 **unit13(트랜잭션)**을 참고할 것
