## SQL 튜닝과 실행 계획

**같은 결과를 반환하는 SQL이라도 실행 방식에 따라 성능이 수십 배 이상 차이 날 수 있다.** DBMS가 쿼리를 어떻게 처리할지 결정하는 옵티마이저와 그 결정의 결과물인 실행 계획을 읽는 방법, 그리고 인덱스를 제대로 활용하는 튜닝 기본 수칙을 다룬다.

> 💡 인덱스의 내부 구조(B-Tree, 클러스터드 인덱스, 복합 인덱스 등)는 **unit14(인덱스)**를 참고할 것. 이 유닛은 인덱스를 "어떻게 잘 타게 만들 것인가"에 집중한다.

<br>

### 1. 옵티마이저(Optimizer)

**사용자가 요청한 SQL을 가장 효율적으로 처리할 방법을 결정하는 DBMS의 핵심 엔진**이다. 동일한 결과를 얻는 실행 방법은 여러 가지(어떤 인덱스를 쓸지, 어떤 테이블부터 조인할지 등)가 있는데, 옵티마이저가 그중 하나를 선택한다.

| **구분**      | **규칙 기반 옵티마이저(RBO)**            | **비용 기반 옵티마이저(CBO)**                     |
| ------------- | ---------------------------------------- | ------------------------------------------------- |
| **판단 기준** | 미리 정해진 **우선순위 규칙**            | 통계 정보 기반 **예상 비용(Cost) 계산**           |
| **활용 정보** | 인덱스 유무, SQL 작성 형태               | 레코드 수, 인덱스 선택도, 데이터 분포 등 통계     |
| **장점**      | 동작이 단순하고 예측 가능                | 데이터 상황에 맞는 **더 나은 선택** 가능          |
| **단점**      | 데이터 분포를 반영하지 못함              | 통계가 오래되면 잘못된 계획 수립 가능             |
| **현재 사용** | 거의 사용하지 않음                       | **MySQL, Oracle 등 대부분의 RDBMS 기본**          |

> ⚠️ CBO는 통계 정보에 의존하므로, 대량의 데이터 변경 후에는 통계가 실제와 어긋나 비효율적인 실행 계획이 선택될 수 있다. 이때는 `ANALYZE TABLE` 등으로 통계를 갱신해야 한다.

<br>

### 2. 실행 계획(Execution Plan)이란

**옵티마이저가 수립한 SQL 처리 절차를 보여주는 결과물**이다. 어떤 인덱스를 사용하는지, 몇 건의 행을 읽을 것으로 예상하는지, 정렬·임시 테이블 같은 추가 작업이 발생하는지를 확인할 수 있다.

- SQL 튜닝의 시작은 **실행 계획을 읽는 것**이다
- 쿼리가 느리다면 "인덱스를 타는가", "몇 건을 읽는가"를 실행 계획으로 먼저 확인한다
- 실행 계획이 바뀌는 요인: 인덱스 추가/삭제, 통계 갱신, 데이터 분포 변화

<br>

### 3. EXPLAIN 사용법

쿼리 앞에 `EXPLAIN` 키워드를 붙이면 실제 실행 없이 실행 계획을 확인할 수 있다.

```sql
CREATE INDEX idx_status_created ON orders(status, created_at);

EXPLAIN
SELECT order_id, status, created_at
FROM orders
WHERE status = 'pending' AND created_at > '2024-01-01';
```

```
+----+--------+--------------------+--------------------+---------+-------------+
| id | table  | type               | key                | rows    | Extra       |
+----+--------+--------------------+--------------------+---------+-------------+
| 1  | orders | range              | idx_status_created | 1,200   | Using where |
+----+--------+--------------------+--------------------+---------+-------------+
```

**결과 해석**: `idx_status_created` 인덱스를 사용해(**key**) 범위 스캔(**type: range**)으로 약 1,200건만 읽는다(**rows**). 인덱스가 없었다면 type이 **ALL**(풀 테이블 스캔)로 표시되고 rows가 전체 행 수에 가까워진다.

<br>

**주요 컬럼 읽는 법 (MySQL 기준)**

| **컬럼**  | **의미**                       | **확인 포인트**                                              |
| --------- | ------------------------------ | ------------------------------------------------------------ |
| **type**  | 테이블 접근 방식               | **ALL**(풀 스캔)이면 개선 대상 1순위                          |
| **key**   | 실제 사용된 인덱스             | **NULL**이면 인덱스를 전혀 사용하지 못한 것                   |
| **rows**  | 읽을 것으로 **추정**되는 행 수 | 결과 건수 대비 지나치게 크면 인덱스 설계 재검토               |
| **Extra** | 추가 처리 정보                 | **Using filesort**, **Using temporary**는 정렬·임시 테이블 발생 신호 |

❗️**rows는 추정치**: rows는 통계 기반의 예상값일 뿐 실제 읽은 행 수가 아니다. 실제 수치가 필요하면 MySQL 8.0의 `EXPLAIN ANALYZE`로 실측값을 확인한다.

<br>

**type 컬럼 성능 순서**

type은 아래로 갈수록 읽는 범위가 넓어져 성능이 나빠진다.

| **type**   | **의미**                                        | **성능**       |
| ---------- | ----------------------------------------------- | -------------- |
| **const**  | PK 또는 UNIQUE 인덱스로 **단 1건** 조회         | 가장 빠름      |
| **eq_ref** | 조인에서 PK/UNIQUE 인덱스로 1건씩 매칭          | 매우 빠름      |
| **ref**    | 일반 인덱스로 동등(=) 비교                      | 빠름           |
| **range**  | 인덱스를 이용한 **범위 스캔** (BETWEEN, >, <)   | 양호           |
| **index**  | **인덱스 전체**를 처음부터 끝까지 스캔          | 느림           |
| **ALL**    | **풀 테이블 스캔** — 인덱스 미사용              | 가장 느림      |

<br>

### 4. 인덱스를 타지 못하는 쿼리 패턴

인덱스가 존재해도 쿼리 작성 방식에 따라 옵티마이저가 인덱스를 사용하지 못한다. 대표적인 패턴 네 가지를 나쁜 예/좋은 예로 비교한다.

<br>

### 4-1. 인덱스 컬럼 가공

인덱스 컬럼에 **함수나 연산을 적용하면** 인덱스에 저장된 원본 값과 비교할 수 없어 인덱스를 타지 못한다.

```sql
-- ❌ 나쁜 예: 인덱스 컬럼을 함수로 가공
SELECT * FROM orders WHERE DATE(created_at) = '2024-01-01';
SELECT * FROM users  WHERE SUBSTRING(phone, 1, 3) = '010';

-- ✅ 좋은 예: 컬럼은 그대로 두고 조건 값을 조정
SELECT * FROM orders
WHERE created_at >= '2024-01-01 00:00:00'
  AND created_at <  '2024-01-02 00:00:00';
SELECT * FROM users  WHERE phone LIKE '010%';
```

<br>

### 4-2. 앞쪽 와일드카드 LIKE

인덱스는 문자열 **앞부분부터 정렬**되어 있으므로, 시작 부분이 불명확한 패턴은 탐색 시작점을 찾을 수 없다.

```sql
-- ❌ 나쁜 예: 앞쪽 와일드카드 → 풀 스캔
SELECT * FROM users WHERE email LIKE '%@gmail.com';

-- ✅ 좋은 예: 전방 일치는 인덱스 활용 가능
SELECT * FROM users WHERE email LIKE 'hong%';

-- ✅ 좋은 예: 도메인 검색이 잦다면 별도 컬럼을 만들어 인덱싱
SELECT * FROM users WHERE email_domain = 'gmail.com';
```

<br>

### 4-3. 암시적 형변환

컬럼과 조건 값의 **타입이 다르면** DBMS가 내부적으로 형변환을 수행하는데, 이 과정이 인덱스 컬럼 가공과 같은 효과를 낸다.

```sql
-- user_no 컬럼이 VARCHAR 타입일 때

-- ❌ 나쁜 예: 숫자와 비교 → 컬럼이 숫자로 변환되며 인덱스 미사용
SELECT * FROM users WHERE user_no = 12345;

-- ✅ 좋은 예: 컬럼 타입에 맞는 문자열로 비교
SELECT * FROM users WHERE user_no = '12345';
```

<br>

### 4-4. OR 남용

OR로 연결된 조건 중 **하나라도 인덱스를 타지 못하면** 전체가 풀 스캔으로 처리될 수 있다.

```sql
-- ❌ 나쁜 예: name에만 인덱스가 있고 nickname에는 없는 경우
SELECT * FROM users WHERE name = 'kim' OR nickname = 'kim';

-- ✅ 좋은 예: 각각 인덱스를 태운 뒤 UNION으로 합침
SELECT * FROM users WHERE name = 'kim'
UNION
SELECT * FROM users WHERE nickname = 'kim';

-- ✅ 좋은 예: 같은 컬럼의 OR는 IN으로 변경
SELECT * FROM users WHERE status IN ('active', 'dormant');
```

<br>

### 5. 커버링 인덱스 활용

쿼리에 필요한 모든 컬럼이 인덱스에 포함되면 **테이블 접근 없이 인덱스만으로 결과를 반환**한다. 실행 계획의 Extra에 **Using index**가 표시되면 커버링 인덱스가 동작한 것이다.

```sql
CREATE INDEX idx_status_created ON orders(status, created_at);

-- 커버링 인덱스 동작: SELECT 컬럼이 모두 인덱스 안에 있음
EXPLAIN SELECT status, created_at FROM orders WHERE status = 'pending';
-- Extra: Using index

-- 커버링 실패: amount는 인덱스에 없어 테이블 접근 필요
EXPLAIN SELECT status, amount FROM orders WHERE status = 'pending';
-- Extra: (Using index 없음)
```

<br>

### 6. 튜닝 기본 수칙

- **SELECT \* 를 지양한다**: 불필요한 컬럼 조회는 I/O와 네트워크 비용을 늘리고, 커버링 인덱스가 동작할 기회를 없앤다
- **WHERE 조건 컬럼은 가공하지 않는다**: 가공은 조건 값 쪽에서 한다
- **느린 쿼리는 EXPLAIN부터 확인한다**: type이 ALL인지, key가 NULL인지, Extra에 Using filesort가 있는지 순서로 점검한다
- **LIMIT과 함께 필요한 만큼만 조회한다**: 화면에 10건을 보여주면서 전체를 읽을 이유가 없다
- **인덱스를 무분별하게 늘리지 않는다**: 인덱스는 쓰기 성능과 저장 공간을 희생한다(unit14 참고)

> 💡 튜닝의 우선순위는 "쿼리를 고쳐 기존 인덱스를 타게 만들기 → 인덱스 추가/재설계 → 테이블 구조 변경" 순이다. 인덱스 추가는 쓰기 비용을 수반하므로 쿼리 수정으로 해결 가능한지 먼저 확인한다.
