## 커넥션과 커넥션 풀(Connection Pool)

**애플리케이션이 DB와 통신하려면 먼저 커넥션(연결)을 맺어야 하는데, 이 작업은 생각보다 비싸다.** 커넥션 생성 비용이 왜 큰지, 그리고 이를 해결하는 커넥션 풀의 원리와 올바른 사용법을 다룬다.

<br>

### 1. DB 커넥션 생성 비용

커넥션 하나를 새로 맺는 과정은 여러 단계를 거치는 **무거운 작업**이다.

```
[애플리케이션]                         [DB 서버]
      |                                    |
      |--- ① TCP 3-way 핸드셰이크 -------->|   네트워크 연결 수립
      |<-- (SYN → SYN+ACK → ACK) ---------|
      |                                    |
      |--- ② 인증 (계정/비밀번호 검증) --->|   DB 접속 권한 확인
      |<----------------------------------|
      |                                    |
      |--- ③ 세션 생성 ------------------->|   DB 내부에 세션 자원 할당
      |<--- 커넥션 사용 가능 --------------|
```

- **① 네트워크 비용**: TCP 3-way 핸드셰이크로 왕복 통신이 발생한다 (network 과목의 TCP 유닛 참고)
- **② 인증 비용**: 계정 정보 검증을 위한 추가 왕복이 발생한다
- **③ 세션 비용**: DB 서버가 세션용 메모리와 프로세스(또는 스레드) 자원을 할당한다

> 💡 커넥션 생성은 단순 쿼리 실행보다 훨씬 오래 걸리는 경우가 많다. 수 밀리초짜리 SELECT 한 번을 위해 수십 밀리초짜리 연결 과정을 매번 반복하는 것은 명백한 낭비다.

<br>

### 2. 매 요청마다 커넥션을 생성하면 생기는 문제

커넥션 풀이 없다면 요청이 올 때마다 아래 과정을 반복한다.

```
[요청 1] → 커넥션 생성 → 쿼리 실행 → 커넥션 종료
[요청 2] → 커넥션 생성 → 쿼리 실행 → 커넥션 종료
[요청 3] → 커넥션 생성 → 쿼리 실행 → 커넥션 종료
   ...        (매번 반복되는 낭비 구간)

한 요청의 시간 구성:
|---- 연결 수립 ----|-- 쿼리 --|---- 연결 종료 ----|
    (낭비)            (실제 작업)      (낭비)
```

- **응답 지연**: 실제 쿼리 시간보다 연결 수립/종료에 더 많은 시간이 소요될 수 있음
- **자원 낭비**: DB 서버가 세션 생성과 해제를 끊임없이 반복함
- **순간 폭주 취약**: 트래픽이 몰리면 커넥션 생성 요청이 한꺼번에 쏟아져 DB가 과부하됨

<br>

### 3. 커넥션 풀의 원리

**커넥션을 미리 여러 개 만들어 풀(Pool)에 보관해두고, 필요할 때 빌려 쓰고(대여) 다 쓰면 돌려놓는(반납) 방식**이다. 애플리케이션 시작 시점에 커넥션을 생성해두므로 요청 처리 중에는 연결 수립 비용이 발생하지 않는다.

```
              [커넥션 풀]
          +----------------+
          |  C1  C2  C3    |   ← 미리 생성해둔 커넥션들
          |  C4  C5        |
          +----------------+
             |          ↑
        ① 대여        ③ 반납
             ↓          |
[요청] → [애플리케이션 스레드] → ② 쿼리 실행 → [DB]
```

1. **초기화**: 애플리케이션 시작 시 커넥션을 미리 생성해 풀에 채움
2. **대여**: 요청 처리 스레드가 풀에서 유휴 커넥션을 하나 가져옴
3. **사용**: 쿼리를 실행함 (연결 수립 비용 없음)
4. **반납**: 커넥션을 닫지 않고 풀에 되돌려놓아 다음 요청이 재사용함

<br>

### 4. 풀 크기의 트레이드오프

풀 크기는 크다고 좋은 것이 아니며, 애플리케이션과 DB 양쪽 상황을 고려해 정해야 한다.

| **풀 크기**     | **문제점**                                                       |
| --------------- | ---------------------------------------------------------------- |
| **너무 작으면** | 커넥션을 얻기 위한 **대기 발생** → 응답 지연, 타임아웃 예외      |
| **너무 크면**   | DB 서버의 세션 자원·메모리 **부하 증가**, 컨텍스트 스위칭 비용   |

> ⚠️ 커넥션 풀을 키우면 애플리케이션은 여유로워 보이지만, 그 부담은 고스란히 DB 서버로 넘어간다. DB의 최대 커넥션 수(max_connections)와 서버 자원을 고려하지 않고 풀만 키우면 오히려 전체 처리량이 떨어진다. HikariCP 공식 문서는 `CPU 코어 수 × 2 + 디스크 수` 수준의 작은 풀을 출발점으로 권장한다.

<br>

### 5. DBCP와 HikariCP

**DBCP(Database Connection Pool)**는 커넥션 풀 기법 또는 이를 구현한 라이브러리를 통칭한다. 자바 진영의 대표 구현체는 다음과 같다.

- **Apache Commons DBCP**: 아파치 재단의 전통적인 커넥션 풀 구현체
- **Tomcat JDBC Pool**: 톰캣에 내장된 커넥션 풀
- **HikariCP**: 빠른 속도와 안정성으로 사실상 표준이 된 구현체 — **Spring Boot 2.0부터 기본 커넥션 풀**

<br>

### 6. HikariCP 설정 예시

Spring Boot의 `application.properties`에서 주요 항목을 설정할 수 있다.

```properties
# 풀이 유지할 최대 커넥션 수 (기본값 10)
spring.datasource.hikari.maximum-pool-size=10

# 유지할 최소 유휴 커넥션 수 (기본값: maximum-pool-size와 동일)
spring.datasource.hikari.minimum-idle=10

# 커넥션 대여 대기 한계 시간(ms) — 초과 시 예외 발생 (기본값 30000)
spring.datasource.hikari.connection-timeout=30000

# 커넥션의 최대 수명(ms) — 초과 시 폐기 후 재생성 (기본값 1800000)
spring.datasource.hikari.max-lifetime=1800000
```

> 💡 `max-lifetime`은 DB 서버가 유휴 커넥션을 끊는 시간(MySQL의 wait_timeout 등)보다 **짧게** 설정해야 한다. DB가 먼저 끊어버린 죽은 커넥션을 풀이 대여해주는 문제를 예방할 수 있다.

<br>

### 7. 커넥션 풀 사용 전후 비교

| **구분**             | **풀 미사용 (매번 생성)**        | **커넥션 풀 사용**               |
| -------------------- | -------------------------------- | -------------------------------- |
| **요청당 연결 비용** | 매번 발생 (핸드셰이크+인증+세션) | **없음** (재사용)                |
| **응답 시간**        | 느림                             | **빠름**                         |
| **DB 부하**          | 세션 생성/해제 반복으로 큼       | 일정 수준으로 **예측 가능**      |
| **동시 커넥션 수**   | 트래픽에 따라 무제한 증가 위험   | 풀 크기로 **상한 제어**          |
| **트래픽 폭주 시**   | DB 과부하로 장애 위험            | 초과 요청은 대기 → DB 보호       |

<br>

### 8. 커넥션 누수(Connection Leak) 주의

대여한 커넥션을 **반납하지 않으면** 풀의 커넥션이 하나씩 사라져, 결국 모든 요청이 커넥션을 얻지 못하고 타임아웃되는 장애로 이어진다.

```java
// ❌ 나쁜 예: 예외 발생 시 close()가 호출되지 않아 커넥션 누수
Connection conn = dataSource.getConnection();
PreparedStatement ps = conn.prepareStatement("SELECT * FROM users");
ResultSet rs = ps.executeQuery();   // 여기서 예외가 나면 반납 누락
conn.close();

// ✅ 좋은 예: try-with-resources로 반납을 보장
try (Connection conn = dataSource.getConnection();
     PreparedStatement ps = conn.prepareStatement("SELECT * FROM users");
     ResultSet rs = ps.executeQuery()) {
    while (rs.next()) {
        // 결과 처리
    }
} // 블록을 벗어나면 예외 여부와 관계없이 자동 반납
```

❗️**close()는 종료가 아니라 반납**: 커넥션 풀 환경에서 `close()`를 호출하면 실제 연결이 끊기는 것이 아니라 커넥션이 풀로 반납된다. 그래서 사용 후 `close()` 호출(또는 try-with-resources)이 반드시 필요하다. 트랜잭션을 길게 잡는 것도 커넥션 점유 시간을 늘려 풀 고갈을 유발하므로 트랜잭션 범위는 최소화한다(unit13 참고).
