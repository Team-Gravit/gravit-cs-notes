## 확장 전략 — 파티셔닝·샤딩·레플리케이션

**데이터와 트래픽이 계속 늘어나면 단일 DB 서버만으로는 감당할 수 없는 시점이 온다.** 이때 사용하는 대표적인 확장 전략인 파티셔닝, 샤딩, 레플리케이션의 원리와 차이, 그리고 적용 순서를 다룬다.

<br>

### 1. 단일 DB의 한계

- **저장 용량 한계**: 한 서버의 디스크로 담을 수 있는 데이터 크기에 상한이 있음
- **처리 성능 한계**: CPU·메모리·디스크 I/O가 한 서버에 집중되어 병목 발생
- **단일 장애점(SPOF)**: 서버 한 대가 죽으면 서비스 전체가 중단됨
- **테이블 비대화**: 한 테이블이 수억 건이 되면 인덱스가 있어도 조회·변경 성능이 저하됨

<br>

### 2. 스케일 업 vs 스케일 아웃

| **구분**      | **스케일 업(Scale-Up)**            | **스케일 아웃(Scale-Out)**              |
| ------------- | ---------------------------------- | --------------------------------------- |
| **방식**      | 서버 한 대의 **사양을 올림**       | 서버 **대수를 늘림**                    |
| **구현 난이도** | 쉬움 (장비 교체)                 | 어려움 (분산 설계 필요)                 |
| **확장 한계** | 하드웨어 성능의 **물리적 상한** 존재 | 이론상 **수평 확장 지속 가능**          |
| **비용**      | 고사양일수록 비용이 **급격히 증가** | 저사양 다수로 **비교적 완만하게 증가**  |
| **장애 대응** | 단일 장애점 그대로                 | 일부 서버 장애 시에도 서비스 지속 가능  |

파티셔닝은 단일 서버 내부의 구조 개선, 샤딩과 레플리케이션은 스케일 아웃에 해당한다.

<br>

### 3. 파티셔닝(Partitioning)

**하나의 큰 테이블을 논리적으로는 하나로 유지하면서, 물리적으로 여러 조각(파티션)으로 나누어 저장하는 기법**이다. 같은 DB 서버 안에서 이루어진다.

<br>

**수평 파티셔닝 vs 수직 파티셔닝**

```
[수평 파티셔닝: 행(Row) 기준 분할]          [수직 파티셔닝: 열(Column) 기준 분할]

 id | name | created_at                      id | name | bio(대용량)
----+------+------------                    ----+------+-------------
  1 | kim  | 2023-05-01  → 파티션 1              ↓ 분할 ↓
  2 | lee  | 2024-02-10  → 파티션 2          [기본 테이블]     [부가 테이블]
  3 | park | 2025-01-20  → 파티션 3           id | name        id | bio
```

<br>

**수평 파티셔닝의 분할 기준**

```
범위 분할 (Range)                해시 분할 (Hash)              리스트 분할 (List)
─────────────────               ─────────────────             ─────────────────
2023년 → 파티션 1                hash(id) % 3 = 0 → 파티션 1    지역 = '서울' → 파티션 1
2024년 → 파티션 2                hash(id) % 3 = 1 → 파티션 2    지역 = '부산' → 파티션 2
2025년 → 파티션 3                hash(id) % 3 = 2 → 파티션 3    지역 = '제주' → 파티션 3
(날짜·숫자 구간)                  (데이터 균등 분산)              (이산적인 값 목록)
```

- **범위 분할**: 기간별 조회가 많은 로그·주문 데이터에 적합, 오래된 파티션 삭제가 간편함
- **해시 분할**: 특정 파티션에 데이터가 몰리는 것을 방지하고 균등하게 분산함
- **리스트 분할**: 지역·카테고리처럼 값의 종류가 정해져 있을 때 사용함

<br>

**범위 파티셔닝 생성 예시 (MySQL)**

```sql
CREATE TABLE orders (
    order_id   BIGINT,
    created_at DATETIME NOT NULL
)
PARTITION BY RANGE (YEAR(created_at)) (
    PARTITION p2023 VALUES LESS THAN (2024),
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p2025 VALUES LESS THAN (2026)
);

-- 2024년 조건 조회 시 p2024 파티션만 스캔함 (파티션 프루닝)
SELECT * FROM orders
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01';
```

<br>

### 4. 샤딩(Sharding)

**수평 파티셔닝을 서버 단위로 확장한 것**으로, 데이터를 여러 대의 **독립된 DB 서버(샤드)**에 나누어 저장한다. 파티셔닝은 한 서버 안의 분할이지만, 샤딩은 저장 용량과 처리 부하 자체를 여러 서버로 분산한다.

```
                [애플리케이션]
                      |
              샤드 키(user_id)로 라우팅
              /       |        \
        [샤드 1]   [샤드 2]   [샤드 3]
        서버 A     서버 B     서버 C
        id 1~100  id 101~200 id 201~300
```

**샤드 키(Shard Key) 선정**

- 어떤 샤드에 저장할지 결정하는 기준 컬럼 (예: user_id)
- 데이터가 **균등하게 분산**되도록 선정해야 함 — 특정 샤드에 몰리면(핫스팟) 분산 효과가 사라짐
- 대부분의 쿼리가 **샤드 키를 조건에 포함**하도록 설계해야 한 샤드만 조회할 수 있음

> ⚠️ 샤딩을 도입하면 **크로스 샤드 조인이 사실상 불가능**해진다. 서로 다른 샤드에 있는 테이블 간 JOIN, 전체 샤드에 걸친 집계, 여러 샤드에 걸친 트랜잭션은 애플리케이션이 직접 조합해야 하며 복잡도가 크게 증가한다. 샤드 재분배(리샤딩)도 대규모 데이터 이동을 수반하는 고비용 작업이다.

<br>

### 5. 레플리케이션(Replication)

**동일한 데이터를 여러 서버에 복제해 유지하는 기법**이다. 쓰기를 담당하는 **Primary(Master)**와 이를 복제한 **Replica(Slave)**로 구성하는 것이 일반적이다.

```
              쓰기(INSERT/UPDATE/DELETE)
[애플리케이션] ─────────────→ [Primary]
      |                          |
      |                     변경 로그 전달(복제)
      |                     ↓           ↓
      └── 읽기(SELECT) → [Replica 1] [Replica 2]
```

- **읽기 분산**: 조회 요청을 여러 Replica로 분산해 읽기 처리량을 높임 — 대부분의 서비스는 읽기 비중이 압도적이라 효과가 큼
- **고가용성**: Primary 장애 시 Replica를 새 Primary로 승격(Failover)해 서비스를 지속함
- **백업 활용**: Replica에서 백업을 수행해 Primary 부하를 줄임

<br>

### 5-1. 복제 지연(Replication Lag) 문제

복제는 보통 **비동기**로 이루어지므로, Primary의 변경이 Replica에 반영되기까지 시간차가 존재한다.

```
① 사용자가 닉네임 변경  → [Primary]  반영 완료
② 직후 내 정보 조회     → [Replica]  아직 복제 전 → 옛날 닉네임이 보임
```

- **사례**: 게시글 작성 직후 목록에 내 글이 없거나, 결제 완료 직후 주문 내역이 비어 보이는 현상
- **대응**: 쓰기 직후의 조회는 Primary에서 읽기, 지연에 민감한 기능은 Primary 고정, 지연 모니터링

<br>

### 6. 세 전략 종합 비교

| **구분**      | **파티셔닝**             | **샤딩**                     | **레플리케이션**             |
| ------------- | ------------------------ | ---------------------------- | ---------------------------- |
| **분산 단위** | 한 서버 내 **테이블 분할** | **여러 서버**에 데이터 분할 | **여러 서버**에 데이터 복제  |
| **데이터**    | 서로 다른 조각           | 서로 다른 조각               | **모두 동일한 복사본**       |
| **주 목적**   | 대용량 테이블 관리·성능  | 쓰기·저장 용량 **수평 확장** | **읽기 분산**·고가용성       |
| **쓰기 확장** | 제한적                   | **가능**                     | 불가 (쓰기는 Primary 한 대)  |
| **주요 부작용** | 파티션 키 없는 조회 비효율 | 크로스 샤드 조인·리샤딩    | 복제 지연                    |

<br>

### 7. 적용 순서 가이드

> 💡 확장 전략에는 권장 순서가 있다. **① 인덱스·쿼리 튜닝(unit18) → ② 캐시 도입 → ③ 레플리케이션(읽기 분산) → ④ 파티셔닝 → ⑤ 샤딩** 순으로, 운영 복잡도가 낮은 방법부터 적용한다. 샤딩은 조인·트랜잭션·리샤딩의 복잡도를 모두 떠안는 **최후의 수단**이며, 대부분의 서비스는 그 전 단계에서 충분히 해결된다.
