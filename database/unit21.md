## NoSQL과 CAP 이론

**모든 데이터를 관계형 모델로 담기 어려운 시대가 되면서 NoSQL이 등장했다.** NoSQL의 등장 배경과 4가지 유형, 분산 시스템 설계의 근간이 되는 CAP 이론, 그리고 RDBMS와의 선택 기준을 다룬다.

<br>

### 1. RDBMS의 한계와 NoSQL의 등장 배경

RDBMS는 정형화된 스키마와 ACID 트랜잭션(unit13 참고)으로 강한 정합성을 보장하지만, 대규모 웹 서비스 환경에서 다음 한계가 드러났다.

- **수평 확장의 어려움**: 조인과 트랜잭션을 유지한 채 여러 서버로 분산(샤딩, unit20 참고)하기가 매우 복잡함
- **고정 스키마의 경직성**: 컬럼 추가/변경 시 스키마 변경이 필요해, 구조가 자주 바뀌는 데이터에 부적합
- **비정형 데이터 증가**: SNS 게시물, 로그, 센서 데이터 등 관계형 모델에 맞지 않는 데이터가 폭증함

**NoSQL(Not Only SQL)**은 관계형 모델과 스키마 제약을 완화하는 대신, **수평 확장(스케일 아웃)과 유연한 데이터 모델**을 얻는 방향으로 설계된 데이터베이스군이다.

<br>

### 2. NoSQL의 4가지 유형

| **유형**            | **데이터 모델**                          | **대표 제품**        | **적합한 용도**                  |
| ------------------- | ---------------------------------------- | -------------------- | -------------------------------- |
| **키-값(Key-Value)** | 키 하나에 값 하나를 매핑                 | **Redis**, DynamoDB  | 캐시, 세션 저장, 실시간 랭킹     |
| **문서(Document)**  | JSON과 유사한 문서 단위 저장             | **MongoDB**, CouchDB | 스키마가 유동적인 콘텐츠, 카탈로그 |
| **컬럼(Column-Family)** | 행마다 다른 컬럼 집합을 가지는 넓은 컬럼 구조 | **Cassandra**, HBase | 대량 쓰기, 시계열·로그 데이터    |
| **그래프(Graph)**   | 노드와 엣지로 관계 자체를 저장           | **Neo4j**            | 친구 추천, 사기 탐지 등 관계 분석 |

> 💡 유형별로 잘하는 일이 뚜렷하게 다르다. "NoSQL이 RDBMS보다 빠르다"가 아니라, **데이터의 모양과 접근 패턴에 맞는 유형을 골랐을 때** 성능과 확장성 이점이 생기는 것이다.

<br>

### 3. CAP 이론

분산 데이터 시스템은 다음 세 가지 성질을 **동시에 모두 만족할 수 없고, 최대 두 가지만 보장할 수 있다**는 이론이다.

```
                    C (일관성)
                    /\
                   /  \
                  /    \
                 / 셋 중 \
                /  둘만   \
               /   선택    \
              /____________\
      A (가용성) ────────── P (분단 허용성)
```

- **일관성(Consistency)**: 어느 노드에서 읽어도 **가장 최신의 동일한 데이터**를 반환함
- **가용성(Availability)**: 일부 노드에 장애가 있어도 모든 요청이 **항상 응답**을 받음
- **분단 허용성(Partition Tolerance)**: 노드 간 **네트워크가 단절**되어도 시스템이 계속 동작함

<br>

### 3-1. 분산 시스템에서는 CP vs AP

네트워크 장애는 언제든 발생할 수 있으므로, 분산 시스템에서 **P는 선택이 아니라 필수**다. 결국 실제 선택지는 네트워크 분단이 발생했을 때 무엇을 포기할 것인가, 즉 **CP vs AP**가 된다.

```
네트워크 분단 발생: [노드 A] ×──끊김──× [노드 B]

CP 선택: 일관성 우선                    AP 선택: 가용성 우선
"동기화가 안 되면 응답하지 않겠다"        "일단 응답하고 나중에 맞추겠다"
→ 일부 요청 실패/대기 (가용성 희생)      → 잠시 옛 데이터 응답 가능 (일관성 희생)
예: HBase, MongoDB(기본 설정)           예: Cassandra, DynamoDB
```

- **CP 시스템**: 잔액, 재고처럼 **잘못된 값을 보여주면 안 되는** 도메인에 적합
- **AP 시스템**: SNS 피드, 조회수처럼 **잠시 어긋나도 서비스 지속이 더 중요한** 도메인에 적합 — 시간이 지나면 일치하는 **최종적 일관성(Eventual Consistency)** 모델을 따름

<br>

### 3-2. PACELC — CAP의 확장

CAP은 장애 상황만 다루지만, PACELC는 **평상시의 트레이드오프까지 포함**한다.

- **P**artition 발생 시(**P**) → **A**vailability와 **C**onsistency 중 선택 (CAP과 동일)
- **E**lse, 평상시에는(**E**) → **L**atency(지연 시간)와 **C**onsistency 중 선택

즉 정상 상황에서도 모든 노드에 동기 복제를 기다리면 일관성은 높아지지만 응답이 느려지고, 기다리지 않으면 빠르지만 일관성이 약해진다. 복제 지연(unit20 참고)이 바로 이 트레이드오프의 사례다.

<br>

### 4. RDBMS vs NoSQL 종합 비교

| **구분**       | **RDBMS**                              | **NoSQL**                                  |
| -------------- | -------------------------------------- | ------------------------------------------ |
| **스키마**     | **고정 스키마** (사전 정의 필수)       | **유연한 스키마** (동적 필드 허용)         |
| **데이터 모델** | 테이블·행·열, 관계(조인)              | 키-값·문서·컬럼·그래프                     |
| **트랜잭션**   | **ACID** 강한 보장                     | 제한적 (다수는 최종적 일관성 지향)         |
| **확장 방식**  | 주로 **스케일 업** (수평 확장 복잡)    | **스케일 아웃**에 최적화                   |
| **일관성**     | 강한 일관성                            | 제품·설정에 따라 강한 ~ 최종적 일관성      |
| **적합한 경우** | 정합성이 중요한 핵심 업무(결제·회원)  | 대규모 트래픽, 비정형·가변 구조 데이터     |

> ⚠️ NoSQL을 선택한다는 것은 조인·강한 트랜잭션 같은 RDBMS의 보장을 **포기하는 비용**을 치르는 것이다. 확장 요구가 명확하지 않은데 유행 때문에 NoSQL을 도입하면, 애플리케이션 코드에서 정합성을 직접 관리하는 부담만 떠안게 된다.

<br>

### 5. 대표 사용 사례

**Redis — 캐시 계층**

DB 조회 결과를 메모리에 저장해두고, 이후 동일 요청은 DB까지 가지 않고 응답한다.

```
[요청] → [Redis 캐시] ── 히트 → 즉시 응답 (메모리 속도)
              |
             미스
              ↓
          [RDBMS] → 조회 결과를 캐시에 저장 후 응답
```

- 세션 저장소, 실시간 랭킹(Sorted Set), 조회수 카운터 등에도 활용됨

<br>

**MongoDB — 문서 저장**

상품처럼 항목마다 속성이 제각각인 데이터를 하나의 문서로 저장한다.

```javascript
// 상품마다 다른 속성을 가져도 같은 컬렉션에 저장 가능
db.products.insertOne({
  name: "노트북",
  price: 1500000,
  specs: { cpu: "8코어", ram: "16GB" },   // 중첩 구조
  tags: ["전자제품", "노트북"]             // 배열
});

db.products.find({ "specs.ram": "16GB" });  // 중첩 필드 조회
```

- 조인 없이 관련 데이터를 한 문서에 담아 읽기가 단순해지고, 스키마 변경 부담이 없음

<br>

### 6. 폴리글랏 퍼시스턴스(Polyglot Persistence)

> 💡 실무의 결론은 "RDBMS냐 NoSQL이냐"의 양자택일이 아니라 **혼용**이다. 회원·주문은 RDBMS, 세션·캐시는 Redis, 상품 카탈로그는 MongoDB처럼 **데이터 특성에 맞는 저장소를 조합해 사용하는 방식**을 폴리글랏 퍼시스턴스라고 한다. 각 저장소의 강점만 취하는 대신, 운영해야 할 시스템이 늘어나는 비용은 감수해야 한다.
