## 이벤트 루프와 논블로킹 I/O

Node.js는 **단일 스레드**로 JavaScript를 실행하면서도 수만 개의 동시 연결을 처리한다. 그 비밀은 I/O를 기다리지 않는 **논블로킹 I/O(Non-blocking I/O)**와, 완료된 작업의 콜백을 순서대로 실행하는 **이벤트 루프(Event Loop)**에 있다. 이 유닛은 이벤트 루프의 페이즈별 실행 순서와 libuv 스레드 풀의 역할을 정리한다.

<br>

### 1. 블로킹 I/O와 논블로킹 I/O

- **블로킹 I/O**: 파일 읽기·네트워크 응답이 끝날 때까지 스레드가 멈춰 기다림. 동시 요청을 처리하려면 요청마다 스레드를 늘려야 하며, 스레드 생성·컨텍스트 스위칭 비용이 커짐
- **논블로킹 I/O**: I/O를 운영체제에 요청만 하고 즉시 다음 코드를 실행함. 완료 여부는 나중에 **이벤트(콜백)**로 통지받음
- Node.js는 JavaScript 코드를 **한 개의 메인 스레드**에서 실행하고, I/O 대기는 운영체제와 libuv에 맡겨 메인 스레드가 놀지 않게 함

```javascript
const fs = require('node:fs');

// 블로킹: 파일을 다 읽을 때까지 아래 줄이 실행되지 않음
const data = fs.readFileSync('big.log', 'utf8');
console.log('1. 동기 읽기 완료');

// 논블로킹: 요청만 던지고 즉시 다음 줄 실행
fs.readFile('big.log', 'utf8', (err, content) => {
  console.log('3. 비동기 읽기 완료');
});
console.log('2. 읽기 요청 후 바로 실행');
```

> 💡 "Node.js는 싱글 스레드인가?"라는 면접 질문의 정확한 답은 "**JavaScript 실행은 싱글 스레드이지만, 프로세스 전체는 멀티 스레드**"다. libuv 스레드 풀과 V8의 GC 스레드 등이 백그라운드에서 함께 동작한다.

<br>

### 2. Node.js 런타임 구조

```
┌──────────────────────────────────────────────────┐
│  JavaScript 코드 (애플리케이션)                    │
├──────────────────────────────────────────────────┤
│  Node.js 바인딩 (fs, net, http, crypto ...)       │
├─────────────────────┬────────────────────────────┤
│  V8 (JS 엔진)        │  libuv (이벤트 루프, 비동기 I/O) │
│  콜 스택·힙·GC       │  ├ OS 비동기 I/O (epoll/kqueue/IOCP) │
│                     │  └ 스레드 풀 (기본 4개)      │
└─────────────────────┴────────────────────────────┘
```

- **V8**: JavaScript를 컴파일·실행하는 엔진. 콜 스택은 하나뿐이므로 한 번에 한 함수만 실행함
- **libuv**: C로 작성된 크로스 플랫폼 비동기 I/O 라이브러리. 이벤트 루프 자체와 스레드 풀을 제공함
- 운영체제가 지원하는 비동기 API(Linux `epoll`, macOS `kqueue`, Windows `IOCP`)로 소켓 이벤트를 감시하며, 지원하지 않는 작업은 스레드 풀로 우회함

<br>

### 3. 이벤트 루프의 페이즈

이벤트 루프는 아래 **6개 페이즈(phase)**를 순서대로 순회하며, 각 페이즈는 자신의 콜백 큐(FIFO)를 비울 때까지(또는 한도까지) 콜백을 실행한 뒤 다음 페이즈로 넘어간다.

```
   ┌──────────────────────────┐
┌─▶│      1. timers           │  setTimeout / setInterval 콜백
│  └────────────┬─────────────┘
│  ┌────────────▼─────────────┐
│  │  2. pending callbacks    │  이전 루프에서 미뤄진 I/O 콜백 (TCP 오류 등)
│  └────────────┬─────────────┘
│  ┌────────────▼─────────────┐
│  │   3. idle, prepare       │  내부용
│  └────────────┬─────────────┘
│  ┌────────────▼─────────────┐   ┌─────────────────────┐
│  │        4. poll           │◀──│ 새 I/O 완료 이벤트    │
│  │  I/O 콜백 실행·대기        │   └─────────────────────┘
│  └────────────┬─────────────┘
│  ┌────────────▼─────────────┐
│  │        5. check          │  setImmediate 콜백
│  └────────────┬─────────────┘
│  ┌────────────▼─────────────┐
└──│   6. close callbacks     │  socket.on('close') 등
   └──────────────────────────┘
```

<br>

### 3-1. 페이즈별 역할

| **페이즈**            | **실행되는 콜백**                       | **비고**                                        |
| --------------------- | --------------------------------------- | ----------------------------------------------- |
| **timers**            | `setTimeout`, `setInterval`             | 지정 시간이 **지난** 타이머만 실행. 정확한 시각 보장 없음 |
| **pending callbacks** | 지연된 시스템 콜백                      | 일부 TCP 오류 콜백 등                            |
| **idle, prepare**     | 내부 처리                               | 애플리케이션 코드와 무관                         |
| **poll**              | I/O 완료 콜백 (파일, 소켓, DB 응답 등)   | 큐가 비면 **여기서 대기**함                       |
| **check**             | `setImmediate`                          | poll 직후 실행 보장                              |
| **close callbacks**   | `'close'` 이벤트 핸들러                 | 소켓·핸들 종료 시                                |

<br>

### 3-2. poll 페이즈의 대기 규칙

poll 페이즈는 이벤트 루프의 심장으로, 다음 규칙으로 동작한다.

- poll 큐에 콜백이 있으면 **모두 실행**함 (시스템 한도까지)
- 큐가 비었을 때
  - `setImmediate`가 예약되어 있으면 → 대기 없이 **check 페이즈로 이동**
  - 없으면 → 새 I/O 이벤트가 도착하거나 **가장 가까운 타이머 만료 시각**까지 블로킹 대기
- 이 대기 덕분에 할 일이 없을 때 CPU를 낭비하지 않음

> ⚠️ 각 페이즈의 콜백 하나가 오래 걸리면 다음 페이즈는 물론 타이머까지 모두 밀린다. `setTimeout(fn, 100)`은 "**최소** 100ms 후"를 뜻할 뿐, 이벤트 루프가 바쁘면 수 초 뒤에 실행될 수도 있다. 루프를 막는 CPU 작업의 대응은 unit03을 참고할 것.

<br>

### 4. libuv 스레드 풀의 역할

운영체제가 비동기 API를 제공하지 않는 작업은 libuv가 **스레드 풀(기본 4개 스레드)**에서 대신 실행하고, 완료되면 결과를 이벤트 루프의 poll 큐로 전달한다.

| **구분**                  | **처리 방식**                    | **대표 작업**                                                     |
| ------------------------- | -------------------------------- | ----------------------------------------------------------------- |
| **커널 비동기 I/O**       | epoll / kqueue / IOCP (스레드 불필요) | TCP·UDP 소켓, HTTP 요청, 파이프, `dns.resolve*` 계열              |
| **스레드 풀 위임**        | libuv 워커 스레드 4개            | **파일 시스템(`fs.*`)**, `dns.lookup`, `crypto.pbkdf2`·`randomBytes`, `zlib` 압축 |

- 스레드 풀 크기는 환경 변수 `UV_THREADPOOL_SIZE`로 조정 가능 (최대 1024). 프로세스 시작 시점에 결정되므로 코드 실행 후에는 변경되지 않음
- 파일 I/O를 동시에 5개 이상 요청하면 4개가 끝날 때까지 나머지는 **대기**함 → 벤치마크에서 4개씩 묶여 완료되는 현상이 나타남

```javascript
process.env.UV_THREADPOOL_SIZE = 8; // 반드시 스레드 풀이 처음 사용되기 전에 설정
const crypto = require('node:crypto');

console.time('pbkdf2');
for (let i = 0; i < 8; i++) {
  crypto.pbkdf2('pw', 'salt', 100_000, 64, 'sha512', () => {
    console.timeLog('pbkdf2', `작업 ${i} 완료`); // 스레드 수만큼 동시에 끝남
  });
}
```

> 💡 `dns.lookup`은 운영체제의 `getaddrinfo`를 스레드 풀에서 호출하지만, `dns.resolve`는 자체 DNS 프로토콜 구현으로 소켓을 사용하므로 스레드 풀을 쓰지 않는다. HTTP 클라이언트가 호스트명을 많이 조회하면 스레드 풀 경합으로 파일 I/O까지 느려질 수 있다.

<br>

### 5. setTimeout(0) vs setImmediate 실행 순서

두 함수는 서로 다른 페이즈에서 실행되므로, **어느 위치에서 호출했는가**에 따라 순서가 달라진다.

```javascript
// (1) 메인 모듈에서 호출: 순서가 실행마다 달라질 수 있음
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));

// (2) I/O 콜백 안에서 호출: 항상 immediate → timeout
require('node:fs').readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});
```

- (1)은 루프 진입 시점에 1ms 타이머가 만료되었는지가 프로세스 성능에 따라 달라 **비결정적**임 (`setTimeout(fn, 0)`은 내부적으로 1ms로 보정됨)
- (2)는 I/O 콜백이 poll 페이즈에서 실행되므로, 바로 다음 check 페이즈의 `setImmediate`가 다음 루프의 timers보다 **항상 먼저** 실행됨
- 마이크로태스크(`process.nextTick`, Promise)는 이 페이즈 순서와 별개로 콜백 사이사이에 끼어든다 → unit02 참고

<br>

### 6. 이벤트 루프를 막는 흔한 함정

| **함정**                                        | **문제**                                  | **개선**                                       |
| ----------------------------------------------- | ----------------------------------------- | ---------------------------------------------- |
| **동기 API 사용** (`readFileSync`, `execSync`)  | 요청 처리 중 모든 클라이언트가 함께 대기   | 서버 기동 시점(설정 로딩)에만 동기 API 허용    |
| **대용량 `JSON.parse` / 정규식 백트래킹**       | 수백 ms 동안 루프 정지, ReDoS 위험         | 스트림 파서, 정규식 단순화, 입력 크기 제한     |
| **긴 반복문·암호화·이미지 처리**                 | CPU 바운드 작업이 루프 독점                | 워커 스레드·클러스터로 분리 (unit03)            |
| **파일을 한 번에 메모리로 로딩**                 | 메모리 폭증·GC 정지                        | 스트림으로 청크 처리 (unit05)                   |

```javascript
// 안티패턴: 요청마다 동기 파일 읽기 → 모든 요청이 직렬화됨
app.get('/report', (req, res) => {
  res.send(fs.readFileSync('report.html', 'utf8'));
});

// 개선: 비동기 API로 이벤트 루프를 즉시 반환
app.get('/report', async (req, res) => {
  res.send(await fs.promises.readFile('report.html', 'utf8'));
});
```

### 7. 정리

- Node.js는 **JS 실행 싱글 스레드 + 논블로킹 I/O + 이벤트 루프** 조합으로 적은 스레드로 많은 연결을 처리함
- 이벤트 루프 페이즈 순서: **timers → pending callbacks → idle/prepare → poll → check → close callbacks**
- poll 페이즈는 I/O 콜백을 실행하고, 할 일이 없으면 다음 타이머 시각까지 대기함
- 네트워크 I/O는 커널 비동기 API로, **파일·DNS lookup·암호화·압축**은 libuv 스레드 풀(기본 4개)로 처리됨
- `setImmediate`는 I/O 콜백 안에서 `setTimeout(0)`보다 항상 먼저 실행됨
- 이벤트 루프 안의 어떤 콜백도 오래 실행되면 안 되며, 동기 API와 CPU 작업이 대표적 병목임
- 콜백 사이에 끼어드는 마이크로태스크 순서는 **unit02**, CPU 작업 분리는 **unit03**을 참고할 것
