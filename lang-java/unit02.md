## 가비지 컬렉션

**가비지 컬렉션(Garbage Collection, GC)**은 힙에서 더 이상 참조되지 않는 객체를 JVM이 자동으로 찾아 회수하는 메커니즘이다. 개발자가 `free()`를 호출하지 않아도 되지만, GC가 **언제·어떻게·얼마나 오래 멈추는지**를 모르면 지연 시간 급증·메모리 누수 같은 문제를 해결할 수 없으므로 세대별 수집 원리와 컬렉터별 특성을 이해해야 한다.

<br>

### 1. 도달 가능성(Reachability)과 GC 루트

GC는 참조 카운트가 아니라 **도달 가능성**으로 살아 있는 객체를 판단한다. **GC 루트(GC Root)**에서 참조를 따라갈 수 있는 객체는 살아 있고, 그렇지 못한 객체는 가비지다. 이 방식은 순환 참조가 있어도 루트에서 끊겨 있으면 정상적으로 회수한다.

**GC 루트가 되는 대상**

- 실행 중인 스레드의 **스택 프레임 지역 변수와 매개변수**
- 로딩된 클래스의 **static 필드**
- JNI가 보유한 참조, 실행 중인 스레드 객체, `synchronized`로 잠금이 걸린 객체 등

```
 GC 루트(스택·static)
   │
   ├──▶ A ──▶ B ──▶ C        ← 도달 가능: 생존
   │
   └──▶ D

        E ◀──▶ F              ← 서로 참조하지만 루트에서 끊김: 회수 대상
```

> 💡 "순환 참조가 있으면 GC가 회수하지 못하는가?"는 단골 질문이다. 참조 카운팅 방식(Python의 기본 방식, Swift ARC)에서는 문제가 되지만, JVM은 **도달 가능성 기반의 추적(Tracing) GC**를 쓰므로 순환 참조 자체는 누수 원인이 아니다. Java의 메모리 누수는 "쓰지 않는 객체를 루트에서 계속 붙잡고 있는 것"이다.

<br>

### 2. 기본 수집 알고리즘

| **알고리즘**                 | **동작**                                                | **장점**                        | **단점**                                  |
| ---------------------------- | ------------------------------------------------------- | ------------------------------- | ----------------------------------------- |
| **Mark-Sweep**               | 도달 가능 객체를 표시(Mark)하고 나머지를 해제(Sweep)      | 구현 단순, 객체 이동 없음         | **단편화** 발생, 할당 시 빈 공간 탐색 비용     |
| **Mark-Compact**             | Mark 후 생존 객체를 한쪽으로 밀어 정렬(Compact)           | 단편화 해소, 순차 할당 가능       | 객체 이동·참조 갱신 비용이 커 **정지 시간 김**  |
| **Copying**                  | 생존 객체만 다른 공간으로 복사하고 원래 공간을 통째로 비움  | 생존 객체가 적을수록 매우 빠름     | 힙의 절반을 예비로 비워 두어야 함             |

실제 컬렉터는 이 알고리즘을 **영역별로 조합**한다. 생존율이 낮은 Young 영역은 Copying, 생존율이 높은 Old 영역은 Mark-Sweep 또는 Mark-Compact를 쓰는 것이 일반적이다.

<br>

### 3. 세대별 수집(Generational GC)

**약한 세대 가설** — 세대별 수집은 두 가지 경험적 관찰에 기반한다.

- **대부분의 객체는 생성 직후 금방 쓰레기가 된다** (임시 문자열, 반복문 안의 객체 등)
- **오래 살아남은 객체는 계속 살아남을 가능성이 크다** (캐시, 싱글턴, 커넥션 풀 등)

따라서 힙을 **Young**과 **Old**로 나누고, 객체가 많이 죽는 Young 영역을 자주·빠르게 수집하는 것이 효율적이다. 힙의 물리적 구분은 **unit01** 참고.

<br>

### 3-1. Minor GC — Young 영역 수집 흐름

```
 ① 새 객체는 Eden에 할당
    Eden [A B C D E]   S0 [ ]        S1 [ ]        Old [ ]

 ② Eden이 가득 참 → Minor GC. 생존 객체(B, D)만 S0으로 복사, Eden은 통째로 비움
    Eden [ ]           S0 [B1 D1]    S1 [ ]        Old [ ]        (숫자: 나이)

 ③ 다음 Minor GC. Eden과 S0의 생존 객체를 S1으로 복사 (나이 +1)
    Eden [ ]           S0 [ ]        S1 [B2 D2 F1] Old [ ]

 ④ 나이가 임계값(tenuring threshold)을 넘으면 Old로 승격(Promotion)
    Eden [ ]           S0 [ ]        S1 [F.. ]     Old [B D]
```

- Survivor 두 개 중 **항상 하나는 비어 있으며**, 이것이 Copying 알고리즘의 "예비 공간" 역할을 함
- 객체의 나이는 객체 헤더(마크 워드)에 기록되며, HotSpot의 최대 임계값은 15임 (실제 승격 시점은 JVM이 Survivor 사용률을 보고 동적으로 조정)
- Survivor에 들어가지 못할 만큼 큰 객체는 **Old 영역에 바로 할당**되기도 함

<br>

### 3-2. Major GC · Full GC와 카드 테이블

- **Major GC(Old GC)**: Old 영역이 가득 찼을 때 수행되며 Minor GC보다 훨씬 오래 걸림
- **Full GC**: Young과 Old(그리고 메타스페이스)를 전부 수집하는 것. 대부분의 컬렉터에서 **가장 긴 STW**를 유발함
- **카드 테이블(Card Table)**: Old 객체가 Young 객체를 참조하는 경우를 기록해 두는 자료구조. Minor GC 때 Old 영역 전체를 훑지 않고 표시된 카드만 확인하면 되므로 Young 수집이 빨라짐

> ⚠️ **조기 승격(Premature Promotion)**은 흔한 튜닝 함정이다. Young 영역이 너무 작거나 Minor GC가 너무 잦으면 잠깐 쓰고 버릴 객체까지 Old로 올라가고, 결국 Old 영역이 빨리 차서 Full GC가 늘어난다. Minor GC 빈도·Old 증가 속도를 GC 로그로 함께 봐야 원인을 찾을 수 있다.

<br>

### 4. Stop-The-World(STW)

**STW**는 GC가 정확한 객체 그래프를 얻기 위해 **애플리케이션 스레드를 모두 멈추는 것**이다. 스레드는 아무 지점에서 멈추는 것이 아니라 JIT가 삽입한 **세이프포인트(Safepoint)**에 도달했을 때 멈추므로, 긴 반복문 안에 세이프포인트가 없으면 모든 스레드가 그 스레드를 기다리는 "세이프포인트 지연"이 생기기도 한다.

```
 시간 ─────────────────────────────────────────────────▶
 앱 스레드: ████████│         │████████│    │██████████
 GC 스레드:         │ STW GC  │        │STW │
                    └─ 지연 시간 급증(latency spike) ─┘
```

- GC 튜닝의 목표는 결국 **처리량(Throughput)**과 **지연 시간(Latency)** 사이의 균형임
- 처리량 = 전체 실행 시간 중 GC가 아닌 애플리케이션 실행에 쓴 비율
- 지연 시간 = 한 번의 STW가 지속되는 시간 (최대값·백분위수로 관리)

<br>

### 5. 컬렉터별 특성과 선택 기준

| **컬렉터**              | **방식**                                            | **STW 특성**                          | **기본 채택**                       | **적합한 상황**                         |
| ----------------------- | --------------------------------------------------- | ------------------------------------- | ----------------------------------- | --------------------------------------- |
| **Serial**              | 단일 스레드, Young은 Copying·Old는 Mark-Compact       | 힙 크기에 비례해 길어짐                | 단일 코어·작은 힙 환경                | 클라이언트 앱, 컨테이너의 소형 서비스     |
| **Parallel**            | Serial을 다중 스레드로 병렬화                         | 여전히 전체 정지, 대신 짧아짐           | Java 8 기본값                        | 배치 처리 등 **처리량 우선**              |
| **CMS**                 | Old 영역을 앱과 **동시에(Concurrent)** Mark-Sweep      | 짧지만 단편화·동시 모드 실패 시 긴 Full GC | Java 9 deprecated, **Java 14 제거** | 레거시                                   |
| **G1**                  | 힙을 **리전(Region)**으로 나누고 가비지가 많은 리전부터 수집 | 목표 정지 시간(`-XX:MaxGCPauseMillis`) 기반 예측 | **Java 9 이후 기본값**            | 대부분의 서버 애플리케이션               |
| **ZGC**                 | 컬러드 포인터·로드 배리어로 거의 모든 작업을 동시 수행   | **밀리초 미만** 수준, 힙 크기와 무관    | Java 15 정식, **Java 21 세대별 ZGC** 추가 | 수십 GB 이상의 힙, 저지연 서비스        |
| **Shenandoah**          | ZGC와 유사한 동시 컴팩션 (OpenJDK 계열 빌드에 포함)      | 매우 짧음                              | Java 15 정식 (배포판에 따라 미포함)    | 저지연 서비스                            |

**G1의 리전 구조**

```
 힙을 동일 크기 리전으로 분할 (역할이 고정되지 않고 동적으로 바뀜)
 ┌───┬───┬───┬───┬───┬───┬───┬───┐
 │ E │ O │ E │ S │ O │ H │ O │ E │   E: Eden  S: Survivor  O: Old  H: Humongous(거대 객체)
 └───┴───┴───┴───┴───┴───┴───┴───┘
 "Garbage First": 가비지 비율이 높은 리전을 우선 수집해 목표 정지 시간 안에 최대 효과를 냄
```

> 💡 Java 17/21 기준 별도 설정이 없으면 **G1**이 선택되며(단, CPU 1개·메모리 2GB 미만 환경에서는 Serial로 떨어질 수 있음), 저지연이 최우선이면 `-XX:+UseZGC`를 검토한다. Java 21에서는 `-XX:+UseZGC -XX:+ZGenerational`로 세대별 ZGC를 활성화할 수 있고, 이후 버전에서는 세대별이 기본으로 바뀌었으므로 **사용 중인 버전의 문서를 확인**해야 한다.

### 6. 흔한 함정과 실무 팁

**메모리 누수를 만드는 코드**

```java
// 안티패턴: 정적 컬렉션에 계속 추가만 하고 제거하지 않음 → Old 영역이 계속 증가
public class SessionRegistry {
    private static final Map<String, Session> CACHE = new HashMap<>();

    public static void register(Session s) {
        CACHE.put(s.id(), s);      // 만료된 세션을 절대 지우지 않음
    }
}
```

```java
// 개선: 크기·만료 정책이 있는 캐시를 쓰거나, 불필요한 참조를 명시적으로 제거
public class SessionRegistry {
    private static final Map<String, Session> CACHE =
            new LinkedHashMap<>(16, 0.75f, true) {
                @Override
                protected boolean removeEldestEntry(Map.Entry<String, Session> eldest) {
                    return size() > 10_000;   // LRU 방식으로 상한 유지
                }
            };

    public static void register(Session s) { CACHE.put(s.id(), s); }
    public static void unregister(String id) { CACHE.remove(id); }
}
```

- `ThreadLocal`을 스레드 풀에서 쓰고 `remove()`하지 않는 경우, 리스너·콜백을 등록하고 해제하지 않는 경우도 대표적인 누수 원인임
- 자주 쓰지 않는 대형 캐시는 `WeakReference`·`SoftReference`로 감싸면 메모리 압박 시 GC가 회수할 수 있음

**GC 로그와 튜닝 순서**

```bash
java -Xlog:gc*:file=gc.log:time,uptime -Xms2g -Xmx2g -XX:+UseG1GC -jar app.jar   # Java 9+ 통합 로깅
```

- ① 기본 컬렉터로 **GC 로그를 먼저 수집**하고, Full GC 빈도·최대 정지 시간·Old 증가 추세를 확인함
- ② 누수가 의심되면 옵션 튜닝보다 **힙 덤프로 원인 객체를 찾는 것**이 먼저임
- ③ 그다음 힙 크기(`-Xms`=`-Xmx`로 고정해 리사이징 비용 제거), 목표 정지 시간, 컬렉터 순으로 조정함

❗️**`System.gc()` 호출 금지**: 명시적 GC 호출은 대부분의 컬렉터에서 **Full GC를 강제**해 긴 STW를 일으킨다. 실무에서는 `-XX:+DisableExplicitGC`로 아예 무시하도록 설정하는 경우도 많다.

### 7. 정리

| **항목**             | **핵심**                                                                                       |
| -------------------- | ---------------------------------------------------------------------------------------------- |
| **생존 판단 기준**    | GC 루트로부터의 **도달 가능성**. 순환 참조는 누수 원인이 아님                                     |
| **세대별 수집 근거**  | 대부분 객체는 금방 죽고, 오래 산 객체는 계속 산다는 **약한 세대 가설**                              |
| **Minor vs Full GC** | Minor는 Young만 Copying으로 빠르게, Full은 전체 영역을 수집하며 **가장 긴 STW**                      |
| **STW**              | 정확한 객체 그래프를 위해 앱 스레드를 세이프포인트에서 정지. 튜닝은 처리량 vs 지연 시간의 균형        |
| **컬렉터 선택**       | 기본 **G1**, 처리량 우선이면 Parallel, 대용량 힙·저지연이면 **ZGC**(Java 21 세대별 ZGC)             |
| **누수 예방**         | static 컬렉션·`ThreadLocal`·리스너의 참조 해제, 상한 있는 캐시, `System.gc()` 금지                  |

- 힙·메타스페이스 등 영역 구조는 **unit01**, 스레드 풀과 `ThreadLocal` 관리는 **unit09**를 함께 볼 것
