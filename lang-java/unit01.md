## JVM 메모리 구조

Java 프로그램은 운영체제가 아니라 **JVM(Java Virtual Machine)** 위에서 실행되며, JVM은 실행에 필요한 메모리를 **힙·스택·메타스페이스** 등 역할별 영역으로 나누어 관리한다. 어떤 데이터가 어느 영역에 놓이고 누가 공유하는지를 알아야 `OutOfMemoryError`·`StackOverflowError`의 원인을 진단하고, 가비지 컬렉션(unit02)과 동시성(unit08)을 제대로 이해할 수 있다.

<br>

### 1. JVM의 전체 구조

JVM은 크게 **클래스 로더 서브시스템**, **런타임 데이터 영역**, **실행 엔진** 세 부분으로 나뉜다. `.java` 소스는 컴파일러(`javac`)에 의해 플랫폼 독립적인 **바이트코드(`.class`)**로 변환되고, JVM이 이를 로딩·검증한 뒤 인터프리터와 JIT 컴파일러로 실행한다.

```
 .java ──javac──▶ .class (바이트코드)
                     │
      ┌──────────────▼──────────────┐
      │      클래스 로더 서브시스템     │  로딩 → 링킹 → 초기화
      └──────────────┬──────────────┘
      ┌──────────────▼──────────────────────────────────┐
      │            런타임 데이터 영역                       │
      │  [메서드 영역(메타스페이스)]  [힙]     ← 모든 스레드 공유  │
      │  [JVM 스택] [PC 레지스터] [네이티브 스택] ← 스레드별   │
      └──────────────┬──────────────────────────────────┘
      ┌──────────────▼──────────────┐
      │  실행 엔진: 인터프리터 + JIT + GC │
      └─────────────────────────────┘
```

> 💡 "Java는 느리다"는 인식은 인터프리터만 있던 초기 JVM 이야기다. 현재 HotSpot JVM은 자주 실행되는 메서드(핫스팟)를 **JIT(Just-In-Time) 컴파일러**가 네이티브 코드로 변환해 실행하므로, 워밍업 이후에는 네이티브 언어에 근접한 성능을 낸다.

<br>

### 2. 런타임 데이터 영역

런타임 데이터 영역은 **모든 스레드가 공유하는 영역**과 **스레드마다 독립적으로 생성되는 영역**으로 나뉜다. 이 구분이 곧 "어떤 데이터에 동기화가 필요한가"의 기준이 된다.

| **영역**                 | **공유 범위** | **저장 내용**                                        | **관련 오류**                        |
| ------------------------ | ------------- | ---------------------------------------------------- | ------------------------------------ |
| **힙(Heap)**             | 모든 스레드   | `new`로 생성한 **객체와 배열**, 문자열 상수 풀         | `OutOfMemoryError: Java heap space`  |
| **메서드 영역(메타스페이스)** | 모든 스레드   | 클래스 메타데이터, 상수 풀, static 변수 참조, 메서드 바이트코드 | `OutOfMemoryError: Metaspace`        |
| **JVM 스택**             | 스레드별      | 메서드 호출마다 쌓이는 **스택 프레임**(지역 변수·피연산자 스택) | `StackOverflowError`                 |
| **PC 레지스터**          | 스레드별      | 현재 실행 중인 바이트코드 명령의 주소                  | -                                    |
| **네이티브 메서드 스택**  | 스레드별      | JNI로 호출된 C/C++ 코드의 스택                        | -                                    |

<br>

### 2-1. 힙(Heap)

힙은 JVM이 시작될 때 생성되며, `new` 키워드로 만들어지는 **모든 객체 인스턴스와 배열**이 저장되는 영역이다. 가비지 컬렉터의 관리 대상이며, 세대별 수집을 위해 내부가 **Young 영역(Eden, Survivor 0/1)**과 **Old 영역**으로 나뉜다.

```
 힙(Heap)
 ┌───────────────────────────────────┬──────────────────────┐
 │           Young Generation        │    Old Generation    │
 │  ┌────────┬────────┬────────┐     │                      │
 │  │  Eden  │   S0   │   S1   │     │  오래 살아남은 객체    │
 │  └────────┴────────┴────────┘     │                      │
 └───────────────────────────────────┴──────────────────────┘
   새 객체는 Eden에 생성 → 살아남으면 S0/S1 → 임계 횟수 초과 시 Old로 승격
```

- 힙 크기는 `-Xms`(초기)·`-Xmx`(최대) 옵션으로 조정하며, 기본 최대 크기는 물리 메모리의 1/4 정도로 잡히지만 **버전·환경에 따라 다를 수 있음**
- Java 7부터 **문자열 상수 풀(String Constant Pool)**이 PermGen에서 힙으로 옮겨져 GC 대상이 됨
- 세대별 수집 과정과 컬렉터 종류는 **unit02(가비지 컬렉션)** 참고

<br>

### 2-2. JVM 스택(Stack)과 스택 프레임

JVM 스택은 **스레드가 생성될 때 함께 만들어지는** 영역으로, 메서드가 호출될 때마다 **스택 프레임(Stack Frame)**이 push되고 메서드가 끝나면 pop된다. 프레임에는 지역 변수 배열, 피연산자 스택, 현재 클래스의 상수 풀 참조가 담긴다.

```java
public class StackDemo {
    static int depth = 0;

    static void recurse() {
        depth++;
        recurse();          // 프레임이 계속 쌓임
    }

    public static void main(String[] args) {
        try {
            recurse();
        } catch (StackOverflowError e) {
            System.out.println("스택 깊이: " + depth); // 환경마다 수만 단위로 다름
        }
    }
}
```

- 스택은 스레드마다 독립적이므로 **지역 변수는 별도 동기화 없이 스레드 안전**함
- 기본 스택 크기는 64비트 환경에서 대개 1MB 정도이며 `-Xss` 옵션으로 조정함 (플랫폼별 기본값은 다를 수 있음)
- 기본 타입(`int`, `double` 등) 지역 변수는 값 자체가 스택에, 객체 지역 변수는 **참조만 스택에** 저장되고 실제 객체는 힙에 존재함

> ⚠️ "지역 변수 객체는 스택에 저장된다"는 흔한 오답이다. `String s = new String("a");`에서 스택에 있는 것은 참조 `s`뿐이고, 문자열 객체 자체는 힙에 있다. 다만 JIT 컴파일러의 **탈출 분석(Escape Analysis)**이 메서드 밖으로 나가지 않는 객체를 스칼라로 치환해 힙 할당을 생략하는 최적화가 있어, "항상 힙"이라고 단정하기보다 "명세상 힙이며 JIT 최적화로 생략될 수 있다"고 답하는 것이 정확하다.

<br>

### 2-3. 메서드 영역과 메타스페이스(Metaspace)

메서드 영역은 JVM 명세상의 논리적 영역으로, **클래스 구조 정보(필드·메서드 메타데이터), 런타임 상수 풀, 메서드 바이트코드**를 저장한다. HotSpot JVM은 Java 7까지 이를 **PermGen(Permanent Generation)**이라는 힙의 일부로 구현했으나, **Java 8부터 네이티브 메모리를 사용하는 메타스페이스로 교체**했다.

| **항목**          | **PermGen (Java 7 이하)**                     | **Metaspace (Java 8 이상)**                          |
| ----------------- | --------------------------------------------- | ---------------------------------------------------- |
| **위치**          | JVM 힙 내부                                    | **네이티브(OS) 메모리**                                |
| **크기 제한**     | `-XX:MaxPermSize`로 고정, 기본값이 작아 자주 초과 | 기본적으로 **필요에 따라 자동 확장**, `-XX:MaxMetaspaceSize`로 상한 지정 가능 |
| **대표 오류**     | `OutOfMemoryError: PermGen space`             | `OutOfMemoryError: Metaspace`                        |
| **static 변수**   | PermGen에 저장                                 | **힙**의 클래스 객체(`java.lang.Class`)와 함께 저장    |
| **문자열 상수 풀** | Java 6까지 PermGen, Java 7부터 힙               | 힙                                                    |

> 💡 PermGen이 사라진 이유는 크기를 미리 고정해야 해서 동적으로 클래스를 많이 생성하는 애플리케이션(Spring 프록시, 리플렉션, 핫 디플로이 등)에서 `PermGen space` 오류가 빈발했기 때문이다. 메타스페이스는 OS 메모리를 쓰므로 이 문제가 완화되었지만, 클래스 로더 누수가 있으면 **네이티브 메모리를 계속 잠식**하므로 상한을 두고 모니터링해야 한다.

<br>

### 3. 클래스 로딩 과정

클래스는 JVM 시작 시 한꺼번에 올라가는 것이 아니라 **처음 사용되는 시점에 지연(lazy) 로딩**된다. 로딩은 **로딩 → 링킹 → 초기화** 세 단계로 진행된다.

```
 로딩(Loading)      링킹(Linking)                          초기화(Initialization)
 ┌──────────┐   ┌──────────┬──────────┬──────────┐   ┌────────────────────┐
 │ .class를  │──▶│  검증     │  준비     │  분석     │──▶│ static 초기화 블록과  │
 │ 읽어 메서드 │   │(Verify)  │(Prepare) │(Resolve) │   │ static 변수 대입 실행 │
 │ 영역에 배치 │   │ 바이트코드 │ static를 │ 심볼릭 참조│   │ (<clinit> 메서드)    │
 └──────────┘   │ 형식 검사  │ 기본값으로 │ → 실제 참조│   └────────────────────┘
                └──────────┴──────────┴──────────┘
```

- **로딩**: 클래스 로더가 바이너리 `.class`를 읽어 메서드 영역에 배치하고, 힙에 `java.lang.Class` 객체를 생성함
- **검증**: 바이트코드가 JVM 명세를 위반하지 않는지 확인함 (스택 오버플로 유발 코드, 잘못된 타입 변환 등 차단)
- **준비**: static 변수 메모리를 할당하고 **기본값(0, null, false)**으로 초기화함
- **분석**: 상수 풀의 심볼릭 참조를 실제 메모리 참조로 바꿈 (지연될 수 있음)
- **초기화**: 개발자가 작성한 static 초기화 코드가 실행되어 **실제 값**이 대입됨

```java
public class InitOrder {
    static int value = compute();          // 초기화 단계에서 실행
    static { System.out.println("static 블록 실행"); }

    static int compute() {
        System.out.println("value 계산");
        return 42;
    }

    public static void main(String[] args) {
        System.out.println("main 시작");   // 출력 순서: value 계산 → static 블록 실행 → main 시작
    }
}
```

❗️**초기화 트리거**: 클래스의 인스턴스 생성, static 메서드 호출, static 필드 접근(컴파일 타임 상수 제외), 리플렉션, 하위 클래스 초기화가 초기화를 일으킨다. `static final int X = 10;`처럼 컴파일 시점에 값이 확정되는 상수는 클래스 초기화 없이 상수 풀에서 직접 읽어 온다.

<br>

### 4. 클래스 로더 계층과 부모 위임 모델

클래스 로더는 세 계층으로 구성되며, 클래스 로딩 요청을 받으면 **먼저 부모에게 위임하고 부모가 찾지 못할 때만 자신이 로드**한다. 이를 **부모 위임 모델(Parent Delegation Model)**이라고 한다.

| **클래스 로더**                  | **로드 대상**                                     | **비고**                                        |
| -------------------------------- | ------------------------------------------------- | ----------------------------------------------- |
| **부트스트랩(Bootstrap)**        | `java.base` 모듈의 핵심 클래스(`java.lang.*` 등)   | 네이티브 코드로 구현, Java에서 `null`로 표현됨    |
| **플랫폼(Platform)**             | JDK의 나머지 표준 모듈(`java.sql` 등)              | Java 9 이전에는 **확장(Extension) 로더**였음      |
| **애플리케이션(Application)**    | 클래스패스·모듈패스의 사용자 클래스                 | 기본 시스템 클래스 로더                          |

```
 요청: "com.example.User 로드"
   Application ──위임──▶ Platform ──위임──▶ Bootstrap
        ▲                  ▲                   │ 없음
        │ 없음 → 직접 로드   └──── 없음 ──────────┘
        └── 클래스패스에서 발견 → 로드
```

- 부모 위임 덕분에 사용자가 `java.lang.String`이라는 클래스를 직접 만들어도 부트스트랩 로더의 원본이 먼저 로드되어 **핵심 클래스 위조가 차단**됨
- 같은 클래스라도 **다른 클래스 로더가 로드하면 JVM은 다른 타입으로 취급**함 → `ClassCastException`이 발생하는 원인이 되기도 함
- 톰캣 같은 웹 컨테이너는 웹앱마다 별도 로더를 두어 라이브러리 버전을 격리하며, 이 경우 위임 순서를 일부 뒤집기도 함

> ⚠️ 클래스 로더 누수(Class Loader Leak)는 메타스페이스 `OutOfMemoryError`의 대표 원인이다. 웹앱을 재배포할 때 이전 로더가 static 필드·스레드·`ThreadLocal`에 의해 참조로 붙잡혀 있으면, 그 로더가 로드한 모든 클래스 메타데이터가 해제되지 않고 누적된다.

<br>

### 5. 자주 만나는 메모리 오류와 진단

| **오류**                                | **발생 영역**  | **흔한 원인**                                       | **1차 대응**                                   |
| --------------------------------------- | -------------- | --------------------------------------------------- | ---------------------------------------------- |
| **`OutOfMemoryError: Java heap space`** | 힙             | 객체 누수(캐시·컬렉션에 계속 추가), 과도한 대용량 로딩 | 힙 덤프 분석(`-XX:+HeapDumpOnOutOfMemoryError`), `-Xmx` 조정 |
| **`OutOfMemoryError: Metaspace`**       | 메타스페이스   | 클래스 로더 누수, 동적 프록시·바이트코드 생성 과다     | 로더 누수 제거, `-XX:MaxMetaspaceSize` 점검      |
| **`StackOverflowError`**                | JVM 스택       | 종료 조건 없는 재귀, 지나치게 깊은 호출 체인          | 재귀 → 반복 전환, `-Xss` 조정                   |
| **`OutOfMemoryError: unable to create native thread`** | 네이티브 | 스레드 과다 생성(스레드당 스택 메모리 소모)            | 스레드 풀 사용(unit09), `-Xss` 축소             |

- `jcmd <pid> GC.heap_info`, `jmap`, `jstat`으로 영역별 사용량을 확인하고, 힙 덤프는 Eclipse MAT·VisualVM으로 분석함
- Java 21에서 정식 도입된 **가상 스레드(Virtual Thread)**는 스택을 힙에 작은 단위로 저장하므로, 플랫폼 스레드처럼 스레드당 고정 스택을 예약하지 않아 수십만 개를 만들어도 네이티브 스레드 한계에 걸리지 않음

<br>

### 6. 면접·실무 체크포인트

| **질문**                                     | **핵심 답변**                                                                                   |
| -------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| **힙과 스택의 차이는?**                       | 힙은 모든 스레드가 공유하며 객체가 저장되고 GC 대상. 스택은 스레드별로 독립적이며 프레임 단위로 자동 해제 |
| **PermGen이 메타스페이스로 바뀐 이유는?**       | 고정 크기 힙 영역이라 `PermGen space` 오류가 잦았음. Java 8부터 **네이티브 메모리**를 써 자동 확장   |
| **static 변수는 어디에 저장되는가?**           | Java 8 이후 HotSpot 기준 **힙**의 `Class` 객체와 함께 저장됨. 메타데이터는 메타스페이스           |
| **클래스는 언제 로딩되는가?**                  | 처음 사용되는 시점에 지연 로딩. 로딩 → 링킹(검증·준비·분석) → 초기화 순서                         |
| **부모 위임 모델의 목적은?**                   | 핵심 클래스의 **중복 로딩 방지와 보안**(사용자 정의 `java.lang.String` 차단)                      |
| **`StackOverflowError`와 `OutOfMemoryError`의 차이는?** | 전자는 한 스레드의 스택 한계, 후자는 힙·메타스페이스·네이티브 메모리 부족. 둘 다 `Error`라 잡아서 복구하지 않는 것이 원칙 |

- 객체 생명주기와 GC 동작은 **unit02**, 스레드 간 메모리 가시성 문제는 **unit08**에서 이어서 다룸
