## 로드밸런싱·프록시·CDN

서비스 규모가 커지면 서버 한 대로는 트래픽을 감당할 수 없다. 트래픽을 분산하는 **로드밸런싱**, 중간에서 요청을 대신 처리하는 **프록시**, 콘텐츠를 전 세계에 캐싱하는 **CDN**을 다룬다.

<br>

### 1. 단일 서버의 한계와 수평 확장

서버 한 대의 처리 능력에는 한계가 있으며, 장애가 나면 서비스 전체가 중단된다. 해결 방법은 두 가지이다.

- **수직 확장**(Scale-Up): 서버 한 대의 사양(CPU, 메모리)을 높임 — 한계와 비용 문제 존재
- **수평 확장**(Scale-Out): 서버 **대수를 늘림** — 유연하지만 트래픽을 **여러 서버에 나눠주는 장치**가 필요함

이때 트래픽을 분산해 주는 장치가 **로드밸런서**(Load Balancer)이다.

<br>

### 2. 로드밸런서 동작

```
                          ┌──────────────┐
클라이언트들               │              │ ──► [서버 1]
  🖥 🖥 🖥  ──────────────► │  로드밸런서   │ ──► [서버 2]
  (하나의 주소로 접속)      │              │ ──► [서버 3]
                          └──────────────┘
                           요청을 규칙에 따라
                           여러 서버에 분산
```

클라이언트는 로드밸런서의 주소 하나만 바라보고, 로드밸런서가 뒤에 있는 여러 서버로 요청을 나눠 보낸다. 특정 서버에 장애가 나도 나머지 서버로 서비스를 계속할 수 있어 **가용성**도 높아진다.

<br>

### 2-1. L4 vs L7 로드밸런서

| **구분**        | **L4 로드밸런서**                     | **L7 로드밸런서**                                  |
| --------------- | ------------------------------------- | -------------------------------------------------- |
| **동작 계층**   | **전송 계층**(TCP/UDP)                | **응용 계층**(HTTP/HTTPS)                          |
| **분산 기준**   | **IP 주소 + 포트 번호**               | **URL 경로, 헤더, 쿠키** 등 메시지 내용            |
| **기능**        | 단순 분산 — 빠르고 저렴함             | 경로 기반 라우팅(`/api`→A서버, `/img`→B서버), 콘텐츠 기반 제어 |

<br>

### 2-2. 분산 알고리즘

| **알고리즘**                     | **방식**                                        | **특징**                            |
| -------------------------------- | ----------------------------------------------- | ----------------------------------- |
| **라운드 로빈**(Round Robin)     | 서버에 **순서대로** 돌아가며 배분               | 단순하고 균등, 서버 성능 차이 무시  |
| **최소 연결**(Least Connections) | **연결 수가 가장 적은** 서버에 배분             | 요청 처리 시간이 제각각일 때 유리   |
| **IP 해시**(IP Hash)             | 클라이언트 **IP를 해시**해 항상 같은 서버로 배분 | 같은 사용자를 같은 서버에 고정 가능 |

<br>

### 2-3. 헬스 체크

로드밸런서는 주기적으로 각 서버에 요청을 보내 정상 동작 여부를 확인하는 **헬스 체크**(Health Check)를 수행한다. 응답이 없거나 오류를 반환하는 서버는 분산 대상에서 **자동으로 제외**하고, 복구되면 다시 편입시킨다.

<br>

### 3. 포워드 프록시 vs 리버스 프록시

**프록시**(Proxy)는 클라이언트와 서버 사이에서 요청을 대신 전달하는 중계 서버이다. **누구를 대신하는지**에 따라 두 종류로 나뉜다.

```
[포워드 프록시] — 클라이언트 쪽에 위치, 클라이언트를 대신함

클라이언트 ──► 포워드 프록시 ──► 인터넷 ──► 서버
(내부망)       (출구 역할)

[리버스 프록시] — 서버 쪽에 위치, 서버를 대신함

클라이언트 ──► 인터넷 ──► 리버스 프록시 ──► 서버 1, 2, 3
                          (입구 역할)      (내부에 숨겨짐)
```

| **구분**        | **포워드 프록시**                         | **리버스 프록시**                             |
| --------------- | ----------------------------------------- | --------------------------------------------- |
| **위치**        | **클라이언트 앞**                         | **서버 앞**                                   |
| **숨기는 대상** | 클라이언트 (서버는 프록시만 봄)           | 서버 (클라이언트는 프록시만 봄)               |
| **주요 용도**   | 사내망 접근 통제, 우회 접속, 캐싱         | 로드밸런싱, SSL 종료, 캐싱, 보안(서버 은닉)   |

> 💡 **Nginx**는 리버스 프록시 겸 L7 로드밸런서로 가장 널리 쓰이는 소프트웨어이다. 아래처럼 몇 줄의 설정으로 트래픽 분산을 구성할 수 있다.

```nginx
upstream backend {
    least_conn;
    server 10.0.0.1:8080;
    server 10.0.0.2:8080;
}

server {
    listen 80;
    location / {
        proxy_pass http://backend;
    }
}
```

### 4. CDN(Content Delivery Network)

**CDN**은 전 세계에 분산 배치된 **엣지 서버**(Edge Server)에 콘텐츠를 캐싱해, 사용자와 **물리적으로 가까운 곳**에서 콘텐츠를 전달하는 네트워크이다.

- **오리진 서버**(Origin Server): 원본 콘텐츠를 가진 서비스의 본래 서버
- **엣지 서버**: 오리진의 콘텐츠 사본을 캐싱해 두고 인근 사용자에게 대신 응답하는 서버

```
                 ┌─ 엣지 서버(서울) ◄── 한국 사용자
오리진 서버 ─────┼─ 엣지 서버(도쿄) ◄── 일본 사용자
(미국, 원본)     └─ 엣지 서버(파리) ◄── 유럽 사용자
                    (원본의 사본을 캐싱)
```

<br>

### 4-1. CDN 동작 흐름

1. 사용자가 콘텐츠를 요청하면 DNS가 **가장 가까운 엣지 서버**로 안내함
2. 엣지 서버에 캐시가 있으면(**캐시 히트**) 즉시 응답함 — 오리진까지 갈 필요 없음
3. 캐시가 없으면(**캐시 미스**) 엣지 서버가 오리진 서버에서 콘텐츠를 받아와 응답하고, 사본을 캐싱함
4. 이후 같은 지역의 요청은 캐시에서 바로 처리됨

> ⚠️ CDN은 이미지·영상·JS·CSS 같은 **정적 콘텐츠**에 효과가 크다. 사용자마다 내용이 달라지는 동적 응답은 캐싱이 어려우므로 캐시 정책(TTL, 무효화)을 신중히 설계해야 한다.

<br>

### 5. 세 기술의 관계 정리

셋 모두 "클라이언트와 서버 사이에 중간 계층을 두어" 성능·확장성·보안을 개선한다는 공통점이 있다.

| **기술**          | **핵심 목적**                     | **위치**                  | **비고**                                  |
| ----------------- | --------------------------------- | ------------------------- | ----------------------------------------- |
| **로드밸런서**    | 트래픽을 여러 서버에 **분산**     | 서버군 바로 앞            | 리버스 프록시의 한 형태로 볼 수 있음      |
| **리버스 프록시** | 서버를 **대신·은닉**, 부가 기능   | 서버 앞                   | 로드밸런싱·캐싱·SSL 종료를 겸함           |
| **CDN**           | 콘텐츠를 **가까운 곳에서 전달**   | 전 세계 엣지(사용자 근처) | 지리적으로 분산된 거대한 캐싱 프록시망    |

실제 대규모 서비스에서는 **사용자 → CDN → 로드밸런서(리버스 프록시) → 서버** 순으로 세 기술이 함께 사용된다.
