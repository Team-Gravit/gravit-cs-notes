## ARP와 DHCP

**ARP**는 IP 주소로 상대방의 **MAC 주소**를 알아내는 프로토콜이고, **DHCP**는 호스트에게 **IP 주소 등 네트워크 설정을 자동으로 할당**하는 프로토콜이다. 두 프로토콜은 통신을 시작하기 위한 **주소 준비 단계**를 담당한다.

<br>

### 1. IP 주소와 MAC 주소가 모두 필요한 이유

네트워크 통신에는 두 종류의 주소가 함께 사용된다.

- **IP 주소**: 네트워크 계층의 **논리 주소**. 최종 목적지를 식별하고 라우팅 경로를 결정함
- **MAC 주소**: 데이터 링크 계층의 **물리 주소**. 같은 네트워크(LAN) 안에서 프레임을 전달할 **바로 다음 장비**를 식별함

IP 주소만으로는 실제 전송이 불가능하다. 패킷은 항상 **프레임에 캡슐화**되어 전달되는데, 프레임 헤더에는 **다음 홉의 MAC 주소**가 필요하기 때문이다. 즉 IP 주소가 **최종 목적지**를 가리킨다면, MAC 주소는 **한 구간(홉)씩 실제로 전달할 상대**를 가리킨다.

> 💡 목적지가 다른 네트워크에 있으면 프레임의 목적지 MAC 주소는 상대 호스트가 아니라 **기본 게이트웨이(라우터)의 MAC 주소**가 된다. 라우터를 거칠 때마다 IP 주소는 유지되고 MAC 주소만 홉 단위로 바뀐다.

<br>

### 2. ARP(Address Resolution Protocol) 동작 과정

**ARP**는 "이 IP 주소를 쓰는 장비의 MAC 주소는 무엇인가?"를 묻는 프로토콜이다. **브로드캐스트 요청**과 **유니캐스트 응답**의 두 단계로 동작한다.

1. **ARP 요청(Request)**: 목적지 MAC을 모르는 호스트가 네트워크 전체에 **브로드캐스트**(FF:FF:FF:FF:FF:FF)로 질문함
2. **ARP 응답(Reply)**: 해당 IP를 가진 호스트만 자신의 MAC 주소를 담아 **유니캐스트**로 응답함

```
호스트 A (192.168.0.10)                          호스트 B (192.168.0.20)
       │                                                │
       │── ARP 요청 (브로드캐스트) ────────────────────▶│  ← LAN의 모든 호스트가 수신
       │   "192.168.0.20의 MAC 주소를 알려달라"          │     (B 외에는 무시)
       │                                                │
       │◀─────────────────── ARP 응답 (유니캐스트) ──────│
       │        "나의 MAC 주소는 bb:bb:bb:bb:bb:bb"      │
       │                                                │
       │── 이후 데이터 프레임 전송 (목적지 MAC 확보) ──▶│
```

<br>

### 3. ARP 캐시(테이블)

ARP 요청·응답으로 알아낸 IP-MAC 매핑은 **ARP 캐시**(ARP Table)에 일정 시간 저장된다. 같은 상대와 통신할 때마다 브로드캐스트를 반복하면 네트워크에 부담이 되므로, 캐시에 항목이 있으면 ARP 과정을 생략한다. 캐시 항목은 일정 시간이 지나면 만료되어 삭제된다.

```bash
arp -a
# ? (192.168.0.1) at aa:aa:aa:aa:aa:aa on en0 ifscope [ethernet]
# ? (192.168.0.20) at bb:bb:bb:bb:bb:bb on en0 ifscope [ethernet]
```

<br>

**GARP(Gratuitous ARP)**: 자기 자신의 IP 주소에 대해 보내는 특수한 ARP 요청이다. 응답을 기대하는 것이 아니라, **IP 주소 충돌 감지**와 **주변 장비의 ARP 캐시 갱신**(장비 교체·장애 조치 시) 목적으로 사용된다.

> ⚠️ **ARP 스푸핑**(ARP Spoofing)은 공격자가 위조된 ARP 응답을 보내 피해자의 ARP 캐시에 **자신의 MAC 주소를 게이트웨이인 것처럼 등록**시키는 공격이다. ARP에는 응답을 검증하는 인증 절차가 없어, 피해자의 트래픽이 공격자를 경유하는 **중간자 공격**(MITM)으로 이어질 수 있다. 정적 ARP 항목 설정, 동적 ARP 검사(DAI) 등으로 방어한다.

<br>

### 4. DHCP의 필요성

호스트가 통신하려면 **IP 주소, 서브넷 마스크, 기본 게이트웨이, DNS 서버** 설정이 필요하다. 이를 수동으로 설정하면 다음 문제가 생긴다.

- **설정 실수**: 오타나 잘못된 게이트웨이 입력으로 통신 장애 발생 가능
- **IP 충돌**: 같은 주소를 두 장비에 입력하면 네트워크 오류 발생
- **관리 부담**: 장비 수가 많아질수록 할당·회수 관리가 어려움
- **이동성 부족**: 노트북·스마트폰이 네트워크를 옮길 때마다 재설정 필요

**DHCP**(Dynamic Host Configuration Protocol)는 이 설정 전체를 서버가 **자동으로 임대(Lease)** 해 주는 프로토콜이다. UDP 기반으로 동작하며 서버는 **67번**, 클라이언트는 **68번** 포트를 사용한다.

<br>

### 5. DHCP DORA 4단계

IP 주소가 없는 클라이언트는 브로드캐스트로 서버를 찾고, **Discover → Offer → Request → Ack**의 4단계를 거쳐 주소를 임대받는다. 각 단계의 앞 글자를 따 **DORA**라고 부른다.

```
클라이언트 (IP 없음)                              DHCP 서버
       │                                              │
       │── 1. DHCP Discover (브로드캐스트) ──────────▶│
       │      "DHCP 서버가 있는가? IP가 필요하다"       │
       │                                              │
       │◀───────────── 2. DHCP Offer ─────────────────│
       │      "192.168.0.50을 제안한다"                │
       │      (서브넷 마스크·게이트웨이·임대 기간 포함) │
       │                                              │
       │── 3. DHCP Request (브로드캐스트) ───────────▶│
       │      "192.168.0.50을 사용하겠다"              │
       │      (여러 서버 중 선택했음을 전체에 알림)     │
       │                                              │
       │◀───────────── 4. DHCP Ack ───────────────────│
       │      "할당 확정. 임대 기간 동안 사용하라"      │
       │                                              │
   설정 적용 후 통신 시작
```

1. **Discover**: 클라이언트가 아직 IP가 없으므로 브로드캐스트로 DHCP 서버를 탐색함
2. **Offer**: 서버가 사용 가능한 IP 주소와 네트워크 설정, 임대 기간을 제안함
3. **Request**: 클라이언트가 제안받은 주소의 사용을 공식 요청함. 서버가 여러 대일 수 있으므로 브로드캐스트로 보내 선택 결과를 알림
4. **Ack**: 서버가 할당을 확정하고 클라이언트는 설정을 적용함

> 💡 DORA 4단계는 정보처리기사와 기술 면접에서 모두 빈출이다. "왜 처음 두 단계가 브로드캐스트인가?"라는 질문에는 **클라이언트가 아직 IP 주소가 없고 서버 위치도 모르기 때문**이라고 답하면 된다.

<br>

### 6. 임대(Lease)와 갱신

DHCP는 주소를 영구히 주는 것이 아니라 **임대 기간**(Lease Time) 동안 빌려준다. 기간이 끝나면 주소는 회수되어 다른 장비에 재할당될 수 있다.

- **갱신(Renewal)**: 임대 기간의 **50%(T1)** 가 지나면 클라이언트는 기존 서버에 유니캐스트 Request를 보내 임대 연장을 시도함
- **재바인딩(Rebinding)**: **87.5%(T2)** 시점까지 응답이 없으면 브로드캐스트로 아무 서버에나 연장을 요청함
- **만료**: 갱신에 실패하면 주소 사용을 중단하고 처음부터 DORA 과정을 다시 수행함

<br>

### 7. ARP vs DHCP 역할 비교

| 구분          | ARP                                | DHCP                                     |
| ------------- | ---------------------------------- | ---------------------------------------- |
| **목적**      | IP 주소 → **MAC 주소** 변환        | **IP 주소 등 네트워크 설정** 자동 할당   |
| **동작 시점** | 같은 LAN의 상대에게 **전송 직전**  | 네트워크에 **접속(부팅)할 때**           |
| **동작 방식** | 브로드캐스트 요청 → 유니캐스트 응답 | DORA 4단계 (Discover-Offer-Request-Ack) |
| **관련 계층** | 네트워크 계층과 데이터 링크 계층 사이 | 응용 계층 (UDP 67/68 사용)             |
| **결과 저장** | ARP 캐시 (짧은 만료 시간)          | 임대(Lease) 정보 (임대 기간 단위)        |

❗️**선후 관계**: DHCP로 IP 주소를 받은 뒤에도 실제 프레임을 보내려면 ARP로 상대(또는 게이트웨이)의 MAC 주소를 알아내야 한다. 즉 **DHCP가 먼저 주소를 마련하고, ARP가 전송 직전에 상대를 찾는다**.
