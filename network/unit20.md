## 쿠키·세션·토큰

**HTTP**는 상태를 저장하지 않는 프로토콜이므로, 로그인 상태처럼 요청 간에 유지해야 하는 정보는 별도의 기술로 관리해야 한다. 이를 해결하는 대표적인 세 가지 방식인 **쿠키**, **세션**, **토큰**을 다룬다.

<br>

### 1. HTTP 무상태성과 상태 유지의 필요성

**HTTP**는 **무상태성**(Stateless)을 갖는다. 서버는 이전 요청의 정보를 기억하지 않으며, 모든 요청을 독립적으로 처리한다.

- **장점**: 서버가 상태를 저장하지 않으므로 구조가 단순하고 확장에 유리함
- **문제**: 로그인, 장바구니처럼 **사용자별 상태를 유지해야 하는 기능**을 구현할 수 없음

이 문제를 해결하기 위해 클라이언트 또는 서버에 상태 정보를 저장하는 **쿠키·세션·토큰** 방식이 등장했다.

<br>

### 2. 쿠키(Cookie)

**쿠키**는 서버가 클라이언트(브라우저)에 저장하도록 지시하는 **작은 데이터 조각**이다. 브라우저는 저장한 쿠키를 같은 서버로 보내는 모든 요청에 자동으로 포함시킨다.

```
클라이언트                                  서버
    │                                        │
    │ ──── ① 로그인 요청 ──────────────────► │
    │                                        │
    │ ◄──── ② 응답 + Set-Cookie 헤더 ─────── │
    │       (브라우저가 쿠키 저장)            │
    │                                        │
    │ ──── ③ 이후 요청 + Cookie 헤더 ──────► │
    │       (쿠키 자동 첨부)                  │
    │                                        │
    │ ◄──── ④ 사용자를 식별한 응답 ────────── │
```

```http
HTTP/1.1 200 OK
Set-Cookie: sessionId=abc123; Max-Age=3600; HttpOnly; Secure; SameSite=Lax

GET /mypage HTTP/1.1
Host: www.example.com
Cookie: sessionId=abc123
```

<br>

### 2-1. 쿠키 주요 속성

| **속성**            | **설명**                                                                 |
| ------------------- | ------------------------------------------------------------------------ |
| **Expires/Max-Age** | 쿠키 만료 시점 지정 — 없으면 브라우저 종료 시 삭제되는 **세션 쿠키**가 됨 |
| **HttpOnly**        | 자바스크립트에서 쿠키 접근 차단 — **XSS 공격으로 인한 탈취 방어**         |
| **Secure**          | **HTTPS 연결에서만** 쿠키 전송                                            |
| **SameSite**        | 다른 사이트에서 시작된 요청에 쿠키 전송 제한 — **CSRF 공격 완화**         |

> ⚠️ 쿠키는 클라이언트에 저장되므로 사용자가 열람·수정할 수 있다. 비밀번호 등 민감한 정보를 쿠키에 직접 저장해서는 안 된다.

<br>

### 3. 세션(Session)

**세션**은 상태 데이터를 **서버에 저장**하고, 클라이언트에는 이를 찾기 위한 **세션 ID만 쿠키로** 전달하는 방식이다.

```
클라이언트                         서버                 세션 저장소
    │                               │                      │
    │ ── ① 로그인 요청 ───────────► │                      │
    │                               │ ── 세션 생성 ──────► │
    │                               │    { user: kim }     │
    │ ◄─ ② Set-Cookie:              │                      │
    │      sessionId=abc123 ─────── │                      │
    │                               │                      │
    │ ── ③ Cookie:                  │                      │
    │      sessionId=abc123 ──────► │ ── abc123 조회 ────► │
    │                               │ ◄─ { user: kim } ─── │
    │ ◄─ ④ kim의 마이페이지 응답 ── │                      │
```

- **장점**: 실제 데이터가 서버에 있으므로 클라이언트 노출 위험이 적고, 서버에서 즉시 **무효화**(강제 로그아웃) 가능함
- **단점**: 사용자 수만큼 서버 메모리·저장소를 사용하며, 서버가 여러 대로 늘어나면 세션 공유 문제가 발생함

<br>

### 4. 토큰(JWT)

**토큰** 방식은 사용자 정보를 서버가 아닌 **토큰 자체에 담아** 클라이언트가 보관하는 방식이다. 대표 형식인 **JWT**(JSON Web Token)는 점(`.`)으로 구분된 세 부분으로 구성된다.

```
헤더(Header)   .   페이로드(Payload)   .   서명(Signature)

eyJhbGciOi...  .   eyJ1c2VySWQiOi...   .   SflKxwRJSM...
(서명 알고리즘)     (사용자 정보, 만료 시간)   (위·변조 검증용)
```

```json
{
  "userId": 42,
  "role": "member",
  "exp": 1767225600
}
```

- 서버는 **비밀 키로 서명을 검증**하기만 하면 되므로 상태를 저장할 필요가 없음 — **서버 무상태 유지**
- 서명 덕분에 페이로드를 위조하면 즉시 탐지됨

❗️**주의**: JWT 페이로드는 **암호화가 아니라 Base64 인코딩**일 뿐이다. 누구나 디코딩해 내용을 읽을 수 있으므로 민감한 정보를 절대 담아서는 안 된다.

<br>

### 5. 세 방식 종합 비교

| **구분**        | **쿠키(단독)**            | **세션**                          | **토큰(JWT)**                       |
| --------------- | ------------------------- | --------------------------------- | ----------------------------------- |
| **저장 위치**   | **클라이언트**            | 데이터는 **서버**, ID만 클라이언트 | **클라이언트** (토큰 자체에 정보)   |
| **확장성**      | 좋음                      | **낮음** — 세션 공유 필요          | **좋음** — 서버 무상태              |
| **보안**        | 노출·변조 위험 큼         | 데이터가 서버에 있어 상대적 안전   | 서명으로 변조 방어, 탈취 시 위험    |
| **무효화**      | 만료 설정에 의존          | **서버에서 즉시 가능**             | **어려움** — 만료 전까지 유효       |

<br>

### 6. 서버 확장과 세션 문제

서버를 여러 대로 **수평 확장**하면, 로그인은 1번 서버에서 했는데 다음 요청이 2번 서버로 가는 경우 세션을 찾지 못하는 문제가 발생한다.

- **세션 클러스터링**: 서버들끼리 세션 정보를 복제해 공유함 — 서버 수가 늘수록 복제 비용 증가
- **세션 스토리지 분리**: **Redis** 같은 외부 저장소에 세션을 모아두고 모든 서버가 공유함 — 실무에서 가장 널리 쓰이는 방식

> 💡 토큰 방식은 애초에 서버가 상태를 저장하지 않으므로 이 문제가 발생하지 않는다. 서버 확장성이 중요한 환경에서 JWT가 선호되는 이유이다.

<br>

### 7. 보안 참고
