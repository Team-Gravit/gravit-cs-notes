## HTTP 심화 — 버전과 캐시

unit11에서 응용 계층 프로토콜로 소개한 **HTTP**의 심화 내용으로, **버전별 발전 과정**(1.0 → 1.1 → 2 → 3)과 **HTTP 캐시** 동작 원리를 다룬다. 두 주제 모두 웹 성능 최적화의 핵심이자 기술 면접 단골 주제이다.

<br>

### 1. HTTP/1.0 — 연결 비용 문제

**HTTP/1.0**은 요청 하나마다 **TCP 연결을 새로 맺고 응답 후 즉시 끊는** 방식이다. 이미지·CSS·JS가 수십 개인 현대 웹 페이지에서는 자원마다 3-Way Handshake가 반복되어 **연결 비용이 페이지 로딩 시간을 지배**하게 된다.

<br>

### 2. HTTP/1.1 — 지속 연결과 그 한계

**HTTP/1.1**은 **지속 연결**(Keep-Alive)을 기본값으로 하여 하나의 TCP 연결로 여러 요청·응답을 처리한다.

- **파이프라이닝(Pipelining)**: 응답을 기다리지 않고 여러 요청을 연속 전송하는 기능이지만, 응답은 반드시 **요청 순서대로** 와야 해서 첫 응답이 느리면 뒤 응답이 모두 막힘. 구현 문제로 대부분의 브라우저가 비활성화함
- **HOL 블로킹**(Head-of-Line Blocking): 앞선 요청의 처리가 늦어지면 같은 연결의 **뒤 요청 전부가 대기**하는 문제. 브라우저는 도메인당 연결을 6개 정도 열어 우회하지만 근본 해결이 아님

```
HTTP/1.0            HTTP/1.1 (Keep-Alive)      HTTP/2 (멀티플렉싱)
연결1: 요청A→응답A   연결1: 요청A→응답A          연결1: 요청A,B,C 동시 전송
연결 종료                   요청B→응답B                 응답B,C,A 순서 무관 도착
연결2: 요청B→응답B          요청C→응답C                 (스트림 단위 독립 처리)
연결 종료            ⚠ A가 느리면 B·C 대기
```

<br>

### 3. HTTP/2 — 하나의 연결, 여러 스트림

**HTTP/2**는 텍스트 기반이던 메시지를 **바이너리 프레이밍** 계층으로 바꾸고, 하나의 연결을 여러 **스트림**으로 나눠 쓴다.

- **바이너리 프레이밍**: 메시지를 **프레임** 단위 이진 데이터로 분할해 파싱이 빠르고 오류에 강함
- **멀티플렉싱(Multiplexing)**: 여러 요청·응답 스트림이 **하나의 TCP 연결에서 순서 제약 없이 병렬 처리**됨 — HTTP 계층의 HOL 블로킹 해소
- **헤더 압축(HPACK)**: 반복 전송되는 헤더를 정적·동적 테이블과 허프만 부호화로 압축함
- **서버 푸시(Server Push)**: 클라이언트가 요청하기 전에 서버가 필요할 자원(CSS 등)을 미리 보냄

❗️**남는 문제**: HTTP/2도 TCP 위에서 동작하므로, **TCP 계층의 HOL 블로킹**은 여전하다. 패킷 하나가 유실되면 TCP가 순서를 보장하느라 그 뒤에 도착한 모든 스트림의 데이터가 함께 대기한다.

<br>

### 4. HTTP/3 — QUIC과 UDP

**HTTP/3**는 TCP 대신 **UDP 기반의 QUIC** 프로토콜 위에서 동작한다.

- **TCP HOL 블로킹 해소**: QUIC은 스트림별로 독립적으로 손실을 복구하므로 한 스트림의 패킷 유실이 다른 스트림을 막지 않음
- **빠른 연결 수립**: 전송 계층 핸드셰이크와 TLS 암호화 협상을 통합해 왕복 횟수를 줄임 (재연결 시 0-RTT 가능)
- **연결 마이그레이션(Connection Migration)**: 연결을 IP·포트가 아닌 **커넥션 ID**로 식별하여, Wi-Fi에서 LTE로 네트워크가 바뀌어도 연결을 끊지 않고 유지함
- **암호화 기본 내장**: TLS 1.3이 QUIC에 통합되어 있어 암호화되지 않은 HTTP/3 통신은 존재하지 않음

<br>

### 5. 버전별 종합 비교

| 구분              | HTTP/1.0        | HTTP/1.1              | HTTP/2                  | HTTP/3                  |
| ----------------- | --------------- | --------------------- | ----------------------- | ----------------------- |
| **전송 계층**     | TCP             | TCP                   | TCP                     | **UDP (QUIC)**          |
| **연결 재사용**   | 없음 (매번 연결) | **Keep-Alive** 기본   | 단일 연결 다중 스트림   | 단일 연결 다중 스트림   |
| **메시지 형식**   | 텍스트          | 텍스트                | **바이너리 프레임**     | 바이너리 프레임         |
| **병렬 처리**     | 불가            | 파이프라이닝(사실상 미사용) | **멀티플렉싱**     | 멀티플렉싱              |
| **HOL 블로킹**    | —               | HTTP 계층에서 발생    | TCP 계층에서 잔존       | **스트림 독립으로 해소** |
| **헤더 압축**     | 없음            | 없음                  | **HPACK**               | QPACK                   |

<br>

### 6. HTTP 캐시 — Cache-Control

**HTTP 캐시**는 받은 응답을 저장해 두었다가 재사용하여 **응답 속도 향상과 서버·네트워크 부하 감소**를 얻는 메커니즘이다. 캐시 동작은 응답의 `Cache-Control` 헤더 지시자로 제어한다.

| 지시자             | 의미                                                            |
| ------------------ | --------------------------------------------------------------- |
| **max-age=초**     | 지정한 시간 동안 응답이 **신선(fresh)** 하다고 간주하고 재사용   |
| **no-cache**       | 저장은 하되 **사용 전 반드시 서버에 재검증** 요구               |
| **no-store**       | 응답을 **아예 저장 금지** (민감 정보)                            |
| **public**         | 공유 캐시(프록시·CDN)도 저장 가능                                |
| **private**        | 브라우저 등 **개인 캐시만** 저장 가능                            |
| **must-revalidate**| 신선도 만료 후에는 재검증 없이 절대 사용 금지                    |

> ⚠️ **no-cache는 "캐시 금지"가 아니다.** no-cache는 **저장하되 매번 재검증 후 사용**, no-store가 **저장 자체를 금지**하는 지시자이다. 이름 때문에 반대로 이해하기 쉬운 최다 오답 포인트이다.

<br>

### 7. 신선도 판단과 재검증

캐시된 응답의 사용 여부는 두 단계로 판단한다.

1. **신선도 판단**: 저장 후 경과 시간이 `max-age` 이내이면 **신선**(fresh) — 서버에 묻지 않고 즉시 재사용함
2. **재검증(Revalidation)**: 신선도가 만료되면(stale) **조건부 요청**으로 서버에 변경 여부를 확인함
   - 미변경이면 **304 응답**을 받아 캐시를 재사용하고 신선도를 갱신함
   - 변경되었으면 **200 응답**으로 새 본문을 받아 캐시를 교체함

조건부 요청에 쓰이는 검증 헤더 쌍은 두 가지이다.

- **ETag / If-None-Match**: 서버가 응답 본문의 **고유 식별값(ETag)** 을 내려주면, 재검증 시 클라이언트가 `If-None-Match`로 그 값을 보냄. 값이 같으면 미변경
- **Last-Modified / If-Modified-Since**: **최종 수정 시각** 기반의 검증. 초 단위 정밀도라 ETag보다 부정확하며, 둘 다 있으면 ETag가 우선함

```
브라우저 (캐시 만료됨)                              서버
    │                                                │
    │── GET /logo.png ─────────────────────────────▶│
    │   If-None-Match: "abc123"                      │
    │                                                │  ETag 비교 → 변경 없음
    │◀─ 304 Not Modified (본문 없음) ────────────────│
    │                                                │
 캐시 응답 재사용 + 신선도 갱신                       │
    │                                                │
    │   (변경되었다면)                                │
    │◀─ 200 OK + 새 본문 + ETag: "def456" ───────────│
```

**304 Not Modified** 응답에는 본문이 없으므로, 자원이 크더라도 재검증 비용은 헤더 교환 수준으로 작다.

> 💡 실무의 대표 전략은 **정적 자원(JS·CSS)은 파일명에 해시를 넣고 `max-age`를 길게**, **HTML은 `no-cache`로 매번 재검증**하는 조합이다. HTML이 새 해시의 자원을 참조하게 되므로 배포 즉시 갱신되면서도 캐시 효율을 극대화할 수 있다.

<br>

### 8. 정리

HTTP는 **연결 재사용(1.1) → 멀티플렉싱(2) → 전송 계층 교체(3)** 의 방향으로 HOL 블로킹을 단계적으로 제거하며 발전해 왔다. 한편 캐시는 **Cache-Control로 신선도를 정하고, ETag/Last-Modified로 재검증**하는 두 축으로 동작한다. 버전 발전이 "전송을 빠르게"라면, 캐시는 "전송 자체를 줄이는" 최적화이다.
