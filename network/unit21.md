## REST API

**REST API**는 HTTP 프로토콜의 의미론을 최대한 활용해 자원을 다루는 API 설계 방식이다. 웹 서비스 간 통신의 사실상 표준으로, 백엔드 개발과 기술 면접 모두에서 핵심 주제이다.

<br>

### 1. API와 REST의 정의

- **API**(Application Programming Interface): 프로그램끼리 기능과 데이터를 주고받기 위해 정의된 **인터페이스(약속)**
- **REST**(Representational State Transfer): HTTP의 장점을 최대한 활용하도록 제안된 **아키텍처 스타일** — 자원의 표현으로 상태를 주고받는 방식
- **REST API**: REST 원칙을 따라 설계된 API

<br>

### 2. REST 구성 3요소

| **요소**              | **의미**                          | **예시**                        |
| --------------------- | --------------------------------- | ------------------------------- |
| **자원**(Resource)    | 모든 것은 자원이며 **URI**로 식별 | `/users/1`, `/posts/10`         |
| **행위**(Verb)        | 자원에 대한 행위는 **HTTP 메서드**로 표현 | `GET`, `POST`, `PUT`, `DELETE` |
| **표현**(Representation) | 자원의 상태를 주고받는 형식     | **JSON**, XML 등                |

<br>

### 3. REST 6가지 아키텍처 제약 조건

| **제약 조건**                | **설명**                                                       |
| ---------------------------- | -------------------------------------------------------------- |
| **클라이언트-서버**          | UI와 데이터 처리의 관심사를 분리함                             |
| **무상태**(Stateless)        | 각 요청은 필요한 정보를 모두 포함하며 서버는 상태를 저장하지 않음 |
| **캐시 가능**(Cacheable)     | 응답은 캐시 가능 여부를 명시해 재사용할 수 있어야 함           |
| **계층화 시스템**            | 클라이언트는 중간 계층(프록시, 게이트웨이) 존재를 몰라도 됨    |
| **인터페이스 일관성**        | URI·메서드 등 통일된 방식으로 자원에 접근함                    |
| **주문형 코드**(선택)        | 필요 시 서버가 실행 가능한 코드를 전달할 수 있음 (선택 사항)   |

<br>

### 4. HTTP 메서드별 용도·멱등성·안전성

- **안전성**(Safe): 요청이 서버의 자원 상태를 변경하지 않는 성질
- **멱등성**(Idempotent): 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질

| **메서드** | **용도**            | **멱등성** | **안전성** |
| ---------- | ------------------- | ---------- | ---------- |
| **GET**    | 자원 조회           | **O**      | **O**      |
| **POST**   | 자원 생성           | X          | X          |
| **PUT**    | 자원 **전체 교체**  | **O**      | X          |
| **PATCH**  | 자원 **부분 수정**  | X          | X          |
| **DELETE** | 자원 삭제           | **O**      | X          |

> 💡 PUT이 멱등인 이유: 같은 데이터로 전체 교체를 반복해도 최종 상태가 동일하다. 반면 POST는 반복할 때마다 새 자원이 생성되므로 멱등이 아니다.

<br>

### 5. URI 설계 규칙

- **동사가 아닌 명사**를 사용함 — 행위는 HTTP 메서드가 표현함
- 계층 관계는 `/`로 표현함 — `/users/1/posts` (1번 사용자의 게시글)
- 소문자를 사용하고, 단어 구분은 하이픈(`-`)을 사용함
- URI 마지막에 `/`를 붙이지 않으며, 파일 확장자를 포함하지 않음

| **나쁜 예**                 | **좋은 예**              | **이유**                          |
| --------------------------- | ------------------------ | --------------------------------- |
| `GET /getUsers`             | `GET /users`             | 동사 대신 **명사** 사용           |
| `POST /users/1/delete`      | `DELETE /users/1`        | 행위는 **HTTP 메서드**로 표현     |
| `GET /users/1/posts-list/`  | `GET /users/1/posts`     | 불필요한 단어·마지막 `/` 제거     |

<br>

### 6. 요청/응답 예시

```http
POST /users HTTP/1.1
Host: api.example.com
Content-Type: application/json

{
  "name": "kim",
  "email": "kim@example.com"
}
```

```http
HTTP/1.1 201 Created
Location: /users/42
Content-Type: application/json

{
  "id": 42,
  "name": "kim",
  "email": "kim@example.com"
}
```

자원 생성에 성공하면 **201 Created**와 함께 **Location** 헤더로 생성된 자원의 URI를 알려주는 것이 REST다운 설계이다.

<br>

### 7. 상태 코드 활용

REST API는 처리 결과를 **HTTP 상태 코드**로 명확히 전달해야 한다.

| **코드**                    | **의미**                              | **사용 상황**              |
| --------------------------- | ------------------------------------- | -------------------------- |
| **200 OK**                  | 요청 성공                             | 조회·수정 성공             |
| **201 Created**             | 자원 생성 성공                        | POST 성공                  |
| **204 No Content**          | 성공, 응답 본문 없음                  | DELETE 성공                |
| **400 Bad Request**         | 잘못된 요청                           | 유효성 검증 실패           |
| **401 / 403**               | 인증 실패 / 권한 없음                 | 로그인 필요 / 접근 금지    |
| **404 Not Found**           | 자원 없음                             | 존재하지 않는 URI          |
| **500 Internal Server Error** | 서버 내부 오류                      | 서버 측 예외 발생          |

> ⚠️ 모든 응답을 `200 OK`로 보내고 본문에만 성공/실패를 담는 것은 흔한 안티패턴이다. 클라이언트와 중간 계층(캐시 등)이 HTTP 의미론을 활용할 수 없게 된다.

<br>

### 8. RESTful과 성숙도 모델

**RESTful**은 REST 원칙을 충실히 따르는 API를 일컫는 표현이다. **리처드슨 성숙도 모델**(Richardson Maturity Model)은 REST 적용 수준을 4단계로 나눈다.

- **0단계**: 단일 URI에 POST만 사용 (HTTP를 단순 전송 수단으로만 사용)
- **1단계**: 자원별로 URI를 구분함
- **2단계**: HTTP 메서드와 상태 코드를 의미에 맞게 사용함 — **실무 대부분의 API가 목표로 하는 수준**
- **3단계**: 응답에 다음 행동 가능한 링크를 포함함(HATEOAS)

<br>

### 9. REST vs 웹소켓

| **구분**        | **REST API**                        | **웹소켓**(WebSocket)               |
| --------------- | ----------------------------------- | ----------------------------------- |
| **통신 방식**   | 요청-응답 **단방향** (클라이언트 주도) | **양방향** — 서버가 먼저 보낼 수 있음 |
| **연결**        | 요청마다 처리 후 종료               | 한 번 연결 후 **지속 유지**         |
| **적합한 경우** | 일반적인 CRUD, 자원 조회·관리       | 채팅, 실시간 알림, 주식 시세        |

> 💡 REST는 클라이언트가 요청해야만 데이터를 받을 수 있다. 채팅처럼 **서버가 먼저 데이터를 밀어줘야 하는 실시간 양방향 통신**이 필요하다면 웹소켓을 선택한다.
