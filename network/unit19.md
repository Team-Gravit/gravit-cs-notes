## HTTPS와 TLS

**HTTPS**는 **HTTP**에 **TLS**(Transport Layer Security) 암호화 계층을 더해 안전한 통신을 보장하는 프로토콜이다. 평문으로 전송되는 HTTP의 보안 취약점을 해결하며, 현대 웹 통신의 표준으로 자리잡았다.

<br>

### 1. HTTP 평문 통신의 3가지 위험

**HTTP**는 데이터를 암호화하지 않고 평문 그대로 전송하기 때문에 다음 세 가지 위험에 노출된다.

| **위험**                       | **설명**                                                     | **예시**                              |
| ------------------------------ | ------------------------------------------------------------ | ------------------------------------- |
| **도청**(Eavesdropping)        | 통신 경로상의 제3자가 패킷을 가로채 내용을 읽을 수 있음      | 공용 와이파이에서 비밀번호 탈취       |
| **변조**(Tampering)            | 전송 중인 데이터를 중간에서 바꿔치기할 수 있음               | 응답 페이지에 악성 스크립트 삽입      |
| **위장**(Spoofing)             | 통신 상대가 진짜 서버인지 확인할 방법이 없음                 | 가짜 은행 사이트로 사용자 유인        |

**HTTPS**는 **암호화**로 도청을, **무결성 검증**으로 변조를, **인증서**로 위장을 각각 방어한다.

<br>

### 2. HTTPS = HTTP + TLS

**HTTPS**는 별도의 프로토콜이 아니라, HTTP 메시지가 **TLS 계층을 거쳐 암호화된 후** TCP로 전달되는 구조이다. 기본 포트는 HTTP의 **80번** 대신 **443번**을 사용한다.

```
[HTTP]                      [HTTPS]

응용 계층 (HTTP)            응용 계층 (HTTP)
    │                           │
    │  평문 그대로              ▼
    │                       보안 계층 (TLS) ← 암호화·무결성·인증
    ▼                           │
전송 계층 (TCP)             전송 계층 (TCP)
```

> 💡 과거에는 **SSL**(Secure Sockets Layer)이라 불렀으나, 현재는 후속 표준인 **TLS**가 사용된다. 관례상 "SSL 인증서"라는 표현이 여전히 널리 쓰이지만 실제로는 TLS를 의미한다.

<br>

### 3. 대칭키 vs 공개키(비대칭키) 암호화

| **구분**        | **대칭키 암호화**                          | **공개키(비대칭키) 암호화**                        |
| --------------- | ------------------------------------------ | -------------------------------------------------- |
| **키 구성**     | 암호화·복호화에 **동일한 키 1개** 사용     | **공개키**(암호화)와 **개인키**(복호화) 쌍 사용    |
| **속도**        | **빠름** — 대량 데이터 처리에 적합         | **느림** — 연산 비용이 큼                          |
| **키 전달 문제**| 키를 상대에게 **안전하게 전달하기 어려움** | 공개키는 공개해도 되므로 **키 전달 문제 없음**     |
| **대표 알고리즘**| AES                                        | RSA, ECDHE                                         |

<br>

### 3-1. 하이브리드 방식

TLS의 핵심은 두 방식의 장점만 취하는 **하이브리드 방식**이다.

1. **공개키 암호화**로 안전하게 **대칭키(세션 키)를 교환**한다 — 키 전달 문제 해결
2. 이후 실제 데이터 통신은 교환한 **대칭키**로 암호화한다 — 속도 문제 해결

❗️**핵심**: "공개키로 대칭키를 나눠 갖고, 대칭키로 통신한다" — 이 한 문장이 TLS 암호화 구조의 전부라 해도 과언이 아니다.

<br>

### 4. TLS 핸드셰이크 과정

TCP 3-Way Handshake로 연결을 맺은 뒤, 암호화 통신을 시작하기 전에 **TLS 핸드셰이크**를 수행한다.

```
클라이언트                                        서버
    │                                              │
    │ ──── ① ClientHello ────────────────────────► │
    │      (지원 TLS 버전, 암호 스위트 목록,        │
    │       클라이언트 랜덤값)                      │
    │                                              │
    │ ◄──── ② ServerHello + 인증서 ─────────────── │
    │      (선택된 버전·암호 스위트, 서버 랜덤값,   │
    │       서버 인증서 전달)                       │
    │                                              │
    │ ③ 인증서 검증                                │
    │   (CA 서명 확인 → 서버 신원 확인)             │
    │                                              │
    │ ──── ④ 키 교환 ────────────────────────────► │
    │      (공개키 기반으로 대칭키 재료 교환,       │
    │       양쪽에서 동일한 세션 키 생성)           │
    │                                              │
    │ ──── ⑤ Finished ──────────────────────────► │
    │ ◄──── ⑤ Finished ─────────────────────────── │
    │                                              │
    │ ◄═══ 이후 대칭키로 암호화된 HTTP 통신 ═════► │
```

1. **ClientHello**: 클라이언트가 지원 가능한 TLS 버전과 암호 알고리즘 목록(암호 스위트)을 제시함
2. **ServerHello**: 서버가 사용할 버전·알고리즘을 선택하고 **인증서**를 전달함
3. **인증서 검증**: 클라이언트가 인증서의 **CA 서명**을 확인해 서버의 신원을 검증함
4. **키 교환**: 공개키 방식으로 대칭키 생성 재료를 교환하고, 양쪽이 동일한 **세션 키**를 만듦
5. **Finished**: 핸드셰이크 완료를 서로 확인하고 암호화 통신을 시작함

<br>

### 5. TLS 1.2 vs TLS 1.3

| **구분**            | **TLS 1.2**                    | **TLS 1.3**                              |
| ------------------- | ------------------------------ | ---------------------------------------- |
| **핸드셰이크 왕복** | **2-RTT**                      | **1-RTT** — 왕복 1회로 단축              |
| **암호 스위트**     | 다양하지만 취약한 알고리즘 포함 | 안전한 알고리즘만 남기고 **대폭 정리**   |
| **키 교환**         | RSA 키 교환 허용               | **ECDHE** 등 순방향 비밀성 방식만 허용   |

> 💡 TLS 1.3은 재접속 시 **0-RTT** 모드도 지원해 이전에 접속했던 서버와는 핸드셰이크 지연 없이 바로 데이터를 보낼 수 있다.

<br>

### 6. 인증서와 CA

**인증서**(Certificate)는 "이 공개키가 진짜 이 서버의 것"임을 증명하는 전자 문서이다.

- **CA**(Certificate Authority, 인증 기관): 서버의 신원을 확인하고 인증서에 **디지털 서명**을 하는 신뢰된 제3자
- 브라우저는 신뢰하는 CA 목록을 내장하고 있으며, 서버가 제시한 인증서의 서명을 검증해 **위장 공격을 차단**함
- 인증서에는 도메인 이름, 공개키, 유효 기간, 발급 CA 정보 등이 포함됨

```http
GET / HTTP/1.1
Host: www.example.com

HTTP/1.1 200 OK
Strict-Transport-Security: max-age=31536000
Content-Type: text/html
```

위 예시의 **Strict-Transport-Security**(HSTS) 헤더는 브라우저가 이후 해당 도메인에 항상 HTTPS로만 접속하도록 강제한다.

> ⚠️ 인증서 체인(루트 CA → 중간 CA → 서버 인증서)의 상세 검증 과정과 인증서 관련 공격 기법은 **web-security** 과목에서 자세히 다룬다.

<br>

### 7. SNI

하나의 IP 주소에서 여러 도메인을 서비스하는 경우, 서버는 어떤 도메인의 인증서를 보내야 할지 알 수 없다. **SNI**(Server Name Indication)는 클라이언트가 **ClientHello 단계에서 접속하려는 도메인 이름을 미리 알려주는** TLS 확장으로, 이 문제를 해결한다.

SNI 덕분에 하나의 서버(하나의 IP)에서 여러 HTTPS 사이트를 운영하는 **가상 호스팅**이 가능하다.
