## DNS(Domain Name System)

**DNS**는 사람이 기억하기 쉬운 **도메인 이름**(www.example.com)을 컴퓨터가 사용하는 **IP 주소**(93.184.216.34)로 변환하는 분산 데이터베이스 시스템이다. unit11에서 응용 계층 프로토콜로 소개한 DNS의 내부 동작을 상세히 다룬다.

<br>

### 1. 도메인 이름이 필요한 이유

- **기억 용이성**: 숫자 IP 주소는 외우기 어렵지만 이름은 기억하기 쉬움
- **주소 변경 유연성**: 서버 IP가 바뀌어도 DNS 레코드만 수정하면 사용자는 같은 이름으로 접속 가능
- **부하 분산**: 하나의 이름에 여러 IP를 연결해 트래픽을 분산할 수 있음
- **서비스 분리**: 웹(www), 메일(mail) 등 용도별로 이름을 나눠 운영 가능
- **확장성**: 전 세계 도메인을 하나의 서버가 아닌 **계층별 분산 구조**로 관리 가능

<br>

### 2. 도메인 계층 구조

도메인 이름은 **역트리 구조**의 계층으로 관리된다. `www.example.com.`은 오른쪽부터 **루트 → 최상위 도메인(TLD) → 2단계 도메인 → 호스트** 순으로 읽는다.

```
                        . (루트)
                        │
        ┌───────────────┼────────────────┐
      com              org              kr        ← TLD (최상위 도메인)
        │                                │
   ┌────┴────┐                        co.kr
example    google                        │
   │                                  naver
  www  ← 호스트
```

이 계층 그대로 네임서버도 나뉘어 있다.

- **루트 네임서버**: TLD 네임서버의 위치를 알려줌 (전 세계 13개 주소 체계)
- **TLD 네임서버**: `com`, `kr` 등 최상위 도메인을 관리하며 권한 네임서버 위치를 알려줌
- **권한 네임서버**(Authoritative): 해당 도메인의 **실제 레코드(정답)** 를 보유함

<br>

### 3. 재귀적 질의 vs 반복적 질의

클라이언트는 보통 통신사나 회사가 운영하는 **리졸버**(Recursive Resolver, 예: 8.8.8.8)에게 **재귀적 질의**를 보낸다. 리졸버는 최종 답을 찾을 책임을 지고, 루트부터 권한 네임서버까지 **반복적 질의**를 수행한다.

```
클라이언트          리졸버              루트 NS      com TLD NS    example.com 권한 NS
    │                 │                  │              │                │
    │─ 재귀적 질의 ──▶│                  │              │                │
    │ "www.example.com│─ 반복적 질의 ───▶│              │                │
    │  의 IP는?"      │◀─ "com은 저쪽" ──│              │                │
    │                 │                  │              │                │
    │                 │─ 반복적 질의 ────────────────▶│                │
    │                 │◀─ "example.com은 저쪽" ─────────│                │
    │                 │                  │              │                │
    │                 │─ 반복적 질의 ──────────────────────────────────▶│
    │                 │◀─ "93.184.216.34" (정답) ───────────────────────│
    │◀─ 최종 응답 ────│                  │              │                │
    │  93.184.216.34  │                  │              │                │
```

| 구분          | 재귀적 질의(Recursive)          | 반복적 질의(Iterative)                 |
| ------------- | ------------------------------- | -------------------------------------- |
| **요청 의미** | "**최종 답**을 찾아서 달라"     | "아는 만큼만 알려달라(**다음 서버**)"  |
| **사용 구간** | 클라이언트 → **리졸버**         | 리졸버 → **루트·TLD·권한 네임서버**    |
| **응답 내용** | 최종 IP 주소 (또는 실패)        | 정답 또는 다음에 질의할 네임서버 주소  |
| **부담 주체** | 리졸버가 조회 전 과정을 책임짐  | 각 네임서버는 한 단계 안내만 담당함    |

<br>

### 4. DNS 캐싱과 TTL

매번 루트부터 질의하면 느리고 상위 서버에 부하가 집중되므로, 결과는 여러 단계에서 **캐싱**된다. 조회는 아래 순서로 진행되며 어느 단계든 캐시에 답이 있으면 즉시 반환된다.

1. **브라우저 캐시**: 브라우저가 자체 보관하는 최근 조회 결과
2. **OS 캐시**: 운영체제의 DNS 캐시 (hosts 파일도 이 단계에서 확인)
3. **리졸버 캐시**: 리졸버가 보관하는 결과 — 다른 사용자의 조회 결과도 공유됨
4. 캐시 미스 시 루트부터 **반복적 질의** 수행

각 레코드에는 **TTL**(Time To Live, 초 단위)이 설정되어 있어 그 시간 동안만 캐시가 유효하다. TTL이 짧으면 변경이 빨리 반영되지만 질의가 늘고, 길면 그 반대이다.

> 💡 OS는 DNS 질의 전에 **hosts 파일**(리눅스·맥 `/etc/hosts`, 윈도우 `C:\Windows\System32\drivers\etc\hosts`)을 먼저 확인한다. 여기에 등록된 이름은 DNS보다 **우선 적용**되므로 로컬 개발 환경에서 테스트 도메인을 연결할 때 자주 활용된다.

<br>

### 5. 주요 레코드 타입

| 레코드    | 이름                  | 역할                                             |
| --------- | --------------------- | ------------------------------------------------ |
| **A**     | Address               | 도메인 이름 → **IPv4 주소** 매핑                 |
| **AAAA**  | IPv6 Address          | 도메인 이름 → **IPv6 주소** 매핑                 |
| **CNAME** | Canonical Name        | 도메인의 **별칭**을 다른 도메인 이름으로 연결    |
| **MX**    | Mail Exchange         | 해당 도메인의 **메일 서버** 지정 (우선순위 포함) |
| **NS**    | Name Server           | 해당 도메인을 관리하는 **네임서버** 지정         |
| **TXT**   | Text                  | 임의 텍스트 저장 — SPF 등 **소유권·인증** 용도   |

```bash
dig www.example.com A +short
# 93.184.216.34

nslookup -type=MX example.com
# example.com  mail exchanger = 10 mail.example.com
```

<br>

### 6. 전송 프로토콜 — UDP 53과 예외

DNS는 기본적으로 **UDP 53번 포트**를 사용한다. 질의·응답이 각각 패킷 하나로 끝나는 단순한 교환이라 연결 설정 비용이 없는 UDP가 적합하기 때문이다. 다만 다음 경우에는 **TCP 53번**을 사용한다.

- **응답 크기 초과**: 응답이 UDP로 담기 어려울 만큼 크면(전통적으로 512바이트 기준) TCP로 재질의함
- **존 전송(Zone Transfer)**: 주 네임서버에서 보조 네임서버로 레코드 전체를 복제할 때는 신뢰성이 필요해 TCP를 사용함
- **DoT·DoH**: 질의 내용을 암호화하는 DNS over TLS(853), DNS over HTTPS(443)도 TCP 기반으로 동작함

> ⚠️ "DNS는 UDP만 쓴다"고 답하면 감점 요인이다. **기본은 UDP, 큰 응답과 존 전송은 TCP**라는 예외까지 알아야 정확하다.

<br>

### 7. 웹 접속 과정과의 연계

unit12(웹 접속 과정과 데이터 흐름)에서 본 것처럼, 브라우저에 URL을 입력하면 **DNS 조회가 가장 먼저** 일어난다. 여기서 얻은 IP 주소가 있어야 TCP 3-Way Handshake(unit09)와 HTTP 요청(unit11)이 이어질 수 있다. 즉 DNS는 모든 웹 통신의 **출발점**이며, DNS가 느리거나 실패하면 이후 단계 전체가 지연·실패한다.
