## 캐싱 레이어

App Router는 **요청 메모이제이션 → 데이터 캐시 → 전체 라우트 캐시 → 라우터 캐시**의 네 계층으로 캐시를 나누어 "같은 일을 두 번 하지 않도록" 설계되어 있다. 각 계층이 **무엇을·어디에·얼마나 오래** 저장하는지 구분하지 못하면 "데이터를 바꿨는데 화면이 안 바뀐다"는 가장 흔한 Next.js 버그를 해결할 수 없으며, 특히 Next.js 15에서 기본값이 크게 바뀌었으므로 버전별 차이까지 함께 알아야 한다.

<br>

### 1. 네 계층 한눈에 보기

| **계층**                 | **저장 대상**                     | **위치**  | **수명**                          | **목적**                                   |
| ------------------------ | --------------------------------- | --------- | --------------------------------- | ------------------------------------------ |
| **요청 메모이제이션**    | `fetch`·`cache()` 함수의 반환값   | 서버      | **한 번의 렌더링 요청 동안**      | 한 트리 안에서 같은 요청의 중복 실행 방지  |
| **데이터 캐시**          | `fetch` 응답 본문                 | 서버      | **영속** (재검증·재배포까지)      | 요청·사용자를 넘어 원본 API 호출 감소      |
| **전체 라우트 캐시**     | 렌더링된 HTML + RSC 페이로드      | 서버      | 영속 (재검증·재배포까지)          | 정적 라우트의 렌더링 비용 제거             |
| **라우터 캐시**          | 방문한 라우트의 RSC 페이로드      | **브라우저 메모리** | 세션 동안 (또는 짧은 시간) | 뒤로가기·재방문 시 서버 요청 생략          |

```
브라우저                                       서버
┌──────────────┐   내비게이션    ┌────────────────────┐  fetch   ┌───────────┐
│ ④ 라우터 캐시 │ ───────────→ │ ③ 전체 라우트 캐시   │ ──────→ │ ② 데이터  │ ──→ 원본 API
│  (RSC 페이로드)│ ←─────────── │  (HTML+RSC)         │ ←────── │   캐시    │ ←──
└──────────────┘                │   ↑ 렌더링 중        │          └───────────┘
                                │ ① 요청 메모이제이션   │
                                └────────────────────┘
```

> 💡 면접에서는 "데이터 캐시와 전체 라우트 캐시의 차이"를 자주 묻는다. 데이터 캐시는 **재료(API 응답)**를, 전체 라우트 캐시는 **완성된 요리(HTML)**를 저장한다. 재료가 바뀌면 요리도 다시 해야 하므로, 데이터 캐시를 무효화하면 전체 라우트 캐시도 함께 무효화된다.

<br>

### 2. 요청 메모이제이션(Request Memoization)

React가 제공하는 기능으로, **하나의 서버 렌더링 요청이 진행되는 동안** 동일한 URL·옵션의 `fetch` GET 요청은 한 번만 실행하고 결과를 재사용한다.

```tsx
// 레이아웃과 페이지가 같은 데이터를 각각 요청해도 네트워크 호출은 1회
async function getUser(id: string) {
  const res = await fetch(`https://api.example.com/users/${id}`);
  return res.json();
}

export default async function Layout({ children }: { children: React.ReactNode }) {
  const user = await getUser("1");   // 실제 호출
  return <><Nav name={user.name} />{children}</>;
}

export async function Page() {
  const user = await getUser("1");   // 메모이제이션 적중 → 즉시 반환
  return <Profile user={user} />;
}
```

- 렌더링이 끝나면 메모이제이션도 사라진다. **시간이 아니라 "렌더링 패스"가 단위**다.
- `fetch`가 아닌 DB·ORM 호출은 `React.cache()`로 감싸야 같은 효과를 얻는다(unit03 프리로드 패턴 참고).
- 덕분에 "props 드릴링을 피하려고 최상단에서 한 번만 페칭"할 필요 없이, **데이터가 필요한 컴포넌트에서 각자 페칭**해도 비용이 늘지 않는다.

<br>

### 3. 데이터 캐시(Data Cache)

Next.js가 제공하는 **서버 측 영속 캐시**로, `fetch` 응답을 요청과 배포를 넘어 보관한다. 재검증(unit05 참고)이나 재배포 전까지 유지된다.

<br>

### 3-1. 버전별 기본값 차이

| **항목**                          | **Next.js 14**                     | **Next.js 15**                         |
| --------------------------------- | ---------------------------------- | -------------------------------------- |
| **`fetch` 기본 `cache` 값**       | **`force-cache`** (자동 캐시)      | **`no-store`** (캐시 안 함)            |
| **GET 라우트 핸들러**             | 기본 캐시됨                        | 기본 **캐시 안 됨**                    |
| **캐시를 켜는 방법**              | (기본)                             | `cache: 'force-cache'` 또는 `next: { revalidate }` 명시 |
| **파일 단위 기본값 변경**         | `export const fetchCache = 'default-no-store'` | `export const fetchCache = 'default-cache'` |

```tsx
// Next.js 15 기준
const a = await fetch(url);                                   // 캐시 안 함 (요청마다 원본 호출)
const b = await fetch(url, { cache: "force-cache" });         // 데이터 캐시에 저장, 재검증 전까지 재사용
const c = await fetch(url, { next: { revalidate: 3600 } });   // 캐시 + 1시간 뒤 재검증
const d = await fetch(url, { next: { tags: ["posts"] } });    // 태그 부여 → revalidateTag로 무효화
```

> ⚠️ 15에서 `fetch`가 캐시되지 않는다고 해서 **정적 라우트가 매 요청 최신 데이터를 보여 주는 것은 아니다**. 정적 라우트는 빌드 시 한 번 렌더링되어 전체 라우트 캐시에 저장되므로, 그 안의 `fetch`도 빌드 시 한 번만 실행된다. "데이터 캐시 미적용"과 "동적 렌더링"은 별개의 개념이다(unit01 참고).

<br>

### 3-2. `fetch`를 쓰지 않는 데이터의 캐시

ORM·SDK 호출은 데이터 캐시를 거치지 않는다. 같은 효과를 내려면 `unstable_cache`로 감싼다. Next.js 15에서 `"use cache"` 지시자가 실험 기능으로 추가되어 이를 대체하는 방향이나, 안정화 시점은 버전에 따라 다를 수 있다.

```tsx
import { unstable_cache } from "next/cache";

export const getPosts = unstable_cache(
  async () => db.post.findMany(),
  ["posts-list"],                    // 캐시 키
  { revalidate: 60, tags: ["posts"] } // 재검증 옵션 (unit05 참고)
);
```

<br>

### 4. 전체 라우트 캐시(Full Route Cache)

정적으로 렌더링된 라우트의 **HTML과 RSC 페이로드를 서버에 저장**해 두는 캐시다. 빌드 시점(또는 ISR 재생성 시점)에 채워지며, 요청이 오면 렌더링 없이 그대로 응답한다.

- **정적 라우트만 대상**이다. 동적 API를 쓰거나 `dynamic = 'force-dynamic'`인 라우트는 요청마다 렌더링하므로 이 캐시를 건너뛴다.
- 데이터 캐시가 재검증되면 해당 데이터를 쓰는 라우트의 전체 라우트 캐시도 함께 무효화되어 다음 요청에서 다시 렌더링된다.
- `revalidatePath`(unit05 참고)는 이 계층을 직접 무효화한다.

```
빌드                      요청 1 (캐시 적중)             재검증 후 요청 2
[렌더링 → HTML 저장]  →  [저장된 HTML 즉시 응답]  →  [다시 렌더링 → HTML 갱신 → 응답]
```

<br>

### 5. 라우터 캐시(Router Cache) — 유일한 클라이언트 캐시

브라우저 메모리에 **방문했거나 프리페치한 라우트의 RSC 페이로드**를 보관해, 앞·뒤로가기나 재방문 시 서버 요청 없이 즉시 화면을 그린다.

| **항목**                    | **Next.js 14**                          | **Next.js 15**                                   |
| --------------------------- | --------------------------------------- | ------------------------------------------------ |
| **동적 페이지 보관 시간**   | 30초                                    | **0초** (내비게이션마다 새로 요청)               |
| **정적 페이지 보관 시간**   | 5분                                     | 5분                                              |
| **조정 방법**               | 없음                                    | `next.config`의 `experimental.staleTimes`        |
| **뒤로가기·앞으로가기**     | 항상 캐시 사용                          | 항상 캐시 사용 (스크롤 위치 복원 목적)           |

- 서버 캐시를 무효화해도 **브라우저의 라우터 캐시는 자동으로 비워지지 않는다**. 서버 액션에서 `revalidatePath`·`revalidateTag`를 호출하거나 클라이언트에서 `router.refresh()`를 호출해야 갱신된다(unit05·06 참고).
- 14에서 "수정했는데 30초 동안 옛 화면이 보인다"는 문의가 많아 15에서 동적 페이지의 기본 보관 시간이 0으로 바뀌었다.

> 💡 레이아웃은 부분 렌더링(Partial Rendering) 덕분에 내비게이션 시 다시 요청하지 않는다. 라우터 캐시와 레이아웃 재사용은 별개의 최적화지만, 둘 다 "화면 일부가 갱신되지 않는" 현상의 원인이 될 수 있으므로 구분해서 기억한다.

<br>

### 6. "데이터가 안 바뀌는" 문제의 진단 순서

```
① 라우트가 정적인가?         → 빌드 시 고정. 재검증(ISR) 또는 동적 렌더링 필요 (unit01)
② fetch에 캐시 옵션이 있나?   → force-cache / revalidate 값 확인. 15는 기본 no-store (unit05)
③ ORM 호출을 unstable_cache로 감쌌나? → 태그·revalidate 설정 확인
④ 서버는 갱신됐는데 브라우저만 옛날인가? → 라우터 캐시. router.refresh() 또는 서버 액션 재검증
⑤ 개발 서버와 프로덕션이 다른가?  → dev 모드는 전체 라우트 캐시가 꺼져 있어 프로덕션에서만 재현
```

❗️**개발 모드의 함정**: `next dev`에서는 전체 라우트 캐시가 동작하지 않아 항상 최신 데이터가 보인다. 캐시 관련 동작은 반드시 `next build && next start`로 검증한다.

<br>

### 7. 정리 — 면접·실무 체크포인트

| **계층**              | **한 줄 정의**                                            | **무효화 수단**                                |
| --------------------- | --------------------------------------------------------- | ---------------------------------------------- |
| **요청 메모이제이션** | 한 렌더링 안에서 같은 요청은 한 번만                      | 자동 (렌더링 종료)                             |
| **데이터 캐시**       | `fetch` 응답을 서버에 영속 저장                           | `revalidateTag`·`revalidatePath`·시간 재검증   |
| **전체 라우트 캐시**  | 정적 라우트의 HTML·RSC를 서버에 저장                      | 데이터 캐시 무효화 시 연동, `revalidatePath`   |
| **라우터 캐시**       | 브라우저 메모리의 RSC 페이로드                            | `router.refresh()`, 서버 액션 내 재검증        |

- 네 계층은 **서버 3개 + 클라이언트 1개**이며, 앞의 세 계층은 위에서 아래로 연쇄 무효화된다.
- Next.js 15의 핵심 변경은 **`fetch`·GET 핸들러의 기본 미캐시**와 **동적 페이지 라우터 캐시 0초**다. 14 기준 자료를 볼 때 기본값을 반대로 이해하지 않도록 주의한다.
- 각 계층을 언제·어떻게 무효화하는지는 unit05, 변경 후 재검증 흐름은 unit06을 참고할 것.
