## 하이드레이션

**하이드레이션(Hydration)**은 서버가 만든 정적 HTML에 브라우저의 React가 이벤트 핸들러와 상태를 "붙여" 상호작용 가능한 앱으로 되살리는 과정이다. 서버 렌더링의 이점(빠른 첫 화면·SEO)은 이 단계가 성공해야 완성되며, 서버와 클라이언트의 렌더링 결과가 다르면 발생하는 **하이드레이션 미스매치**와 이를 부분·점진적으로 처리하는 **스트리밍 SSR**의 원리를 알아야 "화면은 보이는데 클릭이 안 된다", "콘솔에 hydration 오류가 뜬다" 같은 문제를 근본적으로 해결할 수 있다.

<br>

### 1. 하이드레이션이 하는 일

```
① 서버:   컴포넌트 트리 렌더링 → HTML 문자열 + RSC 페이로드 전송
② 브라우저: HTML 파싱 → 화면 표시 (아직 클릭·입력 불가, "보이기만 하는" 상태)
③ 브라우저: JS 번들 다운로드·실행 → 클라이언트 컴포넌트를 메모리에서 다시 렌더링
④ 브라우저: 렌더링 결과와 기존 DOM을 비교(대조) → 일치하면 DOM을 재사용하고 이벤트 핸들러 부착
⑤ 완료:    상호작용 가능 (TTI, Time to Interactive)
```

- 하이드레이션은 DOM을 **새로 만들지 않고 이미 있는 DOM에 React 트리를 연결**한다. 그래서 ④에서 구조가 다르면 문제가 된다.
- 하이드레이션 대상은 **클라이언트 컴포넌트뿐**이다. 서버 컴포넌트(unit02 참고)는 JS가 브라우저로 가지 않으므로 하이드레이션 비용이 0이다.
- ②와 ⑤ 사이의 간격이 길면 "보이지만 반응하지 않는" 구간이 생긴다. 번들 크기(unit09 참고)와 스트리밍이 이 간격을 줄이는 수단이다.

> 💡 "SSR인데 왜 JS가 필요한가"라는 질문에는 **HTML은 화면을, 하이드레이션은 동작을 담당한다**고 답한다. HTML만으로는 `onClick`이 붙지 않으므로 클라이언트 컴포넌트의 JS는 여전히 필요하다.

<br>

### 2. 하이드레이션 미스매치 — 발생 원인

서버가 만든 HTML과 브라우저가 첫 렌더링에서 만든 결과가 다르면 React는 경고를 띄우고, 심하면 해당 서브트리를 **버리고 클라이언트에서 처음부터 다시 렌더링**한다(성능 손실 + 깜빡임).

| **원인 유형**                    | **예시**                                                        | **왜 달라지는가**                                       |
| -------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------- |
| **시간·난수**                    | `new Date().toLocaleString()`, `Math.random()`                  | 서버 실행 시점과 브라우저 실행 시점의 값이 다름         |
| **브라우저 전용 API 분기**       | `typeof window !== 'undefined' ? A : B`                         | 서버는 B, 브라우저 첫 렌더링은 A를 그림                 |
| **로컬 저장소·쿠키 의존 초기값** | `useState(localStorage.getItem('theme'))`                       | 서버에는 localStorage가 없음                            |
| **로케일·타임존**                | `Intl.DateTimeFormat()` 기본 로케일                             | 서버(UTC·en)와 사용자 브라우저(KST·ko) 설정이 다름      |
| **잘못된 HTML 중첩**             | `<p>` 안에 `<div>`, `<table>` 안에 직접 `<tr>`                  | 브라우저가 파싱하며 구조를 자동 교정해 DOM이 달라짐     |
| **브라우저 확장 프로그램**       | 번역기·광고 차단기가 DOM에 속성·노드 삽입                       | 서버 HTML 도착 후 하이드레이션 전에 DOM이 변조됨        |
| **서버·클라이언트 데이터 불일치** | 서버 렌더링 후 클라이언트 fetch 결과로 즉시 렌더링              | 두 시점의 데이터가 다름                                 |

```tsx
// ❌ 안티패턴: 서버에서는 "light", 브라우저 첫 렌더링에서는 저장된 "dark"를 그림
"use client";
export function ThemeLabel() {
  const theme = typeof window !== "undefined"
    ? localStorage.getItem("theme") ?? "light"
    : "light";
  return <span>{theme}</span>;   // Hydration failed: text content mismatch
}
```

### 3. 미스매치 해결 패턴

### 3-1. 첫 렌더링은 서버와 동일하게, 브라우저 값은 이펙트에서

```tsx
// ✅ 개선: 첫 렌더링은 서버와 같은 기본값 → 마운트 후 실제 값으로 교체
"use client";
import { useEffect, useState } from "react";

export function ThemeLabel() {
  const [theme, setTheme] = useState("light");          // 서버·클라이언트 첫 렌더링 동일
  useEffect(() => {
    setTheme(localStorage.getItem("theme") ?? "light"); // 하이드레이션 이후 실행
  }, []);
  return <span>{theme}</span>;
}
```

- `useEffect`는 하이드레이션이 끝난 뒤 실행되므로 안전하다. 대신 첫 화면에 기본값이 잠깐 보이는 **깜빡임**은 감수해야 한다.
- 외부 저장소를 구독하는 형태라면 `useSyncExternalStore`의 세 번째 인자 `getServerSnapshot`으로 서버용 값을 따로 제공해 같은 효과를 더 깔끔하게 얻을 수 있다.

<br>

### 3-2. 그 외 도구

| **도구**                                  | **용도**                                                      | **주의**                                        |
| ----------------------------------------- | ------------------------------------------------------------- | ----------------------------------------------- |
| **`suppressHydrationWarning`**            | 시각·타임스탬프처럼 **불일치가 불가피한 텍스트 한 곳**        | 한 단계 깊이의 텍스트·속성만 억제. 남용 금지    |
| **`next/dynamic` + `ssr: false`**         | 브라우저 API에 전적으로 의존하는 컴포넌트(차트·에디터·지도)   | 서버 HTML에서 빠지므로 SEO·첫 화면에 영향       |
| **HTML 구조 검증**                        | `<p>` 안의 블록 요소, `<a>` 안의 `<a>` 등 제거                | React 19(Next.js 15)는 오류 메시지에 **diff**를 보여 줌 |
| **서버에서 값 결정 후 props 전달**        | 쿠키의 테마·로케일을 서버 컴포넌트에서 읽어 넘김              | 깜빡임 없이 처리 가능. 단, 라우트가 동적 렌더링됨(unit01) |

> ⚠️ `ssr: false`는 "미스매치를 고치는" 것이 아니라 "서버 렌더링을 포기하는" 선택이다. 미스매치 원인이 값 하나라면 `useEffect` 패턴으로 충분하며, 전체 컴포넌트를 CSR로 돌리는 것은 마지막 수단이다.

<br>

### 4. 스트리밍 SSR — HTML을 나눠 보내기

기존 SSR은 페이지의 **모든 데이터가 준비돼야** HTML을 한 번에 응답했다(느린 API 하나가 전체를 막음). 스트리밍 SSR은 HTML을 **여러 청크(chunk)로 나눠 준비된 순서대로** 보낸다. App Router는 이를 기본으로 사용하며, 단위는 `Suspense` 경계(unit03 참고)다.

```
시간 →   0ms                    120ms                        900ms
서버     [헤더+뼈대+fallback] ──→ [Posts 청크 + 교체 스크립트] ──→ [추천 청크 + 교체 스크립트]
브라우저  즉시 표시                fallback → 게시글 교체          fallback → 추천 교체
         (TTFB 확보)              (Posts 먼저 하이드레이션)       (추천 하이드레이션)
```

- 첫 청크에는 셸(레이아웃·헤더)과 각 `Suspense`의 fallback이 담겨 **TTFB와 FCP가 빨라진다**.
- 이후 청크는 `<div hidden>`으로 숨겨진 실제 콘텐츠와, fallback 자리에 그것을 옮겨 넣는 **작은 인라인 스크립트**로 구성된다. 순서에 상관없이 준비된 것부터 온다(out-of-order streaming).
- 라우트 세그먼트 단위의 스트리밍은 `loading.tsx`(unit08 참고)를 두면 자동으로 `Suspense`가 감싸진다.

```tsx
// app/dashboard/page.tsx — Suspense 경계마다 별도 청크로 스트리밍
import { Suspense } from "react";

export default function Dashboard() {
  return (
    <section>
      <h1>대시보드</h1>                                    {/* 첫 청크 */}
      <Suspense fallback={<div className="skeleton" />}>
        <SalesChart />                                      {/* 준비되면 두 번째 청크 */}
      </Suspense>
      <Suspense fallback={<div className="skeleton" />}>
        <RecentOrders />                                    {/* 준비되면 세 번째 청크 */}
      </Suspense>
    </section>
  );
}
```

### 5. 선택적 하이드레이션(Selective Hydration)

스트리밍과 짝을 이루는 React 18의 기능으로, **도착한 청크부터 독립적으로 하이드레이션**하며, 사용자가 아직 하이드레이션되지 않은 영역을 클릭하면 **그 영역을 우선 처리**한다.

- 전체 번들이 도착·실행될 때까지 아무것도 반응하지 않던 문제를 해결한다. `Suspense` 경계가 곧 하이드레이션의 단위가 된다.
- 클릭 이벤트는 React가 기록해 두었다가 하이드레이션 완료 직후 재생(replay)한다.
- 결과적으로 `Suspense` 경계는 **데이터 대기 단위 + 스트리밍 청크 단위 + 하이드레이션 우선순위 단위**라는 세 가지 역할을 동시에 한다.

> 💡 스트리밍이 동작하려면 응답 헤더가 먼저 전송된 뒤 본문이 나뉘어 와야 한다. 따라서 **스트리밍이 시작된 뒤에는 상태 코드·헤더·쿠키를 바꿀 수 없다**. `redirect()`나 `notFound()`는 첫 청크가 나가기 전(레이아웃·페이지 최상단)에 호출해야 정상 동작하며, 이미 스트리밍 중이라면 클라이언트 측 리다이렉트로 처리된다.

<br>

### 6. 흔한 함정 정리

- **레이아웃 시프트**: fallback과 실제 콘텐츠의 크기가 다르면 청크가 도착할 때 화면이 밀린다. 스켈레톤은 실제 콘텐츠와 **같은 높이**로 만든다.
- **fallback 안의 상호작용**: fallback은 하이드레이션 우선순위가 낮으므로 중요한 버튼을 넣지 않는다.
- **캐시 헤더와 스트리밍**: 프록시·CDN이 응답을 버퍼링하면 스트리밍 효과가 사라진다. 인프라(unit08 미들웨어 포함)에서 압축·버퍼링 설정을 확인한다.
- **개발 모드에서만 안 보이는 오류**: 하이드레이션 경고는 개발 모드에서 상세히, 프로덕션에서는 축약되어 나타난다. 배포 전에 개발 콘솔의 경고를 모두 없앤다.

❗️**`typeof window` 분기 자체가 문제**: 서버·클라이언트에서 다른 JSX를 반환하는 분기는 어떤 형태든 미스매치를 만든다. "브라우저에서만 다르게"는 반드시 **하이드레이션 이후(이펙트)**로 미룬다.

### 7. 정리 — 면접·실무 체크포인트

| **질문**                                          | **핵심 답변**                                                                                   |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| **하이드레이션이란?**                             | 서버 HTML에 React가 이벤트·상태를 연결해 상호작용 가능하게 만드는 과정. DOM 재생성 없이 대조·부착 |
| **미스매치의 대표 원인은?**                       | 시간·난수, `window` 분기, 저장소 초기값, 로케일, 잘못된 HTML 중첩, 확장 프로그램                |
| **해결 원칙은?**                                  | **첫 렌더링은 서버와 동일하게**, 브라우저 값은 `useEffect`·`useSyncExternalStore`로 이후에 반영 |
| **스트리밍 SSR의 이점은?**                        | 느린 데이터가 전체 응답을 막지 않음. 셸을 먼저 보내 TTFB·FCP 개선, `Suspense` 단위로 순서 무관 전송 |
| **선택적 하이드레이션이란?**                      | 도착한 청크부터, 사용자가 상호작용한 영역부터 우선 하이드레이션                                  |
| **스트리밍 중 리다이렉트가 안 되는 이유는?**      | 헤더가 이미 전송됨. `redirect`·쿠키 설정은 첫 청크 전에 수행                                    |

- 서버 컴포넌트를 늘리고 클라이언트 경계를 잎으로 내리면(unit02) 하이드레이션 대상 자체가 줄어든다.
- `Suspense` 경계 배치 기준은 unit03, 번들 크기 최적화는 unit09를 참고할 것.
