## 렌더링 전략 선택

Next.js는 한 애플리케이션 안에서 페이지(라우트)마다 **SSR·SSG·ISR·CSR**을 다르게 선택할 수 있는 프레임워크다. "언제, 어디서 HTML을 만들 것인가"라는 질문에 대한 답이 곧 렌더링 전략이며, 이 선택이 초기 로딩 속도·데이터 신선도·서버 비용·SEO를 한꺼번에 결정하므로 App Router(Next.js 14/15)의 판단 기준과 트레이드오프를 정확히 알아야 한다.

<br>

### 1. 렌더링 전략이란 — "HTML을 누가, 언제 만드는가"

- **CSR(Client-Side Rendering, 클라이언트 사이드 렌더링)**: 빈 HTML을 받고 브라우저가 JavaScript를 실행해 화면을 그림
- **SSR(Server-Side Rendering, 서버 사이드 렌더링)**: 요청이 올 때마다 서버가 HTML을 생성해 응답함
- **SSG(Static Site Generation, 정적 사이트 생성)**: 빌드 시점에 HTML을 미리 만들어 두고 CDN에서 그대로 서빙함
- **ISR(Incremental Static Regeneration, 증분 정적 재생성)**: SSG로 만든 페이지를 일정 주기나 이벤트에 따라 **백그라운드에서 다시 생성**함

```
                 빌드 시점            요청 시점                 브라우저
SSG   :  [HTML 생성] ──────────→  CDN에서 그대로 응답  ──→  하이드레이션
ISR   :  [HTML 생성] ─(만료 후)─→ 캐시 응답 + 백그라운드 재생성 → 하이드레이션
SSR   :  (없음)      ──────────→  [요청마다 HTML 생성] ──→  하이드레이션
CSR   :  (빈 껍데기) ──────────→  빈 HTML 응답        ──→  JS 실행 후 렌더링
```

> 💡 App Router에서는 이 네 가지가 별도 API로 존재하지 않는다. 라우트가 **정적(Static)으로 렌더링되는지, 동적(Dynamic)으로 렌더링되는지**가 기본 축이고, 정적 라우트에 재검증 주기를 붙이면 ISR, 클라이언트 컴포넌트에서 `useEffect`로 데이터를 가져오면 CSR이 된다.

<br>

### 2. App Router의 정적 렌더링과 동적 렌더링

### 2-1. 기본값은 정적 렌더링

App Router의 서버 컴포넌트는 기본적으로 **빌드 시점에 정적으로 렌더링**된다. 결과 HTML과 RSC 페이로드는 전체 라우트 캐시(unit04 참고)에 저장되어 요청마다 재사용된다.

```tsx
// app/about/page.tsx — 데이터 의존성이 없으므로 빌드 시 정적 생성(SSG)
export default function AboutPage() {
  return <h1>회사 소개</h1>;
}
```

<br>

### 2-2. 동적 렌더링으로 전환되는 조건

다음 중 하나라도 사용하면 Next.js는 해당 라우트를 **요청 시점 렌더링(SSR)**으로 자동 전환한다. 이를 **동적 API(Dynamic API)** 사용이라 부른다.

| **전환 조건**                            | **이유**                                             |
| ---------------------------------------- | ---------------------------------------------------- |
| **`cookies()`, `headers()`**             | 요청 정보를 읽어야 하므로 빌드 시 알 수 없음         |
| **`searchParams` 접근**                  | URL 쿼리마다 결과가 달라짐                           |
| **`fetch(url, { cache: 'no-store' })`**  | 캐시하지 않는 데이터에 의존함                        |
| **`export const dynamic = 'force-dynamic'`** | 개발자가 명시적으로 강제함                       |
| **`connection()` / `unstable_noStore()`** | 정적 생성에서 명시적으로 제외함                     |

```tsx
// app/dashboard/page.tsx — cookies()를 읽는 순간 라우트 전체가 SSR로 전환
import { cookies } from "next/headers";

export default async function DashboardPage() {
  const cookieStore = await cookies(); // Next.js 15부터 비동기 API
  const theme = cookieStore.get("theme")?.value ?? "light";
  return <main data-theme={theme}>대시보드</main>;
}
```

> ⚠️ Next.js 15부터 `cookies()`, `headers()`, `params`, `searchParams`는 **Promise를 반환하는 비동기 API**로 바뀌었다. 14에서는 동기적으로 접근했으므로 코드 예시를 볼 때 버전을 확인해야 한다. 또한 15에서는 `fetch`가 **기본적으로 캐시되지 않으므로**(unit04 참고) 옵션 없는 `fetch`만으로는 정적 라우트가 자동으로 동적 라우트가 되지는 않지만, 정적 라우트 안의 `fetch` 결과는 빌드 시 한 번 실행된 값이 HTML에 고정된다는 점에 주의한다.

<br>

### 3. 네 가지 전략의 트레이드오프 비교

| **항목**            | **SSG**                   | **ISR**                            | **SSR**                        | **CSR**                          |
| ------------------- | ------------------------- | ---------------------------------- | ------------------------------ | -------------------------------- |
| **HTML 생성 시점**  | **빌드 시**               | 빌드 시 + **주기적 재생성**        | **요청 시**                    | 브라우저에서 JS 실행 후          |
| **TTFB(첫 바이트)** | 가장 빠름 (CDN)           | 빠름 (캐시 적중 시)                | 느림 (서버 연산 대기)          | 빠름 (빈 HTML)                   |
| **데이터 신선도**   | 빌드 시점에 고정          | **재검증 주기만큼 지연**           | **항상 최신**                  | 항상 최신                        |
| **서버 부하**       | 거의 없음                 | 낮음                               | **요청마다 발생**              | API 서버만 부담                  |
| **SEO**             | 우수                      | 우수                               | 우수                           | 불리 (크롤러가 빈 HTML을 볼 수 있음) |
| **개인화**          | 불가                      | 불가 (공용 캐시)                   | **가능** (쿠키·헤더 활용)      | 가능                             |
| **적합한 예**       | 문서·랜딩·약관            | 블로그·상품 목록·뉴스              | 대시보드·검색 결과·장바구니    | 실시간 채팅·에디터·관리자 툴     |

<br>

### 4. 판단 기준 — 질문 세 가지로 결정한다

```
Q1. 사용자마다 내용이 다른가? (로그인·쿠키·헤더 의존)
    ├─ 예 → Q3으로
    └─ 아니오 → Q2로
Q2. 데이터가 얼마나 자주 바뀌는가?
    ├─ 거의 안 바뀜(배포 때만)      → SSG
    ├─ 분·시간 단위로 바뀜           → ISR (revalidate 지정)
    └─ 요청마다 달라야 함            → SSR
Q3. 검색 노출(SEO)과 첫 화면 속도가 중요한가?
    ├─ 예  → SSR (+ 스트리밍으로 TTFB 보완, unit07 참고)
    └─ 아니오 → CSR (클라이언트 컴포넌트 + useEffect·SWR·TanStack Query)
```

- **개인화 여부**가 첫 번째 분기점이다. 공용 캐시에 개인 데이터가 섞이면 보안 사고로 이어지므로, 개인화가 필요하면 SSG·ISR은 선택지에서 빠진다.
- **변경 빈도**는 SSG와 ISR·SSR을 가르는 기준이다. "1분 정도 늦어도 괜찮은가"를 물어보면 대부분의 콘텐츠 페이지가 ISR로 수렴한다.
- **SEO와 첫 화면 속도**가 필요 없다면 서버에서 HTML을 만들 이유가 줄어들어 CSR도 충분하다.

<br>

### 5. 하나의 페이지 안에서 전략 섞기

App Router의 핵심 장점은 **페이지 단위가 아니라 컴포넌트 단위**로 전략을 섞을 수 있다는 점이다. 뼈대는 정적으로 만들고, 개인화·실시간 영역만 동적으로 처리한다.

```tsx
// app/products/[id]/page.tsx
import { Suspense } from "react";
import { ProductDetail } from "./product-detail";      // 서버 컴포넌트, ISR
import { LiveStock } from "./live-stock";              // 클라이언트 컴포넌트, CSR

export const revalidate = 60; // 상품 정보는 60초 주기로 재생성(ISR)

export default async function ProductPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  return (
    <>
      <ProductDetail id={id} />
      <Suspense fallback={<p>재고 확인 중...</p>}>
        <LiveStock id={id} /> {/* 브라우저에서 주기적으로 폴링 */}
      </Suspense>
    </>
  );
}
```

> 💡 이렇게 "정적 껍데기 + 동적 구멍" 구조를 한 라우트 안에서 자동으로 처리하는 것이 **부분 사전 렌더링(Partial Prerendering, PPR)**의 목표다. Next.js 14에서 실험 기능으로 공개됐고 15에서도 여전히 실험 단계였으므로, 안정화 시점과 설정 방법은 버전에 따라 다를 수 있다.

<br>

### 6. 흔한 실수와 함정

- **정적 라우트에 시간 의존 코드 넣기**: `new Date()`로 "현재 시각"을 찍어 두면 빌드 시각이 영원히 표시된다. 시간·난수는 클라이언트 컴포넌트에서 처리하거나 동적 렌더링을 선택한다.
- **루트 레이아웃에서 `cookies()` 호출**: 레이아웃은 하위 모든 라우트가 공유하므로, 여기서 동적 API를 쓰면 **사이트 전체가 SSR로 전환**된다. 개인화가 필요한 부분만 하위 컴포넌트로 분리한다.
- **SSR을 "항상 최신"으로 과신하기**: SSR이라도 안에서 호출한 `fetch`에 `force-cache`나 `revalidate`가 붙어 있으면 데이터 캐시에서 오래된 값을 읽을 수 있다(unit05 참고).
- **CSR로 도망가기**: 하이드레이션 오류나 캐시 문제가 어렵다고 모든 페이지를 클라이언트 컴포넌트로 만들면 번들이 커지고 SEO·초기 로딩이 나빠진다. 문제의 원인은 unit02·unit07에서 다룬다.

❗️**빌드 로그 확인 습관**: `next build` 결과의 라우트 목록에서 `○`(Static)·`●`(SSG with params)·`ƒ`(Dynamic) 기호를 확인하면 의도한 전략대로 빌드됐는지 즉시 알 수 있다. 기호 표기는 버전에 따라 다를 수 있다.

<br>

### 7. 정리 — 면접·실무 체크포인트

| **질문**                                              | **핵심 답변**                                                                 |
| ----------------------------------------------------- | ----------------------------------------------------------------------------- |
| **SSR과 SSG의 차이는?**                               | HTML 생성 시점이 **요청 시**냐 **빌드 시**냐. 신선도와 서버 부하를 맞바꿈     |
| **ISR은 왜 필요한가?**                                | SSG의 속도를 유지하면서 **재배포 없이** 콘텐츠를 갱신하기 위해                |
| **App Router에서 SSR로 전환되는 조건은?**             | `cookies()`·`headers()`·`searchParams`·`no-store`·`force-dynamic` 등 동적 API 사용 |
| **CSR의 단점은?**                                     | 빈 HTML로 인한 SEO 불리, JS 로딩 전까지 빈 화면, 번들 크기 증가               |
| **한 페이지에 여러 전략을 섞을 수 있는가?**           | 가능. 서버 컴포넌트 + `Suspense` + 클라이언트 컴포넌트로 컴포넌트 단위 분리    |
| **Next.js 14와 15의 차이 중 렌더링과 관련된 것은?**   | 15에서 `fetch` 기본 미캐시, 요청 API(`cookies` 등)의 비동기화                  |

- 판단 순서는 **개인화 여부 → 변경 빈도 → SEO·초기 속도 필요성**이다.
- 기본값은 정적 렌더링이며, 동적 API를 쓰는 순간 라우트 전체가 동적으로 바뀐다는 점이 가장 자주 나오는 함정이다.
- 서버·클라이언트 컴포넌트의 경계는 unit02, 캐시 계층은 unit04, 스트리밍과 하이드레이션은 unit07을 참고할 것.
