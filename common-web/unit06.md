## 브라우저 저장소와 세션 유지

HTTP는 상태를 기억하지 않으므로(stateless) 로그인 상태·장바구니·사용자 설정을 유지하려면 **브라우저 쪽 저장소**가 필요하다. Cookie·LocalStorage·SessionStorage의 동작 차이, 쿠키 속성(특히 `SameSite`)의 의미, 그리고 세션 유지에 어떤 저장소를 써야 하는지를 다룬다.

<br>

### 1. 세 저장소 한눈에 비교

| **항목**               | **Cookie**                              | **LocalStorage**                 | **SessionStorage**               |
| ---------------------- | --------------------------------------- | -------------------------------- | -------------------------------- |
| **용량**               | 쿠키당 약 **4KB**, 도메인당 개수 제한   | 출처당 약 **5MB** (브라우저별 상이) | 출처당 약 5MB (브라우저별 상이) |
| **서버 전송**          | 조건에 맞는 **모든 요청에 자동 첨부**   | 전송 안 함                       | 전송 안 함                       |
| **수명**               | `Expires`/`Max-Age`로 지정, 없으면 브라우저 종료 시 | **명시적 삭제 전까지 영구** | **탭(브라우징 컨텍스트) 닫으면 삭제** |
| **범위**               | 도메인 + 경로 (**포트·스킴 구분 안 함**) | 출처(Origin) 단위                | 출처 + **탭 단위**               |
| **탭 간 공유**         | 공유                                    | 공유 (`storage` 이벤트로 감지)   | **공유 안 함**                   |
| **JS 접근 차단**       | `HttpOnly`로 가능                       | 불가 (항상 JS에서 읽힘)          | 불가                             |
| **API**                | `document.cookie` (문자열 파싱 필요)    | `localStorage.setItem` (동기)    | `sessionStorage.setItem` (동기)  |
| **서버에서 설정**      | `Set-Cookie` 헤더로 **가능**            | 불가                             | 불가                             |

> 💡 셋의 차이를 물으면 **"서버로 자동 전송되는가", "수명", "JS에서 읽을 수 있는가"** 세 축으로 답한다. 이 세 축이 곧 unit08에서 다루는 "토큰을 어디에 저장할 것인가" 판단의 근거가 된다.

<br>

### 2. Cookie

### 2-1. 동작 방식

쿠키는 서버가 `Set-Cookie` 응답 헤더로 내려주고, 브라우저가 저장했다가 **조건이 맞는 요청마다 `Cookie` 헤더에 자동으로 실어 보내는** 작은 데이터다. 개발자가 코드로 첨부하지 않아도 전송된다는 점이 다른 저장소와의 결정적 차이다.

```
① 로그인 요청
   POST /login
   ──────────────────────────────────────────────▶ 서버: 세션 생성, id=abc123
② 응답
   Set-Cookie: sid=abc123; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=86400
   ◀──────────────────────────────────────────────
③ 이후 모든 요청 (브라우저가 자동 첨부)
   GET /orders
   Cookie: sid=abc123
   ──────────────────────────────────────────────▶ 서버: abc123 → 사용자 식별
```

```javascript
// JS에서 쿠키 다루기 — HttpOnly가 아닌 쿠키만 보임
document.cookie = 'theme=dark; Path=/; Max-Age=2592000; SameSite=Lax';
const theme = document.cookie
  .split('; ')
  .find((row) => row.startsWith('theme='))
  ?.split('=')[1];
```

<br>

### 2-2. 쿠키 속성

| **속성**         | **의미**                                                        | **미지정 시**                                 |
| ---------------- | --------------------------------------------------------------- | --------------------------------------------- |
| **Expires / Max-Age** | 만료 시각 / 남은 초. 둘 다 있으면 `Max-Age` 우선           | **세션 쿠키** — 브라우저 종료 시 삭제         |
| **Domain**       | 쿠키를 보낼 도메인. 지정하면 **서브도메인 포함**                | 설정한 호스트에만 (서브도메인 제외)           |
| **Path**         | 쿠키를 보낼 경로 접두사                                         | `Set-Cookie`를 보낸 URL의 디렉터리            |
| **Secure**       | **HTTPS**에서만 전송                                            | HTTP에서도 전송 (탈취 위험)                   |
| **HttpOnly**     | `document.cookie`로 **읽기·쓰기 불가**                          | JS에서 읽힘 → XSS로 탈취 가능                 |
| **SameSite**     | 크로스 사이트 요청에 쿠키를 첨부할지 결정                       | 최신 Chrome 등은 **Lax**로 취급 (브라우저별 상이) |

> ⚠️ 쿠키의 범위는 **도메인과 경로**로만 정해지며 **포트와 스킴을 구분하지 않는다**. `http://example.com`이 설정한 쿠키는 `https://example.com:8443`에도 전송된다(`Secure`가 없다면). 반면 LocalStorage는 스킴·호스트·포트가 모두 같은 **출처(Origin)** 단위다. 출처 개념은 unit07 참고.

<br>

### 2-3. SameSite 속성

`SameSite`는 **다른 사이트에서 시작된 요청**에 쿠키를 붙일지 결정하며, CSRF(unit08) 방어의 1차 수단이다. 여기서 "사이트"는 출처보다 넓은 개념으로, **등록 가능한 도메인(eTLD+1) + 스킴** 기준이다. `a.example.com`과 `b.example.com`은 다른 출처지만 **같은 사이트**다.

| **값**       | **크로스 사이트 요청에 쿠키 전송**                                        | **용도**                                |
| ------------ | ------------------------------------------------------------------------- | --------------------------------------- |
| **Strict**   | **절대 전송 안 함**. 외부 링크로 들어와도 로그인 풀린 것처럼 보임        | 은행·결제처럼 보안이 최우선인 쿠키      |
| **Lax**      | **최상위 탐색(주소창 이동·링크 클릭) + 안전한 메서드(GET)**만 전송. 이미지 태그·`fetch`·POST 폼은 제외 | 일반 세션 쿠키의 기본 선택 |
| **None**     | 항상 전송. **반드시 `Secure`와 함께** 써야 함                            | 서드파티 임베드(결제 위젯, SSO iframe)  |

```
외부 사이트(evil.com)에서 mybank.com으로 향하는 요청       Strict   Lax   None
─────────────────────────────────────────────────────────  ──────  ────  ────
<a href="https://mybank.com/">  링크 클릭(최상위 GET)          ✗       ○     ○
<form method="POST" action="https://mybank.com/transfer">   ✗       ✗     ○
fetch('https://mybank.com/api', { credentials: 'include' })  ✗       ✗     ○
```

안티패턴 — 속성 없는 세션 쿠키는 HTTP 전송·JS 접근·크로스 사이트 POST를 모두 허용한다.

```http
Set-Cookie: sid=abc123
```

개선 — 전송 조건을 최대한 좁힌다.

```http
Set-Cookie: sid=abc123; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=86400
```

❗️**SameSite=None 없이 크로스 사이트 쿠키가 안 붙는 문제**: 프론트엔드 `app.example.com`과 API `api.example.com`은 같은 사이트라 `Lax`로도 동작하지만, 프론트 `app.com`과 API `api.io`처럼 **사이트가 다르면** `SameSite=None; Secure`와 CORS `credentials` 설정(unit07)이 모두 필요하다.

<br>

### 3. Web Storage — LocalStorage와 SessionStorage

둘 다 **키-값 문자열 저장소**이며 API가 같고 수명과 범위만 다르다.

```javascript
// 객체는 반드시 문자열로 직렬화해야 함 — 값은 항상 string
localStorage.setItem('settings', JSON.stringify({ theme: 'dark', lang: 'ko' }));
const settings = JSON.parse(localStorage.getItem('settings') ?? '{}');
localStorage.removeItem('settings');

// 탭 단위: 새 탭에서는 비어 있고, 탭을 닫으면 사라짐. 새로고침에는 살아남음
sessionStorage.setItem('draft', textarea.value);

// 다른 탭의 localStorage 변경을 감지 (같은 탭에서는 발생하지 않음)
window.addEventListener('storage', (e) => {
  if (e.key === 'settings') applySettings(JSON.parse(e.newValue ?? '{}'));
});
```

**특성과 주의점**

- API가 **동기**라서 큰 값을 자주 읽고 쓰면 메인 스레드를 막음 (unit03). 수 MB 이상의 데이터는 비동기인 **IndexedDB**를 사용함
- 용량 초과 시 `QuotaExceededError` 예외가 발생하므로 `try/catch`로 감쌈
- 시크릿 모드·저장소 차단 설정에서는 접근 자체가 예외를 던질 수 있음
- **서버로 전송되지 않으므로** 서버가 필요로 하는 식별자(세션 ID)를 여기에 두면 매 요청마다 JS가 헤더에 직접 실어야 함

> ⚠️ Web Storage는 `HttpOnly` 같은 보호 수단이 **없다**. 페이지에서 실행되는 모든 JS(서드파티 스크립트, XSS로 주입된 스크립트 포함)가 읽을 수 있다. 액세스 토큰을 LocalStorage에 두는 관행이 위험한 이유이며, 판단 기준은 unit08에서 다룬다.

<br>

### 4. 세션 유지 방식

로그인 상태를 유지하는 방식은 크게 **서버 세션 + 쿠키**와 **토큰 기반**으로 나뉜다.

```
[서버 세션 방식]
브라우저 ── Cookie: sid=abc ──▶ 서버 ── 세션 저장소(메모리·Redis)에서 abc 조회 ──▶ 사용자 식별
           (브라우저가 자동 첨부)         (상태를 서버가 보관)

[토큰 방식]
브라우저 ── Authorization: Bearer <JWT> ──▶ 서버 ── 서명 검증만으로 사용자 식별
           (JS가 저장소에서 꺼내 직접 첨부)   (상태를 서버가 보관하지 않음)
```

| **항목**            | **서버 세션 + 쿠키**                         | **토큰(JWT) + Web Storage**                    | **토큰 + HttpOnly 쿠키**                     |
| ------------------- | -------------------------------------------- | ---------------------------------------------- | -------------------------------------------- |
| **전송 방식**       | 브라우저 자동 첨부                           | JS가 헤더에 직접 첨부                          | 브라우저 자동 첨부                           |
| **XSS 시 탈취**     | `HttpOnly`면 **불가**                        | **가능** (JS로 읽힘)                           | **불가**                                     |
| **CSRF 위험**       | 있음 → `SameSite`·CSRF 토큰으로 방어         | 없음 (자동 첨부되지 않음)                      | 있음 → `SameSite`로 방어                     |
| **서버 상태**       | 세션 저장소 필요 (다중 서버면 공유 필요)     | 없음 (확장 용이)                               | 없음                                         |
| **즉시 무효화**     | 세션 삭제로 **즉시 가능**                    | 만료 전까지 어려움 (블랙리스트 필요)           | 만료 전까지 어려움                           |

세션 저장 위치 선택은 결국 **"자동 첨부의 편리함(=CSRF 노출)"과 "JS 접근 가능성(=XSS 노출)" 사이의 트레이드오프**다. 어느 쪽 위험을 어떤 수단으로 막을지는 unit08에서 판단 기준을 정리한다.

<br>

### 5. 정리

| **필요한 것**                         | **적합한 저장소**                      | **이유**                                        |
| ------------------------------------- | -------------------------------------- | ----------------------------------------------- |
| **서버가 매 요청마다 알아야 하는 식별자** | Cookie (`HttpOnly; Secure; SameSite`) | 자동 첨부 + JS 접근 차단                        |
| **탭을 닫아도 남을 UI 설정·캐시**     | LocalStorage                           | 영구, 출처 단위, 서버 전송 불필요               |
| **작성 중인 폼·탭별 임시 상태**       | SessionStorage                         | 탭 닫으면 자동 정리, 탭 간 간섭 없음            |
| **수 MB 이상의 구조화된 데이터**      | IndexedDB                              | 비동기, 대용량, 인덱스 지원                     |

- 쿠키는 **자동 전송**되고 `Set-Cookie`로 서버가 제어하며, `HttpOnly`·`Secure`·`SameSite`로 노출 범위를 좁힘
- `SameSite=Lax`는 **최상위 GET 탐색에만** 쿠키를 붙이고, `None`은 반드시 `Secure`와 함께 씀
- 쿠키 범위는 도메인·경로 기준(포트 무시), Web Storage는 **출처(Origin)** 기준임
- LocalStorage는 영구·탭 공유, SessionStorage는 탭 단위·탭 종료 시 삭제이며 둘 다 JS에서 항상 읽힘
- 세션 유지는 "자동 첨부(CSRF 노출)"와 "JS 접근(XSS 노출)"의 트레이드오프이며, 상세 판단은 unit08 참고
