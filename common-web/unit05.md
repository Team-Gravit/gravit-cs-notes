## 렌더링 전략

HTML을 **누가(클라이언트·서버·빌드 도구), 언제(요청 시·빌드 시·주기적으로)** 만들어 내느냐에 따라 CSR·SSR·SSG·ISR로 나뉜다. 각 전략이 첫 화면 속도·SEO·서버 비용·데이터 최신성에 미치는 영향과, 서버 렌더링에 따라오는 **하이드레이션(Hydration) 비용**을 이해해야 서비스 특성에 맞는 전략을 고를 수 있다.

<br>

### 1. 렌더링 전략이란

브라우저는 결국 HTML을 받아 unit01의 파이프라인으로 화면을 그린다. 렌더링 전략의 차이는 **"의미 있는 HTML이 언제, 어디서 만들어지는가"**에 있다.

```
CSR   서버: 빈 HTML + JS 번들 ──▶ 브라우저: JS 실행 → 데이터 요청 → DOM 생성 → 화면
SSR   서버: 요청마다 데이터 조회 + HTML 생성 ──▶ 브라우저: HTML 즉시 표시 → JS 로드 → 하이드레이션
SSG   빌드 시: HTML 생성 ──▶ CDN 배포 ──▶ 브라우저: HTML 즉시 표시 → 하이드레이션
ISR   빌드 시: HTML 생성 ──▶ CDN 배포 ──▶ 일정 주기·조건으로 백그라운드 재생성
```

> 💡 면접에서는 "CSR과 SSR의 차이"로 시작해 "그럼 SSR은 항상 좋은가", "하이드레이션이 뭔가"로 파고든다. **HTML이 만들어지는 위치·시점**, **첫 화면(FCP)과 상호작용 가능 시점(TTI)의 분리**, **서버 비용** 세 축으로 답하면 된다.

<br>

### 2. CSR (Client-Side Rendering)

서버는 거의 빈 HTML(`<div id="root"></div>`)과 JavaScript 번들만 보내고, 브라우저가 JS를 실행해 데이터를 받아 화면을 만든다.

```html
<!-- 서버가 보내는 HTML: 내용이 없음 -->
<body>
  <div id="root"></div>
  <script src="/static/bundle.js" defer></script>
</body>
```

```
타임라인
HTML 도착 ─▶ JS 다운로드 ─▶ JS 실행 ─▶ API 요청 ─▶ 응답 ─▶ DOM 생성 ─▶ 첫 화면
   │                                                           │
   └──────────── 이 구간 동안 사용자는 흰 화면을 봄 ─────────────┘
```

- **장점**: 서버는 정적 파일만 서빙하므로 부하가 적고 CDN만으로 배포 가능. 한 번 로드된 뒤 페이지 전환이 빠름
- **단점**: 번들을 받고 실행하기 전까지 **흰 화면**. 검색 엔진 크롤러가 JS를 실행하지 않거나 늦게 실행하면 **SEO 불리**. 번들이 커질수록 첫 화면이 늦어짐
- **적합**: 로그인 뒤에만 쓰는 관리자 도구·대시보드처럼 SEO가 무의미하고 상호작용이 많은 앱

<br>

### 3. SSR (Server-Side Rendering)

요청이 올 때마다 서버가 데이터를 조회해 **완성된 HTML**을 만들어 보낸다. 브라우저는 HTML을 받자마자 내용을 표시할 수 있다.

```typescript
// 서버 측 의사 코드: 요청마다 데이터 조회 후 HTML 문자열 생성
async function handleRequest(req: Request): Promise<Response> {
  const product = await db.findProduct(req.params.id);      // 요청 시점의 최신 데이터
  const html = renderToString(<ProductPage product={product} />);
  return new Response(`<!doctype html>${html}`, {
    headers: { 'content-type': 'text/html; charset=utf-8' },
  });
}
```

- **장점**: 첫 화면(FCP)이 빠르고, 크롤러가 완성된 HTML을 바로 읽어 **SEO에 유리**. 항상 최신 데이터
- **단점**: 요청마다 서버가 렌더링하므로 **서버 비용과 TTFB(첫 바이트 도착 시간)가 증가**. 데이터 조회가 느리면 HTML 자체가 늦게 도착함
- **적합**: 상품 상세·뉴스처럼 SEO가 중요하고 데이터가 자주 바뀌는 페이지

> ⚠️ SSR로 HTML이 먼저 보인다고 해서 바로 클릭이 되는 것은 아니다. 이벤트 핸들러는 JS가 로드되고 **하이드레이션이 끝나야** 붙는다. "보이는데 안 눌리는" 구간이 생기며, 이 간극이 클수록 사용자는 혼란을 느낀다.

<br>

### 4. SSG와 ISR

### 4-1. SSG (Static Site Generation)

**빌드 시점**에 모든 페이지의 HTML을 미리 만들어 두고 CDN에 배포한다. 요청 시 서버 연산이 전혀 없어 가장 빠르고 저렴하다.

- **장점**: TTFB 최소, 서버 비용 거의 0, CDN 캐시 적중률 최고, 트래픽 폭증에 강함
- **단점**: 내용이 바뀌면 **재빌드·재배포**가 필요함. 페이지 수가 수만 개면 빌드 시간이 길어짐
- **적합**: 블로그, 문서 사이트, 마케팅 랜딩 페이지처럼 변경이 드문 콘텐츠

<br>

### 4-2. ISR (Incremental Static Regeneration)

SSG의 "재빌드 필요" 문제를 완화한 방식이다. 정적 HTML을 서빙하되, **일정 시간이 지나거나 특정 이벤트가 발생하면 해당 페이지만 백그라운드에서 다시 생성**한다.

```
요청 ① (캐시 신선)      ─▶ 캐시된 HTML 즉시 응답
요청 ② (만료 시간 경과) ─▶ 오래된(stale) HTML 즉시 응답 + 백그라운드로 재생성 시작
요청 ③ (재생성 완료 후) ─▶ 새 HTML 응답
```

이 패턴은 unit09에서 다루는 HTTP 캐시의 **stale-while-revalidate**와 같은 사고방식이다. 사용자는 항상 빠른 응답을 받고, 데이터는 "약간 오래됐을 수 있지만 곧 갱신되는" 상태를 유지한다.

- **시간 기반 재검증**: N초마다 갱신 (예: 상품 목록은 60초)
- **온디맨드 재검증**: CMS에서 글을 수정하면 웹훅으로 해당 페이지만 즉시 갱신
- **적합**: 커머스 카테고리, 블로그 목록처럼 자주는 아니지만 갱신되는 페이지

❗️**ISR의 첫 방문자는 오래된 데이터를 본다**: 재생성은 백그라운드에서 일어나므로 만료 직후의 요청은 stale 콘텐츠를 받는다. 재고·가격처럼 오차를 허용할 수 없는 값은 클라이언트에서 별도 API로 덧씌우거나 SSR을 써야 한다.

<br>

### 5. 하이드레이션(Hydration)과 그 비용

서버가 만든 HTML은 **정적인 그림**일 뿐이다. 클릭·입력에 반응하려면 브라우저에서 JS가 실행되어 기존 DOM에 **이벤트 핸들러와 상태를 연결**해야 하는데, 이 과정이 하이드레이션이다.

```
서버 HTML 도착 ─▶ 화면 표시(FCP) ─▶ JS 번들 다운로드 ─▶ 컴포넌트 트리 재구성 ─▶ DOM과 대조·이벤트 연결 ─▶ 상호작용 가능(TTI)
                     │                                                                          │
                     └─────────────── "보이지만 반응하지 않는" 구간 (Uncanny Valley) ────────────┘
```

**비용이 발생하는 이유**

- 서버에서 이미 렌더링한 컴포넌트 트리를 클라이언트에서 **한 번 더 실행**해야 DOM 구조와 대응시킬 수 있음 (사실상 두 번 렌더링)
- 하이드레이션에 필요한 JS 번들은 CSR 앱과 **크기가 거의 같음**. SSR이 JS 양을 줄여 주지는 않음
- 하이드레이션은 보통 **하나의 긴 태스크**로 실행되어 그동안 입력에 반응하지 못함 (unit03의 긴 태스크 문제)
- 서버 HTML과 클라이언트 렌더 결과가 다르면 **하이드레이션 불일치(mismatch)** 경고가 나고 DOM을 다시 그림

```typescript
// 하이드레이션 불일치를 만드는 대표 코드: 서버와 클라이언트에서 값이 다름
function Greeting() {
  const hour = new Date().getHours();                // 서버 시각 ≠ 브라우저 시각
  return <p>{hour < 12 ? '좋은 아침' : '좋은 오후'}</p>;
}

// 개선: 서버에서는 중립 값을 렌더링하고, 마운트 이후에만 브라우저 값을 사용
function Greeting() {
  const [hour, setHour] = useState<number | null>(null);
  useEffect(() => setHour(new Date().getHours()), []);   // 클라이언트에서만 실행
  return <p>{hour === null ? '안녕하세요' : hour < 12 ? '좋은 아침' : '좋은 오후'}</p>;
}
```

**비용을 줄이는 접근**

| **기법**                        | **아이디어**                                                      |
| ------------------------------- | ----------------------------------------------------------------- |
| **스트리밍 SSR**                | HTML을 조각 단위로 흘려보내 느린 데이터 영역을 기다리지 않고 표시 |
| **선택적·점진적 하이드레이션**  | 뷰포트 안·상호작용 필요한 부분부터 우선 하이드레이션              |
| **아일랜드 아키텍처**           | 상호작용이 필요한 "섬"만 JS를 보내고 나머지는 정적 HTML로 유지     |
| **서버 컴포넌트**               | 서버에서만 실행되는 컴포넌트는 JS 번들에 포함하지 않음            |

> 💡 하이드레이션 개선 기법의 세부 동작과 이름은 프레임워크·버전에 따라 다르다. 면접에서는 특정 API보다 **"클라이언트에 보내는 JS 양을 줄이거나, 하이드레이션 순서를 쪼개 긴 태스크를 피한다"**는 원리로 답하는 것이 안전하다.

<br>

### 6. 선택 기준

| **기준**                  | **CSR**          | **SSR**            | **SSG**            | **ISR**                |
| ------------------------- | ---------------- | ------------------ | ------------------ | ---------------------- |
| **HTML 생성 시점**        | 브라우저 런타임  | **요청 시**        | **빌드 시**        | 빌드 시 + 주기적 재생성 |
| **첫 화면(FCP)**          | 느림             | 빠름               | **가장 빠름**      | 가장 빠름              |
| **TTFB**                  | 빠름(정적 파일)  | **느림**(연산 필요) | 빠름              | 빠름                   |
| **SEO**                   | 불리             | 유리               | 유리               | 유리                   |
| **데이터 최신성**         | 실시간(API 호출) | **항상 최신**      | 빌드 시점          | 갱신 주기만큼 지연     |
| **서버 비용**             | 최소             | **높음**           | 최소               | 낮음                   |
| **하이드레이션 비용**     | 없음(전부 CSR)   | 있음               | 있음               | 있음                   |

**판단 순서**

- SEO나 링크 공유 미리보기가 필요 없고 로그인 뒤 화면이 대부분인가 → **CSR**
- 내용이 거의 바뀌지 않고 페이지 수가 감당 가능한가 → **SSG**
- 가끔 바뀌지만 약간의 지연을 허용할 수 있는가 → **ISR**
- 사용자·요청마다 다르거나 항상 최신이어야 하는가 → **SSR** (필요한 페이지에만 적용)
- 실제 서비스는 페이지별로 전략을 **혼합**하는 것이 일반적임 (랜딩은 SSG, 상세는 ISR, 마이페이지는 CSR)

<br>

### 7. 정리

- 렌더링 전략의 본질은 **"의미 있는 HTML을 언제·어디서 만드는가"**이며, 이것이 FCP·SEO·서버 비용·데이터 최신성을 결정함
- **CSR**은 서버가 가볍지만 흰 화면과 SEO 문제가 있고, **SSR**은 첫 화면과 SEO에 유리하지만 서버 비용과 TTFB가 늘어남
- **SSG**는 빌드 시 생성해 가장 빠르고 저렴하며, **ISR**은 여기에 백그라운드 재생성을 더해 갱신 문제를 완화함
- 서버 렌더링 방식은 모두 **하이드레이션** 비용을 지불하며, JS 번들 크기와 긴 태스크가 그 원인임
- 하이드레이션이 끝나기 전 "보이지만 반응하지 않는" 구간은 unit10의 **INP**와 사용자 체감에 직결됨
- ISR의 stale-while-revalidate 사고방식은 unit09의 HTTP 캐싱과 같은 원리임
