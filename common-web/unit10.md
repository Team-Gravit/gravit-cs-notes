## 웹 성능 지표와 측정

"빠르다"를 숫자로 정의하지 않으면 최적화의 효과를 증명할 수 없다. 이 유닛은 사용자 체감을 대표하는 **Core Web Vitals(LCP·INP·CLS)**의 정의와 기준, 각 지표가 앞선 유닛의 어떤 원리와 연결되는지, 그리고 **실사용자 측정(RUM)과 합성 측정(Lab)**을 어떻게 구분해 활용하는지를 다룬다.

<br>

### 1. 왜 사용자 중심 지표인가

과거의 `load` 이벤트 시간이나 `DOMContentLoaded`는 **사용자가 실제로 무엇을 보고 느꼈는지**를 반영하지 못한다. 서버 응답이 빨라도 흰 화면이 오래 보일 수 있고, 로드가 끝나도 클릭이 먹지 않을 수 있다. 사용자 중심 지표는 다음 질문에 대응한다.

| **사용자의 질문**            | **지표**                              | **측정 대상**                                    |
| ---------------------------- | ------------------------------------- | ------------------------------------------------ |
| **뭔가 뜨고 있나?**          | FCP (First Contentful Paint)          | 첫 텍스트·이미지가 그려진 시각                   |
| **핵심 내용이 보이나?**      | **LCP** (Largest Contentful Paint)    | 뷰포트 내 가장 큰 콘텐츠가 그려진 시각           |
| **눌렀는데 반응하나?**       | **INP** (Interaction to Next Paint)   | 상호작용 후 다음 화면 갱신까지의 지연            |
| **화면이 갑자기 튀지 않나?** | **CLS** (Cumulative Layout Shift)     | 예상치 못한 레이아웃 이동의 누적량               |
| **서버는 빨리 답했나?**      | TTFB (Time to First Byte)             | 요청 후 첫 응답 바이트까지의 시간                |

```
페이지 로드 타임라인
요청 ──▶ TTFB ──▶ FCP ──────▶ LCP ────────▶ (하이드레이션·JS 실행) ──▶ 사용자 상호작용 ──▶ INP
                  │ 뭔가 뜸     │ 핵심 콘텐츠 표시                                  │ 반응 속도
                  └─────────── 이 사이에 요소가 움직이면 CLS 누적 ──────────────────┘
```

> 💡 Google이 검색 순위 신호로 사용하는 **Core Web Vitals**는 현재 **LCP·INP·CLS** 세 가지다. INP는 2024년 3월에 FID(First Input Delay)를 대체했다. FID는 첫 입력의 "지연"만 봤지만, INP는 페이지 생애 전체의 상호작용 "반응 완료"까지 본다.

<br>

### 2. LCP — 핵심 콘텐츠 표시 시점

뷰포트 안에서 **가장 큰 이미지 또는 텍스트 블록**이 렌더링된 시각이다. 후보는 이미지 요소, `background-image`, 비디오 포스터, 블록 수준 텍스트 요소 등이며, 로드 중 더 큰 요소가 나타나면 후보가 갱신되다가 **첫 사용자 입력 시점에 확정**된다.

| **등급**          | **기준**            |
| ----------------- | ------------------- |
| **좋음**          | **2.5초 이하**      |
| **개선 필요**     | 2.5초 초과 4.0초 이하 |
| **나쁨**          | 4.0초 초과          |

**LCP를 4구간으로 나눠 진단**

```
TTFB ──▶ 리소스 로드 지연 ──▶ 리소스 로드 시간 ──▶ 요소 렌더 지연
 │           │                    │                    │
 서버·CDN    이미지가 언제         이미지 크기·          JS 실행·CSS 차단으로
 (unit09)    발견되는가(unit04)    네트워크              그리기가 늦어짐(unit01·03)
```

- **리소스 로드 지연**이 길다면 LCP 이미지가 CSS 배경이거나 `loading="lazy"`가 붙어 발견이 늦은 것 → `preload`, `fetchpriority="high"` (unit04)
- **렌더 지연**이 길다면 이미지는 도착했는데 렌더링 차단 CSS·긴 JS 태스크가 그리기를 막는 것 → CSS 분리, 하이드레이션 분할 (unit05)

<br>

### 3. INP — 상호작용 반응성

페이지에서 발생한 **모든 클릭·탭·키 입력**의 지연을 관찰해, 그중 **가장 느린 값(상호작용이 매우 많으면 상위 극단값 일부 제외)**을 보고한다. 호버·스크롤은 포함하지 않는다.

| **등급**          | **기준**            |
| ----------------- | ------------------- |
| **좋음**          | **200ms 이하**      |
| **개선 필요**     | 200ms 초과 500ms 이하 |
| **나쁨**          | 500ms 초과          |

**한 상호작용의 구성**

```
사용자 클릭
  │◀── 입력 지연 ──▶│◀─── 처리 시간 ───▶│◀── 표시 지연 ──▶│ 다음 프레임 페인트
  │ 메인 스레드가    │ 이벤트 핸들러      │ 렌더링 파이프라인 │
  │ 다른 태스크로    │ 실행(JS)           │ (스타일·레이아웃·  │
  │ 바쁨 (unit03)    │                    │  페인트, unit01)   │
```

- **입력 지연**: 긴 태스크(하이드레이션, 무거운 초기화)가 돌고 있으면 클릭 자체가 대기함
- **처리 시간**: 핸들러 안에서 큰 계산·동기 상태 갱신을 하면 길어짐
- **표시 지연**: 핸들러가 큰 DOM 변경을 유발해 레이아웃·페인트가 무거워지면 길어짐 (unit02)

```javascript
// 안티패턴: 클릭 핸들러가 무거운 계산과 대규모 DOM 갱신을 한 태스크에서 수행
button.addEventListener('click', () => {
  const result = expensiveFilter(bigList);    // 처리 시간 ↑
  renderAll(result);                          // 표시 지연 ↑
});

// 개선: 즉각적인 피드백을 먼저 그리고, 무거운 작업은 다음 태스크로 양보
button.addEventListener('click', () => {
  button.disabled = true;                     // 가벼운 상태 변경만 즉시
  setTimeout(() => {                          // 렌더링 기회를 준 뒤 실행 (unit03)
    renderAll(expensiveFilter(bigList));
    button.disabled = false;
  }, 0);
});
```

> ⚠️ INP는 **페이지 생애 전체**에서 측정되므로 초기 로드가 빨라도 소용없다. 무한 스크롤 피드에서 DOM이 수만 개로 불어난 뒤의 클릭, 탭 전환 시 거대한 목록 재렌더링이 INP를 망치는 전형이다. Lighthouse 같은 합성 도구는 상호작용을 재현하지 못해 **INP를 직접 측정할 수 없고**, 대신 TBT(Total Blocking Time)를 대리 지표로 보여준다.

<br>

### 4. CLS — 시각적 안정성

사용자 입력과 무관하게 **이미 보이던 요소가 움직인 정도**의 누적 점수다. 단위가 없는 비율 값이며, 입력 후 500ms 이내의 이동은 사용자가 의도한 것으로 보고 제외한다.

| **등급**          | **기준**            |
| ----------------- | ------------------- |
| **좋음**          | **0.1 이하**        |
| **개선 필요**     | 0.1 초과 0.25 이하  |
| **나쁨**          | 0.25 초과           |

**점수 계산**: `레이아웃 이동 점수 = 영향 비율 × 이동 거리 비율`. 여러 이동은 **세션 윈도우**(간격 1초 이내, 최대 5초)로 묶고, 가장 큰 윈도우의 합이 CLS가 된다.

```
뷰포트 높이 100 기준
┌──────────────┐        ┌──────────────┐
│ 헤더         │        │ 헤더         │
│ [광고 자리]  │  ─▶    │ ▓▓ 광고 ▓▓   │ ← 뒤늦게 삽입되어 30만큼 밀어냄
│ 본문 (높이 50)│        │ 본문         │   영향 비율 0.8 × 거리 비율 0.3 = 0.24
└──────────────┘        └──────────────┘
```

**흔한 원인과 해결**

- 크기 없는 이미지·광고·임베드 → `width`/`height` 속성 또는 `aspect-ratio`로 공간을 **미리 확보**
- 웹 폰트 로드 후 글자 크기 변화(FOUT) → `font-display: optional` 또는 `size-adjust`로 대체 폰트 크기 맞춤, 폰트 `preload` (unit04)
- 뒤늦게 위쪽에 삽입되는 배너·알림 → 아래가 아닌 **오버레이**로 표시하거나 공간을 예약
- `content-visibility: auto` 요소의 높이 미지정 → `contain-intrinsic-size` 지정 (unit02)
- `top`/`height` 애니메이션 → `transform` 애니메이션은 레이아웃 이동으로 **집계되지 않음** (unit02)

```html
<!-- 안티패턴: 크기 없는 이미지 — 로드 후 아래 콘텐츠가 밀림 -->
<figure class="thumb"></figure>

<!-- 개선: 종횡비를 미리 선언해 공간 확보 -->
<figure class="thumb" style="aspect-ratio: 16 / 9; width: 100%"></figure>
```

### 5. 실사용자 측정(RUM)과 합성 측정(Lab)

| **항목**           | **실사용자 측정 (Field / RUM)**                         | **합성 측정 (Lab / Synthetic)**                       |
| ------------------ | ------------------------------------------------------- | ----------------------------------------------------- |
| **데이터 출처**    | **실제 사용자**의 브라우저                              | 통제된 환경의 **시뮬레이션**                          |
| **대표 도구**      | CrUX(Chrome 사용자 경험 리포트), `web-vitals` 라이브러리, 자체 RUM | Lighthouse, WebPageTest, DevTools Performance |
| **측정 가능 지표** | LCP·INP·CLS 모두 (**INP는 RUM에서만**)                  | LCP·CLS·TBT·FCP (INP 불가)                            |
| **장점**           | 기기·네트워크·행동의 **실제 분포** 반영                 | **재현 가능**, 배포 전 검증, 원인 진단 상세           |
| **단점**           | 노이즈 많음, 원인 파악 어려움, 트래픽 필요              | 특정 기기·네트워크 가정, 상호작용 재현 한계           |
| **집계 기준**      | 페이지 뷰의 **75번째 백분위수(p75)**                    | 단일 실행 값 (여러 번 실행해 중앙값 권장)             |

> 💡 "Lighthouse 점수는 90인데 검색 콘솔에는 나쁨으로 나와요"는 두 측정의 차이를 이해하면 설명된다. Lighthouse는 개발자의 좋은 PC·네트워크에서 한 번 로드한 결과이고, 검색 콘솔(CrUX)은 저사양 모바일 사용자를 포함한 **p75** 값이다. 기준은 항상 **실사용자 p75**이며, Lab은 원인을 찾는 현미경으로 쓴다.

```typescript
// 실사용자 측정: web-vitals 라이브러리로 수집해 분석 서버로 전송
import { onLCP, onINP, onCLS } from 'web-vitals';

function report(metric: { name: string; value: number; rating: string; id: string }) {
  const body = JSON.stringify({ ...metric, path: location.pathname });
  // 페이지 이탈 시에도 전송을 보장 — sendBeacon은 응답을 기다리지 않음
  navigator.sendBeacon('/rum', body);
}

onLCP(report);
onINP(report);    // 페이지를 떠날 때(visibility hidden) 최종값이 보고됨
onCLS(report);
```

```javascript
// 라이브러리 없이 원시 API로 LCP 후보 관찰
new PerformanceObserver((list) => {
  const last = list.getEntries().at(-1);            // 마지막 항목이 현재 LCP 후보
  console.log('LCP 후보:', last.element, last.startTime.toFixed(0), 'ms');
}).observe({ type: 'largest-contentful-paint', buffered: true });
```

### 6. 측정 → 진단 → 개선 순환

```
① RUM(p75)으로 나쁜 지표·페이지 식별
       │
② Lab(Lighthouse·DevTools)으로 해당 페이지 재현, 원인 구간 특정
       │   LCP → 4구간 분해 / INP → 긴 태스크·핸들러 / CLS → 이동 요소 확인
③ 개선 적용 (앞선 유닛의 기법)
       │
④ Lab으로 회귀 확인 → 배포 → RUM으로 실제 개선 검증 (수일~수주 소요)
```

| **지표**  | **주된 원인**                                  | **관련 유닛**                                   |
| --------- | ---------------------------------------------- | ----------------------------------------------- |
| **LCP**   | 느린 TTFB, 늦게 발견되는 이미지, 렌더링 차단 리소스 | unit04(로딩), unit05(렌더링 전략), unit09(캐싱) |
| **INP**   | 긴 태스크, 무거운 핸들러, 대규모 DOM 갱신      | unit02(Reflow), unit03(이벤트 루프), unit05(하이드레이션) |
| **CLS**   | 크기 없는 미디어, 폰트 교체, 늦은 삽입         | unit01(레이아웃), unit02(contain), unit04(폰트 preload) |

### 7. 정리

| **지표**  | **측정 내용**                           | **좋음 기준** | **핵심 개선 방향**                                 |
| --------- | --------------------------------------- | ------------- | -------------------------------------------------- |
| **LCP**   | 가장 큰 콘텐츠가 그려진 시각            | **≤ 2.5s**    | TTFB 단축, LCP 리소스 조기 발견·고우선순위, 차단 제거 |
| **INP**   | 상호작용 → 다음 페인트까지 최악 지연    | **≤ 200ms**   | 긴 태스크 분할, 핸들러 경량화, DOM 갱신 최소화     |
| **CLS**   | 예상치 못한 레이아웃 이동 누적          | **≤ 0.1**     | 공간 미리 확보, 폰트 전략, `transform` 사용        |

- Core Web Vitals는 **LCP(로딩)·INP(반응성)·CLS(안정성)**이며 INP가 FID를 대체함
- 판정 기준은 **실사용자 데이터의 p75**이고, Lab 도구는 재현·원인 진단용임. INP는 RUM에서만 측정됨
- LCP는 **TTFB → 로드 지연 → 로드 시간 → 렌더 지연** 4구간으로 분해해 병목을 찾음
- INP는 **입력 지연 → 처리 → 표시 지연**으로 분해되며, 대부분 메인 스레드의 긴 태스크가 원인임
- CLS는 `영향 비율 × 거리 비율`로 계산되며, 입력 직후 500ms 이내와 `transform` 이동은 제외됨
- 측정 없는 최적화는 검증할 수 없으므로 **RUM 수집 → Lab 진단 → 개선 → RUM 검증** 순환을 유지함
