## 브라우저 렌더링 파이프라인

브라우저가 HTML·CSS·JavaScript를 받아 **화면의 픽셀로 바꾸기까지의 단계별 흐름**을 다룬다. DOM·CSSOM 구성부터 렌더 트리, 레이아웃, 페인트, 합성까지의 과정을 이해해야 성능 병목이 어느 단계에서 생기는지 설명할 수 있고, unit02(Reflow와 Repaint)·unit04(리소스 로딩)의 기반이 된다.

<br>

### 1. 렌더링 파이프라인 한눈에 보기

브라우저 렌더링 엔진(Chrome의 Blink, Safari의 WebKit, Firefox의 Gecko)은 문서를 아래 단계로 처리한다. 이 전체 경로를 **크리티컬 렌더링 패스(Critical Rendering Path, CRP)**라 부른다.

```
HTML ──파싱──▶ DOM ─────┐
                        ├──▶ 렌더 트리 ──▶ 레이아웃 ──▶ 페인트 ──▶ 합성 ──▶ 화면
CSS  ──파싱──▶ CSSOM ───┘   (Render Tree)   (Layout)    (Paint)   (Composite)
                 ▲
JavaScript ──────┘ (DOM·CSSOM을 수정하면 이후 단계가 다시 실행됨)
```

| **단계**       | **입력**            | **출력**                     | **핵심 작업**                                   |
| -------------- | ------------------- | ---------------------------- | ----------------------------------------------- |
| **파싱**       | HTML·CSS 바이트     | DOM·CSSOM 트리               | 바이트 → 문자 → 토큰 → 노드 → 트리              |
| **스타일 계산** | DOM + CSSOM         | 렌더 트리                    | 각 노드에 적용될 최종 스타일(Computed Style) 결정 |
| **레이아웃**   | 렌더 트리           | 박스 모델 기하 정보          | 각 요소의 **위치와 크기** 계산                  |
| **페인트**     | 레이아웃 결과       | 페인트 레코드(그리기 명령)   | 색·테두리·그림자 등을 레이어별로 그림           |
| **합성**       | 레이어들            | 최종 프레임                  | 레이어를 GPU에서 **합쳐서** 화면에 표시         |

> 💡 면접에서는 "주소창에 URL을 입력하면 화면이 뜨기까지"의 후반부로 자주 묻는다. 네트워크 단계(DNS·TCP·HTTP)는 network 챕터에서 다루고, 이 유닛은 **응답 HTML을 받은 이후**에 집중한다.

<br>

### 2. DOM과 CSSOM 구성

**HTML 파싱과 DOM**

HTML 파서는 바이트 스트림을 **토큰화(Tokenizing)**한 뒤 노드로 만들어 **DOM(Document Object Model)** 트리를 구성한다. HTML은 오류에 관대해서 닫히지 않은 태그도 파서가 보정하며, 파싱은 **점진적(incremental)**으로 진행되어 문서 전체가 도착하기 전에도 앞부분부터 트리를 만든다.

```html
<body>
  <div class="card">
    <h2>제목</h2>
    <p style="display: none">숨김 문단</p>
  </div>
</body>
```

```
DOM 트리
body
└── div.card
    ├── h2 ── "제목"
    └── p(display:none) ── "숨김 문단"
```

파싱 도중 `<script>`를 만나면 파서가 멈추고 스크립트를 실행한다. 이 **파서 차단(parser blocking)** 동작과 `async`·`defer`로 완화하는 방법은 unit04에서 다룬다.

**CSS 파싱과 CSSOM**

CSS는 **CSSOM(CSS Object Model)** 트리로 변환된다. CSS는 HTML과 달리 **부분 적용이 불가능**하다. 나중에 오는 규칙이 앞의 규칙을 덮어쓸 수 있으므로(캐스케이딩), 스타일시트 전체를 읽기 전에는 어떤 노드의 최종 스타일도 확정할 수 없다. 이 때문에 CSS는 **렌더링 차단(render blocking)** 리소스로 분류된다.

> ⚠️ CSS는 DOM 구성(HTML 파싱)을 멈추지는 않지만, CSSOM이 완성될 때까지 **렌더 트리 생성 이후 단계가 전부 대기**한다. `<head>`에 거대한 CSS 파일 하나를 두면 첫 화면이 늦어지는 이유다. 화면에 필요한 최소 CSS(Critical CSS)만 인라인하고 나머지는 지연 로딩하는 최적화가 여기서 나온다.

<br>

### 3. 렌더 트리와 스타일 계산

DOM과 CSSOM을 결합해 **실제로 화면에 그려질 노드만** 모은 것이 **렌더 트리(Render Tree)**다. 각 노드에는 캐스케이딩·상속·기본값을 모두 반영한 **계산된 스타일(Computed Style)**이 붙는다.

- `display: none`인 요소와 그 자손은 렌더 트리에 **포함되지 않음** (공간도 차지하지 않음)
- `visibility: hidden`인 요소는 렌더 트리에 **포함됨** (보이지 않지만 공간은 차지함)
- `<head>`, `<script>`, `<meta>`처럼 시각적 표현이 없는 노드는 제외됨
- `::before`·`::after` 같은 의사 요소는 DOM에는 없지만 렌더 트리에는 **포함됨**

| **속성**             | **DOM 포함** | **렌더 트리 포함** | **레이아웃 공간** | **이벤트 수신** |
| -------------------- | ------------ | ------------------ | ----------------- | --------------- |
| **display: none**    | 포함         | **제외**           | 차지 안 함        | 불가            |
| **visibility: hidden** | 포함       | **포함**           | **차지함**        | 불가            |
| **opacity: 0**       | 포함         | 포함               | 차지함            | **가능**        |

스타일 계산 비용은 **선택자 매칭**에 비례한다. 브라우저는 선택자를 **오른쪽에서 왼쪽으로** 매칭하므로 `.list li a`처럼 오른쪽 끝이 광범위한 선택자는 후보 노드가 많아져 비용이 커진다.

<br>

### 4. 레이아웃(Layout)

렌더 트리의 각 노드가 뷰포트 안에서 **어디에, 얼마나 큰 크기로** 놓이는지 계산하는 단계다. Firefox에서는 **리플로우(Reflow)**라고 부른다.

- 루트(`html`)부터 시작해 트리를 순회하며 각 박스의 `x, y, width, height`를 결정함
- 한 요소의 크기 변화는 형제·부모·자손의 위치에 연쇄적으로 영향을 주므로 **범위가 넓고 비용이 큼**
- `width: 50%` 같은 상대 값은 이 단계에서 부모 기준의 절대 픽셀로 확정됨

```javascript
// 레이아웃을 강제로 다시 일으키는 대표적인 코드 (자세한 내용은 unit02)
const box = document.querySelector('.box');
box.style.width = '300px';        // 스타일 변경 → 레이아웃 무효화(예약)
console.log(box.offsetWidth);     // 최신 값을 읽으려면 지금 즉시 레이아웃 실행
```

> 💡 브라우저는 스타일 변경을 바로 반영하지 않고 **다음 프레임까지 모아서(batch)** 처리한다. 그런데 `offsetWidth`, `getBoundingClientRect()`처럼 기하 정보를 **읽는** 순간에는 정확한 값을 돌려주기 위해 예약된 레이아웃을 즉시 실행해야 한다. 이것이 **강제 동기 레이아웃(Forced Synchronous Layout)**이다.

<br>

### 5. 페인트(Paint)와 래스터화

레이아웃으로 확정된 박스에 **색·배경·테두리·그림자·텍스트**를 실제로 그리는 단계다.

- 페인트 단계는 먼저 "무엇을 어떤 순서로 그릴지"를 기록한 **페인트 레코드(그리기 명령 목록)**를 생성함
- 그리기 순서는 소스 순서가 아니라 **쌓임 맥락(Stacking Context)**과 `z-index`를 따름
- 명령 목록을 실제 픽셀로 바꾸는 작업을 **래스터화(Rasterization)**라 하며, 최신 브라우저는 별도 래스터 스레드나 GPU에서 수행함

```
페인트 순서 (같은 쌓임 맥락 안에서)
① 배경색 → ② 배경 이미지 → ③ 테두리 → ④ 자식 요소 → ⑤ 아웃라인
z-index가 음수인 자식은 ①~③ 사이, 양수인 자식은 ④ 이후에 그려짐
```

`box-shadow`, `filter: blur()`, 큰 영역의 `border-radius`처럼 픽셀 계산이 많은 속성은 페인트 비용이 크다. Chrome DevTools의 Rendering 탭에서 **Paint flashing**을 켜면 어떤 영역이 다시 그려지는지 초록색으로 확인할 수 있다.

<br>

### 6. 합성(Composite)과 레이어

브라우저는 페이지를 여러 **레이어(Layer)**로 나눠 각각 따로 래스터화한 뒤, **합성 스레드(Compositor Thread)**가 GPU를 통해 하나의 프레임으로 합친다.

```
메인 스레드                       합성 스레드 (GPU)
──────────                       ─────────────
스타일 → 레이아웃 → 페인트  ──▶  레이어 A (배경)   ┐
                                레이어 B (헤더)   ├─▶ 합성 ─▶ 화면
                                레이어 C (애니메이션) ┘
                                  ▲
                    transform·opacity 변경은 여기서만 처리
```

**레이어가 분리되는 대표 조건**

- 3D `transform`(`translate3d`, `translateZ`), `will-change: transform` 또는 `opacity`
- `<video>`, `<canvas>`, `<iframe>` 요소
- `position: fixed`, CSS 애니메이션·트랜지션이 적용된 `transform`·`opacity`
- 다른 합성 레이어 위에 겹쳐지는 요소 (브라우저가 자동으로 분리)

합성은 메인 스레드와 독립적으로 동작하므로, JavaScript가 바쁘더라도 **스크롤과 `transform` 애니메이션은 끊기지 않는다**. `transform`과 `opacity`만 변경하면 레이아웃·페인트를 건너뛰고 합성만 다시 하는 이유는 unit02에서 자세히 다룬다.

> ⚠️ 레이어는 공짜가 아니다. 레이어마다 GPU 메모리(뷰포트 크기 × 4바이트 수준)를 소비하므로 `will-change`를 모든 요소에 남발하면 오히려 메모리 부족으로 느려진다. **실제로 애니메이션되는 요소에만, 필요한 시점에만** 적용한다.

<br>

### 7. 프레임과 렌더링 타이밍

화면 주사율이 60Hz라면 브라우저는 약 **16.7ms마다 한 프레임**을 만들어야 부드럽게 보인다. 한 프레임 안에서 실행되는 순서는 아래와 같으며, JavaScript 실행이 길어지면 이후 단계가 밀려 프레임이 누락(jank)된다.

```
◀────────────────── 1 프레임 (≈16.7ms @60Hz) ──────────────────▶
[ JS 실행 ] → [ rAF 콜백 ] → [ 스타일 ] → [ 레이아웃 ] → [ 페인트 ] → [ 합성 ]
```

```javascript
// requestAnimationFrame: 다음 프레임의 스타일 계산 직전에 실행됨
function step(timestamp) {
  el.style.transform = `translateX(${(timestamp / 10) % 300}px)`;
  requestAnimationFrame(step);      // 프레임마다 정확히 1회 호출
}
requestAnimationFrame(step);

// setInterval(fn, 16)은 프레임 주기와 어긋나 한 프레임에 2번 실행되거나 건너뛸 수 있음
```

이벤트 루프에서 렌더링 기회(rendering opportunity)가 언제 오는지, 마이크로태스크가 렌더링을 어떻게 지연시키는지는 unit03에서 다룬다.

### 8. 정리

| **단계**       | **비용 요인**                    | **대표 최적화**                                    |
| -------------- | -------------------------------- | -------------------------------------------------- |
| **파싱**       | 동기 스크립트, 대용량 CSS        | `defer`·`async`, Critical CSS 인라인 (unit04)      |
| **스타일 계산** | 복잡한 선택자, 노드 수           | 선택자 단순화, DOM 크기 축소                       |
| **레이아웃**   | 기하 속성 변경, 강제 동기 레이아웃 | 읽기·쓰기 분리, `contain` (unit02)               |
| **페인트**     | 그림자·블러·큰 페인트 영역       | 페인트 영역 최소화, 레이어 분리                    |
| **합성**       | 레이어 수·GPU 메모리             | `transform`·`opacity`만 애니메이션, `will-change` 절제 |

- 렌더링은 **DOM + CSSOM → 렌더 트리 → 레이아웃 → 페인트 → 합성** 순으로 진행됨
- CSS는 **렌더링 차단**, 동기 스크립트는 **파서 차단** 리소스임
- `display: none`은 렌더 트리에서 제외되고, `visibility: hidden`은 포함되지만 보이지 않음
- 레이아웃은 연쇄 영향 때문에 가장 비싸며, 기하 정보를 읽는 순간 **강제 동기 레이아웃**이 발생함
- `transform`·`opacity`는 합성 스레드에서 처리되어 메인 스레드가 바빠도 부드럽게 동작함
- 60Hz 기준 한 프레임 예산은 약 **16.7ms**이며, 이를 넘기면 프레임 드롭이 발생함
