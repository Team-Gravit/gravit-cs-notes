## 리소스 로딩과 파서 차단

HTML 파서가 `<script>`·`<link>`를 만났을 때 **왜 멈추고, 무엇을 기다리며, 어떻게 하면 멈추지 않게 할 수 있는지**를 다룬다. `async`와 `defer`의 차이, CSS가 스크립트 실행을 막는 이유, `preload`·`preconnect` 같은 리소스 힌트를 이해하면 첫 화면이 늦게 뜨는 원인을 구조적으로 설명할 수 있다.

<br>

### 1. 파서 차단과 렌더링 차단

unit01에서 본 것처럼 브라우저는 HTML을 위에서 아래로 파싱하며 DOM을 만든다. 이 과정을 멈추게 하는 리소스가 있다.

| **리소스**                     | **HTML 파싱(DOM 구성)** | **렌더링(첫 페인트)** | **이유**                                             |
| ------------------------------ | ----------------------- | --------------------- | ---------------------------------------------------- |
| **동기 `<script>`**            | **차단**                | 차단                  | 스크립트가 `document.write`로 DOM을 바꿀 수 있음     |
| **`<link rel="stylesheet">`**  | 차단 안 함              | **차단**              | CSSOM이 완성돼야 렌더 트리를 만들 수 있음            |
| **CSS 뒤에 오는 `<script>`**   | **차단** (CSS 대기)     | 차단                  | 스크립트가 `getComputedStyle`로 스타일을 읽을 수 있음 |
| **이미지, 폰트**               | 차단 안 함              | 차단 안 함            | 도착하면 해당 영역만 다시 그림                       |

```
<head>
  <link rel="stylesheet" href="app.css">   ── CSSOM 구성 중 ──┐
  <script src="app.js"></script>           ── 다운로드 완료 ──┤ CSS가 끝나야 실행 가능
</head>                                                        ▼
파서: ─────────────────────────────── 대기 ──────────────── 재개 ─▶ <body> 파싱
```

> ⚠️ "CSS는 렌더링만 막고 파싱은 막지 않는다"는 절반만 맞다. CSS 다음에 **동기 스크립트**가 있으면 그 스크립트는 CSSOM 완성을 기다려야 하고, 그동안 파서도 멈춘다. 결과적으로 **CSS가 파서까지 간접적으로 차단**하는 셈이다.

<br>

### 2. 스크립트 로딩 방식 — 동기 · async · defer

### 2-1. 세 방식의 타임라인

```
        HTML 파싱 ─────▶ (파싱 중단) ─────▶ HTML 파싱 재개 ────────▶ 파싱 완료
동기    ───────────[다운로드][실행]────────────────────────────────────▶
                    ▲ 파서가 다운로드부터 실행까지 전부 기다림

        HTML 파싱 ───────────────────▶ (중단) ─▶ 파싱 재개 ──────────▶ 파싱 완료
async   ────────────[다운로드]────────[실행]──────────────────────────▶
                    ▲ 다운로드는 병렬       ▲ 도착 즉시 실행, 그 순간만 파서 중단

        HTML 파싱 ──────────────────────────────────────────────────▶ 파싱 완료
defer   ────────────[다운로드]──────────────────────────────────────── [실행] ─▶ DOMContentLoaded
                    ▲ 다운로드는 병렬                                    ▲ 파싱 끝난 뒤 순서대로
```

| **속성**      | **다운로드**        | **실행 시점**                          | **실행 순서**        | **DOM 접근**             | **적합한 용도**                       |
| ------------- | ------------------- | -------------------------------------- | -------------------- | ------------------------ | ------------------------------------- |
| **(없음)**    | 파서 중단 후 순차   | 다운로드 직후 즉시                     | 문서 순서            | 위쪽 DOM만 가능          | 폴리필처럼 반드시 먼저 실행할 코드    |
| **async**     | 병렬                | 다운로드 완료 즉시 (파싱 중이라도)     | **완료 순서(비보장)** | 그 시점까지의 DOM만      | 애널리틱스·광고처럼 독립적인 스크립트 |
| **defer**     | 병렬                | 파싱 완료 후, `DOMContentLoaded` 직전  | **문서 순서 보장**   | **전체 DOM 가능**        | 앱 번들처럼 DOM에 의존하는 대부분의 코드 |

```html
<!-- 안티패턴: head의 동기 스크립트가 body 파싱을 막고, DOM이 없어 querySelector도 실패 -->
<head>
  <script src="app.js"></script>
</head>

<!-- 개선: defer로 병렬 다운로드 + 파싱 완료 후 순서대로 실행 -->
<head>
  <script src="vendor.js" defer></script>
  <script src="app.js" defer></script>      <!-- vendor.js 다음에 실행됨을 보장 -->
  <script src="analytics.js" async></script> <!-- 독립적이므로 순서 무관 -->
</head>
```

<br>

### 2-2. 함정과 예외

- `defer`·`async`는 **외부 스크립트(`src`)에만** 효과가 있음. 인라인 스크립트에 붙여도 무시됨
- `type="module"` 스크립트는 **기본적으로 defer처럼** 동작함. `async`를 붙이면 async처럼 동작함
- `async` 스크립트가 `DOMContentLoaded` 전에 실행될지 후에 실행될지는 **네트워크 속도에 달려 있어** 예측할 수 없음
- 동기 스크립트라도 `<body>` 맨 끝에 두면 DOM은 이미 구성돼 있지만, 스크립트 다운로드가 **파싱 완료 후에야 시작**되어 `defer`보다 늦음

> 💡 "`defer`와 body 끝 스크립트는 뭐가 다른가요?"에 대한 답: 실행 시점은 비슷하지만 **다운로드 시작 시점**이 다르다. `defer`는 `<head>`에서 발견되는 즉시 병렬 다운로드를 시작하고, body 끝 스크립트는 파서가 거기 도달해야 다운로드를 시작한다.

<br>

### 3. 프리로드 스캐너(Preload Scanner)

동기 스크립트 때문에 파서가 멈춰 있는 동안에도 브라우저가 놀고 있지는 않다. **프리로드 스캐너**라는 보조 파서가 문서를 앞서 훑으며 `script`의 `src`, `link`의 `href`, `img`의 `src` 같은 리소스를 미리 발견해 **다운로드를 먼저 시작**한다.

```
메인 파서:    <head> ─ [script A 실행 대기] ──────────────── 재개 ─▶ ...
프리로드 스캐너:      ─▶ B.js 발견 ─▶ style.css 발견 ─▶ hero.png 발견 → 즉시 다운로드 시작
```

**프리로드 스캐너가 발견하지 못하는 리소스**

- JavaScript로 동적으로 삽입하는 스크립트·이미지 (`document.createElement('script')`)
- CSS 안의 `@import`, `background-image: url()` — CSS를 파싱해야 알 수 있음
- `@font-face`로 선언한 웹 폰트 — 해당 폰트를 쓰는 텍스트가 렌더 트리에 잡혀야 요청됨
- JavaScript 번들 안에서 `import()`로 지연 로딩하는 모듈

이런 리소스는 발견 자체가 늦어 **요청 체인**이 길어진다. 다음 절의 리소스 힌트가 이 문제를 푼다.

<br>

### 4. 리소스 힌트 — preload · preconnect · prefetch

| **힌트**                 | **하는 일**                                        | **우선순위** | **사용 예시**                                    |
| ------------------------ | -------------------------------------------------- | ------------ | ------------------------------------------------ |
| **preload**              | 현재 페이지에 **곧 필요한** 리소스를 즉시 다운로드 | 높음         | 웹 폰트, LCP 이미지, CSS 안의 배경 이미지        |
| **modulepreload**        | ES 모듈과 그 의존성을 미리 가져와 파싱까지 수행    | 높음         | 앱 진입 모듈                                     |
| **preconnect**           | DNS 조회 + TCP + TLS 핸드셰이크를 미리 수행        | -            | API 서버, CDN, 폰트 호스트 등 **곧 연결할 출처** |
| **dns-prefetch**         | DNS 조회만 미리 수행 (preconnect의 가벼운 버전)    | -            | 연결 여부가 불확실한 서드파티 출처               |
| **prefetch**             | **다음 페이지**에 필요할 리소스를 유휴 시간에 가져옴 | 낮음        | 다음 단계 화면의 번들                            |

```html
<head>
  <!-- 웹 폰트: CSS 파싱 → 렌더 트리 → 폰트 요청까지의 지연을 없앰. crossorigin 필수 -->
  <link rel="preload" href="/fonts/Pretendard.woff2" as="font" type="font/woff2" crossorigin>

  <!-- LCP 이미지: 프리로드 스캐너보다 먼저, 높은 우선순위로 -->
  <link rel="preload" href="/img/hero.webp" as="image" fetchpriority="high">

  <!-- API 서버 연결을 미리 준비 -->
  <link rel="preconnect" href="https://api.example.com">

  <!-- 다음 화면 번들을 유휴 시간에 미리 받아 둠 -->
  <link rel="prefetch" href="/js/checkout.chunk.js">
</head>
```

> ⚠️ `preload`는 "이 리소스를 무조건 지금 받아라"라는 강한 명령이다. **너무 많이 걸면** 정말 중요한 리소스와 대역폭을 나눠 쓰게 되어 오히려 느려지고, 3초 안에 사용되지 않으면 콘솔에 경고가 뜬다. `as` 속성을 빠뜨리면 우선순위 판단이 불가능하고 **같은 리소스를 두 번 받을 수** 있다.

### 5. 이미지·CSS 로딩 최적화

**이미지**

- `loading="lazy"`: 뷰포트 근처에 올 때까지 요청을 미룸. 단, **LCP 이미지에 붙이면 안 됨**(발견이 늦어져 LCP 악화)
- `fetchpriority="high"`: 첫 화면 핵심 이미지의 우선순위를 올림
- `decoding="async"`: 이미지 디코딩이 메인 스레드를 막지 않게 함
- `srcset`·`sizes`: 화면 크기에 맞는 이미지만 받아 전송량 절감

**CSS**

- `media="print"`나 `media="(min-width: 1024px)"`처럼 **현재 조건에 맞지 않는 스타일시트는 렌더링을 차단하지 않음**
- 첫 화면에 필요한 최소 CSS(Critical CSS)는 `<style>`로 인라인하고, 나머지는 지연 로딩함

```html
<!-- 현재 뷰포트가 데스크톱이 아니면 렌더링 차단 없이 백그라운드로 받음 -->
<link rel="stylesheet" href="desktop.css" media="(min-width: 1024px)">

```

```javascript
// 첫 화면 이미지는 즉시·고우선순위, 아래쪽 이미지는 지연 (HTML 속성과 동일한 효과)
const hero = document.querySelector('.hero-img');
hero.fetchPriority = 'high';                 // HTML의 fetchpriority="high" 속성과 동일

document.querySelectorAll('.below-fold img').forEach((img) => {
  img.loading = 'lazy';                      // 뷰포트 근처에서만 요청
  img.decoding = 'async';                    // 디코딩이 메인 스레드를 막지 않음
});
```

### 6. 로딩 이벤트 — DOMContentLoaded vs load

```javascript
document.addEventListener('DOMContentLoaded', () => {
  // HTML 파싱 완료 + defer 스크립트 실행 완료. 이미지·CSS 배경은 아직일 수 있음
  // → DOM 조작 시작 지점으로 적합
});

window.addEventListener('load', () => {
  // 이미지·스타일시트·iframe 등 서브리소스까지 전부 완료
  // → 전체 크기 측정, 지연 가능한 초기화에 적합
});
```

| **이벤트**             | **발생 시점**                                            | **defer 스크립트** | **async 스크립트**   |
| ---------------------- | -------------------------------------------------------- | ------------------ | -------------------- |
| **DOMContentLoaded**   | HTML 파싱 완료 직후                                      | **실행 완료 후** 발생 | 발생 전후 **불확정** |
| **load**               | 모든 서브리소스(이미지·CSS·폰트 등) 로드 완료            | 이미 실행됨        | 이미 실행됨          |

> 💡 `defer` 스크립트가 `DOMContentLoaded`보다 먼저 실행된다는 사실은 "defer 안에서 `DOMContentLoaded` 리스너를 등록해도 이미 발생한 뒤라 호출되지 않는 경우"를 설명할 때 유용하다. 실제로는 `document.readyState`를 확인하는 방어 코드가 필요하다.

### 7. 정리

| **문제**                          | **원인**                                   | **해결**                                      |
| --------------------------------- | ------------------------------------------ | --------------------------------------------- |
| **첫 화면이 늦게 뜸**             | head의 동기 스크립트·거대 CSS              | `defer`, Critical CSS 인라인, `media` 분리    |
| **스크립트 실행 순서가 뒤바뀜**   | `async`는 도착 순서로 실행                 | 의존 관계가 있으면 `defer` 사용               |
| **폰트·배경 이미지가 늦게 나타남** | CSS 파싱 후에야 발견됨                     | `preload`로 조기 요청                         |
| **서드파티 API 첫 호출이 느림**   | DNS·TCP·TLS 핸드셰이크 지연                | `preconnect`                                  |
| **LCP 이미지가 늦음**             | `loading="lazy"` 오용, 낮은 우선순위       | `fetchpriority="high"`, `preload`             |

- 동기 스크립트는 **파서를 차단**하고, CSS는 **렌더링을 차단**하며, CSS 뒤의 스크립트는 CSS 완성까지 대기함
- `async`는 **독립 스크립트**, `defer`는 **DOM 의존 스크립트**에 사용하며 `defer`는 순서를 보장함
- 프리로드 스캐너가 찾지 못하는 리소스는 `preload`로, 연결 비용은 `preconnect`로 앞당김
- `DOMContentLoaded`는 파싱 완료(+defer 실행), `load`는 서브리소스까지 완료 시점임
- 이 유닛의 최적화가 unit10의 **LCP** 지표에 직접 영향을 줌
