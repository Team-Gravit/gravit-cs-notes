## 이벤트 루프와 실행 순서

JavaScript는 **단일 스레드**로 동작하지만 타이머·네트워크·사용자 입력 같은 비동기 작업을 자연스럽게 처리한다. 이를 가능하게 하는 것이 **이벤트 루프(Event Loop)**이며, 콜 스택·태스크 큐·마이크로태스크 큐의 관계와 렌더링이 끼어드는 시점을 알아야 `setTimeout`과 `Promise`의 실행 순서, UI가 멈추는 원인을 정확히 설명할 수 있다.

<br>

### 1. 구성 요소

이벤트 루프는 JavaScript 엔진(V8 등)이 아니라 **호스트 환경(브라우저, Node.js)**이 제공한다. 브라우저 기준 구성 요소는 다음과 같다.

```
┌──────────────────────────────────────────────────────────────┐
│ JavaScript 엔진                    │ 브라우저(호스트)             │
│  ┌──────────┐  ┌──────────────┐    │  ┌────────────────────┐  │
│  │ 콜 스택  │  │ 힙(객체 저장) │    │  │ Web API             │  │
│  │ (실행 중) │  │              │    │  │ 타이머·fetch·DOM 이벤트│  │
│  └────▲─────┘  └──────────────┘    │  └─────────┬──────────┘  │
│       │                            │            │ 완료된 콜백  │
│       │  이벤트 루프               │            ▼             │
│       │  "스택이 비면 큐에서 꺼냄"  │  ┌────────────────────┐  │
│       └────────────────────────────┼──│ 마이크로태스크 큐    │  │
│                                    │  │ 태스크(매크로) 큐    │  │
│                                    │  └────────────────────┘  │
└──────────────────────────────────────────────────────────────┘
```

| **구성 요소**            | **역할**                                                       | **예시**                                              |
| ------------------------ | -------------------------------------------------------------- | ----------------------------------------------------- |
| **콜 스택(Call Stack)**  | 현재 실행 중인 함수 프레임을 쌓는 곳. 비어야 다음 작업 진행    | 함수 호출·반환                                        |
| **Web API**              | 브라우저가 별도 스레드로 처리하는 비동기 작업                  | `setTimeout`, `fetch`, DOM 이벤트, `IntersectionObserver` |
| **태스크 큐(Task Queue)** | 매크로태스크가 대기하는 큐. 한 번에 **하나씩** 꺼냄            | `setTimeout` 콜백, 이벤트 핸들러, I/O 완료             |
| **마이크로태스크 큐**    | 현재 태스크 직후 **비워질 때까지 전부** 실행                   | `Promise.then`, `queueMicrotask`, `MutationObserver`  |

> 💡 "JavaScript는 싱글 스레드인데 어떻게 비동기 처리를 하나요?"의 답은 **"엔진은 싱글 스레드지만, 타이머·네트워크 대기는 브라우저(Web API)가 대신 처리하고, 완료된 콜백만 큐를 통해 콜 스택으로 돌아온다"**이다.

<br>

### 2. 태스크와 마이크로태스크

### 2-1. 처리 규칙

이벤트 루프의 한 바퀴(1 tick)는 다음 순서로 진행된다.

```
① 태스크 큐에서 태스크 1개를 꺼내 실행 (콜 스택이 빌 때까지)
② 마이크로태스크 큐가 빌 때까지 전부 실행 (실행 중 추가된 것도 계속)
③ 렌더링 기회가 있으면 렌더링 (rAF → 스타일 → 레이아웃 → 페인트)
④ ①로 돌아감
```

핵심 차이는 **"하나만"과 "전부"**다. 태스크는 한 tick에 한 개만 처리하지만, 마이크로태스크는 큐가 완전히 빌 때까지 처리한다. 마이크로태스크가 마이크로태스크를 계속 추가하면 렌더링과 다음 태스크가 **무한히 미뤄진다**.

<br>

### 2-2. 실행 순서 예제

```javascript
console.log('1: script start');

setTimeout(() => console.log('5: setTimeout'), 0);

Promise.resolve()
  .then(() => console.log('3: promise 1'))
  .then(() => console.log('4: promise 2'));

console.log('2: script end');

// 출력 순서: 1 → 2 → 3 → 4 → 5
// 스크립트 실행 자체가 하나의 태스크이므로, 그 안에서 예약한 마이크로태스크(3, 4)가
// 다음 태스크(5)보다 먼저 전부 실행됨
```

`async/await`도 같은 규칙을 따른다. `await`는 뒤따르는 코드를 마이크로태스크로 예약하는 것과 같다.

```javascript
async function run() {
  console.log('A');
  await null;                 // 여기서 함수가 일시 중단되고, 이후 코드는 마이크로태스크로 예약됨
  console.log('C');
}
run();
console.log('B');
// 출력: A → B → C
```

> ⚠️ `setTimeout(fn, 0)`은 "즉시"가 아니라 **"현재 태스크와 모든 마이크로태스크가 끝난 뒤, 가장 이른 다음 태스크"**를 뜻한다. 또한 HTML 명세상 중첩 깊이가 5를 넘는 타이머는 최소 지연이 **4ms**로 강제되고, 백그라운드 탭에서는 브라우저가 1초 이상으로 늦출 수 있다. 정밀한 타이밍이 필요한 애니메이션에 `setTimeout`을 쓰면 안 되는 이유다.

<br>

### 3. 렌더링은 언제 일어나는가

렌더링은 태스크 사이에 **"기회가 있을 때"** 끼어든다. 브라우저는 보통 화면 주사율(60Hz면 약 16.7ms)에 맞춰 렌더링 기회를 주며, 매 태스크마다 렌더링하지는 않는다.

```
시간 →
[태스크 A][μ][μ]  [태스크 B][μ]  ┃ 렌더링 ┃  [태스크 C][μ][μ][μ]  ┃ 렌더링 ┃
└─── 16.7ms 안에 여러 태스크 처리 ──┘        └── 태스크 C가 길면 다음 렌더링이 밀림 ──┘
```

**렌더링 단계 내부 순서**

```
requestAnimationFrame 콜백 → 스타일 계산 → 레이아웃 → 페인트 → 합성
```

- `requestAnimationFrame(rAF)` 콜백은 **렌더링 직전**에 실행되므로 스타일을 바꾸면 그 프레임에 바로 반영됨
- `setTimeout`으로 스타일을 바꾸면 렌더링 기회와 어긋나 한 프레임에 두 번 실행되거나 건너뛸 수 있음
- 마이크로태스크는 렌더링 **앞에서** 전부 소진되므로, 무거운 마이크로태스크 체인은 화면 갱신을 막음

```javascript
// 안티패턴: 태스크 하나가 오래 걸려 그 사이 렌더링이 전혀 일어나지 않음
button.addEventListener('click', () => {
  spinner.hidden = false;          // 스타일은 바꿨지만
  heavyComputation();              // 이 태스크가 끝날 때까지 스피너가 화면에 안 보임
  spinner.hidden = true;
});

// 개선: 렌더링 기회를 준 뒤 무거운 작업을 다음 태스크로 넘김
button.addEventListener('click', () => {
  spinner.hidden = false;
  requestAnimationFrame(() => {          // 다음 프레임 렌더링 직전
    setTimeout(() => {                   // 렌더링이 끝난 뒤의 새 태스크
      heavyComputation();
      spinner.hidden = true;
    }, 0);
  });
});
```

> 💡 `rAF` 안에서 다시 `setTimeout(…, 0)`을 감싸는 이유는, `rAF` 콜백은 렌더링 **직전**에 실행되므로 그 안에서 바로 무거운 작업을 하면 해당 프레임 렌더링이 또 밀리기 때문이다. `rAF → setTimeout` 조합은 "한 프레임을 그린 뒤 실행"을 보장하는 관용구다.

<br>

### 4. 긴 태스크와 UI 멈춤

콜 스택이 비어야 이벤트 루프가 다음 작업을 처리하므로, **50ms를 넘는 태스크(Long Task)**는 그 시간 동안 클릭·입력·스크롤 반응과 렌더링을 모두 막는다. 이는 unit10의 **INP** 지표를 직접 악화시킨다.

**긴 태스크를 쪼개는 방법**

| **방법**                        | **원리**                                          | **비고**                                   |
| ------------------------------- | ------------------------------------------------- | ------------------------------------------ |
| **setTimeout으로 분할**         | 작업 단위마다 새 태스크로 넘겨 사이에 렌더링 허용 | 가장 단순, 순서 보장은 직접 관리           |
| **scheduler.yield() / postTask** | 브라우저에 명시적으로 양보, 우선순위 지정 가능   | 지원 브라우저 확인 필요 (버전에 따라 다름) |
| **Web Worker**                  | 별도 스레드에서 계산, 메인 스레드는 자유          | DOM 접근 불가, 메시지로 결과 전달          |
| **requestIdleCallback**         | 브라우저가 한가할 때 실행                         | 실행 시점을 보장하지 않음                  |

```javascript
// 큰 배열 처리를 여러 태스크로 쪼개 사이사이에 렌더링과 입력 처리를 허용
async function processInChunks(items, chunkSize = 500) {
  for (let i = 0; i < items.length; i += chunkSize) {
    items.slice(i, i + chunkSize).forEach(handle);
    await new Promise((resolve) => setTimeout(resolve, 0));  // 다음 태스크로 양보
  }
}
```

❗️**Promise로는 양보되지 않는다**: `await Promise.resolve()`는 마이크로태스크라서 렌더링보다 먼저 계속 실행된다. 이벤트 루프에 제어권을 넘기려면 반드시 **태스크**(`setTimeout`, `MessageChannel`, `scheduler.yield`)를 사용해야 한다.

<br>

### 5. 브라우저와 Node.js의 차이

Node.js도 이벤트 루프를 쓰지만 libuv 기반으로 구조가 다르다. 면접에서 혼동하기 쉬운 부분만 정리한다.

- Node.js의 루프는 **timers → pending callbacks → poll → check → close** 등 여러 **페이즈(phase)**로 나뉘며, 페이즈 사이마다 마이크로태스크를 처리함
- `process.nextTick` 큐는 Promise 마이크로태스크보다 **먼저** 비워짐 (Node 전용)
- `setImmediate`는 check 페이즈에서 실행되며, I/O 콜백 안에서는 항상 `setTimeout(…, 0)`보다 먼저 실행됨
- 브라우저에는 렌더링 단계가 있지만 Node.js에는 **렌더링이 없음**

<br>

### 6. 정리

| **질문**                                     | **핵심 답변**                                                                    |
| -------------------------------------------- | -------------------------------------------------------------------------------- |
| **싱글 스레드인데 비동기가 되는 이유**       | 대기는 Web API가 맡고, 완료된 콜백만 큐를 거쳐 콜 스택으로 들어옴                |
| **Promise.then이 setTimeout보다 먼저인 이유** | 마이크로태스크는 현재 태스크 직후 **전부** 실행, 태스크는 다음 tick에 **하나만** |
| **rAF와 setTimeout의 차이**                  | rAF는 렌더링 직전 프레임마다 1회 보장, setTimeout은 렌더링과 무관한 태스크       |
| **UI가 멈추는 원인**                         | 50ms 이상의 긴 태스크나 끝나지 않는 마이크로태스크 체인이 렌더링 기회를 막음     |
| **양보하는 올바른 방법**                     | `setTimeout`·`scheduler.yield` 같은 **태스크**로 쪼갬. `await Promise`는 양보가 아님 |

- 이벤트 루프의 한 tick: **태스크 1개 → 마이크로태스크 전부 → (기회가 있으면) 렌더링**
- 렌더링 내부 순서는 **rAF → 스타일 → 레이아웃 → 페인트 → 합성**이며, 파이프라인 세부는 unit01 참고
- `setTimeout(fn, 0)`은 "즉시"가 아니라 "다음 태스크"이며, 중첩 시 최소 4ms 지연이 붙음
- 긴 태스크는 unit10의 INP를 악화시키므로 태스크 분할·Web Worker로 대응함
