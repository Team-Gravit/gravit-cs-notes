## 렌더링 제어

Vue는 상태가 바뀌면 **가상 DOM(Virtual DOM)**을 다시 만들어 이전 트리와 비교(diff)하고, 달라진 부분만 실제 DOM에 반영한다. 이 과정을 얼마나 효율적으로 만들 수 있는지는 `v-if`/`v-show`의 선택, `v-for`의 `key` 지정, 리스트 갱신 방식에 달려 있으며, 이는 렌더링 성능 면접 질문의 핵심이다.

<br>

### 1. 렌더링 파이프라인 개요

```
상태 변경 ──▶ 렌더 함수 재실행 ──▶ 새 VNode 트리 생성
                                          │
                        이전 VNode 트리와 비교(diff / patch)
                                          │
                        차이가 있는 노드만 실제 DOM에 반영
```

- 템플릿은 컴파일 시점에 **렌더 함수**로 변환되고, 렌더 함수는 반응형 상태를 읽는 이펙트로 등록됨(unit01 참고)
- Vue 3 컴파일러는 템플릿을 분석해 **정적 노드는 건너뛰고 동적 부분만 비교**하도록 힌트(패치 플래그)를 남기므로, 같은 가상 DOM이라도 Vue 2보다 diff 범위가 좁음
- 하지만 컴파일러가 최적화하지 못하는 부분, 즉 **조건부 렌더링과 리스트**는 개발자의 지시 방식이 성능을 좌우함

<br>

### 2. v-if vs v-show

둘 다 "조건에 따라 보이거나 숨긴다"는 점은 같지만, **DOM을 다루는 방식**이 완전히 다르다.

```vue
<script setup lang="ts">
import { ref } from 'vue'
const open = ref(false)
</script>

<template>
  <!-- v-if: false면 DOM에서 제거, true가 되면 새로 생성 -->
  <HeavyChart v-if="open" />

  <!-- v-show: 항상 렌더링하고 display: none 으로 숨김 -->
  <div v-show="open" class="tooltip">도움말</div>
</template>
```

| **항목**              | **`v-if`**                                       | **`v-show`**                                   |
| --------------------- | ------------------------------------------------ | ---------------------------------------------- |
| **동작 방식**         | 조건부로 **DOM 생성·제거**                       | 항상 렌더링, **CSS `display` 토글**            |
| **초기 렌더 비용**    | 조건이 거짓이면 **0** (지연 렌더링)              | 조건과 무관하게 렌더링                         |
| **토글 비용**         | **높음** (컴포넌트 생성·파괴, 생명주기 훅 실행) | **낮음** (스타일 변경뿐)                       |
| **컴포넌트 상태**     | 토글 시 **초기화**됨                             | 유지됨                                         |
| **`<template>` 사용** | 가능                                             | 불가 (실제 요소가 있어야 스타일 적용)          |
| **`v-else` 연계**     | 가능                                             | 불가                                           |

**선택 기준**

- **자주 토글**되는 요소(탭, 툴팁, 아코디언) → `v-show`. 토글마다 생성·파괴하는 비용을 피함
- **조건이 거의 바뀌지 않거나** 초기에 숨겨진 채로 끝날 가능성이 높은 요소(관리자 메뉴, 모달) → `v-if`. 필요 없는 컴포넌트를 아예 만들지 않음
- 숨겨진 동안 **상태를 초기화**해야 하면 `v-if`, 유지해야 하면 `v-show`

> 💡 `v-if`는 자식 컴포넌트의 `onMounted`·`onUnmounted`를 매번 실행시킨다. 무거운 초기화(API 요청, 차트 그리기)가 있는 컴포넌트를 자주 토글해야 한다면 `v-show`가 맞고, 반대로 토글할 때마다 **최신 데이터로 다시 불러와야** 한다면 `v-if`가 그 역할을 자연스럽게 해 준다.

<br>

### 3. v-for와 key

### 3-1. key가 하는 일

`v-for`로 리스트를 렌더링할 때 `key`는 각 노드의 **정체성(identity)**을 알려 주는 식별자다. Vue의 diff 알고리즘은 `key`를 기준으로 "이 노드가 이전에 있던 그 노드인지"를 판단해 **재사용·이동·생성·제거**를 결정한다.

```
이전: [A] [B] [C]           새 목록: [X] [A] [B] [C]  (맨 앞에 X 삽입)

key 없음 (index 기준 비교)          key 있음 (id 기준 비교)
 0: A → X  (내용 패치)              X: 없던 key → 새로 생성
 1: B → A  (내용 패치)              A, B, C: 같은 key → 그대로 재사용
 2: C → B  (내용 패치)
 3: 없음 → C  (새로 생성)
 = 패치 3회 + 생성 1회               = 생성 1회 (+ 위치 이동)
```

- `key`가 없으면 Vue는 **같은 위치의 노드끼리** 비교하는 제자리 패치(in-place patch)로 동작함. 정적 리스트는 문제없지만 순서가 바뀌거나 중간에 삽입·삭제되면 불필요한 패치가 늘어남
- `key`가 있으면 앞·뒤에서 공통 구간을 먼저 맞춘 뒤, 남은 구간은 **최장 증가 부분 수열(LIS)**로 최소 이동 횟수를 계산해 DOM 이동을 줄임

<br>

### 3-2. index를 key로 쓰면 안 되는 이유

```vue
<!-- 안티패턴: index를 key로 사용 -->
<li v-for="(todo, i) in todos" :key="i">
  <input type="checkbox" /> {{ todo.text }}
</li>

<!-- 개선: 항목을 유일하게 식별하는 값을 key로 사용 -->
<li v-for="todo in todos" :key="todo.id">
  <input type="checkbox" /> {{ todo.text }}
</li>
```

index를 key로 쓰면 "리스트 첫 항목을 삭제"했을 때 index 0은 여전히 존재하므로 Vue는 **첫 번째 DOM 노드를 재사용하고 내용만 바꾼다.** 이때 체크박스 상태·입력값·자식 컴포넌트의 로컬 상태처럼 **VNode에 기록되지 않은 DOM 상태**가 엉뚱한 항목에 남는 버그가 생긴다.

> ⚠️ index를 key로 써도 되는 경우는 **순서가 절대 바뀌지 않고, 중간 삽입·삭제도 없으며, 항목에 상태가 없는** 정적 리스트뿐이다. 이 세 조건을 모두 확신할 수 없다면 고유 id를 쓴다. `Math.random()`을 key로 쓰는 것은 매 렌더마다 모든 노드를 새로 만드는 최악의 선택이다.

<br>

### 4. v-if와 v-for를 같은 요소에 쓰지 않는다

Vue 3에서는 같은 요소에 두 디렉티브가 있으면 **`v-if`가 먼저 평가**된다. 따라서 `v-if`에서 `v-for`의 반복 변수를 참조할 수 없어 런타임 오류가 난다. Vue 2는 반대로 `v-for`가 먼저였으므로 동작은 했지만, 매 항목마다 조건을 검사해 비효율적이었다.

```vue
<!-- 안티패턴: Vue 3에서는 item이 정의되지 않아 오류, Vue 2에서는 동작하지만 비효율 -->
<li v-for="item in items" v-if="item.active" :key="item.id">{{ item.name }}</li>

<!-- 개선 1: 필터링은 computed로 미리 끝낸다 -->
<li v-for="item in activeItems" :key="item.id">{{ item.name }}</li>

<!-- 개선 2: 리스트 전체를 조건부로 렌더링하려면 template로 감싼다 -->
<template v-if="items.length">
  <li v-for="item in items" :key="item.id">{{ item.name }}</li>
</template>
```

- Vue 3에서 `<template v-for>`를 쓸 때는 **`key`를 `<template>`에** 붙인다 (Vue 2는 자식 요소에 붙였음)
- 필터·정렬은 템플릿이 아닌 `computed`에서 처리하면 캐싱 이점(unit03 참고)까지 얻음

<br>

### 5. 리스트 갱신 비용 줄이기

리스트는 항목 수만큼 VNode를 만들고 비교하므로 규모가 커질수록 갱신 비용이 커진다. 대응 전략을 비용이 큰 순서로 정리한다.

| **전략**                         | **효과**                                                    | **적용 시점**                                   |
| -------------------------------- | ----------------------------------------------------------- | ----------------------------------------------- |
| **고유 key 지정**                | 노드 재사용·최소 이동, DOM 상태 꼬임 방지                   | **항상**                                        |
| **항목을 컴포넌트로 분리**       | 바뀐 항목의 컴포넌트만 재렌더링 (props가 같으면 건너뜀)     | 항목 템플릿이 복잡할 때                         |
| **`v-memo`** (3.2 이상)          | 지정한 의존성이 바뀌지 않은 항목은 **diff 자체를 건너뜀**    | 수백~수천 항목 중 소수만 바뀔 때                |
| **`shallowRef` 사용**            | 항목 내부까지 Proxy로 감싸는 비용 제거 (unit02 참고)        | 항목을 통째로 교체하는 읽기 전용 대용량 데이터  |
| **가상 스크롤**                  | 화면에 보이는 항목만 DOM에 생성                             | 수천 개 이상, 스크롤 목록                       |

```vue
<!-- v-memo: selected 여부가 바뀐 항목만 다시 비교한다 -->
<div
  v-for="item in list"
  :key="item.id"
  v-memo="[item.id === selectedId]"
>
  <p>{{ item.title }}</p>
  <span v-if="item.id === selectedId">선택됨</span>
</div>
```

> ⚠️ `v-memo`는 배열에 넣은 값이 같으면 **내부의 다른 변경도 무시**한다. 항목 내용이 바뀌는데 `v-memo` 의존성에 그 값이 없으면 화면이 갱신되지 않으므로, 명확한 병목이 확인된 곳에만 신중히 사용한다.

<br>

### 6. key로 강제 재렌더링하기

`key`는 리스트 밖에서도 "이 노드를 **새 것으로 취급하라**"는 신호로 쓸 수 있다. 같은 컴포넌트를 다른 데이터로 다시 초기화해야 할 때 유용하다.

```vue
<!-- 라우트 파라미터가 바뀔 때 컴포넌트를 완전히 새로 마운트 -->
<UserProfile :key="route.params.id" :id="route.params.id" />
```

- `key`가 바뀌면 이전 인스턴스는 언마운트되고 새 인스턴스가 마운트되므로 로컬 상태·훅이 모두 초기화됨
- `watch`로 파라미터 변경을 감지해 상태를 하나씩 리셋하는 것보다 단순하지만, 마운트 비용을 매번 치르므로 남용하지 않음

> 💡 Vue 3는 **프래그먼트(Fragment)**를 지원해 템플릿의 루트 요소가 여러 개여도 된다. 다만 루트가 여러 개면 부모가 내려준 `class`·`style` 같은 속성(fallthrough attrs)이 어디에 붙을지 모호해져 경고가 나므로, 이 경우 `inheritAttrs: false`와 `v-bind="$attrs"`로 명시적으로 지정한다.

<br>

### 7. 면접·실무 체크포인트

| **질문**                                              | **핵심 답변**                                                                                          |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| **`v-if`와 `v-show`의 차이는?**                       | `v-if`는 **DOM 생성·제거**(초기 비용 낮음, 토글 비용 높음), `v-show`는 **CSS 토글**(반대)              |
| **`v-for`에 `key`가 왜 필요한가?**                    | diff 시 노드의 **정체성**을 판단해 재사용·이동을 결정. 없으면 index 기준 제자리 패치                   |
| **index를 key로 쓰면 어떤 문제가?**                   | 삽입·삭제·정렬 시 **DOM 상태(입력값·체크·로컬 상태)가 엉뚱한 항목에 남음**, 불필요한 패치 증가          |
| **`v-if`와 `v-for`를 같이 쓰면?**                     | Vue 3는 `v-if`가 먼저 평가되어 반복 변수 참조 불가. `computed` 필터링이나 `<template>` 분리로 해결     |
| **큰 리스트의 갱신 비용을 줄이려면?**                 | 고유 key → 항목 컴포넌트화 → `v-memo` → `shallowRef` → 가상 스크롤 순으로 적용                         |
| **컴포넌트를 강제로 다시 마운트하려면?**              | **`key`를 변경**. 로컬 상태와 생명주기가 모두 초기화됨                                                 |

- 렌더링 최적화의 출발점은 항상 **올바른 key**이며, 그다음이 조건부 렌더링 방식의 선택이다
- 생성·파괴가 일어나는 시점에 실행되는 생명주기 훅과 DOM 접근 타이밍은 **unit07**을 참고할 것
